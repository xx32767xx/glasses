# 虚拟眼镜（安卓端）

**没有真眼镜时，它就是眼镜。** 一块严格按显示预算（默认 40 列 × 3 行）折行的屏幕，
加上录音上传。眼镜到手后，把"画在屏幕上"换成"蓝牙推过去"，其余全不动。

## 它在整条链路里的位置

```
┌────────────── 安卓手机（这个 App）──────────────┐
│  麦克风 → AudioRecord 裸 PCM → POST /audio      │
│    （识别在电脑上做；手机上只当麦克风）          │
│  收到字幕 → 画在这块屏幕上（以后改成蓝牙推眼镜）│
└───────────────────┬─────────────────────────────┘
                    │ 同一个 WiFi
┌───────────────────┴──── 电脑（三个终端 + 一个调试窗口）──┐
│  node relay/lan-relay.mjs        转发进程（会打印收到什么）│
│  node bridge/asr-bridge.mjs ...  识别（Whisper）          │
│  node scripts/harness-side.mjs   harness + 插件           │
│  node scripts/debug-window.mjs   调试窗口：断在哪一环      │
└──────────────────────────────────────────────────────────┘
```

手机是个**哑终端**：只负责录音、送出音频、显示字幕。所有聪明的事都在电脑上。
好处是换模型、改巴葡口径、调显示预算都只动电脑，手机端一行都不用改。

> **为什么不是"手机自己识别"**：这台设备的系统语音识别服务不可用（App 里原来的诊断
> 功能确认过，不是我们的代码问题）。所以把识别放到电脑上做 —— 质量与手机型号无关，
> 还能用上 GPU。代价是必须连着电脑，而同传本来就要连着电脑（翻译在电脑上）。
>
> 原来那个走系统识别的「开始听写」按钮**已经删掉**：在这台设备上它只会报
> `ERROR_CLIENT`，留着不但没用，还会让人以为"整个语音功能坏了"。

## ⚠️ 先记住这一条：改了电脑侧代码，必须重启进程

**Node 进程启动时就把代码读进内存了，改文件不会影响已经在跑的进程。**
所以 `git pull`、或者我改了继电器/识别/插件之后，都要重启（用 `start-all` 的话就是 Ctrl-C 再跑一次）。
APK 装了新版也要重装（`adb install -r ...`）。

这条不是理论 —— 踩过两次，而且两次的症状都完全不像"代码没生效"：

| 症状 | 真正的原因 |
|---|---|
| 手机点录音上传，立刻 `HTTP 404`（错误里 routes 没有 `/audio`） | 手机连的是一个**加 `/audio` 之前**启动的转发进程 |
| 电脑侧字幕明明在写，手机上却永远是空的，**也不报错** | 手机还揣着**上一个转发进程**的帧序号；新进程的序号从 0 开始，于是手机永远在等一个不会到来的序号 |

第二条已经被**双向修掉**了：转发进程发现手机序号比它大，就明确告诉它"序号重置了"
并把当前帧一起给它；手机那边也会自己把序号拉回来。所以现在重启转发进程不会再让手机失聪。
但"重启进程"这个纪律仍然要守 —— 否则你测的还是旧代码。

第一条现在也防住了：`start-all` 起之前会先探一下 8788，被占着就直接拦住并告诉你怎么找出来杀掉。

## 一、先在电脑上起进程

**推荐：一条命令起齐三个进程**（转发 + 识别 + 大脑），日志带颜色前缀汇总在一个终端：

```powershell
node scripts/start-all.mjs
```

它会：先检查 8788 有没有被旧的转发进程占着（占着就直接告诉你，不会让你白测）；
把三个进程的输出汇总打印；Ctrl-C 一次停掉全部（含识别进程起的 python 子进程）；
顺手清掉上次留下的音频与收件箱（否则启动会先冒一句旧字幕）。
常用开关：`--cpu`（没 N 卡时用 CPU 识别）、`--offline`（不联网）、`--open-window`（另弹一个调试窗口）。

启动后会打印手机要填的地址和密钥，例如：

```
  手机上填：地址 http://<电脑IP>:8788  密钥 ee4b42190b9a
  地址看上面 [转发] 那几行（选标着 WLAN/以太网的那个，别选 VMware 虚拟网卡）
```

**再另开一个终端放调试窗口**（只读，随时 Ctrl-C，不影响链路）：

```powershell
node scripts/debug-window.mjs --url http://127.0.0.1:8788 --secret <上面那个密钥>
```

### 想分开起（调试某个环节时用）

```powershell
node relay/lan-relay.mjs                                        # [转发]
node bridge/asr-bridge.mjs --inbox var/live/asr-inbox.jsonl ^
  --whisper-follow var/live/audio-in.pcm --whisper-device cuda --whisper-compute float16   # [识别]
node scripts/harness-side.mjs                                   # [大脑]（加 --offline 则不联网）
```

三个进程各自负责什么、缺哪个会怎样：

| 前缀 | 干什么 | 不跑会怎样 |
|---|---|---|
| `[转发]` | 收发室：手机 ↔ 电脑，落盘音频、递回字幕 | 手机**根本连不上** |
| `[识别]` | 耳朵：音频 → 文字（Whisper，用 GPU） | 音频在涨、收件箱不动 → 没字幕 |
| `[大脑]` | 大脑：文字 → 判语向 → 调模型翻译 → 排成 40×3 | 收件箱在涨、字幕不动 → 没字幕 |

### 调试窗口长什么样

它每秒钟重画一次，把四个环节的证据并排显示出来：

```
──────────────────────────────────────────────────────────────────────────
  调试窗口 · 14:31:26 · 数据目录 var/live
──────────────────────────────────────────────────────────────────────────
  ① 手机音频   2.3s    73600 字节      16000Hz     语种 pt-BR    最后写入 3s 前  ↑ 本次 +32000 字节
  ② 收件箱     4 行    最后写入 2s 前   最新：我是人
  ③ 字幕总线   [me / pt-BR]  最后写入 1s 前   Eu sou humano
               │ Eu sou humano
  ④ 转发进程   收音频 73600 字节/3 块       收文字 2 句      字幕 13 帧      拒绝 0

  → 字幕刚更新过：这一句走完了。手机上看不到就是手机取字幕那一环（试试断开重连）。
──────────────────────────────────────────────────────────────────────────
```

最后那行是它的重点：**直接告诉你断在哪一环**，而不是让你自己猜。

| 你看到 | 说明 |
|---|---|
| ① 不涨 | 手机的音频没上来（或转发进程是旧代码） |
| ① 电平条几乎全空 + 有 ⚠️ | **手机没录到人声**（不是链路问题）—— 对着手机说一句看电平会不会上去 |
| ① 在涨、② 不动 | **识别进程**没跑（终端 3），或它盯的不是同一个文件 |
| ② 在涨、③ 不动 | **插件**没在消费（harness-side 没跑，或跑的是旧进程） |
| ③ 在更新、手机不显示 | 手机取字幕那一环（先试断开重连） |

它还有个电平条，专门用来回答"**我的声音到底有没有被录进去**"：

```
  ① 手机音频   3.3s    105600 字节   16000Hz   语种 zh-CN   最后写入 5s 前  ↑ 本次 +32000 字节
               最近电平 ████████··     峰值 0.421  RMS 0.0730
  → 字幕刚更新过：这一句走完了。手机上看不到就是手机取字幕那一环（试试断开重连）。
```

底部那个数字很关键：正常对着手机说话的**峰值一般在 0.1 以上**。
如果电平条几乎全空、峰值只有 0.01 上下，说明**手机根本没录到人声** ——
这时无论后面哪一环都白搭，先查麦克风（有没有被挡住 / 被别的应用占着 / 离太远）。
「收到音频」和「收到声音」是两回事，只看字节数会误判。

它**只读文件**，不写任何东西，所以可以一直开着、随时 Ctrl-C，不影响链路。
`--once` 只打一次快照。

转发进程自己也会打印收到的每一件事（不想要就加 `--quiet`）：

```
[14:29:25] 📥 收到手机音频：+32000 字节（第 1 块） → 累计 1.0s @ 16000Hz，语种 pt-BR（新一次录音，已清空）
[14:30:02] 📥 收到手机文字：你好（收件箱第 5 行）
[14:30:03] 📺 字幕已更新（第 14 帧）[me / pt-BR] Eu sou humano
[14:30:03] ➡ 手机取字幕（since=13），立即给第 14 帧
```

转发进程启动后会打印四样你需要的东西：

```
  收件箱（手机的文字进这里）  var\live\asr-inbox.jsonl
  录音上传（手机音频落这里）  var\live\audio-in.pcm
  共享密钥（手机上要填这个）  ee4b42190b9a
  手机上的地址填（要和电脑在同一个 WiFi）：
      http://192.168.1.108:8788      ← WLAN
  这些是虚拟网卡，手机连不上，别填：
      192.168.73.1  (VMware Network Adapter VMnet1)
```

**一定要选标着真实网卡名（WLAN / Wi-Fi / 以太网）的那个地址。**

> ⚠️ 每次改了电脑侧代码（比如 `git pull`）之后，**都要重启这几个进程** ——
> Node 进程启动时就把代码读进内存了，改文件不会影响已经在跑的进程。
> 这条不是理论：有一次就是手机连上了一个"还是旧代码"的转发进程，
> 点录音上传报 `HTTP 404 not-found`，而错误里列出的路由恰好没有 `/audio` ——
> 一眼就能确定是进程没重启，而不是代码有问题。
>
> 为什么终端 3 要写成一条命令、而不是 `python ... | node ...` 管道：
> Windows PowerShell 的原生命令管道会缓冲 stdout，而识别进程是**一直尾随不退出**的，
> 于是缓冲永远不刷新，桥一行都收不到（这个坑真踩到过）。
> 走 `--whisper-follow` 由桥自己起子进程并流式读它的 stdout，没有这个问题。

## 二、构建并安装 App

### 最省事：用 Android Studio

1. Android Studio → Open → 选 `android/` 这个目录（**不是**仓库根目录）
2. 等它同步完，点绿色 ▶ Run
3. 手机用 USB 连上、开"USB 调试"，它会自动装上去

### 命令行（已经验证可用）

```powershell
node scripts/build-apk.mjs        # 会自动找到本机的 gradle，产出 APK
```

产出的 APK 在 `android/app/build/outputs/apk/debug/app-debug.apk`，装法二选一：

```powershell
# 手机插着 USB 且开了 USB 调试
adb install -r android\app\build\outputs\apk\debug\app-debug.apk
```

或者把这个 apk 文件传到手机上点开安装（需要允许"安装未知来源应用"）。

> 为什么 APK 只有 35 KB：这个 App **零第三方依赖**（连 AndroidX 都没用），
> 全部用平台自带 API。依赖越少，构建越稳、也越容易看懂。

## 三、手机上怎么用

界面从上到下就四样东西：**虚拟眼镜面板 → 地址/密钥 → 连接与语言 → 录音上传按钮 → 手输框**。

1. 填**电脑地址**（转发进程打印的那个，例如 `http://192.168.1.108:8788`）
2. 填**共享密钥**（转发进程打印的那串，例如 `ee4b42190b9a`）
3. 点 **连接** —— 成功后上面那块面板会变成"已连接 Leion Pro · 40 列 × 3 行"
4. 选听哪种语言：
   - **听葡语**（默认）：对方说葡语 → 眼镜上显示中文字幕（这是主用途）
   - **听中文**：你说中文 → 译成巴葡。⚠️ 注意这半边**字幕帮不上你**——
     眼镜戴在你自己脸上，对方看不见。这半边最终需要 TTS 念出来（还没做）
5. 点 **开始录音上传**，然后正常说话。每说完一句，电脑翻译后把字幕推回来，
   面板上就出现译文。

首次点会请求麦克风权限，要允许。

**语言按钮可以随时切，录音中切也生效** —— 这个选择会随每一块音频一起发给电脑
（`/audio?lang=`），电脑侧的识别进程跟着换语种，**下一句就按新语种识别**，不用停止再开始。

录音上传启动时会在状态行显示实际采样率。安卓**不保证**每台设备都能以 16 kHz 录音
（Whisper 要 16 kHz），如果这台设备不支持，App 会自动降级到 44.1 kHz 并把它如实告诉
电脑，由电脑重采样 —— 所以看到 44100 是正常的，字幕一样准。

### 「手输一句话」是干什么的

它把"链路验证"和"语音"彻底解耦：不经过麦克风、不经过识别，直接把一句话送给电脑。
所以哪天真出问题时，可以用它一秒判断「是语音那一环坏了，还是后面（翻译/字幕）坏了」。

识别质量相关的几个默认值（都是拿真实手机录音实测后定的，详见 `docs/04` 第 9 节）：

| 参数 | 缺省 | 作用 |
|---|---|---|
| `--no-normalize` | 关（即**做**归一化） | 手机远距离录音电平偏低，归一化能明显提准确率 |
| `--initial-prompt` | 按语种自动 | 中文用「以下是普通话的句子，请用简体中文输出。」（顺带压掉繁体输出） |
| `--beam-size` | 5 | 束搜索比贪心准，GPU 上很便宜 |
| `--min-speech-ms` | 500 | 丢掉 <0.5 秒的碎片（它们只会变成胡话） |
| `--short-utterance-ms` / `--short-silence-ms` | 800 / 1100 | 短句保护：太短的片段等一等，别把一句话切成两半 |

想换模型：`node scripts/start-all.mjs --whisper-model medium`（或 `large-v3`）。
实测本机上三者准确率差别不大，但 small 最快、体积最小，所以是缺省。

## 四、出问题了按这个顺序查
### ① 手机连不上（最常见，90% 是防火墙）

**先在手机浏览器里打开** `http://192.168.1.108:8788/status?secret=你的密钥`：

- **能看到一串 JSON** → 网络通了，问题在 App 里（检查地址/密钥有没有多空格）
- **打不开** → 按顺序查：
  1. **Windows 防火墙很可能拦了**。这是第一次运行时最常见的卡点：
     控制面板 → Windows Defender 防火墙 → 允许应用通过防火墙 → 找到 **Node.js** →
     勾上"专用网络"（**不要**勾公用网络）。或者允许时直接在弹窗里点"允许访问"。
     也可以在管理员 PowerShell 里加一条放行规则：
     ```powershell
     New-NetFirewallRule -DisplayName "Leion 局域网转发" -Direction Inbound -LocalPort 8788 -Protocol TCP -Action Allow -Profile Private
     ```
  2. 手机和电脑是不是**同一个 WiFi**？（手机别开流量、别连访客网络）
  3. 电脑上那个地址填对了吗？如果你连的是有线网，地址可能不是 `192.168.1.x`——
     以转发进程打印的为准。
  4. 有些路由器开了"AP 隔离"，会禁止同一 WiFi 内的设备互相访问。换一个热点试试。

### ② 提示"共享密钥不对"

密钥在转发进程启动时打印，也存在 `var/live/relay-secret.txt`。
两边必须完全一致（注意别把空格带进去）。

### ③ 点了录音上传，手机立刻报 `HTTP 404 not-found`

**先看错误里列出的 `routes` 里有没有 `/audio`。** 这是最快的判断依据：

| 错误里的 routes | 说明 | 怎么办 |
|---|---|---|
| 有 `/audio` | 请求打到了新代码，但路径/参数不对 | 把完整错误发出来 |
| **没有 `/audio`** | **你连的是旧代码的转发进程** | 重启它（见下） |

为什么"没有 `/audio`"就等于旧代码：`routes` 是转发进程**自己**报出来的它认识哪些端点。
它列不出 `/audio`，说明那个进程启动时读的还是加 `/audio` 之前的代码。

**Node 进程启动时就把代码读进内存了**，改文件不会影响已经在跑的进程。所以：

```powershell
# 1) 停掉旧的转发进程（在那个终端里按 Ctrl-C）
# 2) 重新起
node relay/lan-relay.mjs
```

如果 Ctrl-C 之后手机还能连上，说明**还有另一个**转发进程活着（比如上次没关干净的）。
在 Windows 上这样找出来并杀掉：

```powershell
netstat -ano | findstr :8788          # 最后一列是 PID
taskkill /PID <那个PID> /F
```

> 这个坑真踩到过：一个早先启动的转发进程一直占着 8788，手机连的是它，
> 于是点录音上传就报 404，而代码其实是对的。

### ④ 识别出来了，但字幕不出现

在电脑上看**终端 1**（harness 侧）的输出：

- 如果没有任何反应 → 收件箱没被读到。检查两个进程指向的是不是同一对文件
  （默认都是 `var/live/`）
- 如果报"翻译路由：FAIL" → 模型没配好。用 `--offline` 先确认链路是通的
- 如果报"例句表里没有这一句" → 你在用 `--offline`（它只认得那 14 句剧本）。
  换成不带 `--offline` 的真实模型模式

### ⑤ 点了「开始录音上传」，电脑那边没反应

按这个顺序查（每一步都有明确的判断依据）：

1. **终端 3（识别进程）起了吗？** 录音上传这条路必须有它。看它的输出：
   - 打印「尾随 …audio-in.pcm」并停在那里 → 正常，在等你的音频
   - 报「缺少 faster-whisper」→ 先 `pip install faster-whisper numpy`
   - **只停在「加载模型…」很久不动** → 它在**下载模型**，不是在加载。
     它启动时会打印两行，第二行说明模型从哪儿来：

     ```
     [whisper_stream] 加载模型 small（device=cuda, compute_type=float16）…
     [whisper_stream] 模型缓存 E:\GlassesHarness\var\cache\hf；下载源 https://hf-mirror.com
     ```

     如果"模型缓存"显示的是默认的 `~/.cache/huggingface`，说明 `HF_HOME` 没生效 ——
     它会从零下一个几百 MB 的模型。直连 HuggingFace 实测 **3 分钟只下了 2.5MB**，
     看起来就像卡死了（真发生过：识别进程 4 分钟都没开始听，而终端上只有"加载模型…"）。
     **用 `node scripts/start-all.mjs` 就不会有这个问题** —— 它会自动把缓存指到
     仓库里的 `var/cache/hf`（那里已经有下好的模型）、下载源指到镜像，
     并在启动横幅里把这两件事打印出来。自己手动起的时候记得：

     ```powershell
     $env:HF_HOME="E:\GlassesHarness\var\cache\hf"
     $env:HF_ENDPOINT="https://hf-mirror.com"
     ```
2. **音频真的传上去了吗？** 看转发进程的 `/status`：
   ```powershell
   curl "http://127.0.0.1:8788/status?secret=你的密钥"
   ```
   看 `audioBytes` / `audioChunks`：
   - `audioChunks` 在涨 → 音频到了电脑，问题在识别那一侧（回到第 1 步）
   - `audioChunks` 一直是 0 → 音频没上来。看手机状态行有没有报错（密钥错会显示 401）
3. **手机状态行显示的是哪个采样率？** 显示 44100 属于正常降级，不是错误。
4. **必须说完一整句、停顿约 0.7 秒，字幕才会出现** —— 识别是按停顿切句的。
   对着手机连续不停地说，反而会一直不出字幕。

### ⑥ 点了录音上传，转发进程在报"收到音频"，但一直没有字幕

**先看转发进程那两行里的电平。** 它现在每收到一块音频都会打两行：

```
[转发] 📥 收到手机音频：+32000 字节（第 1 块） → 累计 1.0s @ 16000Hz，语种 pt-BR（手机开始了新一次录音）
[转发]    音平 ████████·· 峰值 0.421 RMS 0.0730
```

- **电平条正常满、峰值 0.1 以上** → 录音没问题，往下查识别进程（见 ⑤）
- **电平条几乎全空、峰值 0.01 左右** → **手机没录到人声**。这是麦克风问题，不是链路问题：
  1. 说话时看电平会不会跳 —— 不跳就说明声音没进去
  2. 麦克风孔有没有被挡住（手、壳、桌面）
  3. 有没有别的应用占着麦克风（录音机、通话、语音助手）
  4. 离手机太远/声音太小 —— 对着手机 20~30cm 正常音量说
  5. 手机系统设置里本应用的**麦克风权限**是否真的给了（"仅本次允许"会在切后台后失效）

> 为什么单列这一条：真实遇到过 —— 日志显示"收到手机音频"、字节数一直在涨，
> 但识别结果永远是 0 段。查下来上传的音频**基本是静音**（峰值 0.019，正常说话 1.0）。
> 只看"收到音频"会以为是识别坏了，其实是手机没录到人声。
> 「收到音频」和「收到声音」是两回事。

### ⑦ 收件箱里有行、字幕却一直不出来（识别结果是乱码）

**看大脑（harness 侧）的日志**。如果出现这种：

```
[leion-pro] ✗ 翻译失败：判不出源语种。请显式传 from='zh-CN' 或 from='pt-BR'
```

再看一眼收件箱 `var/live/asr-inbox.jsonl` —— 里面大概是这样的：

```
这是测试        ← 手输的那句（node 写的，正常）
���             ← 本该是「你好」，却成了替换符
��Ļby�����
```

**这是编码问题，不是识别问题**：Python 在 Windows 中文环境下往**管道**写的是 GBK 字节
（`你好` = `C4 E3 BA C3`），而桥按 UTF-8 读 → 变成乱码 → 插件判不出语种 → 一句字幕都没有。
字节层面完全对得上（`C4 E3 BA C3` 按 UTF-8 解正好是 3 个坏字节）。

已经修好了，而且从两个地方一起扛：

- `whisper_stream.py` **导入时**就把 stdout/stderr 重配成 UTF-8（所以手动起也有效）
- `start-all` 会给子进程设 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`

所以如果你看到这个，说明**跑的是旧代码**（Node/Python 都不会热加载）：重启进程、`git pull` 后再跑。
`node tests/python-suite.py` 里有一条专门的回归测试盯着它（不带 UTF-8 环境变量起子进程、
验输出字节），改动到了会被当场抓住。

### ⑧ 字幕出来了，但内容不对

- **整句都错、像乱码** → 采样率对不上。检查 `var/live/audio-in.rate` 里的数字，
  和手机状态行显示的采样率是否一致
- **缺字、少半句** → 说话声音太小，或停顿太短。门槛是自适应的（安静环境会自动调低），
  但离手机太远仍会漏
- **出现"请不吝点赞订阅"这种莫名其妙的话** → Whisper 在静音/噪声上"编话"。
  已经加了两道闸（能量门槛 + 置信度门槛），如果还出现，说明环境噪声太大

## 五、换 ASR / 换眼镜时要改哪里

| 要换的东西 | 改哪里 | 不用改什么 |
|---|---|---|
| **换 ASR**（电脑 Whisper → 云端 ASR） | 只换电脑端识别那一段，或手机端换上传协议 | 插件、收件箱协议、字幕排版全不动 |
| **换眼镜**（虚拟屏幕 → 真蓝牙） | 只在手机端：新增一个输出实现，把 `onFrame` 收到的 `lines` 用蓝牙推出去 | 电脑端、协议、插件全不动 |
| **换模型 / 改巴葡口径** | 只在电脑端：`plugin/core.mjs` 的 `translationSystem`，或配置里的 `modelId` | 手机端全不动 |
| **改显示预算**（量出真眼镜的行列数） | 电脑端 `harness-side.mjs --cols N --lines M` | 手机端会自动跟着变（预算由电脑下发） |

最后一条特别说一下：**显示预算不是手机里硬编码的**。手机连接时通过 `/hello` 从电脑
取回 `cols` / `lineBudget`，面板字号也跟着算。所以你量出真眼镜的数值后，只改电脑端
一个参数，手机端立刻跟着变——这就是"接缝"的意义。

## 六、开发者模式到底"假"在哪

它假在**输出装置**，不假在别处：

- ✅ 真的：麦克风、真的录音上传、真的识别、真的送到电脑、真的调大模型、
  真的按 40×3 折行、真的字幕内容
- ❌ 假的：本该显示在眼镜上的东西显示在手机屏幕上了

所以眼镜到手时，唯一要补的是"把 `lines` 推给眼镜"，而**折行/截断的正确性已经验证过了**——
这一点很重要：字幕太长会不会被截掉，是这类产品最容易出问题的地方，现在就能提前发现。

## 七、没有手机时怎么测这条路

电脑上可以假装自己是手机，协议和安卓端**完全一致**（裸 PCM、每块一秒、第一块带 `?fresh=1`）：

```powershell
node relay/lan-relay.mjs                                          # 终端 1
# 终端 2：识别进程（用桥自己起，不要写 python | node 管道）
node bridge/asr-bridge.mjs --inbox var/live/asr-inbox.jsonl --from zh-CN ^
  --whisper-follow var/live/audio-in.pcm --whisper-device cuda --whisper-compute float16
# 终端 3：把一段录音当"手机上传"发过去
python bridge/make_long_wav.py var/audio/zh/20261004_002001.m4a var/audio/zh/short-16k.wav --times 3 --gap 1
node scripts/fake-phone.mjs --wav var/audio/zh/short-16k.wav --url http://127.0.0.1:8788 --secret 你的密钥
```

`fake-phone.mjs` 就是"假手机"：它逐块上传（加 `--realtime` 会按真实时间），
然后打印继电器侧收到的字节数与秒数。这条路跑通说明**协议这一层没问题**，
剩下的风险只在安卓的录音参数上。实测结果是收件箱里出现正确的 6 句中文。
