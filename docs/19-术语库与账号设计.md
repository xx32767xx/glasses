# 术语库与账号设计（管理员版）

> 依据：老师 2026-10-23 的答复（见 `docs/18` §11 第 3、5 条）
> 替代关系：`docs/15-热词对照表.md` 的**存储与权限部分**由本文取代；
> §5 的匹配规则（边界、危险邻接、实体重叠、折叠、幂等）**继续有效，一字不改**。
> 本文是设计稿，**尚未实现**。

## 1. 角色

| 角色 | 能做什么 | 备注 |
|---|---|---|
| **管理员（admin）** | 建库、改分类、审批申请、强制启用某库、管账号 | 保留的管理员账号；可跨会议 |
| **普通用户（user）** | 在会议配置里**选择**启用哪些库；对库提交**新增/更新/删除**申请 | 不能直接改库内容 |
| **测试账号（dev）** | 与 user 相同的界面能力，但由管理员手动创建、可设过期 | 开发联调用；不进生产数据统计 |

**一条硬规则**：**用户改不了库，只能提申请**。这是老师要求的核心语义，也让"表被用户改坏"这一类事故从设计上消失。

## 2. 库与分类

```
category（分类，一层）
  └─ library（库）
       └─ entry（条目，沿用 docs/15 §4.2 的 schema）
```

| 字段 | 说明 |
|---|---|
| `category.id / name` | 例如 `出口贸易`、`国际物流`、`法务`。**只做一层**，不做二级嵌套（先用起来再谈） |
| `library.id / name / categoryId` | 库属于一个分类 |
| `library.priority` | 数字，跨库冲突时用（见 §4） |
| `library.visibility` | `public`（所有用户可选）/ `restricted`（指定用户/组可选） |
| `library.entries[]` | 条目数组，沿用现有 schema 与校验（`validateTerms`） |
| `library.version / updatedAt` | 审批通过一次 +1 |

**会议级选择**：`meeting.libraryIds[]`（多选，可全空 = 不启用术语库）。
现有"每场只读一次表"的快照机制**保留**：会议开始时把选中库聚合、去重、冻结成一份快照，
会议中途管理员改库不影响正在进行的会议（沿用 `docs/15` §8.1 的语义）。

## 3. 申请与审批

### 3.1 申请类型

| 类型 | 目标 | 必填 |
|---|---|---|
| `add` | 往某库新增条目 | `libraryId`、`zh`、`pt`、`reason` |
| `update` | 改某库已有条目 | `libraryId`、`entryId`、改后字段、`reason` |
| `delete` | 删某库条目 | `libraryId`、`entryId`、`reason` |

### 3.2 状态机

```
pending ──approve──▶ approved（写入库，version+1）
   │
   ├──reject──▶ rejected（记 note）
   └──withdraw──▶ withdrawn（用户自己撤回）
```

- 每条申请记录：`id / type / libraryId / entry / reason / applicant / createdAt / status / by / at / note`
- **审批只有管理员**；管理员自己的改动**直接生效**，不走申请（避免自己批自己）
- **去重**：同一 `(libraryId, 规范化 zh, 类型)` 的 pending 申请只留一条 —— 沿用现有 `queuePendingLearn` 的去重思路
- **审计**：审批记录只追加不删（`requests.jsonl`），保留 90 天

### 3.3 冲突检查（审批时自动提示，不阻塞）

- 同库内 `zh` 重复 → 提示"已有条目，是否改为 update"
- 别的库有同 `zh` 不同 `pt` → 提示**跨库冲突**（见 §4）
- 目标写法与 `policy/br-pt.json` 内置术语冲突 → 提示（内置优先，用户表是叠加层，沿用 `docs/15` §4.3）

## 4. 跨库冲突规则（**待老师确认**）

一场会议同时启用 A、B 两库，都对 `亮亮眼镜` 给了不同目标写法时，谁赢？四个候选：

| 规则 | 做法 | 优点 | 风险 |
|---|---|---|---|
| R1 分类优先 | 子类/更具体分类的库优先 | 直观 | 分类要能表达"更具体"，可能不成立 |
| R2 选择顺序 | 创建者在会议里先选的库优先 | 无需新字段 | 用户不知道顺序意味着优先级 |
| **R3 显式优先级**（推荐） | `library.priority` 大的赢；同优先级即冲突 | 语义明确、可解释 | 管理员要维护优先级 |
| R4 冲突即禁用 | 有歧义就不启用该条目，会前提示 | 最安全（不会输出错译名） | 可能整库失效，体验差 |

**我的建议**：R3 + R4 组合 —— 库带 `priority`，同 `priority` 且目标写法不同的条目**不参与归一**，
并在会议配置页给出"存在冲突条目（3 条）"的提示，让创建者去改优先级。
理由：术语错的代价远高于"没有术语"（会输出错误的专名，用户无法察觉）。

## 5. 存储与接口

沿用现有"文件接缝 + 原子写"的做法（`lib/terms.mjs` 的 `atomicWrite`），不引入数据库：

```
var/data/
  accounts.json            # { users: [{ id, email, role, createdAt, status }] }
  codes.json               # 验证码短期存放（TTL）
  categories.json
  libraries/<libId>.json   # 单库一份，便于 diff 与审批写入
  requests.jsonl           # 申请与审批的只追加审计
  meetings/<meetingId>.json# 房间状态（成员/发言权/选中的库/计时）
```

**新增端点**（relay 扩展或并入房间服务）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/code` | 发验证码（邮箱） |
| POST | `/auth/login` | 验证码登录，返回会话令牌 |
| GET | `/libraries?category=` | 列出可见库 |
| GET | `/libraries/:id` | 单库详情（含条目） |
| PUT | `/libraries/:id` | **仅管理员**：改库（直接生效） |
| POST | `/requests` | 用户提交申请 |
| GET | `/requests?status=pending` | 管理员审批列表 |
| POST | `/requests/:id/approve` · `/reject` | 审批 |
| GET | `/meetings/:id/terms` | **聚合快照**（会议开始时冻结；插件读的就是它） |

**兼容**：现有 `GET/PUT /terms`（单表）**保留为 legacy**，`scripts/test-account.mjs` 与所有既有测试继续可用；
新旧并存期间，插件仍然只读"一份聚合快照文件"，所以**插件侧零改动** —— 这是让改造不炸的关键。

## 6. 与播报模块的接缝（P0 不做播报，但要先定接口）

播报由同组其他人的项目提供，我们是**调用方**。我们需要对方给出：

| 项 | 要求 | 为什么 |
|---|---|---|
| 接口 | `synthesize(text, lang, voiceId) → 音频流/URL` | 只播译文、不播原文 |
| 首包延迟 | 目标 < 500 ms | 超了就"声画不同步"，不如只给字幕 |
| 中断 | 支持"立即停止当前播报" | 新句覆盖、退出会议 |
| 多语种 | 中 / 英 / 巴葡 | 与会议语言一致 |
| 队列 | 我们负责排队；对方只需串行接受请求 | 原型要求"多人同时说话进队列、不重叠、切换有提示音" |

**由我们负责的仲裁逻辑**（不属于播报模块）：

1. **通道互斥**：耳机 ＞ 眼镜近耳 ＞ 手机外放；手机外放仅"远程参与"可开
2. **防自环**：开麦期间暂停播报，关麦后补播积压
3. **说话人切换提示音**与队列语义
4. **降级**：无耳机/眼镜 → 纯字幕，不出声

## 7. P0 范围（据 `docs/18` §11）

含：账号（邮箱+验证码、admin、dev 测试账号）、房间与发言权互斥、字幕（原文先行/译文后补）、
眼镜投屏、术语库（库/分类/选择 + 最小审批流）、转写存档。

不含：播报（外接）、AI 纪要、多房间回放、端侧模型、库的复杂权限（先 `public` 够用）。

## 8. 决定状态（2026-10-23 全部确认）

| # | 待确认 | 结论 |
|---|---|---|
| 1 | 跨库冲突规则 | **采纳 R3 + R4**：库带 `priority`，同优先级且目标写法不同 → 该条目不参与归一 + 界面提示 |
| 2 | 申请粒度与范围 | **管理员可以批量导入**；**用户可以对所有可用库提申请**（不限于本场会议启用的库） |
| 3 | 测试账号边界 | **只读 + 独立沙箱库 + 默认 7 天过期**（已实现，见 `lib/accounts.mjs` 的 `DEV_TTL_DAYS`） |

用户追加的两条要求，一并落在这里：

- **管理员与用户是两套界面**：管理端做库/分类/批量导入/审批/账号；用户端只做选库与提申请。
  两套界面共用同一批服务端函数（`lib/libraries.mjs` / `lib/requests.mjs`），**权限差异在服务端**，
  不在界面里 —— 界面隐藏按钮只是体验，真正的门在 `ROLE_PERMISSIONS`。
- **生产与测试两套数据库**：目录 `var/live`（生产）/ `var/live-test`（测试），
  由 `lib/store.mjs` 的 `resolveDataDir` + `assertEnvMatches` 双向断言保证不互串。

### 闭环怎么验（一条命令）

```powershell
node scripts/terms-loop-demo.mjs --env test
```

它会做四件事：建一份演示库（含带变体的条目，**会打印"我造了这个库"**）→ 生成会议快照 →
读**磁盘上的**模拟插件读法 → 用插件自己的纯函数 `normalizeTerms` / `translationSystem`
证明"库里的条目真的能改文本 / 真的能进提示词"，最后打印真会话该用的命令：

```powershell
node scripts/harness-side.mjs --live `
  --terms-path "<data-dir>/meetings/<场次>/terms.json" `
  --terms-active-path "<data-dir>/meetings/<场次>/terms-active.json"
```

⚠️ 两个参数**必须成对**：只换一个时插件会按"另一个文件里的 user 键"去找表，结果是**读到空表且不报错**
（这正是"看起来都对、其实没接上"的典型）。所以参数解析里直接禁止只给一个。

⚠️ 字段语义（踩过一次）：`variants` 是**中文侧**变体，`approved` 是**葡语侧**可接受写法。
把葡语变体写进 `variants` 不会生效 —— 匹配器的葡语索引只取 `pt + approved + wrong`。

### 与 ③（房间服务）的关系：为什么现在这样做不会返工

| | ② 现在 | ③ 以后 |
|---|---|---|
| 谁生成快照 | `start-all` 起服务前一次 | 房间服务**每开一个房间**一次 |
| 调的函数 | `writeMeetingSnapshot()` | **同一个，不改** |
| 快照目录 | `<data-dir>/meetings/<场次>/` | **同样规则**（场次 id 换成房间 id） |
| 怎么让插件读到 | `harness-side --terms-path …` | **同一个参数，不改** |
| 库/申请/账号 | `lib/libraries.mjs` 等 | **完全不动** |

三条纪律保证 ③ 只需"换调用方"：**场次 id 一律是参数**、**绝不写旧的全局 `terms.json`**、
**快照函数无副作用**（可被 N 个房间并发调用）。

```powershell
node scripts/terms-admin.mjs init      --env test
node scripts/terms-admin.mjs admin     --env test --email boss@example.com
node scripts/terms-admin.mjs dev       --env test --email dev1@example.com --days 7
node scripts/terms-admin.mjs category  --env test --name 出口贸易
node scripts/terms-admin.mjs import    --env test --file var/tmp/libs.json
node scripts/terms-admin.mjs request   --env test --type add --library lib-xxx `
     --zh "骁龙 8 Gen 3" --pt "Snapdragon 8 Gen 3" --reason 客户指定 --applicant alice@example.com
node scripts/terms-admin.mjs approve   --env test --id req-xxx --by boss@example.com
node scripts/terms-admin.mjs snapshot  --env test --meeting room-001 --libraries lib-a,lib-b
```

**为什么先做 CLI 而不是先做界面**：建库、审批、出快照这些动作必须在**没有安卓壳、没有网页**的
情况下也能被验证。先有壳没有动作，等于把 bug 藏进 UI 里。CLI 稳定后，两套界面直接对着同一批函数写。
