## 三、技术路线（一张图）

```
【安卓手机】只当麦克风：16kHz 单声道 → 每 1 秒一块，把音频发到电脑
                （手机自带的语音识别在这台设备上不可用，已诊断定死；
                  识别挪到电脑，手机上的按钮只负责"开录/停录"和"听中文/听葡语"）
                              ↓
【电脑·转发进程】收音频 → 落盘 var/live/audio-in.pcm（只追加）+ 采样率/语种旁文件
                              ↓
【电脑·切句与识别】自适应能量门槛 → 静音判定切句 → 每句整段送 Whisper
                （这一段的策略、参数与依据单独成文：docs/06-收音策略.md）
                              ↓
【电脑·ASR 桥】识别结果 → 收件箱文件（一行一句话）
                              ↓
【电脑·harness 插件】判语向 → 调大模型翻译 → 按 40×3 排版 → 字幕帧
                              ↓
【电脑·转发进程】字幕帧 → 局域网发回
                              ↓
【安卓手机】画在「虚拟眼镜」面板上
                              （真机到手后改成蓝牙推给眼镜）
```

**为什么把识别放在电脑上**：手机自带识别服务在这台设备上不可用（见第四节），
而"整段送模型"需要 GPU，手机也没有。手机只负责录音，
识别与翻译都在电脑 —— 这也正好把算力放回了 harness 那一侧。

**核心设计：两个接缝，把两处不确定性各关进一个口子**

| 接缝 | 回答的问题 | 换它要改什么 |
|---|---|---|
| `transport` | 字幕**怎么出去** | 一个函数（`mock` / `file` / 待加蓝牙） |
| `translator` | 译文**从哪来** | **一个配置项**（harness 模型 / HTTP 端点 / 不翻译） |

**这两个接缝的直接价值**：把"翻译搬到端侧"从"要重写"降级成"改一行配置"；
把"换一台眼镜"从"要重写"降级成"改一个函数"。

**第三个设计：巴葡口径是数据，不是写死的提示词**

术语表与规则放在 `policy/br-pt.json`（唯一一份），提示词、动态插件、技能文档三处都由它生成。
改口径只改那一个文件。

## 五、过程中发现并修掉的关键问题（这一节最能说明工程能力）

**都是靠验证发现的，不是靠看代码看出来的：**

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | 工具的输出 schema 用了**错误的写法** | 会导致插件在真实 harness 里**第一个工具就加载失败**。是靠"把测试台从自造校验器换成检出里真实的 `defineTool`"抓到的 |
| 2 | 模型返回的结束标记是**对象不是字符串**，被代码当成"流异常" | **每一句完全正确的译文都被丢弃**，眼镜上什么都不显示。离线模式连掩盖了好几轮 |
| 3 | 提示词在「译成中文」方向上带着「用巴葡表达」的规则 | 把提示词打印出来才看到——看代码看不出来 |
| 4 | 巴葡术语表**在两个地方各存一份**，而且有错行 | 造成 agent 路径与自动翻译路径**质量不一致**；且这是"搬到端侧会失败"的直接原因 |
| 5 | 安卓 `ERROR_CLIENT`（代码 5） | 先修了代码里两个成因；仍失败后，**把诊断做进 App**（报出设备声明的识别服务 + 一次不指定语种的测试），从而**定死是设备问题**，不再猜 |
| 6 | 仓库里出现**符号链接环** | `git clean -xdf` 有顺着链接删到**另一个项目源码**的风险。已修并写入文档防复发 |
| 7 | ASR 的**自适应音量门槛死锁** | 环境一吵（底噪 0.012 > 缺省阈值 0.01），整段 66 秒被并成 5 句，**字幕只能每 15 秒出一次**。而且程序不报错、不崩溃 —— 纯静默失败 |
| 8 | 前导缓存被算进"说话长度" | 一声 0.1 秒的爆音被当成 0.35 秒的"一句话"送去识别，白算一次还容易诱发幻听 |
| 9 | Whisper 首次推理有 **11~25 秒**隐藏开销 | 不预热的话，用户说的**第一句话**会卡十几秒 —— 同传最不能接受的失败方式 |
| 10 | 用**错误的方法测速度**，结论会完全反过来 | 同一份代码：5.7 秒音频测出"不能用"（RTF 1.01），整段测出"能用"（0.56），按真实形态测出"确实跟不上"（1.15）。**方法错了，数字越精确越误导** |
| 11 | `--truncate` 是**惰性**的（写第一行时才清空） | 一行都没写时它静默失效，旧内容原样留着，看起来像"新识别没生效"；而且它是"写第一行"那刻才删，会删掉别人刚写进去的行 |
| 12 | 日志被当成"对方说的话"写进了同传链路 | 用 `python … 2>&1 \| node …` 接管道时，报错文本会变成字幕。**接管道永远不要写 `2>&1`** |
| 13 | Windows PowerShell 的原生命令管道**会缓冲 stdout** | 识别进程是"一直尾随不退出"的，于是缓冲永不刷新，桥一行都收不到 —— 表现成"录音上传没反应"。改为由桥自己起子进程并流式读 stdout |
| 14 | **切句是按手机上传节奏切的，不是按人说话的节奏** ★ | 见下一节 |
| 15 | **15 秒处硬切**，长对话被拦腰截断 | 到上限时在固定样本上切，两条字幕各拿半句。现在改为**优先在内部停顿处断** |
| 16 | 静音判定**太慢**（700ms）导致句子并成长段 | 用带标准答案的中文语料量出：判太慢代价 +14~17 个百分点，判太快只 +2 —— 缺省改为 **500ms**，同时延迟从 0.7s 降到 0.5s |
| 17 | 回显过滤会**吃掉正常短句** | 提示词全是常用字，而判据只看"是不是子串"，于是「中文」「输出」「句子」这类正常短句会被静默吃掉 |

## 五之二、合并到主分支时收掉的两处（"各自都对、合起来才炸"）

这两条值得单列，因为它们说明**分开测过的东西合起来仍可能坏**：

| # | 问题 | 为什么它很危险 |
|---|---|---|
| 18 | 校对的**修订帧没带原文** | 手机端是按**原文**认"这是同一条字幕"的。修订帧的 `source` 退化成译文本身 → 认不出来 → 屏幕上**多出一行**（那一行的"原文"位置还显示成译文），而不是原地改正。写校对那会儿帧里还没有 `source` 这个字段，所以两个功能各自都测过、合起来才炸 |
| 19 | 相对的 `--data-dir` 让收件箱**静默失效** | 继电器照写、插件读不到、屏幕上永远没字幕、**一个错都不报** —— 看上去像"翻译坏了"。现在启动脚本一律 `resolve()` 成绝对路径，插件见到相对路径**直接抛错并打日志** |

> 这两条的共同点：**故障表现都在"别处"**（屏幕上多一行 / 什么都不显示），
> 而根因在配置与字段契约里。所以现在都有测试直接盯着**总线上的帧**和**路径解析结果**。

**方法论**：每一步都留下可重跑的验证；假替身必须与真实实现一致（#1 和 #2 都是"假替身比真实宽容"造成的）。
第 7~17 条全部来自"真跑一遍"，看代码一条都发现不了。

### 最要命的一个（第 14 条）：切句是按**上传节奏**切的

**现象**：测试时"经常出现 `[识别] [丢弃 …：回显了提示词]`"，日志里还看不出丢的是什么。

**定位**：用户的录音还在，转发进程的日志里记着每个上传块的大小和到达时刻，于是可以把那次运行完整重放：

| 同一段音频、同样参数，只改"数据什么时候到" | 切出来的段（秒） |
|---|---|
| 整文件一次性喂 | `[2.9, 4.9]` |
| 按真实上传节奏喂（每秒一块） | **`[2.6, 1.0, 0.9, 1.9, 2.0]`** |

**同样的音频、同样的参数，只因为网络时序不同，切句结果就不同** ——
说明切句不是音频的函数，而是**时序的函数**：同样一句话，网络抖一下，字幕就变了。

**根因**：尾随循环里"没数据就补静音"那段（本意是"你半句松开按钮时把最后半句逼出来"），
判据是"连续 5 次轮询没读到数据"，而两次轮询之间睡 80ms → **实际只有 400ms**，
比手机**每秒一块**的上传间隔还短。于是正常上传时它反复判定"说话人停了"，
塞数字零伪造静音，**按上传节奏把句子切开**。
重放里那段 1.0 秒片段的电平与转发日志里某一块**完全相同**，就是被切开的一整块上传音频。

**为什么表现成"经常丢弃"**：切出来的 1 秒碎片正好是 Whisper 最容易出幻觉的长度。
重放里两种坏结果各出现一次 —— 一段被正确判为回显而丢弃；另一段变成假字幕
「谢谢观看,下次见!」**发到了眼镜上**。所以**丢字幕只是症状，按上传节奏切句才是病**。

**修法**：判据改成按**毫秒**累计；阈值改为 **2000ms**（明显长于上传间隔）；
不再伪造静音、直接把半句交出去；并把**被丢弃的原文**打进日志（否则永远只能靠猜）。

**验证**：同一个真实节奏重放 → 恢复成 `[2.9, 4.9]`，**与离线结果完全一致，0 丢弃 0 幻听**。

**统一收进一份文档**：[`06-收音策略.md`](06-收音策略.md) ——
从麦克风到"一句完整的话"分了几层、**当前所有缺省值及其实测依据**、
切句的八条原则、换场景时按什么顺序调、收音问题怎么诊断（诊断口诀在 §7）。

## 七、现场演示脚本（3 分钟版）

```powershell
# ① 不需要真机、不需要麦克风：一键演示整条同传链路，逐帧画出"眼镜屏幕"
node scripts/demo.mjs

# ② 手机端实测（电脑两个终端 + 手机装 App）
node scripts/harness-side.mjs     # 终端 1：harness + 插件
node relay/lan-relay.mjs          # 终端 2：局域网转发（会打印地址与密钥）
```

演示时重点看两件事：
1. **眼镜屏幕上的排版**——40 列 × 3 行是真实显示约束，长译文会被正确折行
2. **双向路由**——对方说葡语 → 显示中文字幕；佩戴者说中文 → 译成巴葡（标注为"出站给对方"）

**③ 真实录音跑通语音识别那一段**（有音频文件就能演示，不需要麦克风）：

```powershell
node tests/run-all.mjs                                  # 216 项 + 106 项语音分段/音频尾随断言，全绿
python tests/python-suite.py                            # 只跑分段器与音频尾随那 106 项
python bridge/whisper_stream.py --file 你的录音.wav --stats `
    --model large-v3 --device cuda --compute-type float16 --language zh
```

演示时重点看：**每句的耗时与 RTF**，以及最后那张统计表里的「理论最短延迟」。
这是"同传到底来不来得及"的直接答案，数字与测法见 `docs/04-语音识别验证.md`。

**④ 手机「录音上传」那条路（没有手机也能演示）**：

```powershell
node relay/lan-relay.mjs                                          # 终端 1
node bridge/asr-bridge.mjs --inbox var/live/asr-inbox.jsonl --from zh-CN ^
  --whisper-follow var/live/audio-in.pcm --whisper-device cuda --whisper-compute float16   # 终端 2
python bridge/make_long_wav.py var/audio/zh/20261004_002001.m4a var/audio/zh/short-16k.wav --times 3 --gap 1
node scripts/fake-phone.mjs --wav var/audio/zh/short-16k.wav --url http://127.0.0.1:8788 --secret 你的密钥 --realtime
```

`fake-phone.mjs` 用**和安卓 App 完全相同**的协议逐块上传音频，所以这条命令跑通，
就说明"手机只当麦克风、识别在电脑上做"这条路协议层是通的 —— 剩下的风险只在安卓的录音参数上。
实测结果是收件箱里出现 6 句正确中文。
