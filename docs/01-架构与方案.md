# 亮亮视野眼镜插件 + 中↔巴葡同传 app：方案与架构

> 目标：在 DeepSeek Harness（DSH）里自定义一个「亮亮视野（LLVision）眼镜某型号」的插件，
> 并在它之上搭一个中文↔巴西葡语的双向同传 app。
> 起点条件：**没有真机、没有厂商 SDK**，先把纯软件链路跑通。

---

## 一、先说三条改变方案的事实（都是查源码 / 实测得到的，不是推测）

### 1. DSH 没有任何音频能力

在 `packages/` 全量搜索 `microphone` / `getUserMedia` / `MediaRecorder` / `audioCapture`，**零命中**。
DSH 的 LLM 层也明确写着「多模态内容（图像、音频等）没有核心块类型」。

**结论：ASR（语音→文字）必须在 harness 之外。** 插件能做的只是驱动外部进程、拿它的文本结果。
这决定了系统必须有一条清晰的「文本注入」接缝，而不是假装插件能听。

### 2. 「在 harness 里自定义插件」有两条完全不同的路

| | 路线 A：动态插件（创造模式） | 路线 B：正式插件包 |
|---|---|---|
| 机制 | `cordis_define` 提交 `code.host`，`cordis_run` 在 `node:vm` 沙箱里求值并挂载 | 导出 `apply(ctx, config)` 的模块，经 profile 的 `cordis.patch.yml` / `--patch` 加载 |
| 沙箱能力 | 只有 `ctx`（受限）、`harness`、`console`、`btoa/atob/TextEncoder/TextDecoder`；`require`/`fetch`/`setTimeout` 被拦 | 完整 Node |
| 寿命 | 进程内存，重启即消失，**不能自动转正** | 持久，可交付 |
| 配置通道 | 无（只能改源码字面量） | `cordis.yml` 里那一行的 `config` |
| 何时用 | 试协议、试链路 | 交付 |

**结论：两条都做，且用同一份业务逻辑喂它们**（见第三节）。

### 3. preset 只能在会话「还没产出内容」时切换

宿主对已产出内容的会话返回 `agent-preset-locked`。
**所以动态插件必须在一个新建的「创造模式」会话里加载**，不能在已有会话里切过去。

### 4. 一个会直接卡死路线 A 的契约细节（实测出来的）

harness 的 `defineTool` 用的是自己的 **value schema DSL**，不是原始 JSON Schema。实测边界：

- `required` 只能是**每个属性上的** `required: true`；写成 `required: ['ok']` 数组 → 直接报错；
  写 `required: false` 也报错（要么 `true`，要么省略）；
- 每个 `type: 'object'` 节点**必须显式**声明 `additionalProperties: true|false`；
- `array` 的 `items` 上不能写 `required`；
- 可空字段（`string|null`）要用 `oneOf` 表达；
- `parameters: {}` 是**合法**的（这一点最初被怀疑，实测通过）。

第一版插件就是按原始 JSON Schema 写的 `output.schema`，**6 个工具会在第一个 `defineTool` 就全炸**。
这个坑是在把测试台从「仿造校验器」换成「检出里真实的 `defineTool`」之后立刻暴露出来的——
仿造校验器曾经放过它，给出的是虚假的安全感。修完之后加了门禁，这类错误不会再溜过去。

## 二、分层架构

```
┌──────────────────────────────────────────────────────────────────────┐
│  L4  工具层（agent 可调用）                                          │
│      leion_status · leion_display · leion_translate ·                │
│      leion_history · leion_inbox · leion_clear · leion_selftest      │
├──────────────────────────────────────────────────────────────────────┤
│  L3  同传管线（核心业务逻辑）                                        │
│      · 文本注入   ASR 收件箱：轮询外部追加的文本行（真实 timer 服务） │
│      · 语向判定   中→巴葡 / 巴葡→中 / 判不出就问，绝不猜              │
│      · 流式翻译   走 harness 已配好的模型路由（不用另配 key）         │
│      · 字幕节流   增量按 partialThrottleMs 合并，防止逐字刷屏         │
│      · 失败处理   finish≠stop 时丢弃半截译文，不显示残句              │
├──────────────────────────────────────────────────────────────────────┤
│  L2  字幕排版                                                        │
│      · 折行（CJK 算 2 列，拉丁算 1 列）                              │
│      · 截行（保留尾部 = 读者永远在追最新那句话）                      │
│      · 显示预算 40 列 × 3 行（AR 眼镜显示区很小，不排版就是溢出）     │
├──────────────────────────────────────────────────────────────────────┤
│  L1  transport seam  ← 唯一会随真机变化的一层                        │
│      · 'mock'  console + 内存，无真机也能跑完整链路                   │
│      · 'file'  把当前字幕帧写成 JSON，外部桥轮询后推真机              │
│      · 待加：'adb'（ctx.shell）、'ble'（外部守护进程）                │
└──────────────────────────────────────────────────────────────────────┘
        ↑ 文本注入（ASR 结果）              ↓ 字幕帧
   ┌─────────────────────────┐      ┌──────────────────┐
   │ harness 之外：          │      │ harness 之外：   │
   │ 麦克风 → ASR            │      │ 真机桥（adb/BLE/ │
   │ （本项目的 asr-bridge） │      │ 厂商 SDK 程序）  │
   └─────────────────────────┘      └──────────────────┘
        └─ 按行追加到收件箱文件（这是它与插件之间唯一的约定）
```

**「文本注入」不是抽象说法，是一个具体协议**：外部程序往 `inboxPath` 按行追加文本（纯文本行或
`{"text":...,"from":...}` JSON 行），插件轮询它。所以外部桥不认识插件、插件也不认识外部桥，
两边只共享「一行一句话」这个约定。**打开收件箱是「同传」，不打开就只是「agent 调用的翻译工具」。**

左侧那个框本项目已经实现了：`bridge/asr-bridge.mjs`（见第五节）。

**为什么这么分**：整份代码里，「眼镜怎么收字幕」是唯一一个我们**现在无法确定**的东西（没有 SDK、
没有协议文档）。所以它被压缩成一个函数 `createTransport()`。真机到手时改动面 = 这一个函数，
其它三层一行不动。这就是把不确定性关进一个接缝里，而不是让它渗进整个系统。

### 两个接缝，不是一个

后来我们意识到还有**第二个不确定性**，而且它的后果更大：**翻译这一步将来可能不在电脑上做**。

所以 L3 里也切开一道口子：

| 接缝 | 回答的问题 | 三种实现 | 换它要改什么 |
|---|---|---|---|
| `createTransport()` | 字幕**怎么出去** | `mock` / `file` / 待加的 `adb`·BLE | 一个函数 |
| `config.translator` | 译文**从哪来** | `harness-llm` / `http` / `none` | **一个配置项** |

`translator` 的三种取值：

- `'harness-llm'`（现状）：用 harness 的模型服务 `ctx.llm`，译文来自云端大模型
- `'http'`：POST 到外部端点。**把模型搬到手机端甚至眼镜端时用这一条**——端侧只要暴露一个
  HTTP 服务，插件配置一行就能接上，`core.mjs` 一行不改
- `'none'`：不做翻译。收件箱里的文字**就是最终字幕**，插件退化成纯显示通道（帧归属由收件行的
  `speaker` 字段决定）

同一份判断也适用于 **ASR**：收件箱那条协议里，"手机已经转写好"与"手机送音频、电脑转写"只是
两种写入方式，架构上无需区分。

### 巴葡口径是数据，不是提示词

L3 里最容易被忽略的资产是"巴葡不是葡葡"这个要求。它以前散在两处且**已经出现了漂移**：

| 在哪 | 长什么样 | 问题 |
|---|---|---|
| `plugin/core.mjs` 的 `translationSystem()` | 5 句原则 | 没有具体词表，模型只能自己猜 |
| `skills/…/SKILL.md` | 一张术语表 | 与那 5 句无关，会各自漂移；且有两行是写坏的 |

结果：**agent 走工具路径看到一张表，插件自动路径只看到一句原则**，两条路质量不一样。

现在 `policy/br-pt.json` 是唯一来源，三处产物全部由生成器派生（提示词、动态包内联、技能文档
那一节）。这不只是去重——**它是让这份策略资产能跟着模型走的前提**：提示词只在"大模型 + 云端"
这个组合里有效；搬到端侧小模型上，同一份数据要变成解码约束或后处理替换表。详见
[`policy/README.md`](../policy/README.md)。

## 三、一套逻辑，两个包装目标（避免两份代码腐烂）

同一个功能要用两种方式交付，最容易出的问题是**两份实现慢慢漂移**。本方案的做法：

```
              plugin/core.mjs            ← 业务逻辑唯一来源（零 import）
                    │
        ┌───────────┴────────────┐
        │                        │
        ▼                        ▼
  plugin/index.mjs        dynamic/leion-pro.host.js
  （正式插件，持久）        （动态插件，创造模式粘贴用）
  走 ctx.tools.register()   由 lib/artifacts.mjs 把 core.mjs **内联**后
  schema 取预编译产物       接上沙箱适配器生成（沙箱里没有模块系统）
```

两个生成器（`node scripts/generate.mjs`）：

1. **`plugin/schemas.generated.mjs`** —— 把 core 里的 schema DSL 经**真实 `defineTool`** 编译成
   原始 JSON Schema，供正式插件走 `ctx.tools.register()`。派生而不是手抄。
2. **`dynamic/leion-pro.host.js`** —— 内联 core 源码 + 沙箱适配器。

配套两道门禁（都在 `tests/run-all.mjs` 里）：

- **新鲜度门禁**：两个产物必须与生成器的输出**逐字节一致**，否则测试直接红。
- **一致性对比**：同一套 20 项契约断言跑在两个版本上，然后逐字段对比
  `fingerprint`、工具描述、`parameters` schema、`output.schema`、`render` 输出。

于是「两个版本行为一致」是**被持续验证的事实**，而不是靠人记得同步。

## 四、一个容易被做错的产品决策：谁在看眼镜？

Leion Pro / GLXSS ME 是**戴在自己脸上**的眼镜，屏幕只给佩戴者看。所以：

| 场景 | 谁说话 | 译文给谁 | 眼镜显示什么 |
|---|---|---|---|
| 听对方说巴葡 | 对方（葡语） | 佩戴者（中文） | **中文译本**（主线，`displaySpeaker: 'them'`） |
| 自己说中文 | 佩戴者（中文） | 对方（巴葡） | 只做一行回显确认；译文走**出站通道**（`outbound`，需 TTS / 第二块屏） |

把这两条混成一条通道是最常见的错误：会造成「把给对方的葡语字幕显示给了听不懂葡语的佩戴者」。

## 五、已经落地的东西

### 插件（两个版本，一份逻辑）

| 文件 | 说明 |
|---|---|
| `plugin/core.mjs` | 业务逻辑唯一来源：排版、语种判定、翻译管线、ASR 收件箱、transport seam、7 个工具规格 |
| `plugin/index.mjs` | 正式插件入口：`export name / inject / apply(ctx, config)`，零第三方依赖 |
| `plugin/schemas.generated.mjs` | 生成：预编译的原始 schema |
| `plugin/cordis.patch.yml` | bundle 层（装进 profile 用） |
| `plugin/cordis.local.patch.yml` | 开发 overlay（`--patch` 用，绝对路径） |
| `dynamic/leion-pro.host.js` | 生成：可直接粘贴给 `cordis_define` 的动态插件 |

7 个工具：`leion_status` / `leion_display` / `leion_translate`（双向同传主入口）/ `leion_history` /
`leion_inbox`（收件箱控制：status / start / stop / drain / reset）/ `leion_clear` /
`leion_selftest`（五条链路自检，一次说清「哪一段断了」）。

### ASR 收件箱：把「翻译工具」变成「同传」

没有它的时候，每一句话都要 agent（或人）调用一次 `leion_translate`——那是**翻译工具**，不是同传。
打开 `inboxPath` 之后：外部语音识别程序往文件里追加一行，插件用**真实 timer 服务**轮询，
自动判语向、流式翻译、排版、推字幕。

三条纪律（都有对应断言）：

| 纪律 | 为什么 |
|---|---|
| 只处理**以换行结束**的完整行 | 外部程序可以随时 flush；写了一半的 JSON 不会被当成一句话 |
| 坏行**只计数、不中断** | 一条写坏的 JSON 不该让整条同传停摆 |
| 翻译**串行**执行 | 并发会让字幕互相穿插，同传不能那样 |

另外文件被截断/轮转时自动从头重读，不会永远卡在旧偏移上。

### ASR 桥 `bridge/asr-bridge.mjs`（harness 之外的那一半）

插件那一侧只认「一行一句话」，但真实 ASR 的输出来得很碎：逐词打、用 `\r` 就地刷新同一行、
或者根本不换行。**如果直接转发，插件会收到半句话并把它翻出去——字幕就废了。**
所以桥里有三个东西：

| 机制 | 为什么 |
|---|---|
| `\n` 与 `\r` 都当行结束 | 很多 ASR CLI 用 `\r` 在原地刷新同一行 |
| 空行与多余空白被清掉 | 不往收件箱塞空句；顺带把句内换行压平，防止一句话被撑成多行 |
| **停顿即断句**（`--flush-on-pause-ms`） | ASR 不换行时字幕唯一能出来的方式；这个值就是字幕的延迟上限 |

四种引擎：`stdin`（管道给任意 ASR）、`command`（ASR CLI / 自写脚本）、`replay`（重放录制好的
转写，**演示与回归测试用，不需要麦克风**）、`whisper`（本地 faster-whisper + 麦克风）。
另有 `--truncate`（演示从干净屏开始）、`--dry-run`、`--format text|json`（json 可带
`from`/`to`/`speaker` 标记，等价于插件侧的 `inboxFrom`）。

随包附带 `bridge/sample-transcript.txt`：一段中葡交替的会议转写，用于**完全没有麦克风与 ASR 的演示**。

> `bridge/whisper_stream.py`（本地 Whisper 引擎）**未在本机验证** —— 它需要 `pip install
> faster-whisper sounddevice numpy` 并下载模型，开发环境里没有装。它是起点，不是已验证的实现。

### 同传操作规范 `skills/leion-interpreter/SKILL.md`

把「巴葡不是葡葡」写成硬约束，含用词差异表（ônibus/autocarro、celular/telemóvel、
geladeira/frigorífico、planejar/planear、time/equipa、trem/comboio…）、巴葡口语特征
（você 而非 tu、a gente、estar+gerúndio），以及 AR 字幕的长度纪律
（**数字必须原样保留，不许为了塞进 3 行做二次摘要**）。

这是强度最高的一层，因为它把「复刻的检查」换成了**真实实现**：

| 验证内容 | 用的东西 |
|---|---|
| 工具注册 | 真实的 `ToolRuntime.register()`（不是复刻的检查器） |
| 模型可见 schema | 从真实注册表 `ctx.tools.schemas()` 读出 |
| 工具调用 | 真实执行流水线（identity 保护、策略、分发、结果归一化） |

| 参数校验 | 真实流水线拒绝缺必填参数的调用 |
| 定时器 | 真实的 `@deepseek-ai/cordis-plugin-timer`（也就是真实部署里 base bundle 挂的那个） |
| 自检诊断 | `leion_selftest` 在只有 tools 服务时会如实报「翻译路由：FAIL」「收件箱：FAIL」，补齐假 llm / 假 fs 后五条全绿 |
| **桥 → 收件箱 → 真实 timer → 真实流水线** | 桥的两种写法都跑：json 行直接写入，以及**逐词到达、不换行**时靠停顿断句合成整句；两条都被真实 timer 取走并翻译（已处理 2 条、错误 0 条） |

顺带验证了一件事：给插件加上 `inject: ['timer']` 之后，**这个没挂 timer 的组合立刻让插件停在
PENDING**（探针 30 秒超时并如实报告）。这不是故障，而是「依赖没就绪」的真实表现——也说明
`inject` 声明不是装饰，它对加载行为有实际约束。

这个组合是**独立的一次性进程**，不影响正在运行的 Web GUI。

**实际跑出来的价值**（这一轮抓到的真 bug，都不是靠肉眼）：

1. `output.schema` 用了原始 JSON Schema → 6 个工具会在真实环境**第一个就炸**；
2. `leion_clear` 清空历史后又被那帧「清屏」污染，历史变成 1 而不是 0；
3. 自检工具的布尔字段把 shell 里的 `transport` 字符串**覆盖**了（旧测试台不校验类型，所以放过了）；
4. 逻辑抽取进 core 时，`translate` 的成功路径**漏了 `ok: true`**（原来是靠 shell 补的）；
5. 原版把状态放在模块级 —— 正式插件被多个 agent preset 同时挂载时会**互相串字幕**（已改成实例级状态）；
6. 加 `inject: ['timer']` 之后，真实组合立刻让插件**停在 PENDING**（组合里没挂 timer）——这正是「依赖没就绪」的真实表现，也说明测试台能抓到它；
7. 契约套件里收件箱的 `setInterval` 没人停 → Node 进程不退出（真实 Cordis 会随 fiber 释放，我的假 ctx 不会）；顺带发现 run-all 需要一个确定性退出。

## 七、真机接入：三条路，按可行性排序

亮亮视野有公开的 [UX SDK 页面](https://www.llvision.com/sdk-ux-sdk.html)（[产品页](https://www.llvision.com/h-col-118.html)），
另有 [GLXSS Pro 说明书](https://fccid.io/2AKLNG20A1/User-Manual/Users-Manual-3311506.pdf) 这类公开材料。
但 SDK 通常需要商务/开发者申请。

| 路径 | 做法 | 前提 | 风险 |
|---|---|---|---|
| **A. 厂商 SDK** | 申请 UX SDK，按 SDK 写显示接口，插件加一支 `'sdk'` transport | 拿得到 SDK 和授权 | 需要时间，可能要签协议 |
| **B. adb 侧路** | GLXSS 系列是 Android 设备；用 `adb` 推到设备上的显示程序 / 广播 Intent。加 `'adb'` transport（走 `ctx.get('shell')`） | 设备开 ADB、能连上 | 需要知道设备上的显示组件 |
| **C. 伴随 App 投屏** | 完全绕过底层：翻译结果走系统通知/悬浮窗，由厂商 App 呈现 | 只需要手机 | 控制不了排版，等于放弃 L2 |

**建议**：先用 B 打通「能显示」这一步（验证链路最有价值的部分），同时并行申请 A。

## 八、ASR 接入：三条路

| 路径 | 做法 | 延迟 | 前提 |
|---|---|---|---|
| **本地 Whisper** | 外部进程跑 faster-whisper / whisper.cpp，把文本写进收件文件 | 中（1–3 s 句级） | 本机算力 |
| **ASR 云** | 讯飞/腾讯/Deepgram 等流式识别 | 低 | API key |
| **眼镜/App 自带 ASR** | 厂商 App 已经做了识别，直接取它的文本 | 最低 | 取决于厂商是否开放 |

三者都通过同一个接缝进入插件：**「文本注入」= ASR 收件箱**。外部桥只做一件事——把识别结果按行
追加到 `inboxPath`。协议是「一行一句话」，插件侧已实现并验证（见第五节）。

| 路径 | 做法 | 缺什么 |
|---|---|---|
| **本地 Whisper** | `faster-whisper` / `whisper.cpp` 实时转写，每句 append 一行到收件箱 | 那个桥程序（~50 行 Python） |
| **ASR 云** | 讯飞/腾讯/Deepgram 流式接口，收到 final 结果就 append | API key |
| **眼镜/App 自带 ASR** | 厂商 App 已经识别了，取它的文本 | 厂商是否开放文本出口 |

> 注意：`ctx.web.fetch` **只支持 GET**（`WebFetchRequest` 只有 `url` 一个字段），
> 所以不能用它当 POST 桥。要 HTTP 推送得走正式插件包里的 Node `fetch`，或外部进程。

## 十、汇报时可以强调的三个点

1. **不确定性被关进了一个接缝**：没有 SDK、没有真机的情况下仍交付了完整可跑的系统；
   真机变化只影响 `createTransport()` 一个函数。而且接缝的**两侧**都能验证：
   对外是假 llm 跑通全链路，对内是真实 harness 的 schema 校验器。
2. **验证用的是产品代码，不是自造的校验器**：测试台加载检出里真实的 `defineTool` 与
   `validateJsonSchemaValue`，并进一步用**真实的 Cordis 组合 + 真实 `ToolRuntime` + 真实执行流水线**
   跑通注册与调用。正因为换了真实校验器，才立刻暴露出「`output.schema` 写法非法会让加载在第一个
   工具就炸」——**这个坑原本会在演示当天才炸**。
3. **一套逻辑两个交付形态，且有防漂移门禁**：生成器 + 新鲜度门禁 + 20 项契约套件跑两遍 +
   逐字段一致性对比。
4. **「同传」和「翻译工具」的分界被明确实现并验证**：ASR 收件箱让外部语音识别一写就上屏，
   不需要 agent 或人参与每一句。这不是接口预留，而是跑通了的路径（真实 timer + 真实流水线）。
5. **接缝的两侧都用真东西测过**：插件侧用真实 `ToolRuntime` 与真实执行流水线；外部侧有真实的桥
   与真实 CLI 运行。而且桥里那个「停顿即断句」是用**可控时钟**测的——不靠 sleep 赌时间。
