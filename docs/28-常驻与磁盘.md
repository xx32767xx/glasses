# 28 · 常驻运行与磁盘空间

> 两个现场问题，一个文档解决：
> **① SSH 一断进程就没了；② 日志/音频一直长，怕把盘写满。**
>
> 结论先说：
> - 常驻用 **systemd**（不是 `nohup`，也不是"别关终端"）——SSH 断开与本机终端完全无关；
> - 日志交给 systemd 自己收（**journald**，§3），**不要**再套 `| tee`；
> - 磁盘用 `scripts/leion-clean.mjs` 定期看/清（它**永不碰模型与评测数据**）。

---

## 1. 为什么 SSH 一断进程就死

你在终端里看到的是"进程跟着会话走"。实际原因是这个：

```
你 ssh 登录 → 得到 pts/0 → 在里面起 node start-multi.mjs
断开时，sshd 给它那个 pts 发 SIGHUP → 同**前台进程组**的所有进程收到 SIGHUP → 退出
```

所以任何"在前台跑的、或者挂在那个 shell 下的"东西都会死。`start-multi` 还会连带收掉它 spawn 的
relay / 切句 / 大脑 / python（因为它把它们当成自己的子进程管）。

> 注意：**`nohup … &` 只能救一部分**。它能挡住 SIGHUP，但解决不了三件事：
> 开机不会自启、进程崩了没人拉起、日志还得自己管。所以下面用 systemd。

## 2. systemd：一条命令搞定常驻 + 开机自启 + 崩溃重启

### 2.1 单元文件（多场会，也就是现在这套）

`sudo tee /etc/systemd/system/leion.service`

```ini
[Unit]
Description=亮亮眼镜 · 同传服务（多场会）
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/home/ubuntu/glasses

# ── 环境：这四样漏一个就会"手动能跑、systemd 起不来"（见 docs/10 §6 的排障表）──
Environment=HF_HOME=/opt/leion/models
Environment=DSH_CHECKOUT=/home/ubuntu/deepseek-harness
Environment=PYTHONUTF8=1
Environment=PYTHONIOENCODING=utf-8
Environment=PATH=/opt/leion/venv/bin:/usr/local/bin:/usr/bin:/bin
# 密钥与云端端点放单独文件（权限 600，不进仓库）
EnvironmentFile=/etc/leion/secrets.env

# ── 启动命令：与手敲的那条一致，只是**不要**再带 `| tee`（systemd 会自己收日志）──
# ⚠ `node` 必须写**你手敲时用的那个绝对路径**。apt 装在 /usr/bin/node 的往往是 18/20，
#   而项目要 Node ≥ 22.5（lib/db.mjs 用内置 node:sqlite）——写错就是启动即崩、
#   3 秒一重启的崩溃循环（见 §2.4）。先 `which -a node; node -v` 确认再填。
ExecStart=/usr/local/bin/node scripts/start-multi.mjs --public \
          --data-dir /var/lib/leion/test --port 8789 \
          --compute int8_float32 --max-models 3 --idle-flush-ms 5000 \
          --quiet-logs

# 崩了 3 秒后重来；连续崩 5 次就先停下（免得把日志刷爆、把显卡占死）
Restart=always
RestartSec=3
StartLimitBurst=5
StartLimitIntervalSec=120

# 停服务时把整个进程组一起收掉（start-multi 的子进程都在这个 cgroup 里）
KillMode=control-group
TimeoutStopSec=20

# ── 日志：交给 journald（按大小自动轮转，见 §3.1）──
StandardOutput=journal
StandardError=journal
SyslogIdentifier=leion

[Install]
WantedBy=multi-user.target
```

`/etc/leion/secrets.env`（**权限 600**，只放密钥类）：

```bash
sudo mkdir -p /etc/leion && sudo chmod 700 /etc/leion
sudo tee /etc/leion/secrets.env >/dev/null <<'EOF'
DEEPSEEK_API_KEY=sk-xxxx
DASHSCOPE_API_KEY=sk-ws-xxxx
DASHSCOPE_WS_URL=wss://ws-xxxx.cn-beijing.maas.aliyuncs.com/api-ws/v1/inference
EOF
sudo chmod 600 /etc/leion/secrets.env
```

### 2.2 启用、查看、重启

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now leion
sudo systemctl status leion --no-pager

# 看实时日志（这是**唯一**看日志的正确姿势，不用再 tee 到文件）
sudo journalctl -u leion -f
sudo journalctl -u leion --since '10 min ago' | grep '\[切句\]'
```

现在**关掉 SSH 也没关系**：进程在 systemd 的 cgroup 里，和你的终端没有关系了。

### 2.3 两条必须知道的 systemd 行为

| 行为 | 含义 |
|---|---|
| `Restart=always` | 崩溃/被 OOM 杀掉都会自动拉起；**但正常 `systemctl stop` 不会重启** |
| `KillMode=control-group` | 停服务时把 start-multi 以及它 spawn 的 relay/切句/大脑/python **一起收掉**（不会留下孤儿 python 占着显存） |

> 一个坑：如果你**同时在终端里手跑一份**，systemd 那份会因为端口被占而起不来
> （`EADDRINUSE`），日志里能看见。**先 `systemctl stop leion` 再手跑**，或反过来。

### 2.4 服务"起来了又立刻重启"（崩溃循环）怎么查

`systemctl status` 显示 `activating (auto-restart)`、`status=1/FAILURE`，就是**崩了、`Restart=always` 又拉起、再崩**。
这不是配置没生效，是**进程自己退出**——先看它为什么退出，别看 systemd：

```bash
sudo systemctl status leion --no-pager     # 看 "Process: … status=1" 和 "restart counter"
sudo journalctl -u leion -n 60 --no-pager  # 看最后那段堆栈，第一行 Error/throw 才是真因
```

排查顺序（按出现频率）：

| 日志里看到 | 真因 | 怎么修 |
|---|---|---|
| `ERR_UNKNOWN_BUILTIN_MODULE: No such built-in module: node:sqlite` | 单元里的 node **太旧**（apt 的 18/20 < 22.5）；手动跑用的是 PATH 里的新版，所以"手动能跑、服务起不来" | `which -a node; node -v; /usr/bin/node -v` 找出新版绝对路径 → `sudo systemctl edit leion` 里覆盖 `ExecStart=` → `daemon-reload` + `reset-failed` |
| `EADDRINUSE` | 端口被另一份进程占着（终端里手跑的那份没关） | `ss -ltnp \| grep 8789` 找到 pid，或 `systemctl stop leion` 后手跑 |
| `Error: 数据目录…` / `EACCES` | `User=` 对数据目录没写权限 | `sudo chown -R ubuntu /var/lib/leion` |
| `spawn python3 ENOENT` | 单元里的 `PATH` 没带 venv | `Environment=PATH=/opt/leion/venv/bin:…`（§2.1 已写） |
| 什么都没有、秒退 | `ExecStart` 路径/参数写错（相对路径、换行续行丢空格） | `WorkingDirectory` + 绝对路径；`systemd-analyze verify leion.service` |

修完这三条才算真的重启成功（**`reset-failed` 别忘**：`StartLimitBurst=5` 刷满后 systemd 会拒绝再启动，只改文件不重置就一直 `failed`）：

```bash
sudo systemctl daemon-reload
sudo systemctl reset-failed leion
sudo systemctl restart leion && sleep 5 && sudo systemctl status leion --no-pager
```

自检：启动头几行日志里 `node -v` 必须 ≥ 22.5；`node scripts/preflight.cjs` 六项全绿再交给 systemd。

## 3. 日志：只配一处，就是 journald

**先给结论**：日志只有一个去处 —— systemd 的 **journald**。

- 不要 `| tee main.log`（它**永不切割**，一份文件会一直涨到把盘写满）；
- 不要在单元里 `StandardOutput=append:/var/log/…`（那样 journald 就不收了，还得再配 logrotate 自己造轮子）；
- 不要让程序另写一套 `<data-dir>/var/logs/*.log`（同一份内容写两遍，磁盘翻倍）。

### 3.1 一次做完的配置（之后不用再管）

```ini
# /etc/systemd/journald.conf —— 改完 sudo systemctl restart systemd-journald
[Journal]
Storage=persistent
SystemMaxUse=2G
SystemMaxFileSize=200M
MaxRetentionSec=2week
```

| 键 | 作用 | 不配会怎样 |
|---|---|---|
| `Storage=persistent` | 落到 `/var/log/journal`，重启/重启服务后还在 | 默认 `auto` 在内存（`/run/log/journal`），**一重启日志全没了** |
| `SystemMaxUse=2G` | 整个 journal 的硬上限，超了从最旧的删 | 无限长，直到把盘写满 |
| `SystemMaxFileSize=200M` | 单个 journal 文件上限 | 单文件过大，`--vacuum` 粒度粗 |
| `MaxRetentionSec=2week` | 最多留两周 | 同上 |

```bash
sudo systemctl restart systemd-journald
journalctl --disk-usage            # 现在占多少
sudo journalctl --vacuum-size=1G   # 想立刻压到 1G 就这么干
```

容量参考：一场两小时会议，纯文本日志大约 20–60 MB，`2G` 够放一个月以上。
真实的**音频/库文件**才是吃盘的（见 §4），日志从来不是主角。

### 3.2 启动命令里加一个 `--quiet-logs`

```ini
ExecStart=/usr/local/bin/node scripts/start-multi.mjs --public … --quiet-logs
```

不加的话 `start-multi` 除了往终端（也就是 journald）写，还会把每一路
（relay / 切句·房间 / 大脑·房间 / 识别）再落一份到 `<data-dir>/var/logs/<步骤>.log`
—— 内容完全重复，而且随会话时长线性增长（每路一份）。交给 journald 就够了。

### 3.3 日常就这四条命令

```bash
sudo journalctl -u leion -f                      # 实时跟（等价于原来 tail -f）
sudo journalctl -u leion --since '10 min ago'    # 最近十分钟，排障最常用
sudo journalctl -u leion --since today | grep '\[切句\]'   # 按标签捞
journalctl --disk-usage                          # 日志自己占了多少盘
```

> 没有服务单元、正在手跑的时候，`-u leion` 换成 `-t leion` 或直接看终端输出即可。

### 3.4 附录：确实需要一份纯文本文件时

只有"要把日志发给别人"这一个理由值得落文件。那就**别用 `tee`**，用 logrotate 管：

```
# /etc/logrotate.d/leion
/var/log/leion/*.log {
    daily
    rotate 7
    maxsize 200M
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
```

`copytruncate` 让进程不用重启也能切割（代价：切割瞬间可能丢几行，够用）。
`sudo logrotate -d /etc/logrotate.d/leion` 是演练，不真转。

## 4. 磁盘：先看清楚是谁在长，再决定删什么

```bash
node scripts/leion-clean.mjs --data-dir /var/lib/leion/test            # 只报告（缺省）
node scripts/leion-clean.mjs --data-dir /var/lib/leion/test --clean    # 真删（3 天前）

# 换阈值：只清 7 天前的
node scripts/leion-clean.mjs --data-dir /var/lib/leion/test --older-than 7 --clean
```

它报出来的是这些（**都只增不减**，除非你动手）：

| 类别 | 谁在写 | 会不会自己清 | 能不能删 |
|---|---|---|---|
| `audio/<房间>/<说话人>.pcm` | relay 追加（**从不清空**，为了不丢音频） | ❌ 永不 | ✅ 历史音频可以删 |
| `asr-inbox-<房间>.jsonl` | 识别进程追加 | 只在开新会话时按房间清 | ✅ 历史可以删 |
| `queue/asr/*` | 切句写、识别删 | ✅ 被消费就删 | 卡住才会积（报告里会显示） |
| `buses/<房间>.json` | 大脑写 | ❌ 散会后留着 | ✅ 可以删 |
| `var/logs/*.log` | start-multi | ❌ | ✅ 可以删 |
| `var/cache/`（模型 6.7G） | HF / faster-whisper | ❌ | ⛔ **绝不能删**（重下几 GB） |
| `var/asr-eval/`（评测数据） | 评测脚本 | ❌ | ⛔ **不能删**（要重跑） |
| 数据库（`leion.db`） | relay | 有保留期清理 | ⛔ 走 `--purge-history`，别手删 |

它**永远不会**碰模型、评测数据、数据库 —— 这三样删错的代价远大于省下的空间。

### 4.1 定时跑（每天凌晨 4 点清一次 7 天前的）

`sudo tee /etc/systemd/system/leion-clean.service`

```ini
[Unit]
Description=亮亮眼镜 · 清历史音频与日志

[Service]
Type=oneshot
User=ubuntu
WorkingDirectory=/home/ubuntu/glasses
ExecStart=/usr/local/bin/node scripts/leion-clean.mjs --data-dir /var/lib/leion/test --older-than 7 --clean
```

`sudo tee /etc/systemd/system/leion-clean.timer`

```ini
[Unit]
Description=每天 04:00 清一次

[Timer]
OnCalendar=*-*-* 04:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now leion-clean.timer
systemctl list-timers leion-clean.timer
```

### 4.2 一次性应急（盘快满了）

```bash
df -h /                                  # 先看还有多少
sudo journalctl --vacuum-size=500M       # 日志先压
du -sh /var/lib/leion/test/* | sort -h   # 谁最大
node scripts/leion-clean.mjs --data-dir /var/lib/leion/test --older-than 0   # 看"全清"能腾多少
node scripts/leion-clean.mjs --data-dir /var/lib/leion/test --older-than 0 --clean
```

> `--older-than 0` = 不按时间筛（**会删光**这几类历史数据）。应急用，别当日常。

## 6. 附录：systemd 是什么，以及那几条命令各自在干什么

### 6.1 一句话

**systemd 是 Linux 的 1 号进程（PID 1），也是「服务的管家」。**
系统里所有长期运行的东西（ssh、cron、docker、我们的 `leion`）都注册在它名下，
由它**启动、看护、重启、记日志、关机时按顺序停**。

它接管了以前三个工具的活：`init`（开机启动）、`cron`（定时任务），
外加一套统一日志 `journald`（替掉 `syslog`）。所以一个 `leion-clean.timer` 就替掉了 crontab。

### 6.2 四个概念，够用一辈子

| 概念 | 是什么 | 我们这里的例子 |
|---|---|---|
| **unit（单元）** | systemd 管的一个对象，写成一份文本配置 | `leion.service`（服务）、`leion-clean.timer`（定时器） |
| **unit 文件放哪** | 自己写的放 `/etc/systemd/system/`；系统自带的在 `/lib/systemd/system/` | `/etc/systemd/system/leion.service` |
| **cgroup（控制组）** | 把服务的**所有子进程**归成一组，统一杀、统一算资源 | `start-multi` 起的 relay、切句、大脑、python 都在 `leion` 这个组里 |
| **target（目标）** | 一组 unit 的集合，相当于"开机阶段" | `multi-user.target` ≈ 旧式的多用户运行级 |

**cgroup 这一条对我们特别重要**：`KillMode=control-group` 让 `systemctl stop leion`
能把整棵进程树一起收掉。少了它，停服务只杀 `node start-multi.mjs`，
**python 识别进程会变成孤儿**，继续占着那几 GB 显存 —— 下次启动就 OOM。

### 6.3 unit 文件的三段，每段管什么

```ini
[Unit]        # 元信息与依赖：描述、什么时候启动（After= / Wants=）
Description=…
After=network-online.target

[Service]     # 怎么跑：谁、在哪、什么命令、崩了怎么办、日志去哪
Type=simple            # 前台进程（我们的 node 就是这种）
User=ubuntu
WorkingDirectory=/home/ubuntu/glasses
Environment=…          # 单个变量
EnvironmentFile=…      # 一整份变量文件（密钥放这儿，权限 600）
ExecStart=…
Restart=always         # 崩了自动拉起
KillMode=control-group # 停服务时连子进程一起杀
StandardOutput=journal # 日志进 journald

[Install]     # enable 时挂到哪个 target 上（决定"开机自启"）
WantedBy=multi-user.target
```

`[Service]` 里的 `Environment=` 是**最常见的坑**：systemd **不读你的 `.bashrc`、也不继承你终端里的变量**。
"手动能跑、systemd 起不来" 99% 是少了一个（venv 的 `PATH`、`HF_HOME`、`DSH_CHECKOUT`、`LD_LIBRARY_PATH`）。

### 6.4 那几条命令分别在干什么

| 命令 | 干什么 | 什么时候用 |
|---|---|---|
| `sudo systemctl daemon-reload` | 让 systemd **重新读一遍** `/etc/systemd/system/` 下的 unit 文件 | **只有改了 unit 文件才需要**；它不会重启任何服务 |
| `sudo systemctl enable --now leion` | `enable` = 建软链让它**开机**被拉起（`WantedBy=multi-user.target`）；`--now` = 顺便**立刻启动** | 第一次装、新写的 unit 第一次跑 |
| `sudo systemctl status leion --no-pager` | 看**状态**：`active (running)` / `failed`、PID、内存、最近 10 行日志、是否 enabled | 怀疑"它到底在不在跑" |
| `sudo journalctl -u leion -f` | `-u` 指定 unit、`-f` = **follow**（像 `tail -f`），新日志实时打出来 | 盯实时；**Ctrl-C 只是退出看日志，不停服务** |
| `sudo journalctl -u leion --since '10 min ago' \| grep '\[切句\]'` | 先按时间取一段，再筛出切句那几行 | 查"刚才那几分钟切句怎么了" |

关于 `daemon-reload` 的一句人话：systemd 启动时把 unit 文件**读进内存**。
你用编辑器改 `/etc/systemd/system/leion.service` 之后，内存里那份还是旧的 ——
`daemon-reload` 就是"把磁盘上的重新装进内存"。所以流程永远是
**改 unit → `daemon-reload` → `systemctl restart`**；
只改代码（`git pull`）则**不需要** `daemon-reload`，直接 `restart` 即可。

### 6.5 日常操作速查（都在 `sudo systemctl …` 后面接）

| 命令 | 作用 |
|---|---|
| `start leion` / `stop leion` | 起 / 停（停会把整个 cgroup 收掉） |
| `restart leion` | 重启（= stop + start）；**改了代码或 `Environment=` 之后用它** |
| `status leion` | 状态 + 最近日志 |
| `is-active leion` | 只回 `active` / `inactive` / `failed`（给脚本用） |
| `is-enabled leion` | 只回 `enabled` / `disabled`（开机自启与否） |
| `cat leion` | 打印它**实际生效**的 unit 内容（含覆盖片段） |
| `disable --now leion` | 撤销开机自启**并**立刻停止 |
| `mask leion` | 彻底禁掉（连手动 start 都不行），排查时用 |
| `list-units --failed` | 当前所有失败的 unit（一眼看还有没有别的坏了） |
| `list-timers` | 所有定时器 + 下次触发时间（查 `leion-clean.timer`） |
| `show -p MainPID leion` | 只看某个属性（脚本里好用） |

### 6.6 日志（journalctl）常用参数

```bash
journalctl -u leion                    # 这个 unit 的全部日志
journalctl -u leion -f                 # 实时跟进（Ctrl-C 退出，不停服务）
journalctl -u leion -n 200             # 最近 200 行
journalctl -u leion --since '10 min ago'
journalctl -u leion --since today --until '11:00'
journalctl -u leion -p err             # 只看 error 及以上
journalctl -u leion -b -1              # 上一次开机（崩溃重启后查这个）
journalctl --disk-usage                # journal 占了多少
sudo journalctl --vacuum-size=500M     # 立刻压到 500M
journalctl -u leion -o cat             # 去掉时间戳前缀（程序自己打了时间时好读）
```

### 6.7 状态怎么读（`status` 输出的三行关键）

```
Active: active (running) since ...          ← 正在跑
     ↑      ↑
     |      运行子状态：running / exited / failed
     主状态：active / inactive / failed / activating
Main PID: 434380 (node)                      ← 主进程
   CGroup: /system.slice/leion.service        ← 这一组里还有哪些进程（我们的 python 在这儿）
```

看到 `Active: failed` 或 `start-limit-hit`，意思是**它连续崩了 5 次、被 systemd 主动放弃了**
（`StartLimitBurst=5`）。先 `journalctl -u leion -n 100` 看真正的报错，修好后
`systemctl reset-failed leion && systemctl start leion`。

### 6.8 定时器（替掉 crontab）

`leion-clean.timer` 就是一个 unit：`OnCalendar=*-*-* 04:00:00` 是每天 4 点，
`Persistent=true` 表示"错过了（比如当时关机）下次开机补跑"。等价 cron 的 `0 4 * * *`，
好处是**输出进同一套 journald**，不用另配日志重定向。

```bash
systemctl list-timers leion-clean.timer     # 下次什么时候跑
sudo systemctl start leion-clean.service    # 手动立刻跑一次（是 .service，不是 .timer）
sudo journalctl -u leion-clean              # 看它干了什么
```

### 6.9 不用 root 的版本（可选）

想以普通用户跑、不用 `sudo`：把 unit 放到 `~/.config/systemd/user/leion.service`，
命令用 `systemctl --user …`。**但必须**开一次 linger，否则你注销后它会被停：

```bash
loginctl enable-linger ubuntu
systemctl --user enable --now leion
```

副作用：普通用户服务**读不到 600 权限的 root 文件**（`/etc/leion/secrets.env` 会失败）。
要么把那个文件 chown 给运行用户，要么继续用系统级 unit（§2.1）。
