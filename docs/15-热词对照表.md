> **这份文档是什么**：老师提出「允许用户上传热词对照表、绕过模型直接对输出做形式化替换」之后，
> 把这个功能**说清楚到可以照着写代码**的程度 —— 数据长什么样、匹配怎么做、什么时候生效、
> 失败时怎么办、怎么证明它没把事情搞坏。
>
> **写入目的不是"方案已定"，而是"分歧已收敛"**：下面每条规则都标了它是**已定**（你或老师

## 1. 一页结论

- 这件事的本质是**术语后编辑**：不训练模型、不改模型权重，在译文**出来之后**按用户给的对照表
  做形式化替换；如果按用户要求做"强制"，还要能发现"该出现却没出现"并修掉。
- 用户上传对照表这件事，**把原先的阻塞点消掉了**：我们原来不知道"模型会把 `亮亮视野` 写成什么"
  （音译？直译？保留中文？），现在用户可以自己声明"必须写成 `LLVision`"。
  但**归一化（把变体收敛到规范形式）仍然需要变体清单** —— 用户至少填名称对照；
变体清单可以让效果更好（见 §11 末尾"变体从哪来"），但**不是使用前提**。
- 同一个中文词在葡语里**有性别**，性别决定冠词/缩合（`na LLVision` / `do LLVision`）。
  这决定了"强制"必须**在译文侧做**、并且**不能用不透明占位符**（占位符会把性别线索抹掉，
  详见 §7.3）。我们的 `policy/br-pt.json` 里已经有 `nounGenders` 这份数据可以复用。
- 我们的判据层 `plugin/translation-lint.mjs` **已经在用同一份专名数据查错**（`properNounProblems`）。
  所以这个功能天生是"**改**"与"**查**"共用一份数据：改错了会被自己的判据抓出来，这是它最值钱的地方。

**一句话**：用户表解决"该写成什么"，匹配规则保证"不会误伤"，判据层保证"改坏了能被发现"。

## 2. 名词先统一，否则会把三件事谈混

| 名字 | 在本文里的意思 | 谁来做 |
|---|---|---|
| **热词表 / 对照表** | 用户上传的 `源写法 → 目标写法` 映射（含可选变体清单、方向、强制级别） | 用户 |
| **术语后编辑（post-edit）** | 在译文出来之后，对译文做形式化替换的**总称** | 我们 |
| **① 归一化** | 译文里出现了**白名单变体**（`Leion Pro` / `leion pro` / `LeionPro`）→ 统一成规范形式 | 字符串 |
| **② 缺失修复** | 源句含该词、译文里**没有**规范形式 → 判为漏翻，再问一次模型 | **本期不做**（§7.1），属后续独立实验 |
| **③ 源侧提示** | 送翻译前把源句改成 `亮亮视野（LLVision）` 让模型照抄 | 改的是**输入**，风险最高 |
| **判据（lint）** | 已有的译文查错层，负责"改完之后还对不对" | 现有代码 |

⚠️ 老师最初说的是 **①+②**，但**本期只做 ①**：② 需要额外一次模型调用，会把"替换器本身"
的效果、耗时、失败原因混在一起，无法单独归因（理由见 §7.1）。② 是后续独立实验。
③（源侧提示）也不在本期范围（理由见 §7.3）。

## 4. 数据结构

### 4.1 存储布局（PC 侧，因为翻译在 PC 上跑）

```jsonc
// var/live/terms.json
{
  "version": 1,
  "updatedAt": "2026-10-19T09:12:33.000Z",
  "tables": {
    "wu": {                        // ← 用户名字符串（暂定按用户名定位用户）
      "updatedAt": "2026-10-19T09:12:33.000Z",
      "entries": [ /* 见 4.2 */ ]
    },
    "default": { "updatedAt": "...", "entries": [] }
  }
}
```

- **单一文件 + map**：按你说的"用户-热词表映射 map"，读一次全量、取自己那一份；
  relay 是单进程，写入用「临时文件 + rename」保证不被读到半个文件。
- **为什么不在手机本地**：翻译发生在电脑/服务器侧，手机存了也看不见、用不上。
  手机端只是**编辑与上传的界面**。
- **没有用户表时的行为**：回落到 `"default"`；再没有就当作空表（功能等同关闭），
  **不报错、不降级**，只在上传/日志里说明。

### 4.2 条目 schema

```jsonc
{
  "id": "t_7f3a",                 // 服务端生成，日志与报错都引用它（用户不用管）
  "zh": "亮亮视野",                // 中文侧写法（源或目标，取决于方向）
  "pt": "LLVision",               // 葡语侧写法（按巴葡正字法）
  "variants": ["亮亮视野科技", "亮亮视野（北京）"], // 可选：额外的**中文侧**写法，命中后收敛到 zh
  "approved": ["LL Vision"],      // 可选：译文侧的**可接受写法**（命中后收敛到 pt）
  "wrong": ["Liangliang Vision"], // 可选：**已知的错误写法** —— 命中后必须改成 pt
  "fold": true,                   // 可选：默认 true；有歧义的名字可关掉折叠（secretária/secretaria）
  "direction": "auto",            // auto | zh-to-pt | pt-to-zh（本次只实现 auto）
  "enforce": "must",              // must（强制）| hint（只提示）| off
  "gender": "f",                  // 可选："m" / "f"；写进译文侧语法提示用
  "note": "公司英文名",            // 可选：给人看的备注，不参与匹配
  "createdAt": "2026-10-19T09:12:33.000Z"
}
```

设计说明：

- **`zh` / `pt` 两侧都必填**。这是"双向"能成立的**前提**：反向时我们不是"从葡语反推中文"，
  而是用条目里**用户自己写的中文**。反推是不可靠的（`LLVision` 该翻成"亮亮视野"还是
  干脆保留英文？只有用户知道），所以协议上强制两侧都填。
- **`variants` / `approved` / `wrong` 是"①归一化"的燃料**。用户只填名称对照也能用，
  但**变体清单越全，归一化覆盖得越多**（docs/15 §11 末尾"变体从哪来"）。
  `wrong` 是**系统从真实译文里积累**的那一类（模型实际写成什么样），不是使用前提。
- **`gender` 是留给②用的**：将来若做缺失重译，能把"阴性、用 `na`/`da`"一起告诉模型，
  修复质量会高一个档。本期**只存不用**（不做②），所以它不影响当前行为；
  不填则退化为"只钉写法"。这也解释了为什么 §7.3 的占位符方案不划算。
- **`enforce: "must"` 的语义**：译文里没有 `pt`（或其 `approved` 形式）→ 视为失败，走 §7 修复。
  **不是**"尽量写成这样"。

### 4.3 与内置 `policy/br-pt.json` 的关系

内置文件里已经有同形的结构（`properNouns[].zh / approved[] / sourceForms[] / mustKeep`）
和 `nounGenders`。**不改动它**，用户表是叠加层：

| 层 | 谁维护 | 优先级（我的建议） |
|---|---|---|
| 用户表（`var/live/terms.json`） | 用户上传 | **高** |
| 内置 `policy/br-pt.json` 的 `properNouns` | 我们 | 低（被用户同名条目覆盖时记 `shadowed`） |
| 内置 `terminology`（ônibus/autocarro 这类用词偏好） | 我们 | 不参与本功能（它是"用词偏好"，不是"对照表"） |

## 5. 匹配规则（这是最容易出事的一段，逐条写死）

### 5.1 基本规则

1. **精确匹配**：葡语按词元（空白/标点切分）做**整词比较**；中文按字符做**精确子串**比较
   （中文没有词边界，见 5.1.1）。**不做**编辑距离、同音、正则、前缀/后缀。
2. **实体重叠规则（必需，不能只靠"最长优先"）**：
   同一批候选匹配里，**任何被更长的匹配完全覆盖的短匹配一律丢弃**。
   例：表里同时有 `Leion Pro` 与 `Leion`，碰到 `Leion Pro` 时只允许前者命中 ——
   因为 `Leion` 在 `Leion Pro` 里**有空格边界**，普通整词规则会把它算成一次命中。
   "最长优先"只在**同一位置**起作用，覆盖不了这种情况，所以单列一条。
3. **不跨界**：匹配结果不得跨标点、跨换行、跨句。
4. **每段文本里同一实体只替换一次**（幂等，见 §5.5）。

#### 5.1.1 中文边界规则（**必需**，因为中文没有词边界）

⚠️ 中文用字符子串匹配，**"最长优先"并不能保证不误伤**：`高通` 仍会命中 `高通量`、
`高通路` —— 只要表里没有更长的条目，最长优先就无事可做。所以另设两条：

| 规则 | 内容 |
|---|---|
| **R1 上下文抑制** | 匹配紧邻的汉字若与条目拼成"更长的常见词"，则不替换。判定用**保守的封闭集合**：紧邻字符属于 `的 了 是 在 和 与 及 等 都 就 而 但 又 也 很 更 最 不 没 有` 或标点/数字/拉丁字母 → 允许替换；其余汉字（如 `量`、`路`）→ **跳过并记 `boundary_skip`** |
| **R2 短词从严** | 中文条目只有 2 个字时（`高通`/`安卓`），R1 **强制执行** —— 这类条目上传时本来就带 `WARN_SHORT_ZH` 警告 |

R1 的代价要说明白：它会**漏掉**一些合法用法（「我们和亮亮视野合作」里 `合` 不在允许集合，
这条就会被跳过）。所以：

- R1 **只对 2 字条目强制执行**（风险最高的一档）；
- **3 字及以上**的中文条目按普通子串匹配，但**记录命中上下文**（前后各 6 个字）写进
  `terms.jsonl`，供事后审计 —— 这是"用审计换漏报"的取舍，不是假装没问题。

> ⚠️ 这一节是我在规程里写错过的地方：初稿只写了"最长优先"，那不足以挡住
> `高通/高通量` 与 `Leion/Leion Pro`。上面的重叠规则与 R1/R2 是补丁，
> 但它们仍然**不是数学保证** —— 所以 §10.2 的负对照是必过门槛，
> 而且 §10.1 要求人工抽检（有些误伤只有人看得出来）。

### 5.2 边界定义（葡语侧）

- 词边界字符集：空白、`.,;:!?¡¿()[]{}"'«»—–…/` 以及行首行尾。
- 大小写与变音符号**不参与边界判断**：`Leion` 与 `leion` 是同一个词元。
- 不把连字符当词内字符，除非条目本身含连字符（`Snapdragon 8 Gen 3` 里的空格也一样：
  条目含空格时按整串匹配，但两端仍要求边界）。
- **空格也参与折叠**：`LeionPro` 与 `Leion Pro` 折叠后同一串（§5.3）。这是有意的 ——
  模型确实会把产品名连写。

### 5.3 大小写 / 变音符号折叠（**已定：方案 D**）

**规则**（对应三个方案的第三种，即"折叠大小写 + 折叠重音，但短词不折叠"）：

1. `Leion Pro` ≡ `leion pro` ≡ `LEION PRO` ≡ `LeionPro`（忽略大小写与空格差异）；
2. `Léion` ≡ `Leion`、`ação` ≡ `acao`、`São Paulo` ≡ `Sao Paulo`（忽略重音符号，先做 NFC 归一）；
3. **但拉丁条目有效长度 ≤ 3 时，不做重音折叠**（`pau` 与 `pão` 不相等），中文条目不受此限；
4. 折叠只影响**"是不是同一个词"的判断**，不影响输出：输出永远用用户填的规范形式；
5. **条目可以关掉折叠**（`fold: false`）。有歧义的名字必须能关 —— 例：`secretária`（女秘书）
   与 `secretaria`（秘书处）折叠后同一串，硬折叠会让两条互相命中；
6. **上传校验必须用同一套折叠规则**查别名冲突（`ALIAS_CONFLICT`），
   否则"校验说没问题、匹配时两个条目互相覆盖"就会发生（见 §6.2）。

**为什么这么定**（三段理由，强度不同）：

- ✅ **上游噪声就是这样的**：ASR 输出的巴葡，重音符号时有时无（`acao`/`ação`、`nao`/`não`）；
  而用户用中文键盘填表时，几乎不会去打 `ã`。不折叠 = 双方都嫌麻烦、还认不出来。
- ✅ **它不属于"模糊匹配"**：模糊匹配是"看起来像就替换"（`equipa` → `equipamentos`，
  我们真的踩过）；折叠是"同一串字母的不同书写"。误伤面差一个数量级。
- ⚠️ **碰撞风险存在但可控**：`avô`/`avó`、`pão`/`pau` 折叠后会互相命中。
  概率我判断很低（用户表里是专名，不是普通名词），但**没测过**，所以用第 3 条规则
  把最短的拉丁词排除在外；并且把下面这组负对照写进测试，跑不过就不许上：
  `avô/avó`、`pão/pau`、`e/é`、`Sao/São`、`Leion/Leion Pro`（后者必须**不会被**前者整词命中）。

**为什么关掉折叠是更差的选项**（记录一下，免得以后反复讨论）：`LEION PRO` 认不出来 →
被判成"缺失" → 触发一次多余的模型重译；而重译大概率还是写成 `LEION PRO`（模型就爱这么写），
于是这一句永远修不好、还每次多花一次调用。**关折叠会把"零风险的书写问题"变成"要花钱的问题"。**


### 5.4 明确**不做**的匹配方式（每条都有理由）

| 不做 | 理由 |
|---|---|
| 编辑距离/相似度 | 实测教训：`equipa` 会命中 `equipamentos`（`docs/08` 判据自检的负对照就是这条） |
| 同音/拼音归一 | 中文同音字极多，误触发面大于收益；且那是**改 ASR 输出**，需要单独决策 |
| 正则 | 用户输入当正则 = 注入风险；转义写错就误伤大面积文本 |
| 大小写外的形态变化 | `LLVision` 的复数 `LLVisions`、所有格 —— 不做，交给用户写进 `approved` |
| 跨语言"猜测" | 例：葡语译文里出现 `亮亮视野`（中文残留）→ 不做自动识别，那属于 lint 的职责 |

### 5.5 幂等

同一条字幕可能三次经过（增量 → 定稿 → 校对修订）。规则：

- 替换**必须幂等**：`replace(replace(x)) == replace(x)`。
- 实现上的约束：替换后若再次匹配到"已规范形式"，**不得再替换**（把它加入"本次已处理"集合），
  避免 `LLVision` → `LLVision (LLVision)` 这类滚雪球。
- 增量帧**不替换**（半截词 `Leion Pr` 会被误判），只对定稿与校对后的帧替换。

## 6. 上传、校验与接口

### 6.1 端点（relay 侧新增，鉴权沿用现有共享密钥）

沿用 `relay/lan-relay.mjs` 的路由风格（`/hello`、`/say`、`/audio`、`/frame`、`/diag`、`/status`）：

| 方法 / 路径 | 作用 | 请求 | 响应 |
|---|---|---|---|
| `POST /terms/validate` | **只校验、不落盘**（界面可反复点） | `{ "user": "wu", "entries": [...] }` | `{ "ok": true/false, "accepted": N, "rejected": [{"index":3,"code":"TOO_SHORT","reason":"…"}] }` |
| `PUT /terms` | **全合法才整体替换**该用户的表 | 同上 | 成功：`{ "ok": true, "accepted": N, "effectiveAt": "next-session", "overwritten": false }`；有非法条目：**400 + 完整 rejected 清单，一个都不落盘** |
| `GET /terms?user=wu` | 取当前生效表（手机端回显） | — | `{ "ok": true, "user": "wu", "entries": [...], "updatedAt": "…" }` |

- **两阶段是已定方案（C）**：校验与落盘分开。这样界面能"边填边看红字"，而落盘语义保持
  **全有或全无** —— "看到 ok:true" 就等于"整张表生效"，不存在"一半生效而用户不知道"。
  为什么不做部分落盘：静默的部分生效**能绕过所有自动判据**（判据只看表里有的条目，
  看不到"本该在表里却没存进去"的条目），而我们给"误替换"定的门槛是 0。
- **整体替换而非增量**：用户传的是自己那张表，增量合并会产生"我以为删了其实还在"的错觉。
- **同名覆盖要明说**：同一用户名先传过表，这次再传 → 响应里 `overwritten: true` 并带
  `previousEntries: N`；界面显示"你覆盖了已有的 7 条"。
- **上限**（防滥用，与 `--public` 的加固思路一致）：条目 ≤ 500、单条文本 ≤ 200 字符、
  总请求 ≤ 64 KB、`user` ≤ 64 字符且只允许 `[A-Za-z0-9_\-.@]`。
- **不要**在 `/terms` 里做翻译或触发模型调用（它是纯存储 + 校验）。


### 6.2 上传时的静态校验（拒绝码）

> **阈值只有一套，就在这张表里**。§5.1 原来还写过一份"单字/双字黑名单"，两份不一致
> —— 已删掉那一份，以本表为准（代码：`lib/terms.mjs` 的 `validateTerms`）。

| 码 | 触发 | 处理 |
|---|---|---|
| `MISSING_SIDE` | `zh` 或 `pt` 有一侧为空 | 拒绝（双向要求两侧都有） |
| `TOO_LONG` | 任一侧 > 200 字符 | 拒绝 |
| `TOO_SHORT` | **中文侧只有 1 个汉字**，或**葡语侧 ≤ 2 字符** | 拒绝（见下面那条"阈值改过一次"） |
| `DUPLICATE_SOURCE` | 同一源写法出现两次（含仅大小写/重音不同），且目标不同 | 拒绝并指出第几条 |
| `ALIAS_CONFLICT` | **按折叠规则**看，同一个写法被两个条目占用（含藏在 `variants`/`approved` 里的），或同一条目里源侧与目标侧撞车 | 拒绝并指出被谁占用 |
| `CYCLE` | A→B 同时 B→A 且两侧互为源 | 拒绝（会来回替换） |
| `HAN_IN_PT` | 葡语侧含汉字 | 拒绝并提示"两侧可能写反" |
| `CONTROL_CHARS` | 含制表/换行/零宽字符 | 拒绝（不可见字符是最难查的误伤源） |
| `BAD_ENUM` | `direction` / `enforce` / `gender` 不在允许值里 | 拒绝 |
| `ENTRY_MALFORMED` | 条目不是对象，或 `variants`/`approved` 不是字符串数组 | 拒绝 |
| `TABLE_TOO_LARGE` / `TABLE_MALFORMED` | 条目数超上限 / `entries` 不是数组 | 拒绝整个请求 |

**警告（不拦上传，但要在界面上说）**

| 码 | 触发 | 为什么要说 |
|---|---|---|
| `WARN_SHORT_ZH` | 中文侧只有 2 个汉字（如「高通」「安卓」） | 会命中更长的词（「高通量」），而 §5.1.1 的 R1 就是为它强制开的 |
| `WARN_SHORT_LATIN` | 葡语侧只有 3 个字符（如 `IBM`、`BYD`） | 同上 |
| `WARN_NO_HAN_ZH` | 中文侧没有汉字（如 `Leion Pro`） | **只提醒，不拦** —— 中文句子里保留英文名是正常需求 |

**两条被改过的规则（记录原因，免得以后改回去）**

1. **阈值分两档**。初稿写"中文 ≤2 字 / 拉丁 ≤3 字符一律拒绝"，实现完拿真实专名一验，
   它把「高通」「安卓」「IBM」「BYD」**全拒了** —— 而那些恰恰是最需要钉住的名字。
   现在只硬拒"几乎必然误伤"的（中文 1 个汉字、拉丁 ≤2 字符），其余降为警告；
   真正的防线是 §5.1.1 的边界规则与 §10.2 的负对照，不是长度阈值。
2. **`LATIN_IN_ZH` 不再是拒绝码**。字段表示的是**语言方向**，不该强制字符种类 ——
   中文侧写 `Leion Pro` 是完全正常的（**两侧同名、原样保留**也算合法：那是空操作，
   不会来回替换）。写反的那种仍会被 `HAN_IN_PT` 拦住。

校验**全部通过才落盘**（已定方案 C：`validate` 可以随便调，`PUT` 只在全合法时生效）。
这样用户一次传 50 条、第 3 条写错时，会看到"哪一条、什么错"，改完再提交，
而不是"一部分悄悄没存上"。

**⚠️ 这里与"误替换"的关系要说清**：本阶段的校验**还不知道**匹配会不会误伤
（表合法 ≠ 表安全）。§10.2 那批负对照属于阶段 2 的匹配器；即便那时全过，
"上传成功"也只意味着"格式没问题、已知的坑都挡住了"，不意味着"用得没问题"。

## 7. 本期做什么、不做什么（"must"的准确含义）

### 7.1 本期只做一件事：**已知变体 → 规范写法**

对每条 `enforce: "must"` 的条目，在**定稿译文**上只做两件事：

1. **找**：译文里出现了该条目的某个**已知变体**（`wrong` / 非规范写法），按 §5.3 的折叠规则比较；
2. **换**：换成**同一语种的规范写法** —— 译文是葡语就换葡语规范写法，译文是中文就换中文规范写法。
   只做字符串替换，**不调用模型**。

> ⚠️ **"同语种归一"这件事我在实现时第一次搞反了**：写成"把中文名换成葡语写法"，
> 结果把中文塞进了葡语译文。正确定义是：**译文是什么语言，就在那种语言内部把写法收敛成本表的规范写法**。
> 跨语种替换（中文文本 → 葡语写法）只在 §7.3 那类"源侧提示"实验里才有意义，生产路径不用它。

**没有出现就记一笔，然后什么都不做。**

> ### ⚠️ `must` 的准确含义
>
> **`must` = "一旦命中了可替换的变体，就必须输出规范写法"。**
> **不是**"保证这个名字一定出现在译文里"。
>
> 这两件事差得很远，而规程初稿把它们混在一起了（§7.1 原来写着"未命中就默认重译一次"，
> 与 §12.1 已定的方案 C 直接冲突）。现在**以方案 C 为准**，全文统一：
>
> | 情况 | 本期行为 |
> |---|---|
> | 译文里有变体（`Liangliang Vision` / `leion pro`） | **换成规范写法** |
> | 译文里根本没有这个名字 | **只记录，不重译** |

**为什么本期坚决不做"缺失重译"**（这不是保守，是方法问题）：

- 一旦"缺了就重译"，**替换器的效果、耗时、失败原因就再也分不清了** ——
  一条字幕被改过，你无法判断是字符串替换起的作用，还是模型重写起的作用；
- 缺失率本来就是我们**还没测准**的量（§12.3 现在是按实体提及次数统计，第一次测量
  分母只有 4 条）；拿一个没测准的量去驱动一次模型调用，等于用一个未知去解释另一个未知；
- 单独测"形式化替换"这件事，本来就该在**零模型调用**的条件下做干净。

**缺失重译 = 后续独立实验**，见 §11 阶段 4（条件性）、§12.3（触发讨论的暂定阈值）。
本节与 §12.1、§11 三处口径**已经统一**，不再有两处相反的规定。

### 7.2 "源文未命中"到底是什么，以及它**不能**说明什么

本期唯一需要记录的"没做到"，是这样一个事实：**源文里没有出现该条目的任何写法**。

记录名从 `source_not_found` 改成 **`source_miss`（源文未命中）**，因为旧名字暗示了一个
我们**证明不了**的结论：

> ❌ 旧口径（错）："本场：3 句提到了表内名字，但 ASR 没听准。"
>
> 仅凭 ASR 文本 + 热词表，这句话推不出来。文本里没有「亮亮视野」时，系统无法区分：
> ① 说话人确实没提；② 提了，但 ASR 听成了别的字。
> 这两种情况在数据上**完全一样**。

所以：

- **可以自动记录的**：源文里没有命中（`source_miss`）—— 这是**关于文本的事实**；
- **不能自动统计的**：「提到了但听错了」—— 那需要**人工听音频、人工转写**作为独立依据。

**逐句记录正常未命中这件事，本期直接取消**。理由：一句话里没提公司名是常态，
逐句记录只会把 `terms.jsonl` 灌满噪声，而且那个计数回答不了任何问题。

**替代方案（改进词表的正确入口）**：让用户**标记有问题的字幕**，再关联那一小段录音
由人确认"他其实说的是什么"。这是一条人工回路，产出的是**经确认的真实说法**，
可以直接加进 `variants` —— 而不是一条猜出来的"可能是 ASR 错了"。

### 7.3 为什么不用"源侧占位符"（记录理由，免得上线后又被提出来）

占位符（`⟦T1⟧`）会把**性/数与搭配**的线索从模型视野里抹掉，而葡语的冠词与缩合
（`na`/`do`/`à`）依赖它。要治好就得给每个实体人工标性别和搭配 —— 那是
"人工语言标注"的工作量，却只换来和"缺失重译"重叠的收益。

⚠️ 但**"要不要给模型一点实体信息"这件事本身，还没有被验证过**。
真正该先验的是：**带实体说明的标记，能不能稳定穿过我们的中葡翻译模型** ——
例如把源句写成「亮亮视野（LLVision）」再翻，模型会不会原样保留那串葡语、还是
改写成别的、还是把括号也翻掉。这个实验便宜（20 句、一次模型调用），结论决定
后面要不要考虑源侧提示。**它属于 §11 阶段 6，不在本期。**

## 8. 生效时机与运行时

### 8.1 "下一次同传开始时生效"的精确语义

- 每场同传开始时（`createInterpreter` 之后第一次翻译前）**读一次** `var/live/terms.json`，
  按用户名取表，**快照进内存**；这一场之内不再重读。
- 运行中 `PUT /terms` 只改文件，**不改正在跑的这一场**；响应里 `effectiveAt: "next-session"` 明说。
- 手机端在"开始同传"按钮旁显示一行：`本次生效热词 12 条（wu）`；改了表没重开 → 显示
  `热词表已更新，下次开始同传生效`。
- **理由**（与现有设计一致）：我们连音源切换、`--context-depth` 都是"下次生效"。
  一场同传中间换术语表，会出现"前半场旧写法、后半场新写法"，这在字幕里看起来像 bug。

### 8.2 代码落点（实施时才动，这里只标位置）

| 位置 | 现状 | 本功能要做的事 |
|---|---|---|
| `plugin/core.mjs` ≈1596（`finalFrame = buildFrame({text: result.text…})`） | 定稿译文出口 | 加一道 `applyTerms(…)` |
| `plugin/core.mjs` ≈878 / 895（`enqueueProofread` / `runOneProofread`） | 校对后可能改字幕 | 校对修订**也要过一遍** `applyTerms`（否则校对会把归一结果改回去） |
| `plugin/core.mjs` ≈1606（`state.recent.push`） | 上下文记忆用 `result.text` | 存**替换后**的文本，保证上下文一致 |
| `plugin/translation-lint.mjs` ≈679（`properNounProblems`） | 已有的"查" | 复用；`must` 条目未出现时直接产出 `enforce_failed` 判据 |
| `relay/lan-relay.mjs`（路由表） | 6 个端点 | 加 `PUT/GET /terms` |
| `lib/paths.mjs` | 路径唯一来源 | 加 `TERMS_NAME = 'terms.json'`、`TERMS_LOG = 'terms.jsonl'` |
| `android/`（MainActivity） | 无用户名概念 | **底部导航第 4 栏「热词表」**（4.4 起，不再是设置里的入口）：表格形式一条一行（中文 / 葡语 / 删除）、「新增」弹两格对话框、「批量导入」吃粘贴来的 Tab/逗号/等号分隔内容、「从电脑拉取」把电脑上的表填回表格；用户名在页面顶部 |

### 8.3.0 测试账户：一条命令准备好，用来验证而不是靠手点

验证热词表这条线时，最费事的不是功能本身，而是**每次都要在手机上注册、一条条敲名字** ——
既慢又不可复现。所以有一个只写磁盘的脚本：

```bash
node scripts/test-account.mjs           # 建/刷新账户 + 写入默认热词表（7 条）
node scripts/test-account.mjs --show    # 看当前状态（不打印密码）
node scripts/test-account.mjs --reset   # 删掉账户、token、表与凭据
node scripts/test-account.mjs --terms my.json  # 用自己准备的表
```

它写的东西：

| 文件 | 内容 |
|---|---|
| `var/live/accounts.json` | 账户（密码 scrypt 加盐哈希，token 只存 sha256） |
| `var/live/terms.json` | 这个账户的热词表 |
| `var/live/terms-active.json` | "下一个会话用哪个用户"，插件下一场就按它取表 |
| `var/live/test-account.json` | **明文**凭据（用户名 / 密码 / token），只给本地测试用 |

默认账户是 `test` / `test123456`，默认表是本项目**真实在用的名字**，
并且带了 `wrong`（实测出现过的音译写法，例如 `Liangliang Vision`）——
不带 wrong 的话，归一化只能"把正确的再写一遍"，等于空转。

⚠️ 两条边界：

1. 它是**测试账户**：密码固定、凭据明文落盘，只应该出现在本机开发目录（`var/` 不进版本控制）；
2. 一旦它存在，`/terms` 就要求 token（§8.3 的迁移期规则会被关掉），
   所以手机上要先在「设置 → 账户」用 `test / test123456` 登录。

### 8.3 用户名从哪来（**已定：方案 D**）

现在代码里**没有用户概念**（`/hello` 只回 device/cols/lineBudget）；而且架构本身是
**一次一台手机**（共享 `audio-in.pcm`、一个收件箱），所以"多台手机各自一张表"在现有链路里
本来就不成立，不必为它设计。

**已定做法**：

1. 手机设置里一个"用户名"文本框，**预填设备名**（`Build.MODEL`），可改；留空 → 落 `default`；
2. 用户名随握手带上（`/hello` 的查询参数或 `/terms` 的 body），relay 记住"当前会话是哪个用户"，
   并写一份 `var/live/terms-active.json`（`{ "user": "wu", "at": "…" }`）——插件读它取表，
   沿用现有"文件接缝"的做法，不新造机制；
3. **同名覆盖要明说**（见 §6.1 的 `overwritten`），否则两台手机填同一个名字会静默互相覆盖；
4. 每次同传开始的日志里带上用户名（`[terms] 本次生效 12 条（user=wu）`），
   这样"这场用的是谁的表"永远查得到。

为什么不选"服务器分配 id"：日志里是一串 id，排查时要反查，而排查恰恰是我们最需要这个字段的时刻。
为什么不选"仅设备名自动"：同型号两台手机直接撞车，而撞车的后果是**别人的术语表生效**。

## 9. 日志与可观测性（需求 6）

### 9.1 事件（一行一条 JSON，写 `var/live/terms.jsonl`）

实现里实际写的事件（`plugin/core.mjs` 的 `logTermsEvents`）：

```jsonc
{"t":"2026-10-19T09:15:02.311Z","where":"final","event":"replace","id":"t_7f3a",
 "from":"leion pro","to":"Leion Pro","context":"…o Leion Pro da…"}   // 命中并改成规范写法
{"t":"…","where":"final","event":"hit","id":"t_7f3a","context":"…"}  // 已是规范写法，只记一笔
{"t":"…","where":"final","event":"boundary_skip","id":"t_7f3a","context":"高通量的"}  // 疑似更长词，跳过
{"t":"…","where":"final","event":"watch","id":"t_7f3a","zh":"亮亮视野",
 "source":"我们和亮亮视野合作。","translation":"Colaboramos com a Liangliang Visão."}  // 观测：提到了但没写出（§17）
{"t":"…","where":"final","event":"rescue","id":"t_7f3a","from":"LLVisão","to":"LLVision"}  // 临时修正（§18，实验分支）
```

**与设计稿的差异（如实登记）**：事件里没有 `session` / `user` / `dir` / `ms` 字段 ——
实现只带"时间 + 阶段（final/proofread）+ 事件 + 条目 id + 上下文/原文+译文"；
会话范围靠进程日志（`relay.log`）与时间窗对齐，不重复塞进每一行。

**没有的事件**（明确写出来，避免误以为它们在跑）：

- `enforce_retry` / `enforce_failed` / `enforce_budget` —— 都属于"缺失重译"，
  本期不做（§7.1），所以也不产生这些事件；
- `source_miss` —— **不逐句记**（§7.2）。源文未命中是常态，逐句记录只会灌满日志，
  而且它回答不了"是不是听错了"。需要时按 session 统计一次即可，不落事件流；
- `shadowed` / `session_start` —— 设计稿里提过，实现没做（内置表与用户表尚未合并，见 §14.1 丙）。

### 9.2 人读的一行

同传开始时打一行到控制台（`relay.log`/`brain.log` 见各自日志）：

```
[leion-pro] 热词表：12 条（user=wu）
```

每命中一条**不**打到主日志（会淹没字幕流水），只在 `terms.jsonl` 里；出问题再按时间/上下文捞。

### 9.3 为什么单独一个文件

- 可统计（`jq` 一行就能算"误替换率 / 修复成功率"）；
- 不污染字幕流水日志（`relay.log` 现在是排查的主线索，塞进去会稀释）；
- 归档时跟 `archive/<时间戳>/` 一起走，保留历史。

## 10. 怎么证明它有用、而且没搞坏东西

### 10.0 先说清一件容易说错的话：**共用数据只能查一致性，不能证明正确**

规程早先写过一句"改错了会被自己的判据抓出来"。**这个承诺太强，撤回。**

设想用户把「亮亮视野」错配成另一家公司的名字：

- 替换器按表替换 → 输出的是错的名字；
- 质检也按**同一张表**检查 → 它认为"表里要求的写法出现了"，判绿；
- 两边一致，**两边都错**。

所以必须把两种判断分开，别混成一句话：

| 类型 | 能回答什么 | 靠什么 |
|---|---|---|
| **自动质检**（relay 的 `properNounProblems` + `terms.jsonl`） | **是否按本场词表执行了**：该替换的替换了没有、有没有漏处理、有没有跳过的边界 | 代码 + 日志，可重复、可自动 |
| **人工标注测试** | **映射本身对不对**：这个名字该不该这么写、有没有改错实体、句意有没有受损 | 人工读 + 正确答案（标注集） |

**`terms.jsonl` 只能统计替换次数，算不出误替换率** —— 误替换率需要"正确答案"作对照，
而正确答案只有人（或经人确认的标注集）能给。

因此下面这些说法都要改写：

- ❌ "误替换率必须 0" → ✅ **"在固定验收集上观测到零误替换"**（集合固定、结论随集合走，
  换一批句子就可能变）；
- ❌ "质检会抓出替换错误" → ✅ "质检能抓出**与本场词表不一致**的情况；
  词表本身错了它抓不出来"。

### 10.1 指标：按**实体提及次数**统计，分三档报告

**主指标（改用次数，不用句数）**

```
实体缺失率 = 缺失的实体提及次数 / 应保留的实体提及次数
```

为什么改：一句话里出现三个名字、漏掉一个，按句统计和三个全对是同一个数（0 或 1），
把程度抹平了。按**提及次数**统计才看得出"漏了多少"。

**必须分三档报告**（同一批输入，三次结果并排）：

| 档位 | 是什么 | 为什么必须单独列 |
|---|---|---|
| **A 初译原始结果** | 模型直接输出，不经任何处理 | 基线。**没有它，改进量无法归因** |
| **B 术语替换后** | 只做 §7.1 的变体替换（零模型调用） | **本期的效果**，也是本期唯一可归因的增量 |
| **C 校对并再次替换后的最终结果** | 若开了校对（默认关），再过一遍替换 | 与 B 的差 = 校对的作用；**不许把两者混成一个数** |

**辅助指标（只报数，不当承诺）**

| 指标 | 定义 | 用来干什么 |
|---|---|---|
| 写法错误率 | 「专名新造」的提及次数 / 应保留的提及次数 | 与缺失率并列看：失败是"写错"还是"没有" |
| 边界跳过次数 | `boundary_skip` 计数（§5.1.1 的 R1 触发） | 看边界规则是不是在吞掉合法用法 |
| 替换次数 / 命中数 | `terms.jsonl` 里的 `replace` / `hit` | **只能说明"执行了多少"**，不是效果 |
| 句长变化 | 替换前后字数差 | 排版/翻页会变，记录副作用 |
| 人工可读性抽检 | 20 句人工读 | 有类误伤只有人看得出来（§10.2 挡不住全部） |

**硬门槛（不过就不许上）**

| # | 门槛 | 说明 |
|---|---|---|
| 1 | **在固定验收集上观测到零误替换** | 口径见 §10.0：这是"观测到"，不是"证明没有" |
| 2 | **已知变体的归一生效率 = 100%** | 给了变体就必被收敛（`leion pro` → `Leion Pro`），纯字符串，做不到就是 bug |
| 3 | **空表 / 表不存在 / 用户不存在 → 行为与"功能关闭"逐字一致** | 防"功能上线却悄悄改了默认行为" |

### 10.2 负对照（先写这个，跑不过就不许上）

沿用 `tests/bench-suite.mjs` 的做法（"判据自检不过就不许调模型"）。
本功能的负对照**成对**：左边验"该改的改了"，右边验"不该改的一个都没改"。

1. `equipa` 的条目**不得**命中 `equipamentos`（词边界）；
2. `高通` 的条目**不得**命中 `高通路` / `高通量`（中文边界，§5.1.1 R1）；
3. 表里同时有 `Leion Pro` 与 `Leion` 时，`Leion Pro` **只能**命中长的那条（重叠规则）；
4. `亮亮视野` 在 `北京亮亮视野科技有限公司` 里应命中整串，**不得**只命中中间的短片段；
5. 折叠负对照：`avô/avó`、`pão/pau`、`Sao/São` 折叠后**允许**互相命中（它们本就是同一词的不同写法），
   但**不得**因此把无关句子改掉；`secretária`/`secretaria` 在 `fold:false` 条目下**不得**互相命中；
6. 句子不含源词时**不得**触发任何替换；
7. 同一条字幕替换两次 = 替换一次（幂等）；
8. 空表 / 表不存在 / 用户名不存在 → 与"功能关闭"完全一致（不许报错、不许降级字幕）。

> 这 8 条**都不是"证明不会误伤"**，只是"已知的坑都钉住了"。§10.0 的区分同样适用：
> 它们证明的是**一致性**，正确性仍然要靠 §10.4 的人工标注集。

### 10.3 还没量的东西（**诚实标注**）

- **缺失重译的延迟代价未测**（本期不做它，所以也不该拿它的数字说话）；
- 双向在**葡→中**方向上的实际需求频度未统计（对方念公司名时才会用到）；
- **R1 的漏报率未测**：它会在「我们和亮亮视野合作」这类句子上跳过替换，
  跳过多少、值不值，要等 §10.4 的标注集跑出来才知道。

### 10.4 验收集怎么建（决定上面所有数字可信不可信）

30~50 句可以起步，但**必须同时包含三类**，否则很容易只证明"规则适配了我自己挑的例子"：

| 类 | 内容 | 用来看 |
|---|---|---|
| **专名密集句** | 每句 1~3 个真名，含"同一个名字出现两次""名字在句首/句中/句尾" | 缺失率、写法错误率 |
| **易误命中的普通句** | 含 `高通量`、`equipamentos`、`secretaria`、`São/Sao` 这类**陷阱词**的日常句 | 误替换（这类句子是负对照的真实版本） |
| **留出集（holdout）** | 一部分**不参与规则调整**，只在最后跑一次 | 防"规则照着例子改" |

规则调整时**不许看留出集**；每次改规则都要在留出集上重跑一次并记录（这一点抄
`docs/14` 的评测包纪律，理由一样：可复现、可比较）。

**已经落地的文件与命令**（阶段 2.5 已完成）：

| 文件 | 是什么 |
|---|---|
| `scripts/terms-eval-corpus.mjs` | 验收集本体：25 条专名密集 + 9 条陷阱 + 10 条留出，**43 次实体提及**；每条都标了「该出现什么」和「为什么这么标」；自带卫生检查 `checkCorpus()` |
| `scripts/terms-eval.mjs` | 评分器：`--check` 只查验收集；`--records a.jsonl [--corrected c.jsonl]` 出 A/B(/C) 三档指标，结果写到 `var/terms-eval/results/` |

```bash
node scripts/terms-eval.mjs --check                           # 验收集卫生检查（先跑这个）
node scripts/terms-eval.mjs --records var/terms-eval/a.jsonl  # A 档与 B 档并排
```

**B 档不需要模型**：它就是把 A 档的译文过一遍匹配器。这正是「形式化替换可以单独测清楚」
的实现方式 —— 替换的效果、改动数、可疑改动，全都与模型无关。

**留出集怎么用**：调规则（改匹配器 / 改边界表）时**只看非留出集**的结果；改完之后
全量跑一次，把留出集的数字单独记下来。留出集数字变差 = 规则过拟合了。

### 12.1 已定：一句话里提到了、但译文里没有这个词时怎么办 → **方案 C**（附条件）

场景：用户在表里写了「亮亮视野 → LLVision」。这一句讲话里提到了这个名字，
但译文里没写出来。三个选择（说人话版）：

| | 我们的行为 | 好处 | 坏处 |
|---|---|---|---|
| **A 只有"必须"和"关"** | 没出现就重翻一次（最多一次） | 最稳，说了一定在 | 有些句子本来就不该出现这个名字（中文「我跟老王说了」→ 葡语可以说 `falei com ele`），会被迫重翻、还可能把句子写僵 |
| **B 让模型"最好这么写"** | 翻译时悄悄告诉模型一声，听不听由它 | 省钱、句子自然 | **同一句话今天对、明天错**，你没法保证；而且给模型加要求会让现有横评数字失去可比性 |
| **C 只改写法、缺了不补** | 出现了就必须写成 `LLVision`（大小写/空格写错我改回来）；没出现就不管 | 完全可控、零延迟、不会写坏句子 | 真的漏了也补不回来 |

**已定 C**，但附一个条件 —— **必须把"漏译比例"测出来**（见 §12.3）。
理由：C 的坏处能不能接受，完全取决于"提到了名字、译文里却完全没有"这种情况到底有多常见。
如果它很罕见，C 就是对的（用一个罕见的坏情况换"绝不会把句子写坏"）；
如果它其实不少，那就得回头考虑 A。

### 12.2 已定：一句话里挤了好几个热词时的预算 → **方案 D**

场景：「高通的骁龙 8 Gen 3 用在亮亮视野的 Leion Pro 上」——一句里 4 个名字，
译文大概会漏掉一两个。重翻时如果要求"这 4 个都得有"，模型容易把句子写拧。

| | 我们的行为 | 好处 | 坏处 |
|---|---|---|---|
| **A 最多要求 3 个** | 一句只挑前 3 个必须出现，多出来的不要求（记一笔日志） | 模型负担可控 | 第 4 个永远保不住 |
| **B 名字太多就不重翻** | 一句里要求出现超过 3 个，就只做"写了就改对"，不重翻 | 不会写坏句子 | 名字密集的句子（恰恰是最需要准确的）被放弃 |
| **C 重翻后量一下句子** | 重翻结果如果变长太多 / 屏幕上放不下，就退回原来的译文 | 有一道"别写坏"的保险 | 光看长短看不出"句式崩了"，只能挡住明显变形 |
| **D = A + C + 全场限额** | 最多 3 个 + 量句子 + **全场重翻次数上限**（用完了就只改写法，并在手机上说明） | 三层保险，且防"表配错导致每句都重翻"这种烧钱故障 | 用户可能看到"本场不再重翻了"这句话 |

**已定 D**。三层挡的是三种不同的坏情况：A 挡"句子被塞爆"，C 挡"重翻结果明显变形"，
限额挡"表配错了还一路重翻下去"。

限额的具体数值**先按实测延迟定**，暂填保守值（每分钟 ≤ 10 次）；实测后调。

### 12.3 必测项：实体缺失率（`entity_miss_rate`）

> 原名 `missing_rate`、按**句**统计；按你指出的问题改成**按实体提及次数**统计 ——
> 一句话里三个名字漏掉一个，按句统计和三个全对是同一个数，把程度抹平了。

**定义**

```
entity_miss_rate = 缺失的实体提及次数 / 应保留的实体提及次数

  一次"实体提及"     ：原文里出现表内某个名字的某种写法，每出现一处算一次
  应保留的提及        ：该提及在期望译文里应当以规范写法（或 approved 写法）出现
  缺失的提及          ：最终译文里既没有规范写法、也没保留原中文、也不是已知音译写法
```

**必须分三档报告**（与 §10.1 同一套，不合并）：

| 档位 | 说明 |
|---|---|
| A 初译原始结果 | 基线，用于归因 |
| B 术语替换后 | **本期的效果** |
| C 校对并再次替换后 | 只有开校对时才有；与 B 的差才是校对的作用 |

**首次测量（已做，样本极小，只作方向性参考，口径仍是旧的"按句"）**

数据：`var/logs/bench-models-v2.json`（4 个模型 × 18 句 = 72 条已记录译文），
判据用产线同一份 `properNounProblems`：

| 模型 | 条数 | 点名句 | 写法正确 | 新造写法 | **完全缺失** |
|---|---|---|---|---|---|
| deepseek | 18 | 1 | 1 | 0 | 0 |
| hunyuan-mt | 18 | 1 | 0 | 1 | 0 |
| qwen2.5-72b | 18 | 1 | 0 | 1 | 0 |
| glm | 18 | 1 | 1 | 0 | 0 |
| **合计** | 72 | **4** | 2 | **2** | **0** |

**读法（必须连样本量一起读）**：18 句里只有 **1 句**点了表内的名，分母只有 4 条 ——
**0% 不是结论**。能说的只有：现有唯一那句上，失败形态是**写法错（音译）**而不是"整个没了"，
与 `docs/08` 一致；同时说明我们那批验证句集**专名太少，不适合验这个指标**。

**要求**：验收集按 §10.4 建（专名密集 + 陷阱普通句 + 留出集），并按上面三档出数。
拿到那张表之前，§12.1 的"只改写法、缺了不补"只能算**暂定**，不能算验证通过。

**阈值怎么用（降级：只触发讨论，不直接决定上线）**

- `entity_miss_rate` > 20% → **启动讨论**是否做缺失重译。**不是**自动立项，更不是上线条件；
- 还要同时看三件事才能决定：
  1. **缺的是什么实体**：产品型号 / 公司名 / 人名，价值差别很大（型号缺了对方就不知道是哪个产品；
     人名缺了往往还能靠上下文读通）；
  2. **额外延迟**：一次重译会让这一句的定稿晚多少毫秒（实测，不估）；
  3. **它是不是"本来就该缺"**：中文「我跟老王说了」→ 葡语 `falei com ele` 是正确译法，
     不该被算成缺失。这类样本要在标注集里显式标成"允许不出现"。

## 14. 与「校对」「质检」的关系（已定，含一次职责移交）

这一节是回答一个真实疑问：**现有的校对（第二遍模型）和热词表，是不是在做同一件事？**
答案是"原来确实重复"，处理办法是**移交职责 + 保留观测者**，而不是两个都做。

### 14.1 三层要分清（否则会删错东西）

| 层 | 是什么 | 位置 | 本功能的处理 |
|---|---|---|---|
| **甲** | **校对模型的指令**：`proofreadRules` 第 2 条的"③ 数字、时间、**人名、公司名**译错或漏译" | `policy/br-pt.json` | **删掉"人名、公司名"**，补一条禁改令（§14.3） |
| **乙** | **质检判据**（只报不改）：`properNounProblems` 判"专名新造 / 专名丢失 / 专名蹭对" | `lib/translation-lint.mjs`；由 `relay/lan-relay.mjs` 对每个定稿帧调用 | **保留并改造**（§14.4）—— 它是唯一独立的"替换成功了吗"检测器 |
| **丙** | **判据的数据**：`properNouns`（5 条，`approved`/`soundsLike`/`mustKeep`） | `policy/br-pt.json` | **降级为"内置默认表"**，与用户表合并，用户表优先 |

### 14.2 为什么把甲的专名职责交出去

- 专名的"正确写法"是**用户自己的事实**，模型只能猜（`亮亮视野 → LLVision` 是模型先验知识，
  换个不有名的名字它就音译）。把它交给用户表，才是"可复现"的来源。
- 校对**只在空闲时跑、超时/换页就丢**（`plugin/core.mjs` 的 `proofread: 'idle'`，默认开），
  不是一个"每次都会检查专名"的机制 —— 把职责押在一个异步、会丢弃的机制上，本身就是设计缺陷。

### 14.3 删职责的同时必须补禁令（否则更糟）

校对不知道用户表。如果只是把"改专名"删掉、不加约束，它看到 `LLVision` 仍可能觉得不对而改掉
（音译回去、或换成中文），于是出现"我们改对 → 校对改回"的**闪烁**。
所以校对提示词要加一条：

> 专有名词（公司名、产品名、人名）的写法由后处理保证，**不要改动、替换或省略**
> 这些名词；只有它在译文里彻底消失、而你确信原文点名了，才补回 —— 补也只用原文里的写法。

### 14.4 乙：改造，不删（这条坚持的原因）

`properNounProblems` 里有个分支专门报"**专名蹭对**"：

```
专名「亮亮视野」译成了认可写法（LLVision）—— 结果对，但这是模型的先验知识，不是从原文推的
```

它的触发条件就是"译文里出现 `approved`"。**一旦做了替换，`approved` 必然出现在每句里**
→ 这个警告会每句都报 → 日志被淹没。而`docs/08` 已经写过代价：
**"让人开始忽略警告，那比不报还糟"**。

所以乙按三条改造：

1. 数据源：`policy.properNouns` → **用户表 ∪ 内置表**（用户表优先）；
2. **"蹭对"这条在看到替换痕迹时关掉**（替换之后"模型是不是自己猜对的"这个问题已无意义）；
3. 保留"专名丢失 / 专名新造"，语义正好变成 **"术语替换失败"的第二个独立证据源** ——
   不依赖我们自己的 `terms.jsonl`，两边对得上才算数。

### 14.5 代价：必须记账的一处"兜底消失"

`docs/07` §5.3 有一例真实校对记录：

```
定稿  ...um chip de alta capacidade.     ← 初译把 Qualcomm 泛化了
修订  ...um chip da Qualcomm.            ← 约 2.4 秒后校对补回来
```

这说明**校对现在确实在救"不在任何表里的专名"**（靠模型先验知识）。移交之后：

| 名字 | 谁管 | 结果 |
|---|---|---|
| 在用户表里 | 本功能 | **可复现**，比校对强 |
| 不在任何表里 | **没人管** | 初译错了就错到底 |

这是"单一权威 + 可复现"换来"覆盖面"的取舍，**已确认接受**。它同时是"用户必须自己写表"的
最强论据：**名字是谁在用谁知道，模型只能猜。**

### 14.6 执行链（架构不变量，实现时必须遵守）

> **任何能改文本的机制都必须排在术语替换之前；术语替换是所有机制的最后一个环节，且幂等。**

| 顺序 | 谁 | 做什么 |
|---|---|---|
| 1 | 初译模型 | 照常翻 |
| 2 | **术语替换**（只做 ①：已知变体 → 规范写法，**不调用模型**） | 同步、可复现，定稿前完成 |
| 3 | 校对模型（若开；默认 `off`） | 已删专名职责（14.3）+ 已加禁改令；只修"听错跑偏 / 数字时间 / 巴葡不地道" |
| 4 | **术语替换再过一遍**（幂等） | **最终裁决**；若校对把规范形式改掉 → 改回，并记 `proofread_reverted_term` |
| 5 | relay 质检（只报不改） | 判据按 14.4 改造，独立发现替换失败 |

**为什么不把替换放在校对之后只做一次**：校对是异步的（只在空闲时跑、超 `proofreadMaxAgeMs`
或屏幕换页就丢弃），放在它后面等于"强制"依赖一个会丢的机制。所以定稿前必须有替换，
校对后又必须再核一次 —— 这就是"两处替换 + 一次裁决"的由来。

### 14.7 连带要重跑的数字（记账）

- 改 `proofreadRules`（删专名职责）**等于改模型行为** → `docs/07` 那批 18+6 句的实测结论
  **口径变了**，要在文档里写明"从哪个版本起不可比"，必要时重跑。
- 改乙的数据源 → `docs/08` 里 `properNouns` 相关判据的通过率**口径也变了**（表更大更具体）。
- 这两件事都属于"上线前必须做、上线后会发现数字对不上"的坑，先记在这里。

### 14.8 本轮定下的（原 §12 未决项，现在有答案了）

| 原问题 | 结论 |
|---|---|
| 与内置表冲突谁优先 | **用户表优先**（由 14.1 丙 + 权威原则确定），覆盖记 `shadowed` |
| 校对里的专名检验 | 甲：**删职责 + 补禁令**；乙：**保留并改造**；丙：**降级为默认表** |
| 要不要先量"校对对专名的影响" | **暂不量**。职责已移交，量化它的意义只剩"评估丢了多少兜底"，等用户表跑起来看 `enforce_failed` 频率更准 |

## 15. 实验记录：词对齐定位（**未进入生产**，2026-10）

> 这一节记录一次**失败的路线探索**，写下来的目的是让后来的人不必再试一遍，
> 而不是为它背书。所有数字都是小样本、单次测量，口径见下。

### 15.1 当时想解决什么

归一化（`normalize` 模式）的前提是**能定位**"译文里哪一段对应表内那个名字"。
别名表只覆盖用户填过的写法；真实译文里的变体（`Liangliang Vision`、`Musk`）
一直是人工填表补上的。于是问：**能不能用词对齐器自动找到那段？** 找到之后
人工只需勾"对/不对"，变体就能批量入库。

做法：`awesome-align`（`bert-base-multilingual-cased`，177.9M 参数、681 MB，
本地跑）把中文原文的每个字对齐到葡语译文的词，取实体字对应的葡语 token 区间，
再用 `lib/align-trim.mjs` 把区间裁成"两端是实词、长度合理、与规范写法形状相似"
的片段（不裁的原始片段 41% 会吞整句或只取头一个词）。

### 15.2 数据与人工标注

两批都是**真实模型的真实译文**（Qwen2.5-72b via SiliconFlow，产线同一套提示词），
不是造的例句。人工只标"有没有明确对应片段"（`span` / `generic` / `missing` / `unsure`），
`span` 时把片段抄下来；写法对不对不影响标注 —— 那正是对齐器的活。

| 批 | 句子 | 人工标注的提及 | 其中 `span` | 对齐器给的片段可替换 |
|---|---|---|---|---|
| 第一批（20 句日常对话） | 20 | 10（程序已判有规范写法的 25 次未标） | 8（80%） | **7 / 8**（另 1 条给错位置，裁后改为拒答） |
| 第二批（18 句串台测试，实体与本表其余词全部不重叠） | 18 | 14（全部是模型写成变体的那些） | **14（100%）** | **10 / 12**（2 条是模型自己输出中文泄漏，样本不算对齐器的错） |
| **合并** | 38 | **24** | **22（91.7%）** | **17 / 20（85%）** |

"可替换"的判定：对齐器片段（经 `align-trim.mjs` 裁切后）与人工片段逐词一致，
或人工片段是它的连续子串。拒答（`null`）算"没能替换"。

### 15.3 对齐器在哪些地方确实不如"填别名"

| 现象 | 例子 | 为什么对齐器救不了 |
|---|---|---|
| **形状对不上** | `北京 → Pequim`（模型写 `Beijing`）、`工信部 → MIIT`（模型写全称 `Ministério da Indústria e Informação`） | 裁切模块只比较**字符串形状**，两种写法形状差太远 → 拒答（免得毁句）。这类**只能靠别名表**（`approved` 写法） |
| **语序不同** | `清华大学 → Universidade Tsinghua`，模型写 `Tsinghua University` | 词序相反，窗口搜索找不到"最像的连续段"，裁后仍夹带邻句实体 |
| **只给头一个词** | `工信部 → Ministério`（模型写的是全称） | 往前后补词只能补"规范写法的下一个词"，缩写 `MIIT` 没有可补的词 |
| **模型输出坏了** | 串台账里出现过 `Ningde时代在北京举行了一次座谈会。`（中文整段泄漏） | 这不是定位问题，是模型输出不可用 —— 要重译/校对，不在本功能范围 |

### 15.4 结论

1. **别名累积路线成立**（事先定的决策规则：可定位变体 ≥50% → 值得填别名；
   实测 **91.7%**，远超门槛）。真实译文里绝大多数"错了的名字"都有明确对应片段，
   用户可以勾选入库，不需要自动替换。
2. **对齐器不进入生产自动替换**：85% 的可替换率、且失败时给不出"我分不清"之外的
   安全信号，不足以支撑"每句都自动改" —— 而它救不了的那 15%（`Pequim`/缩写/语序）
   恰恰是别名表能覆盖的。两者不冲突，是互补。
3. 保留 `lib/align-trim.mjs` 与 `tests/align-trim-suite.mjs`（10 条）：它约束的是
   "片段边界"，将来若有别的定位器（实体识别、更大模型）接入，这道裁切仍然需要。
4. **离线工具化已实现**（结论见 §15.5，工具见 §15.7）：`scripts/discover-variants.mjs`
   拿历史译文跑一遍，把"命中但写法不同"的片段列为候选，用户勾选后进表。
   它不碰产线定稿链路，失败也只是少一条建议。

### 15.5 对照实验：LLM 离线候选发现 vs 对齐器（2026-10）

上面 §15.4 的第 4 条留了一个问题：**"离线发现候选变体"到底该用什么工具？** 为此在同一批
**24 条人工标注提及**（22 `span` + 2 `generic`）上跑了三臂对照：

| 臂 | 做法 |
|---|---|
| 对齐器 | awesome-align + `align-trim.mjs`（已有结果） |
| LLM | Qwen2.5-72b 端到端：给原文、译文、中文名，问"对应哪段葡语"，没有/泛称回 `NONE` |
| 字面基线 | 滑窗 + Dice 相似度（最便宜的对照组） |

| 方法 | 定位命中 | 片段完整可直接用 | 错位 | 泛称误报 | 可判定正确 |
|---|---|---|---|---|---|
| 对齐器 | 18 / 22 | 17 / 22 | 4 | 2 / 2 | 18 / 24（75%） |
| **LLM 端到端** | **20 / 22** | **19 / 22** | **2** | 2 / 2 | **20 / 24（83%）** |
| 字面基线 | 10 / 22 | 10 / 22 | 0 | 0 / 2（正确拒答 2） | 12 / 24（50%） |

**读法**（对齐器臂用的是裁切后的片段，与产线管线一致；"定位命中"是松口径，
"片段完整可用"是严口径，对应 §15.2 的"可替换"）：

- 对齐器的 4 条错位是：`Leion`（把亮亮视野对成亮亮眼镜）、`x09 清华 × 圣保罗` 串台、
  以及 2 条**模型输出损坏**的样本（中文泄漏，它给回了整段中文）；
- LLM 的 2 条错位**全部是那 2 条坏样本** —— 在"译文本身正常"的 20 条上，LLM 全部定位正确；
- 对齐器还有 1 条"定位对、片段不完整"（`工信部` 只给 `Ministério`）；LLM 只有 1 条不完整，
  且那条是**人工标注本身截断了**：`工信部` 人工片段抄成 `inistério da Indústria`，
  LLM 给的是完整的 `O Ministério da Indústria e Informação`；
- 泛称那 2 条，两臂都给了字面直译（`Óculos Brilhantes`），人工判为"泛称、不是名字"。

**结论**：

1. **离线候选发现用 LLM，不用对齐器** —— 定位率和片段质量都更高，而且 Qwen 本来就在链路里，
   不需要新增 681 MB 模型和 Python 进程；
2. 对齐器**不进生产、也不微调**的结论不变：它的独有价值（发现候选）已被 LLM 覆盖，
   而微调它既缺 span 标注数据、又治不了"命名差异"（`Beijing`/`Pequim` 是知识不是对齐）。
3. 离线工具里要**同时展示"退化形态"标记**：像 `Óculos Brilhantes` 这种字面直译，
   应提示用户"这不像名字，可能是泛化"，让用户一票否决，而不是自动当成变体。
4. **局限**：单次运行、24 条小样本、提示词只有一版；数字只作方向性判断，
   不能当成"LLM 一定 100%"。若真做工具，应在更大的历史译文上重跑一次。

记录文件：`var/terms-eval/arm-comparison.json`（逐条）、`var/terms-eval/arm-llm-cache.json`
（LLM 原始回答缓存）、脚本 `scripts/experiments/compare-arms.mjs`（重跑会复用缓存，不再联网）。

### 15.6 记录文件

均在 `var/`（不进 git）：`terms-eval/real-translations-20.jsonl`（第一批译文）、
`terms-eval/crosstalk-translations.jsonl`（第二批，含串台句）、`terms-eval/标注清单-20.md`
与 `标注清单-第二批.md`（人工标注）、`terms-eval/align-eval-report.json`、
`terms-eval/标注评估-第二批.json`（评分结果）、`terms-eval/crosstalk-report-strict.json`。

评分/对照脚本已入库：`scripts/experiments/compare-arms.mjs`（三臂对照，读缓存重跑）、
`scripts/experiments/eval-rescue.mjs`（方向一闸门评估）。词对齐器本体（Python）**没入库**
（本地 `awesome-align-master` + `var/pyenv` 环境），复现步骤见 §15.1。

## 16. 离线候选发现工具（`scripts/discover-variants.mjs`）

> 这是 §15.5 对照实验的落地物：**用 LLM 从历史译文里挖候选变体**，人工勾选后进表。
> 它**不进入产线**：不参与字幕链路、不加延迟、不新增接口；只影响"表里的变体从哪来"。

### 16.1 它解决什么

用户维护热词表最贵的一步是"想到模型可能把名字写成什么"。原来这靠经验猜；
工具把这一步变成"从真实译文里挖"：对每句历史译文问一次模型"这个名字在这里被写成了什么"，
把"提到了但没写成规范写法"的片段列成候选，用户只需勾选。

### 16.2 用法（两步）

```bash
# ① 发现：扫历史译文，产出一份可勾选的清单（不改表）
node scripts/discover-variants.mjs --input var/terms-eval/real-translations-20.jsonl --user test

# ② 入表：把清单里勾成 [x] 采用 的候选写进表（全有或全无，逐条过校验）
node scripts/discover-variants.mjs --apply var/discover/candidates-<时间>.md --user test
```

- 输入是 `{ "source": ..., "translation": ... }` 的 JSONL（`id` 可选）；
- 缺省用 `var/live/` 的表与当前会话用户（`terms-active.json`），`--table` 可指向副本；
- 只问"原文提到了、译文里没有规范写法"的组合；译文里已有规范写法的跳过；
- LLM 回答缓存进 `var/discover/llm-cache.json`，重跑不重复花钱；
- 候选**绝不自动入表**：`--apply` 只收勾了"采用"的，其余记为"未勾选"。

### 16.3 候选怎么入表（与现有数据结构零冲突）

| 字段 | 什么时候用 |
|---|---|
| `wrong`（默认） | 模型写出来的**错误写法**，命中后换成规范写法 |
| `approved` | 认可的同义写法（写法本身没问题，只是统一成规范写法） |
| `variants` | 中文侧的变体（`--apply` 对含汉字候选按中文侧规范写法判重） |

合并规则与产线一致：与规范写法折叠后相同不登记（折叠已覆盖）、已登记的不重复、
表里已删掉的中文名跳过；**每个候选加进去后都过一遍 `validateTerms`**，把表弄脏的候选
退回并说明原因，其余照常写入。

### 16.4 已验证（2026-10-21，真跑）

用 `var/live/terms.json` 的副本（`--table var/discover/demo-terms.json`）跑 20 句真实译文：
问模型 8 次发现 **5 个候选**（`Liangliang Vision` / `Liangliang` / `Liangliang Field` /
`Brilhantes Visão` / `Óculos Brilhantes`）；勾选 `Liangliang Field` 后 `--apply` 写入，
`亮亮视野` 的 `wrong` 从 2 条变 3 条，真实表（`var/live/terms.json`）**未被触碰**；
套件里有 6 条测试守"清单↔apply 往返"和"合并后表仍合法"（`tests/discover-suite.mjs`）。

### 16.5 边界（诚实标注）

- **单次、小样本**：定位质量来自 §15.5 的 24 条人工标注（20/22 在正常译文上全对），
  不是更大规模的重跑；
- 像 `Óculos Brilhantes` 这种**字面直译**会被列为候选，但它是"泛称式"写法 ——
  清单里给了样例句子，由人判断收不收，工具不替用户决定；
- `suspect` 标记只说明"片段在译文里找不到原样或像整句"，不代表语义一定对；
- 候选入表后**下一场同传才生效**（表是每场读一次的快照）。

### 16.6 与产线自动记录的接缝（`--from-watch`）

同传时产线会自动记下"提到了名字、但译文没写出规范写法"的句子（§17 的热词观测，写在
`var/live/terms.jsonl` 的 `watch` 事件里，带完整原文+译文）。工具可以直接吃这份日志：

```bash
node scripts/discover-variants.mjs --from-watch var/live/terms.jsonl --user test
```

好处是**问模型只问真正出过问题的句子**（不是全量历史），失败面小、成本低；
勾选入表的流程与 `--input` 完全相同。

## 17. 热词观测（产线自动记录，`termsWatch`）

> 目的：**用户第一时间知道"这句出问题了"**，而不用等下一场。它不改字幕 ——
> 本场救不了（不知道模型写成了什么），但记下来的原文+译文正好喂给 §16 的离线发现，
> 下一场表就补上了。

### 17.1 它做什么

每句**定稿**时（归一之后、上屏之前）做一次纯本地比对：

```
源文里出现了表内名字的某种已知写法（同侧折叠匹配，含边界规则）
        且
译文里没有出现该条目的规范写法（同侧折叠匹配）
         ↓
记一条 watch 事件（id / zh / 完整原文 / 完整译文）
         ↓
帧里带 termsMiss:[{id, zh}] → 手机在这条字幕下打一行小字
```

- **不改字幕**：译文原样上屏（与"归一替换"不同，它只做观测）；
- **零模型调用**：纯字符串比对，不增加任何延迟；
- **手机提示**：`亮亮视野 未按对照写法显示，已记录`（小字、警示色，定稿帧才显示）；
- **落盘**：`var/live/terms.jsonl` 里 `event: "watch"` 的行 —— 这是离线发现的输入。

### 17.2 为什么不是"逐句记缺失"（与 §7.2 的区别）

§7.2 说**不要逐句记录"源文里没出现名字"**，因为"一句话没提公司名"是常态，记了全是噪声。
这里记的是相反的情况：**源文明确提到了这个名字**（按匹配器同一套边界规则），
而译文里**没有规范写法** —— 这要么是模型写成了别的变体（要补表），
要么是模型把它泛化/省略了（该知道）。信号比"源文没提"强得多，所以值得每句都看。

### 17.3 配置与开关

| 配置 | 缺省 | 说明 |
|---|---|---|
| `terms` | `'on'` | 归一总开关；关掉后观测也不做（行为与加这个功能之前逐字一致） |
| `termsWatch` | `'on'` | 观测开关；单独关掉只停"记录+提示"，归一照常 |

`leion_inbox status` / 手机端 / 自检里的 `terms` 计数多了一个 `watch` 字段。

### 17.4 已验证

- `tests/terms-watch-suite.mjs`（7 条）：变体→记、已含规范写法→不记、没提→不记、
  `高通`/`高通量` 边界→不记、方向不符→不记、pt→zh 方向→记、空输入→不报错；
- 回归：`node tests/run-all.mjs` → Python 320 / JS 404 全绿；
- 手机端（4.10）：`LanClient` 解析 `termsMiss`，`SubtitleList` 在字幕下加 `segNote`
  一行小字，定稿帧显示、校对把名字补对后提示自动消失（校对后重算过一遍观测）。

### 17.5 局限（诚实标注）

- **不知道模型写成了什么**："它答成 `Liangliang Vision` 还是 `这家公司`" 这个信息
  它给不出 —— 那是 §16 离线发现的工作，这里只负责"出问题了"；
- **有误报**：合法省略/泛化（中文说"我跟老王说了"、葡语说 `falei com ele`）也会被记；
  所以它的产物是"待复核清单"，不是"错误清单"；
- **本场不救火**：提示归提示，字幕仍是模型原文；下一场才因表更新而变对；
- **大量新变体时日志增长**：每个提及一句一次，`terms.jsonl` 上限 2000 行（滚动）。

## 18. 方向一实验：热词临时修正（`termsRescue`，**实验分支，默认关**）

> 分支：`exp/rescue-quarantine`（不并入 `main`，除非验收通过）。
> 目标：在**本场**把"写错一点点的名字"换成规范写法，同时**不把改坏句子的风险带回来**。

### 18.1 它做什么

观测（§17）发现"提到了名字、译文却没写出规范写法"之后，**空闲时**问模型一次：

> 这个名字在这句译文里实际写成了什么？（原样抄写，或 NONE）

拿到回答后走 `planRescue` 的**全部闸门**，通过才把**那一小段**换成规范写法
（手工拼回，**不让模型重写整句**）。整个过程不占"下一句的初译"。

### 18.2 闸门（顺序即成本，先便宜的）

| # | 闸门 | 拒掉的典型情况 |
|---|---|---|
| ① | 回答非空、且折叠后不等于规范写法 | 回答 `LLVision`（已经是规范写法） |
| ② | ≤ 6 个词 / ≤ 40 字符 | 模型回了半句或整句 |
| ③ | 回答必须**原样出现在译文里** | 模型编造片段 |
| ④ | 与规范写法共享二元组 ≥ 0.25 | `Liangliang` / `Beijing` / `这家公司` —— **译名、缩写、泛化不在这里修**（别名表的活） |
| ⑤ | 片段里不夹带别的表内名字 | 串台 |
| ⑥ | 拼回后过格式验收（行数/列数） | 修正后屏幕放不下 |

### 18.3 用户定的三条约束（实现里都有对应）

1. **不把"校对/下一帧把它改回来"当撤销依据**：本功能**不监听、不撤销**。
   两个机制如果都改同一句，先落地的生效，后到的按"**过期**"丢弃（屏幕已经不是那一帧了），
   与"谁对"无关 —— 代码里就是 `displaySeq` / 帧对象比对，没有任何"看对方怎么说"的逻辑。
2. **绑定字幕帧与版本**：结果回来时必须 `displaySeq` 未变 **且** `lastFrame` 仍是当初那一帧，
   否则丢弃。因为"最后一句"本身一直在变，只有绑住帧才能避免修错对象。
3. **已经读到的错误不能被完全消除**：只能把后续显示改对，读过的划痕消不掉。
   所以它不能替代"第一次就翻对"（模型/别名表），只是补救。

### 18.4 离线评估（人工标注集，2026-10）

用两批人工标注（24 次提及：22 `span` + 2 `generic`）与对照实验已缓存模型回答，
逐条跑 `planRescue`（`scripts/experiments/eval-rescue.mjs`，不联网）：

| 结果 | 条数 | 说明 |
|---|---|---|
| **改对**（片段与人工标注一致，且只换那段） | **8** | 清华 ×3、马斯克 ×2、王工、圣保罗大学、清华（另一句） |
| **改错** | **0** | 本标注集上零误改 |
| 拒绝：与规范写法不像 | 12 | 主要是 `Liangliang` / `Beijing` / 工信部全称这类**译名/缩写** |
| 拒绝：已经是规范写法 | 3 | 无事可做 |
| 拒绝：片段没原样出现 | 1 | 模型回答的片段与译文不符 |

**读法**：方向一在本标注集上**只覆盖约 36%（8/22）的"未知变体"**，但**没有改坏任何一条**。
覆盖不到的那部分恰是"译名/缩写"—— 那是别名表（§5.3 `approved`）与离线发现（§16）的职责，
不是自动修正的职责。**自动修正只做"看起来就是同一个名字被写错"这一小类。**

### 18.5 与校对的关系（不互相撤销）

两个机制都可能改"最后一句"，谁先落地谁生效，后到的按过期丢弃：

- 校对若先落地（整句修订），临时修正的帧绑定失效 → 修正丢弃；
- 修正若先落地（只换一小段），校对结果回来时 `displaySeq` 已变 → 校对丢弃（按过期，不按"对错"）。

这不是"用校对证明修正错了"，而是"同一句只允许一个后到的修订"—— 用户已经读到的内容
不会因为另一个机制不同意就被回滚。

### 18.6 配置与开关

| 配置 | 缺省 | 说明 |
|---|---|---|
| `termsRescue` | `'off'` | 实验开关；`'on'` 才做临时修正 |
| `termsRescueLimit` | 20 | 每场最多问几次（防"表配错 → 每句都问"） |
| `termsRescueMaxAgeMs` | 8000 | 结果超过这个年龄就丢 |

启动参数（不用手改配置）：`node scripts/start-all.mjs --terms-rescue`（会透传给大脑），
或单独起大脑时 `node scripts/harness-side.mjs --terms-rescue`；两者的启动横幅都会打印
"临时修正 已开启/关闭"，避免"以为开了其实没开"。

状态计数：`leion_inbox status` 的 `terms.rescue`（`asked/applied/rejected/dropped/failed`）。

### 18.7 局限（诚实标注）

- **覆盖有限**：只修"形近"的变体；译名/缩写/泛化一律拒绝（上面 12 条拒绝）；
- **仍然要花一次模型调用**：每场每句至多一次，命中才问；
- **模型可能把该改的名字答成别的**：所以答案必须原样出现在译文里、且与规范写法相似 —— 两道独立证据；
- **不能完全消除已读影响**：只影响之后的显示；
- **未并入 `main`**：本分支只做验证；验收前不进入产线默认路径。
