# 用户热词对照表：设计与实现规程

> **这份文档是什么**：老师提出「允许用户上传热词对照表、绕过模型直接对输出做形式化替换」之后，
> 把这个功能**说清楚到可以照着写代码**的程度 —— 数据长什么样、匹配怎么做、什么时候生效、
> 失败时怎么办、怎么证明它没把事情搞坏。
>
> **写入目的不是"方案已定"，而是"分歧已收敛"**：下面每条规则都标了它是**已定**（你或老师
> 明确过）、**我的建议**（需要你点头）、还是**未决**（问了但还没答案）。
> 读完这份文档，我们要确认的是 §12 那张问题清单，而不是从头讨论方向。
>
> **本文件不含代码改动**。§11 才列实施顺序，等 §12 的问题定了再动手。

## 1. 一页结论

- 这件事的本质是**术语后编辑**：不训练模型、不改模型权重，在译文**出来之后**按用户给的对照表
  做形式化替换；如果按用户要求做"强制"，还要能发现"该出现却没出现"并修掉。
- 用户上传对照表这件事，**把原先的阻塞点消掉了**：我们原来不知道"模型会把 `亮亮视野` 写成什么"
  （音译？直译？保留中文？），现在用户可以自己声明"必须写成 `LLVision`"。
  但**归一化（把变体收敛到规范形式）仍然需要变体清单** —— 用户不填，这一层就退化成只有"缺失修复"。
- 同一个中文词在葡语里**有性别**，性别决定冠词/缩合（`na LLVision` / `do LLVision`）。
  这决定了"强制"必须**在译文侧做**、并且**不能用不透明占位符**（占位符会把性别线索抹掉，
  详见 §7.3）。我们的 `policy/br-pt.json` 里已经有 `nounGenders` 这份数据可以复用。
- 我们的判据层 `plugin/translation-lint.mjs` **已经在用同一份专名数据查错**（`properNounProblems`）。
  所以这个功能天生是"**改**"与"**查**"共用一份数据：改错了会被自己的判据抓出来，这是它最值钱的地方。

**一句话**：用户表解决"该写成什么"，匹配规则保证"不会误伤"，判据层保证"改坏了能被发现"。

## 2. 名词先统一，否则会把三件事谈混

| 名字 | 在本文里的意思 | 谁来做 |
|---|---|---|
| **热词表 / 对照表** | 用户上传的 `源写法 → 目标写法` 映射（含可选变体清单、方向、强制级别） | 用户 |
| **术语后编辑（post-edit）** | 在译文出来之后，对译文做形式化替换的**总称** | 我们 |
| **① 归一化** | 译文里出现了**白名单变体**（`Leion Pro` / `leion pro` / `LeionPro`）→ 统一成规范形式 | 字符串 |
| **② 缺失修复** | 源句含该词、译文里**没有**规范形式 → 判为漏翻，修掉 | 需要额外一次模型调用 |
| **③ 源侧提示** | 送翻译前把源句改成 `亮亮视野（LLVision）` 让模型照抄 | 改的是**输入**，风险最高 |
| **判据（lint）** | 已有的译文查错层，负责"改完之后还对不对" | 现有代码 |

老师和你说的是 **①+②**（都发生在译文侧）。③ 不在本次范围（理由见 §7.3），但会在文档里留位置。

## 4. 数据结构

### 4.1 存储布局（PC 侧，因为翻译在 PC 上跑）

```jsonc
// var/live/terms.json
{
  "version": 1,
  "updatedAt": "2026-10-19T09:12:33.000Z",
  "tables": {
    "wu": {                        // ← 用户名字符串（暂定按用户名定位用户）
      "updatedAt": "2026-10-19T09:12:33.000Z",
      "entries": [ /* 见 4.2 */ ]
    },
    "default": { "updatedAt": "...", "entries": [] }
  }
}
```

- **单一文件 + map**：按你说的"用户-热词表映射 map"，读一次全量、取自己那一份；
  relay 是单进程，写入用「临时文件 + rename」保证不被读到半个文件。
- **为什么不在手机本地**：翻译发生在电脑/服务器侧，手机存了也看不见、用不上。
  手机端只是**编辑与上传的界面**。
- **没有用户表时的行为**：回落到 `"default"`；再没有就当作空表（功能等同关闭），
  **不报错、不降级**，只在上传/日志里说明。

### 4.2 条目 schema

```jsonc
{
  "id": "t_7f3a",                 // 服务端生成，日志与报错都引用它（用户不用管）
  "zh": "亮亮视野",                // 中文侧写法（源或目标，取决于方向）
  "pt": "LLVision",               // 葡语侧写法（按巴葡正字法）
  "variants": ["亮亮视野科技", "亮亮视野（北京）"], // 可选：额外的**源侧**写法，命中后可归一到 zh
  "approved": ["LLVision"],       // 可选：译文侧的**可接受写法**（含大小写不同的写法）
  "direction": "auto",            // auto | zh-to-pt | pt-to-zh（本次只实现 auto）
  "enforce": "must",              // must（强制）| hint（只提示）| off
  "gender": "f",                  // 可选："m" / "f"；写进译文侧语法提示用
  "note": "公司英文名",            // 可选：给人看的备注，不参与匹配
  "createdAt": "2026-10-19T09:12:33.000Z"
}
```

设计说明：

- **`zh` / `pt` 两侧都必填**。这是"双向"能成立的**前提**：反向时我们不是"从葡语反推中文"，
  而是用条目里**用户自己写的中文**。反推是不可靠的（`LLVision` 该翻成"亮亮视野"还是
  干脆保留英文？只有用户知道），所以协议上强制两侧都填。
- **`variants` 与 `approved` 是"①归一化"的唯一燃料**。用户不填，① 就无从下手 ——
  这点必须在界面上讲清楚，否则用户会以为"传了表就万无一失"。
- **`gender` 是给②用的**：修复时若能把"阴性、用 `na`/`da`"一起告诉模型，修复质量高一个档；
  不填则退化为"只钉写法"。这也解释了为什么 §7.3 的占位符方案不划算。
- **`enforce: "must"` 的语义**：译文里没有 `pt`（或其 `approved` 形式）→ 视为失败，走 §7 修复。
  **不是**"尽量写成这样"。

### 4.3 与内置 `policy/br-pt.json` 的关系

内置文件里已经有同形的结构（`properNouns[].zh / approved[] / sourceForms[] / mustKeep`）
和 `nounGenders`。**不改动它**，用户表是叠加层：

| 层 | 谁维护 | 优先级（我的建议） |
|---|---|---|
| 用户表（`var/live/terms.json`） | 用户上传 | **高** |
| 内置 `policy/br-pt.json` 的 `properNouns` | 我们 | 低（被用户同名条目覆盖时记 `shadowed`） |
| 内置 `terminology`（ônibus/autocarro 这类用词偏好） | 我们 | 不参与本功能（它是"用词偏好"，不是"对照表"） |

## 5. 匹配规则（这是最容易出事的一段，逐条写死）

### 5.1 基本规则

1. **词级精确匹配**：先按"词元"切分待查文本（葡语按空白/标点切，中文按字符切），
   再与条目做**整词比较**。不做子串包含、不做前缀/后缀、不做编辑距离、不使用正则。
2. **最长优先**：同一位置能匹配多个条目时取最长（`亮亮视野科技` 优先于 `亮亮视野`）。
3. **不跨界**：匹配结果不得跨标点、跨换行、跨句。
4. **中文的"单词"**：中文没有空格，所以取"**精确字符子串 + 最长优先 + 不被更长的条目包含**"；
   这条是本功能最需要小心的地方（`中` 会命中 `中国`、`高通` 会命中 `高通路`）。
5. **单字/双字黑名单**：长度 ≤ 2 的中文条目、长度 ≤ 3 的拉丁条目，**默认拒绝上传**
   （见 §6 拒绝码 `TOO_SHORT`）。用户确实要（例如专名就是两个字）可以显式
   `allowShort: true`，但界面上要红字提醒"极易误伤"。

### 5.2 边界定义（葡语侧）

- 词边界字符集：空白、`.,;:!?¡¿()[]{}\"'«»—–…/` 以及行首行尾。
- 大小写与变音符号**不参与边界判断**：`Leion` 与 `leion` 是同一个词元。
- 不把连字符当词内字符，除非条目本身含连字符（`Snapdragon 8 Gen 3` 里的空格也一样：
  条目含空格时按整串匹配，但两端仍要求边界）。

### 5.3 大小写 / 变音符号折叠（**已定：方案 D**）

**规则**（对应三个方案的第三种，即"折叠大小写 + 折叠重音，但短词不折叠"）：

1. `Leion Pro` ≡ `leion pro` ≡ `LEION PRO` ≡ `LeionPro`（忽略大小写与空格差异）；
2. `Léion` ≡ `Leion`、`ação` ≡ `acao`、`São Paulo` ≡ `Sao Paulo`（忽略重音符号，先做 NFC 归一）；
3. **但拉丁条目有效长度 ≤ 3 时，不做重音折叠**（`pau` 与 `pão` 不相等），中文条目不受此限；
4. 折叠只影响**"是不是同一个词"的判断**，不影响输出：输出永远用用户填的规范形式。

**为什么这么定**（三段理由，强度不同）：

- ✅ **上游噪声就是这样的**：ASR 输出的巴葡，重音符号时有时无（`acao`/`ação`、`nao`/`não`）；
  而用户用中文键盘填表时，几乎不会去打 `ã`。不折叠 = 双方都嫌麻烦、还认不出来。
- ✅ **它不属于"模糊匹配"**：模糊匹配是"看起来像就替换"（`equipa` → `equipamentos`，
  我们真的踩过）；折叠是"同一串字母的不同书写"。误伤面差一个数量级。
- ⚠️ **碰撞风险存在但可控**：`avô`/`avó`、`pão`/`pau` 折叠后会互相命中。
  概率我判断很低（用户表里是专名，不是普通名词），但**没测过**，所以用第 3 条规则
  把最短的拉丁词排除在外；并且把下面这组负对照写进测试，跑不过就不许上：
  `avô/avó`、`pão/pau`、`e/é`、`Sao/São`、`Leion/Leion Pro`（后者必须**不会被**前者整词命中）。

**为什么关掉折叠是更差的选项**（记录一下，免得以后反复讨论）：`LEION PRO` 认不出来 →
被判成"缺失" → 触发一次多余的模型重译；而重译大概率还是写成 `LEION PRO`（模型就爱这么写），
于是这一句永远修不好、还每次多花一次调用。**关折叠会把"零风险的书写问题"变成"要花钱的问题"。**


### 5.4 明确**不做**的匹配方式（每条都有理由）

| 不做 | 理由 |
|---|---|
| 编辑距离/相似度 | 实测教训：`equipa` 会命中 `equipamentos`（`docs/08` 判据自检的负对照就是这条） |
| 同音/拼音归一 | 中文同音字极多，误触发面大于收益；且那是**改 ASR 输出**，需要单独决策 |
| 正则 | 用户输入当正则 = 注入风险；转义写错就误伤大面积文本 |
| 大小写外的形态变化 | `LLVision` 的复数 `LLVisions`、所有格 —— 不做，交给用户写进 `approved` |
| 跨语言"猜测" | 例：葡语译文里出现 `亮亮视野`（中文残留）→ 不做自动识别，那属于 lint 的职责 |

### 5.5 幂等

同一条字幕可能三次经过（增量 → 定稿 → 校对修订）。规则：

- 替换**必须幂等**：`replace(replace(x)) == replace(x)`。
- 实现上的约束：替换后若再次匹配到"已规范形式"，**不得再替换**（把它加入"本次已处理"集合），
  避免 `LLVision` → `LLVision (LLVision)` 这类滚雪球。
- 增量帧**不替换**（半截词 `Leion Pr` 会被误判），只对定稿与校对后的帧替换。

## 6. 上传、校验与接口

### 6.1 端点（relay 侧新增，鉴权沿用现有共享密钥）

沿用 `relay/lan-relay.mjs` 的路由风格（`/hello`、`/say`、`/audio`、`/frame`、`/diag`、`/status`）：

| 方法 / 路径 | 作用 | 请求 | 响应 |
|---|---|---|---|
| `POST /terms/validate` | **只校验、不落盘**（界面可反复点） | `{ "user": "wu", "entries": [...] }` | `{ "ok": true/false, "accepted": N, "rejected": [{"index":3,"code":"TOO_SHORT","reason":"…"}] }` |
| `PUT /terms` | **全合法才整体替换**该用户的表 | 同上 | 成功：`{ "ok": true, "accepted": N, "effectiveAt": "next-session", "overwritten": false }`；有非法条目：**400 + 完整 rejected 清单，一个都不落盘** |
| `GET /terms?user=wu` | 取当前生效表（手机端回显） | — | `{ "ok": true, "user": "wu", "entries": [...], "updatedAt": "…" }` |

- **两阶段是已定方案（C）**：校验与落盘分开。这样界面能"边填边看红字"，而落盘语义保持
  **全有或全无** —— "看到 ok:true" 就等于"整张表生效"，不存在"一半生效而用户不知道"。
  为什么不做部分落盘：静默的部分生效**能绕过所有自动判据**（判据只看表里有的条目，
  看不到"本该在表里却没存进去"的条目），而我们给"误替换"定的门槛是 0。
- **整体替换而非增量**：用户传的是自己那张表，增量合并会产生"我以为删了其实还在"的错觉。
- **同名覆盖要明说**：同一用户名先传过表，这次再传 → 响应里 `overwritten: true` 并带
  `previousEntries: N`；界面显示"你覆盖了已有的 7 条"。
- **上限**（防滥用，与 `--public` 的加固思路一致）：条目 ≤ 500、单条文本 ≤ 200 字符、
  总请求 ≤ 64 KB、`user` ≤ 64 字符且只允许 `[A-Za-z0-9_\-.@]`。
- **不要**在 `/terms` 里做翻译或触发模型调用（它是纯存储 + 校验）。


### 6.2 上传时的静态校验（拒绝码）

| 码 | 触发 | 处理 |
|---|---|---|
| `MISSING_SIDE` | `zh` 或 `pt` 有一侧为空 | 拒绝（双向要求两侧都有） |
| `TOO_SHORT` | 中文 ≤ 2 字 / 拉丁 ≤ 3 字符且未标 `allowShort` | 拒绝 |
| `DUPLICATE_SOURCE` | 同一源写法在表中出现两次且目标不同 | 拒绝后者并指出冲突行号 |
| `CYCLE` | A→B 同时 B→A 且两侧互为源（`zh`↔`pt` 交叉） | 拒绝（会来回替换） |
| `LATIN_IN_ZH` / `HAN_IN_PT` | 方向装反了（葡语侧写的是汉字） | 拒绝并提示"两侧可能写反" |
| `CONTROL_CHARS` | 含制表/换行/零宽字符 | 拒绝（不可见字符是最难查的误伤源） |
| `TABLE_TOO_LARGE` | 超上限 | 拒绝整个请求 |

校验**全部通过才落盘**（已定方案 C：`validate` 可以随便调，`PUT` 只在全合法时生效）。
这样用户一次传 50 条、第 3 条写错时，会看到"哪一行、什么错"，改完再提交，
而不是"一部分悄悄没存上"。

## 7. "强制"怎么落实（本设计最重的部分）

### 7.1 三级动作

对每一条 `enforce: "must"` 的条目，在**定稿译文**上执行：

1. **查**：译文里是否出现 `pt`（或 `approved` 里的任一项，按 §5.3 折叠比较）？
2. **命中** → 记一条 `hit` 事件，结束（不做任何改写，避免"改对的"）。
3. **未命中** → 判为**漏执行**，按下面顺序处理：

| 顺序 | 动作 | 代价 | 何时用 |
|---|---|---|---|
| a | **修复重译**：把源句 + "必须包含 `<pt>`，性别 `<gender>`，不要改别的" 再问一次模型，最多 1 次 | +1 次模型调用（延迟未测，见 §10.3） | 默认路径 |
| b | **保留原样 + 记 `enforce_failed`** | 0 | 重试仍失败 / 超上限 / ASR 源句根本不含该词 |
| c | ~~直接插入~~ | — | **不做**：插入位置靠猜，语法风险高于收益 |

### 7.2 三种"不能强制"的情况，必须如实记录而不是硬来

1. **源句里根本没有这个词**：用户表里写了 `亮亮视野`，但这一句说的是"我们公司"，没提名字。
   → **不触发**（不是漏翻，是本来就没有）。
2. **ASR 把源词听错了**：源句里没有原样的 `亮亮视野`（听成别的字）→ **不触发**，
   记 `source_not_found`。这是**我们实测最大的失败来源**，但修它必须动 ASR，不在本功能范围。
   **但它要让人看见**（已定方案 C）：汇总进 `/status`（`sourceNotFound: {"亮亮视野": 2}`）
   并在**一场结束时**给一条小结（`本场：3 句提到了表内名字但没听准 —— 亮亮视野×2、Leion Pro×1`）。
   原因：这是**"该给哪个词加同音变体"的唯一线索** —— 用户表里加 `variants`（"亮亮视觉"、
   "亮亮视野科技"…）就能让下一次匹配上，所以它其实是本功能**自己的自愈入口**，藏起来等于关掉改进回路。
   不在句子进行中弹提示：一句话没提公司名是常态，弹窗会变成噪音，而且用户当场没有操作空间。
3. **同一句里术语太密**（一条 30 字的句子要钉 5 个名）→ 修复大概率破坏语法，需要预算（**未决，见 §12**）。

### 7.3 为什么不用"源侧占位符"（记录理由，免得上线后又被提出来）

占位符（`⟦T1⟧`）会把**性/数与搭配**的线索从模型视野里抹掉，而葡语的冠词与缩合
（`na`/`do`/`à`）依赖它。要治好就得给每个实体人工标性别和搭配 —— 那是
"人工语言标注"的工作量，却只换来和 ② 重叠的收益。等 ①② 的数据出来、看还剩多少句子
修不回来，再评估。**不做的结论是"排序"，不是"永久否决"。**

## 8. 生效时机与运行时

### 8.1 "下一次同传开始时生效"的精确语义

- 每场同传开始时（`createInterpreter` 之后第一次翻译前）**读一次** `var/live/terms.json`，
  按用户名取表，**快照进内存**；这一场之内不再重读。
- 运行中 `PUT /terms` 只改文件，**不改正在跑的这一场**；响应里 `effectiveAt: "next-session"` 明说。
- 手机端在"开始同传"按钮旁显示一行：`本次生效热词 12 条（wu）`；改了表没重开 → 显示
  `热词表已更新，下次开始同传生效`。
- **理由**（与现有设计一致）：我们连音源切换、`--context-depth` 都是"下次生效"。
  一场同传中间换术语表，会出现"前半场旧写法、后半场新写法"，这在字幕里看起来像 bug。

### 8.2 代码落点（实施时才动，这里只标位置）

| 位置 | 现状 | 本功能要做的事 |
|---|---|---|
| `plugin/core.mjs` ≈1596（`finalFrame = buildFrame({text: result.text…})`） | 定稿译文出口 | 加一道 `applyTerms(…)` |
| `plugin/core.mjs` ≈878 / 895（`enqueueProofread` / `runOneProofread`） | 校对后可能改字幕 | 校对修订**也要过一遍** `applyTerms`（否则校对会把归一结果改回去） |
| `plugin/core.mjs` ≈1606（`state.recent.push`） | 上下文记忆用 `result.text` | 存**替换后**的文本，保证上下文一致 |
| `plugin/translation-lint.mjs` ≈679（`properNounProblems`） | 已有的"查" | 复用；`must` 条目未出现时直接产出 `enforce_failed` 判据 |
| `relay/lan-relay.mjs`（路由表） | 6 个端点 | 加 `PUT/GET /terms` |
| `lib/paths.mjs` | 路径唯一来源 | 加 `TERMS_NAME = 'terms.json'`、`TERMS_LOG = 'terms.jsonl'` |
| `android/`（MainActivity） | 无用户名概念 | 加"用户名"设置项 + 热词表编辑/上传页 |

### 8.3 用户名从哪来（**已定：方案 D**）

现在代码里**没有用户概念**（`/hello` 只回 device/cols/lineBudget）；而且架构本身是
**一次一台手机**（共享 `audio-in.pcm`、一个收件箱），所以"多台手机各自一张表"在现有链路里
本来就不成立，不必为它设计。

**已定做法**：

1. 手机设置里一个"用户名"文本框，**预填设备名**（`Build.MODEL`），可改；留空 → 落 `default`；
2. 用户名随握手带上（`/hello` 的查询参数或 `/terms` 的 body），relay 记住"当前会话是哪个用户"，
   并写一份 `var/live/terms-active.json`（`{ "user": "wu", "at": "…" }`）——插件读它取表，
   沿用现有"文件接缝"的做法，不新造机制；
3. **同名覆盖要明说**（见 §6.1 的 `overwritten`），否则两台手机填同一个名字会静默互相覆盖；
4. 每次同传开始的日志里带上用户名（`[terms] 本次生效 12 条（user=wu）`），
   这样"这场用的是谁的表"永远查得到。

为什么不选"服务器分配 id"：日志里是一串 id，排查时要反查，而排查恰恰是我们最需要这个字段的时刻。
为什么不选"仅设备名自动"：同型号两台手机直接撞车，而撞车的后果是**别人的术语表生效**。

## 9. 日志与可观测性（需求 6）

### 9.1 事件（一行一条 JSON，写 `var/logs/terms.jsonl`）

```jsonc
{"t":"2026-10-19T09:15:02.311Z","session":"s_8f1","user":"wu","dir":"zh-to-pt","event":"replace",
 "id":"t_7f3a","from":"leion pro","to":"Leion Pro","where":"final","ms":0}
{"t":"…","event":"hit","id":"t_7f3a","where":"final"}                       // 已经在正确形态，无需改
{"t":"…","event":"enforce_retry","id":"t_7f3a","attempt":1,"ok":true,"ms":412}
{"t":"…","event":"enforce_failed","id":"t_7f3a","reason":"still_missing","ms":438}
{"t":"…","event":"source_not_found","id":"t_7f3a"}                          // 本句没有该词，正常
{"t":"…","event":"enforce_budget","count":3}                                // 术语过密，只修前 3 条
{"t":"…","event":"shadowed","id":"builtin:llvision"}                        // 用户表覆盖了内置条目
{"t":"…","event":"session_start","entries":12,"source":"user:wu"}
```

### 9.2 人读的一行

每次同传开始打一行到 `relay.log`/`brain.log`：

```
[terms] 本次生效 12 条（user=wu，来自 var/live/terms.json，更新于 09:12）
```

每命中一条**不**打到主日志（会淹没字幕流水），只在 `terms.jsonl` 里；出问题再按 `session` 捞。

### 9.3 为什么单独一个文件

- 可统计（`jq` 一行就能算"误替换率 / 修复成功率"）；
- 不污染字幕流水日志（`relay.log` 现在是排查的主线索，塞进去会稀释）；
- 归档时跟 `archive/<时间戳>/` 一起走，保留历史。

## 10. 怎么证明它有用、而且没搞坏东西

### 10.1 指标（每种配置跑同一批）

**已定验收口径（方案 C）：三条硬门槛 + 一组只报数不承诺的观察指标。**
把"我们能保证的"和"由模型决定的"分开 —— 这是我们一贯的分层，不是形式主义：
①是纯字符串，**做不到 100% 就是 bug**；②依赖模型，只能报数。

**硬门槛（不过就不许上）**

| # | 门槛 | 为什么它是硬门槛 |
|---|---|---|
| 1 | **误替换 = 0** | 一旦改了不该改的，用户就不再信任这块字幕；且这类错无法靠"重译"弥补 |
| 2 | **归一生效率 = 100%** | 给了变体就必被收敛（`leion pro` → `Leion Pro`），纯字符串逻辑，没有任何中间变量 |
| 3 | **空表 / 表不存在 / 用户不存在 → 行为与"功能关闭"逐字一致** | 防止"功能上线但悄悄改变了默认行为"；这条也是它敢开在产线上的前提 |

**观察指标（只报数，不当承诺）**

| 指标 | 定义 | 用来干什么 |
|---|---|---|
| **漏译比例 `missing_rate`** | 完全缺失句数 / 点名句数（定义见 §12.3） | **必测**。它是"方案 C（缺了不补）够不够用"的判据：> 20% 就要回头考虑给 `must` 开缺失重译 |
| **写法错误率** | 「专名新造」句数 / 点名句数 | 与上一行并列看：失败到底是"写错"还是"没有" |
| 规范形式出现率 | 该出现 `pt` 的句子里，最终译文含 `pt` 的比例 | 看整体效果趋势 |
| 漏执行率 | `must` 条目该出现却没出现、且修复失败 | 判断 ② 值不值、预算够不够 |
| 修复开销 | 每场的额外模型调用次数、单次毫秒数 | 评估延迟代价（§10.3） |
| 句长变化 | 替换前后字数差（排版/翻页会变） | 记录副作用，不当判据 |
| 质检独立发现率 | relay 的 `properNounProblems` 仍报"专名丢失/新造"的句数（§14.4） | **第二独立证据源**；不为 0 说明替换没做到 |
| 人工可读性抽检 | 20 句人工读 | 判断有没有把句子读坏 |


### 10.2 负对照（先写这个，跑不过就不许上）

沿用 `tests/bench-suite.mjs` 的做法（"判据自检不过就不许调模型"），本功能要先过的负对照：

1. `equipa` 的条目**不得**命中 `equipamentos`；
2. `高通` 的条目**不得**命中 `高通路` / `高通量`；
3. `亮亮视野` 的条目**不得**命中 `北京亮亮视野科技有限公司` 里的"视野"独立片段（应命中整串）；
4. 句子不含源词时**不得**触发任何替换/修复；
5. 同一条字幕替换两次，结果与替换一次相同（幂等）；
6. 空表 / 表不存在 / 用户名不存在 → 行为与"功能关闭"完全一致（**不许报错、不许降级字幕**）。

### 10.3 还没量的东西（**诚实标注**）

- **修复重译的延迟代价未测**。参考量级：现有翻译一次（large 模型）在我们的使用里是数百 ms 级，
  但那是**测试环境**的数，真实同传链路里"修复"会让这一句的定稿晚到多少，**必须实测**。
- 修一次不成功再修的收益曲线未知（设计上限定为 1 次）。
- 双向在**葡→中**方向上的实际需求频度未统计（对方念公司名时才会用到）。

### 12.1 已定：一句话里提到了、但译文里没有这个词时怎么办 → **方案 C**（附条件）

场景：用户在表里写了「亮亮视野 → LLVision」。这一句讲话里提到了这个名字，
但译文里没写出来。三个选择（说人话版）：

| | 我们的行为 | 好处 | 坏处 |
|---|---|---|---|
| **A 只有"必须"和"关"** | 没出现就重翻一次（最多一次） | 最稳，说了一定在 | 有些句子本来就不该出现这个名字（中文「我跟老王说了」→ 葡语可以说 `falei com ele`），会被迫重翻、还可能把句子写僵 |
| **B 让模型"最好这么写"** | 翻译时悄悄告诉模型一声，听不听由它 | 省钱、句子自然 | **同一句话今天对、明天错**，你没法保证；而且给模型加要求会让现有横评数字失去可比性 |
| **C 只改写法、缺了不补** | 出现了就必须写成 `LLVision`（大小写/空格写错我改回来）；没出现就不管 | 完全可控、零延迟、不会写坏句子 | 真的漏了也补不回来 |

**已定 C**，但附一个条件 —— **必须把"漏译比例"测出来**（见 §12.3）。
理由：C 的坏处能不能接受，完全取决于"提到了名字、译文里却完全没有"这种情况到底有多常见。
如果它很罕见，C 就是对的（用一个罕见的坏情况换"绝不会把句子写坏"）；
如果它其实不少，那就得回头考虑 A。

### 12.2 已定：一句话里挤了好几个热词时的预算 → **方案 D**

场景：「高通的骁龙 8 Gen 3 用在亮亮视野的 Leion Pro 上」——一句里 4 个名字，
译文大概会漏掉一两个。重翻时如果要求"这 4 个都得有"，模型容易把句子写拧。

| | 我们的行为 | 好处 | 坏处 |
|---|---|---|---|
| **A 最多要求 3 个** | 一句只挑前 3 个必须出现，多出来的不要求（记一笔日志） | 模型负担可控 | 第 4 个永远保不住 |
| **B 名字太多就不重翻** | 一句里要求出现超过 3 个，就只做"写了就改对"，不重翻 | 不会写坏句子 | 名字密集的句子（恰恰是最需要准确的）被放弃 |
| **C 重翻后量一下句子** | 重翻结果如果变长太多 / 屏幕上放不下，就退回原来的译文 | 有一道"别写坏"的保险 | 光看长短看不出"句式崩了"，只能挡住明显变形 |
| **D = A + C + 全场限额** | 最多 3 个 + 量句子 + **全场重翻次数上限**（用完了就只改写法，并在手机上说明） | 三层保险，且防"表配错导致每句都重翻"这种烧钱故障 | 用户可能看到"本场不再重翻了"这句话 |

**已定 D**。三层挡的是三种不同的坏情况：A 挡"句子被塞爆"，C 挡"重翻结果明显变形"，
限额挡"表配错了还一路重翻下去"。

限额的具体数值**先按实测延迟定**，暂填保守值（每分钟 ≤ 10 次）；实测后调。

### 12.3 新增必测项：漏译比例（`missing_rate`）

**定义**（分母很关键，不写清就会算出一个没意义的百分比）：

```
missing_rate = 完全缺失句数 / 点名句数
  点名句   ：原文里出现了表内某个名字的某种写法（sourceForms 命中）
  完全缺失 ：译文里既没有该名字的认可写法、没有保留中文、也不是某个已知音译写法
             （判据就是 lib/translation-lint.mjs 的「专名丢失」）
另附两个同级统计：写法错误率（「专名新造」）、写法正确率
```

**为什么分母是"点名句"而不是"全部句"**：一句话里没提公司名是常态，
把它算进分母会让比例低到毫无意义（真实语料里可能 90% 的句子都不点名）。

**首次测量（已做，样本很小，只作方向性参考）**

数据：`var/logs/bench-models-v2.json`（4 个模型 × 18 句 = 72 条已记录译文），
判据用产线同一份 `properNounProblems`：

| 模型 | 条数 | 点名句 | 写法正确 | 新造写法 | **完全缺失** |
|---|---|---|---|---|---|
| deepseek | 18 | 1 | 1 | 0 | 0 |
| hunyuan-mt | 18 | 1 | 0 | 1 | 0 |
| qwen2.5-72b | 18 | 1 | 0 | 1 | 0 |
| glm | 18 | 1 | 1 | 0 | 0 |
| **合计** | 72 | **4** | 2 | **2** | **0** |

**读法（必须连样本量一起读）**：18 句里只有 **1 句**点了表内的名，
所以分母只有 4 条 —— **0% 不能当作结论**。能说的只有两件事：
① 现有唯一那句上，失败形态是**写法错（音译）**而不是"整个没了"，与 `docs/08` 一致；
② 我们自己那批验证句集**不适合**验这个指标（专名太少），要用专门的数据。

**因此下一步要建一个"专名密集句集"**（阶段 2.5，纯离线）：

- 30~50 句真实场景句，每句 1~3 个真名（公司名 / 产品型号 / 人名 / 机构名 / 地名混排，
  含"同一个名字在一句里出现两次""名字在句首/句中/句尾"这类边界）；
- 每句标注：原文点名了哪个名、期望的葡语写法；
- 用途：**同时**给出 `missing_rate`、`写法错误率`，并作为本功能全部指标的固定分母
  （避免"只在我挑的句子上有效"）；
- 拿到这张表之前，§12.1 的 C 只能算"暂定"，**不能算验证通过**。

**触发回退的条件**（先写在前面，免得到时候凭感觉改主意）：
若 `missing_rate` 在专名密集句集上 > 20%（即五句里超过一句整个名字消失），
就回头讨论是否给 `must` 条目打开"缺失重译"。

## 14. 与「校对」「质检」的关系（已定，含一次职责移交）

这一节是回答一个真实疑问：**现有的校对（第二遍模型）和热词表，是不是在做同一件事？**
答案是"原来确实重复"，处理办法是**移交职责 + 保留观测者**，而不是两个都做。

### 14.1 三层要分清（否则会删错东西）

| 层 | 是什么 | 位置 | 本功能的处理 |
|---|---|---|---|
| **甲** | **校对模型的指令**：`proofreadRules` 第 2 条的"③ 数字、时间、**人名、公司名**译错或漏译" | `policy/br-pt.json` | **删掉"人名、公司名"**，补一条禁改令（§14.3） |
| **乙** | **质检判据**（只报不改）：`properNounProblems` 判"专名新造 / 专名丢失 / 专名蹭对" | `lib/translation-lint.mjs`；由 `relay/lan-relay.mjs` 对每个定稿帧调用 | **保留并改造**（§14.4）—— 它是唯一独立的"替换成功了吗"检测器 |
| **丙** | **判据的数据**：`properNouns`（5 条，`approved`/`soundsLike`/`mustKeep`） | `policy/br-pt.json` | **降级为"内置默认表"**，与用户表合并，用户表优先 |

### 14.2 为什么把甲的专名职责交出去

- 专名的"正确写法"是**用户自己的事实**，模型只能猜（`亮亮视野 → LLVision` 是模型先验知识，
  换个不有名的名字它就音译）。把它交给用户表，才是"可复现"的来源。
- 校对默认是关的（`plugin/core.mjs` 的 `proofread: 'off'`），所以**关着的时候没人管专名** ——
  把职责押在一个默认关闭的机制上，本身就是设计缺陷。

### 14.3 删职责的同时必须补禁令（否则更糟）

校对不知道用户表。如果只是把"改专名"删掉、不加约束，它看到 `LLVision` 仍可能觉得不对而改掉
（音译回去、或换成中文），于是出现"我们改对 → 校对改回"的**闪烁**。
所以校对提示词要加一条：

> 专有名词（公司名、产品名、人名）的写法由后处理保证，**不要改动、替换或省略**
> 这些名词；只有它在译文里彻底消失、而你确信原文点名了，才补回 —— 补也只用原文里的写法。

### 14.4 乙：改造，不删（这条坚持的原因）

`properNounProblems` 里有个分支专门报"**专名蹭对**"：

```
专名「亮亮视野」译成了认可写法（LLVision）—— 结果对，但这是模型的先验知识，不是从原文推的
```

它的触发条件就是"译文里出现 `approved`"。**一旦做了替换，`approved` 必然出现在每句里**
→ 这个警告会每句都报 → 日志被淹没。而`docs/08` 已经写过代价：
**"让人开始忽略警告，那比不报还糟"**。

所以乙按三条改造：

1. 数据源：`policy.properNouns` → **用户表 ∪ 内置表**（用户表优先）；
2. **"蹭对"这条在看到替换痕迹时关掉**（替换之后"模型是不是自己猜对的"这个问题已无意义）；
3. 保留"专名丢失 / 专名新造"，语义正好变成 **"术语替换失败"的第二个独立证据源** ——
   不依赖我们自己的 `terms.jsonl`，两边对得上才算数。

### 14.5 代价：必须记账的一处"兜底消失"

`docs/07` §5.3 有一例真实校对记录：

```
定稿  ...um chip de alta capacidade.     ← 初译把 Qualcomm 泛化了
修订  ...um chip da Qualcomm.            ← 约 2.4 秒后校对补回来
```

这说明**校对现在确实在救"不在任何表里的专名"**（靠模型先验知识）。移交之后：

| 名字 | 谁管 | 结果 |
|---|---|---|
| 在用户表里 | 本功能 | **可复现**，比校对强 |
| 不在任何表里 | **没人管** | 初译错了就错到底 |

这是"单一权威 + 可复现"换来"覆盖面"的取舍，**已确认接受**。它同时是"用户必须自己写表"的
最强论据：**名字是谁在用谁知道，模型只能猜。**

### 14.6 执行链（架构不变量，实现时必须遵守）

> **任何能改文本的机制都必须排在术语替换之前；术语替换是所有机制的最后一个环节，且幂等。**

| 顺序 | 谁 | 做什么 |
|---|---|---|
| 1 | 初译模型 | 照常翻 |
| 2 | **术语替换**（① 归一 + ② 缺失修复） | 同步、可复现，定稿前完成 |
| 3 | 校对模型（若开；默认 `off`） | 已删专名职责（14.3）+ 已加禁改令；只修"听错跑偏 / 数字时间 / 巴葡不地道" |
| 4 | **术语替换再过一遍**（幂等） | **最终裁决**；若校对把规范形式改掉 → 改回，并记 `proofread_reverted_term` |
| 5 | relay 质检（只报不改） | 判据按 14.4 改造，独立发现替换失败 |

**为什么不把替换放在校对之后只做一次**：校对是异步的（只在空闲时跑、超 `proofreadMaxAgeMs`
或屏幕换页就丢弃），放在它后面等于"强制"依赖一个会丢的机制。所以定稿前必须有替换，
校对后又必须再核一次 —— 这就是"两处替换 + 一次裁决"的由来。

### 14.7 连带要重跑的数字（记账）

- 改 `proofreadRules`（删专名职责）**等于改模型行为** → `docs/07` 那批 18+6 句的实测结论
  **口径变了**，要在文档里写明"从哪个版本起不可比"，必要时重跑。
- 改乙的数据源 → `docs/08` 里 `properNouns` 相关判据的通过率**口径也变了**（表更大更具体）。
- 这两件事都属于"上线前必须做、上线后会发现数字对不上"的坑，先记在这里。

### 14.8 本轮定下的（原 §12 未决项，现在有答案了）

| 原问题 | 结论 |
|---|---|
| 与内置表冲突谁优先 | **用户表优先**（由 14.1 丙 + 权威原则确定），覆盖记 `shadowed` |
| 校对里的专名检验 | 甲：**删职责 + 补禁令**；乙：**保留并改造**；丙：**降级为默认表** |
| 要不要先量"校对对专名的影响" | **暂不量**。职责已移交，量化它的意义只剩"评估丢了多少兜底"，等用户表跑起来看 `enforce_failed` 频率更准 |
