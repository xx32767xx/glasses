## 1. Node 12：一串 SyntaxError，看不出是谁的问题

```
const activeUser = JSON.parse(activeRaw).user ?? null
                                               ^ SyntaxError: Unexpected token '?'
```

**根因**：Ubuntu 22.04 的 `apt install nodejs` 装的是 **12.22**（24.04 是 18），
而 `??`（空值合并）要 Node 14+，本项目要 20+。

**为什么难查**：这个错在**解析阶段**发生 —— 文件里写任何"友好的版本提示"都没机会执行。

**修法**：

```bash
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs && node -v          # 必须 v20+
```

**防线**：`scripts/preflight.cjs` 故意用 **CommonJS + 老语法**写（不用 `??`/`?.`/`import`），
所以它能跑起来告诉你"你的 Node 太旧"；`package.json` 加了 `engines`，`npm start` 会先跑它。
`tests/run-all.mjs` 有两条断言盯着"preflight 不许被现代化"。

## 2. 大脑要一份构建过的 deepseek-harness 检出

原来的报错是：

```
无法加载真实的 @deepseek-ai/dsh-tools 构建产物 …
Invalid module ".../D:%5CDeepSeekHarness%5Cdeepseek-harness/packages/..." must not include encoded "/" or "\" characters
```

两层原因叠在一起：

1. **这台机器上根本没有检出**。`start-all` 的第三个进程（大脑）必须跑在真实的 DSH 工具运行时上
   —— 这是刻意拒绝降级的设计（仿一个校验器会给假的"契约没问题"的安全感）。
2. **我们的候选路径里写死了开发机的 `D:\...`**，于是"没检出"被渲染成"模块说明符含编码字符"。

**修法**：

```bash
git clone <deepseek-harness 仓库> ~/deepseek-harness
cd ~/deepseek-harness && pnpm install && pnpm build
export DSH_CHECKOUT="$HOME/deepseek-harness"     # systemd 里也要写
```

**防线**：候选路径按平台给（`D:\` 只在 Windows 上才是候选）；一个都没命中时**直接**
抛"没有检出"并给出三条可执行的路；`preflight.cjs` 第 ⑥ 项专门查这一条。

## 3. 数据目录写在 `/var/lib` 下：EACCES

```
EACCES: permission denied, mkdir '/var/lib/leion'
```

**根因**：`/var/lib` 属于 root。而文档示例里只写了 `--data-dir /var/lib/leion/live`，
没写"先建目录并改属主"——**是我给的示例漏了一步**。

**修法**：`sudo mkdir -p /var/lib/leion && sudo chown "$USER": /var/lib/leion`

**防线**：`start-all` 在起任何进程**之前**先试写一次，失败就直接打印上面这条命令并返回 1
（而不是"起两个进程、第三个退出、然后全停"）；`preflight.cjs` ③ 也查。

## 4. 模型下不动：SSL + Xet

```
'[SSL: UNEXPECTED_EOF_WHILE_READING] EOF occurred in violation of protocol'
Retrying in 1s [Retry 1/5] ...  https://huggingface.co/api/models/.../xet-read-token/...
```

**根因**：国内直连 huggingface.co 不稳；而新版 `huggingface_hub`（本机 1.33）默认用 **Xet**
传大文件，**镜像站不转 Xet 接口** —— 所以只设 `HF_ENDPOINT` 仍会报同一个 SSL 错。

**修法**（两个开关缺一不可）：

```bash
export HF_ENDPOINT=https://hf-mirror.com
export HF_HUB_DISABLE_XET=1
python3 scripts/fetch-model.py large-v3 --mirror      # 断了重跑即续传
```

**防线**：`fetch-model.py` 默认就关 Xet、支持镜像与续传，`--list` 打印真实占用
（large-v3 = 2.9 GB）；`check-asr-env.py` 会把这条 SSL 报错翻译成上述两条处置。

## 5. cu12 运行库：ctranslate2 要的是 CUDA 12

```
libcublas.so.12: cannot open shared object file
Could not locate cudnn_ops64_9
```

**根因**：`ctranslate2` 按 CUDA 12 构建。机器上是 CUDA 13 时，`libcublas.so.12` 根本不存在；
P40 那台更典型 —— 装了驱动但**没有** cu12 运行库。

**修法**：`pip install nvidia-cublas-cu12 "nvidia-cudnn-cu12==9.*"`，
再把 `site-packages/nvidia/*/lib` 加进 `LD_LIBRARY_PATH`（**cuBLAS 与 cuDNN 在不同目录，
只给一个会报 cuDNN 缺库**）。

**防线**：`check-asr-env.py` ② 一次给全两个目录；`make-env-file.py` 直接生成 systemd 的
`EnvironmentFile`（PATH + LD_LIBRARY_PATH），不让手抄。

## 6. Tesla P40（Pascal）：默认的 `float16` 用不了

**根因**：P40 是算力 6.1，**有 FP16 存储、没有 FP16 矩阵乘**。`ctranslate2` 按卡查表，
Pascal 上**根本不提供** `float16` / `int8_float16`。而我们的 GPU 缺省值正是 `float16`。

实测这台卡能跑的：`float32, int8, int8_float32`（**没有** `int16`）。
正确档位是 `int8_float32` / `int8`。

**防线**：`whisper_stream.resolve_compute_type()` 启动时查到不支持就自动换档并打一行 ⚠️；
`check-asr-env.py` ③ 直接把"这张卡能跑哪些精度 + 推荐档位"打出来；
`start-all --compute` 白名单加了 `int8_float32`。

## 7. 顺带纠正一个测量错误：那 27% 是假的

第一轮自检（没预热）：`int8_float32` RTF 0.28、`int8` RTF 0.22 → 看着"int8 快 27%"。
加上"每档先预热"再测：

| 档位 | 解码 | RTF |
|---|---|---|
| `int8_float32` | 668 ms | **0.22** |
| `int8` | 680 ms | **0.23** |

差 1.8%，在噪声内。**第一档要替后面所有档付 CUDA 上下文与 cuDNN 选算法的固定开销**
（约 0.2~0.4 s），而生产链路本来就有预热（`whisper_stream` 启动先用 1 秒静音跑一遍），
只有自检没做 —— 是我两边测法不一致。

**防线**：`check-asr-env.py` ④ 每档先预热再计时，并在输出里说明原因。

**教训**：一个排名 / 一个百分比，只要可能受**执行顺序**影响，就必须先排除顺序再下结论。

## 8. "在服务器上能连上自己" ≠ "手机能连上"

在服务器上 `check-relay --base http://10.60.234.77:8788` 全绿 —— 但 `10.x` 是**云主机内网地址**，
同机/同 VPC 内当然通，手机不在这个 VPC 里就完全够不着（公网也不会路由 `10.x`）。

**防线**：文档 §4.1 写清"换一台不在 VPN 里的机器测"，并把三条路（同一局域网 / 公网 IP+TLS /
SSH 隧道）列出来。

## 9. 有公网 IP，从外面连还是超时 → 入站端口没放行

症状组合：服务器上 `--say` 全绿，笔记本上 `timed out`。
**TCP 超时 = 包没送到进程**（"连接被拒"才是服务没起），所以基本只有一个原因。

**修法**：云控制台安全组放行 `TCP 8788`（+ `sudo ufw allow 8788/tcp`）。

**防线**：文档 §4.2 给了三步自证（`ss -ltnp` 看是否 `0.0.0.0` / ufw / 公网 IP 是否在网卡上）、
各厂商菜单位置、以及放行后仍不通的四个后续怀疑（EIP 未绑/NAT 映射、子网 ACL、出站被限、运营商封端口）。

**顺带一个有用的结论**：非标端口（8788）不受 80/443 的备案约束，验证阶段能马上开工；
但**明文上公网 = 密钥与会议音频裸奔**，正式用之前必须 TLS。

## 10. 我给的验收命令用 `curl -s`，失败时一片空白

`curl -s` 静默错误，于是"连不上 / 401 / 大脑没工作"三种完全不同的原因，在屏幕上**长得一样**。

**防线**：`check-relay.py --say "这是一条测试信息"` —— 写入收件箱 → 长轮询 `/frame` 等译文 →
打印"原文 / 译文（增量或定稿）"，失败时列出四条排查（进程 / brain.log / 翻译凭据 / 先用 `--offline`）。

期间还修了一个自己挖的坑：`/frame` 是**长轮询**（服务端挂最多 25 秒），
单次请求超时是"还没有译文"的正常表现，不能当错误。

## 11. 流程上我自己的两次疏漏（记下来，别重演）

1. **只 commit 没 push**：于是让你在服务器上 `git pull` 拉不到东西。
   → 以后凡是让你"在服务器上拉代码"，必须先确认 `git push` 成功并且远端分支一致。
2. **误把 POSIX 命令贴在 Windows 上**（你做的）：`source`/`export` 在 PowerShell 里不是命令，
   于是整段基本没生效（已核查：没有下载、没有残留、没有多余文件）。
   → 给命令时标明"在哪台机器、用什么 shell 跑"，别混在一起给。
