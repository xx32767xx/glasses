# 集成契约：同传翻译官 ⇄ 会议室主 App（2026-10-29 重写 v2）

> **读者**：做「同传翻译官」那一端的人，以及维护主 App 的人。
>
> **本文的前提（用户已明确）**：翻译官那边**已经是一个完整流程**（录音 → 阿里云识别翻译 → 展示），
> 它**不需要**为了接入我们而改自己的管线。接入只做一件事：**把我们 App 的入口和登录态交给它**。
>
> ⚠️ 因此本文和两份旧稿都不同：
> - 2026-10-28 版假设翻译官**复用我们的识别/翻译管线**（`/audio` → whisper → 插件 → `/frame`）—— 不再适用；
> - 上一版（2026-10-29 早间）要他们**往我们的历史库写记录与转写** —— 那是**反向强加**，降级为**可选增强**（§6）。
>
> 我们的字幕管道与会议流程，翻译官**一律不接**；翻译官的数据通路（阿里云）我们**一律不改**。

## 0. 一页速览

```
┌─────────── 主 App（我们）───────────┐         ┌──── 同传翻译官（他们，已有完整流程）────┐
│ 登录 · 账号 · 界面语言               │  ①入口  │ 录音 → 阿里云 → 译文展示 → 眼镜/手机    │
│ 房间 · 发言权 · 术语库 · 历史        │ ──────► │                                        │
└─────────────────────────────────────┘         └────────────────────────────────────────┘
        ②把登录态（host/secret/token/user/语言）交过去 —— 只读，不参与他们的翻译
```

| 谁 | 要做什么 | 不该做什么 |
|---|---|---|
| **我们** | ①首页「同传翻译官」卡变成真入口；②把登录态与语言交给翻译官；③（可选）把他们的记录展示进历史 | 不改他们的翻译管线；不要求他们调 `/audio`、`/frame` |
| **他们** | ①提供一个"被拉起"的入口（§2）；②接住我们给的登录态（§3）；③（可选）结束时调**一个**接口（§6） | 不改自己的阿里云管线；不碰房间/发言权 |

## 1. 三种接入形态（按他们的改造成本从小到大挑一个）

| 形态 | 适用 | 他们要做的 | 我们要做的 |
|---|---|---|---|
| **A. 同一 App 内模块**（推荐） | 他们的流程能打成 AAR/源码模块 | 提供一个 `Activity`（或 Fragment）作为入口，读我们注入的 prefs | 引模块 + 首页卡片 `startActivity` |
| **B. 独立 App + 显式拉起** | 他们坚持独立发版 | 声明一个接收 `Intent` 的入口组件；按 §3 读 extras/prefs | 首页卡片 `startActivity` + 传 extras |
| **C. 独立 App + Deep Link** | 两边发版节奏完全不同 | 注册自己的 scheme（如 `leion-translator://open`） | 首页卡片发隐式 Intent |

三种都不改他们的内部流程 —— 区别只在"进程内还是进程间""谁先发版"。

### 1.1 形态 A / B 的入口约定（建议）

```text
组件：  <他们的包名>/.TranslatorEntryActivity      （或他们指定的名字，告知我们即可）
Action：com.leion.action.INTERPRETER               （形态 B/C 用隐式 Intent 时）
Extras（发明文，避免我们两个 App 抢同一个 prefs 文件）：
  host      "http://117.50.180.93:8788"     // 服务器地址（与我们一致）
  secret    "…"                             // 共享密钥
  token     "…"                             // 账号 token（可空：空 = 未登录）
  user      "boss"                          // 账号名（用于显示）
  role      "user"                          // admin / user / dev
  uiLang    "zh" | "pt-BR" | "en"           // 界面语言（空 = 跟随系统）
  speakLang "zh-CN" | "pt-BR"               // 说话语言
```

> ⚠️ **不要**让翻译官去读我们的 `SharedPreferences("leion")`（形态 B/C 时）：两个 App 各有自己的私有目录，
> 读不到；而且我们的字段名以后可能变。**用 extras 传**，字段名就是上面这张表。

## 2. 我们要改的东西（主 App 侧，工作量很小）

1. `page_home.xml` 的「同传翻译官」卡：去掉「即将上线」标签，点击改为拉起翻译官入口（§1）；
2. 拉起前把 §1.1 的 extras 从 `SharedPreferences("leion")` 读出来填上；
3. 若他们没装/没接上：`startActivity` 失败要**兜住**，提示"未安装同传翻译官"而不是崩；
4. 返回主 App 后保持登录态不变（他们不该改我们的 token）。

## 3. 登录态：谁负责什么

| 事项 | 归属 | 说明 |
|---|---|---|
| 登录/注册/注销 | **我们** | 翻译官不做账号体系，只接收 token |
| token 有效期、被顶下线 | **我们** | 我们推 `{type:'kicked'}`；翻译官也应在收到 401 时回自己的登录入口（或提示用户回主 App 登录） |
| `whoami`（角色/有效期） | 我们提供接口 | `GET /auth/whoami` → `{ok, user, role, status, expiresAt}` |
| 单会话冲突 | **待拍板**（§8） | 同账号后登录会吊销前一个 token；两 App 共用同一账号会互踢 |

> 现实约束：如果翻译官和主 App **同时**用同一个账号在线，现在会互踢。
> 三种解法：①各自用不同账号（临时）；②把单会话改成 per-label（推荐，§8）；
> ③翻译官只在我们退到后台时用（不好，体验差）。**推荐 ②**。

## 4. 术语库（可选，只读）

如果翻译官愿意用我们审批过的术语（推荐 —— 否则用户在会议室维护的术语对它不生效）：

```
GET /org/libraries          → { ok, libraries:[{id,name,categoryName,entries,priority}] }
GET /org/libraries/<id>     → { ok, library:{ id, name, entries:[{zh,pt}] } }
```

- 只读。**审批流在我们这边**：用户改库要提申请、管理员批；翻译官不实现改库；
- 他们的用法：把 `entries` 注入阿里云侧的 prompt（术语优先、专名写法统一）；
- 不接也可以 —— 那就不读，不影响接入成功。

## 5. 界面语言

主 App 已有三套资源（`values` / `values-en` / `values-pt-rBR`），选中的语言用 extra `uiLang` 传过去。
翻译官自己的文案用它们自己的资源即可，**不必与我们逐字一致**；只需要保证"语言别反着来"（用户在中文界面里点进去，不该是葡语界面）。

## 6. 历史记录：默认不写（可选增强）

**默认方案（零改动）**：翻译官的记录留在他们自己那边，我们的历史页**不显示**。
用户在主 App 的「历史」里只看到「同传会议」。

**可选方案（他们愿意的话）**：结束时调**一个**接口把整场记录交给我们，我们负责入库与展示：

```http
POST /org/history/interpreter        X-Leion-Token: <token>
{ "name": "与圣保罗客户沟通",
  "langs": ["zh-CN", "pt-BR"],
  "startedAt": "2026-10-29T09:10:00.000Z",
  "endedAt":   "2026-10-29T09:42:10.000Z",
  "utterances": [ { "at": "…09:10:32Z", "srcText": "我们先确认交期",
                    "dstText": "Vamos confirmar o prazo primeiro", "srcLang": "zh-CN" } ] }

200 { "ok": true, "id": "record-xxxx" }
```

- **一次提交整场**，不是逐句上报 —— 这样他们不需要管理"会话 id"，失败重试也简单（同 `startedAt` + `name` 幂等）；
- 我们落库后，历史页就会多一条类型为「同传翻译官」、人数「仅自己」的记录，详情页能看转写与导出 Word；
- **这是可选的**：不做这条，接入照样算完成。

## 7. 翻译官**不要**碰的东西（重要）

| 端点 | 为什么不要碰 |
|---|---|
| `POST /audio` | 那是我们字幕管道的音频入口；他们要上传自己的音频会与我们抢同一个 `audio-in.pcm` |
| `GET /frame`、`WS /ws?room=` | 我们的字幕总线（单通道）。他们自己出译文，接了会拿到别人会议的字幕 |
| `/org/rooms/*/floor` 的 POST（take/lock/force-release） | 发言权是**会议流程**，翻译官是单人会话，不参与抢麦 |
| 我们的 `SharedPreferences("leion")` | 形态 B/C 下读不到；字段名我们不承诺稳定 |

## 8. 待拍板（会影响两端）

| # | 事项 | 建议 |
|---|---|---|
| 1 | 单会话是否改成 **per-label** | **建议改**：同 `label` 顶掉旧的、不同 `label` 并存。否则两 App 共用账号必然互踢 |
| 2 | 接入形态选 A / B / C | 建议 **A**（同一 App 内模块，省掉跨进程传参与 token 同步的一堆坑） |
| 3 | 历史记录是否走 §6 的可选增强 | 建议**先不做**（接入优先），等两边流程都稳了再加 |
| 4 | 是否抽 `:core` 安卓库模块共用 `LanClient` 等 | 等会议室收尾 + 一次双人构建验证后再抽 |

## 9. 联调检查清单（照着打勾）

- [ ] 首页点「同传翻译官」→ 能进他们的界面（没装/没接上时是**提示**，不是崩溃）
- [ ] 翻译官界面里显示的账号名、服务器地址正确（`user` / `host` 接到了）
- [ ] 未登录时点进去：提示"请先登录"（或他们自己的登录入口），不出现空白页
- [ ] 在主 App 切到 English / Português 再进去：翻译官那边语言也跟着对（`uiLang` 接到了）
- [ ] 从翻译官返回主 App：**登录态还在**（token 没被改/没被吊销）
- [ ] （若做了 §6）结束一场翻译官会话后，主 App 历史页多一条「同传翻译官」记录，转写能看到
- [ ] （若做了 §6）点开那条记录 → 导出 Word 能打开

## 10. 协议演进规则（沿用）

1. **只做加法**：加 extras 字段、加可选端点都安全；改名/改语义要先通知；
2. 新能力先出现在 `/hello` 的 `features` 里（我们这边的约定），老客户端不认识就忽略；
3. 已经发生过的语义变更（照旧文档写会踩）：4.37 收件箱 JSON 化、4.43 字幕 WS 推送、
   4.44/4.46 结束推送与 410、4.45 被顶下线推送、4.74 帧带 `roomId`；
   **本版**：翻译官不再复用我们的字幕管道，也不必写我们的历史（可选）。

## 11. 假服务器（联调不需要 GPU / 模型 / 凭据）

```bash
node relay/lan-relay.mjs --data-dir var/dev --port 8799 --secret dev-secret
curl -s http://127.0.0.1:8799/hello -H "X-Leion-Secret: dev-secret"
curl -s http://127.0.0.1:8799/auth/whoami -H "X-Leion-Secret: dev-secret" -H "X-Leion-Token: <token>"
```

翻译官要联调的只有 `/hello`、`/auth/*`、以及可选的 `/org/libraries` —— **都不需要 GPU**。
