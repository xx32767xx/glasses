# 集成契约：同传翻译官 ⇄ 会议室主 App（v3 · 2026-11 重写）

> **读者**：做「同传翻译官」那一端的同学、维护主 App 的人、以及要给技术路线拍板的人。
>
> **v2（2026-10-29）的前提已经作废**，这里写明为什么，免得两边按旧稿干活：
>
> | v2 的前提 | 现在的实际情况 |
> |---|---|
> | 翻译官是一个**独立 Feature/独立 App**，我们只把入口和登录态交过去 | **能力并入我们的 App**：UI 由我们用纯 Java 重做，他们的 JS 只当"产品规格" |
> | 他们的阿里云管线**一律不改** | ASR 走哪条链路**还没定**（本地 whisper / 云端 fun-asr），两种都得能接 |
> | 音色克隆是卖点 | **音色克隆要删掉**；播报保留（固定音色） |
> | — | **用户都用最新版 APP** → 不做版本兼容，版本不一致直接拦（见 §9） |
> | — | **密钥一律在服务器**，绝不进 APK |
>
> 仍然成立的部分：登录态、术语库只读、不碰房间/发言权、"不要把能演示说成准确率已达标"。

## 0. 一页速览

```
┌────────────────────── 我们的 App（纯 Java）──────────────────────┐
│ 采集（AudioCaptureArbiter · 已实现 5.28）                          │
│      ↓ PCM 16k                                                    │
│ ASR 后端（**形状固定、实现可换**，见 §3）                           │
│      ↓ {type:'partial'|'final', text, lang, id}                   │
│ 翻译（relay → DeepSeek + 术语注入 + 校对，见 §4）                    │
│      ↓ 译文                                                       │
│ ┌────────────┴─────────────┐                                      │
│ ▼                          ▼                                      │
│ 界面（弹幕/字幕，我们的工艺）   播报（TTS，见 §5）                     │
└───────────────────────────────────────────────────────────────────┘
```

**三段各管一件事，谁也不许跨段猜**：采集只管给我 PCM；ASR 只管给我文本事件；翻译只管给我译文。
这样"ASR 换成云端"或"翻译换成 qwen-MT"都只动一段。

## 1. 采集侧契约（已实现，5.28）

手机上录音会话是**整机一份**的资源。任何组件想录音都必须：

```java
String denied = AudioCaptureArbiter.request(OWNER_INTERPRETER);  // 空串 = 拿到
if (!denied.isEmpty()) { /* 直接把 denied 显示给用户，别自己编话 */ }
AudioCaptureArbiter.attach(OWNER_INTERPRETER, source);           // 登记，释放时才停得掉
AudioCaptureArbiter.release(OWNER_INTERPRETER);                  // 幂等；离开页面/后台必须调
```

规矩：

- **同一时刻只有一个持有者**；抢不到返回的是**给用户看的人话**（「会议房间正在录音，请稍后再试」）；
- `stop()` 是"叫它停"不是"等它停"，所以 `AudioSource.isWindingDown()` 为真期间**新申请会被拒绝**
  （「上一段录音还在收尾，请稍后再试」）；
- **退到前台之外就释放**：翻译官页同样要在 `onStop` 里 `release`，否则就是下一个"偷偷录音"。

## 2. 数据契约：翻译官的"一场"

| 字段 | 值 | 说明 |
|---|---|---|
| `sessionId` | 独立 id（不复用 `roomId`） | 翻译官**不进房间**，历史里也要能和会议分开 |
| `kind` | `'interpreter'` | 与 `'meeting'` 区分，列表/详情按它选版式 |
| 参与者 | 只有本人（单向） | 不涉及发言权、邀请码、成员 |
| 存不存 | **待定**（见 §7 第 2 条） | 存就整场提交一次，不逐句写 |

## 3. ASR 后端契约（**形状固定，实现可换**）

页面**只**认下面这组事件，不认 HTTP 端点、不认 WebSocket 细节：

```text
{ type: 'ready' }                                   // 后端就绪，可以送音频
{ type: 'partial', id, text, lang }                 // 边说边出（可能是空串）
{ type: 'final',   id, text, lang }                 // 这一句定了
{ type: 'error',   code, hint }                     // code 是机器码，hint 是人话（三语由界面翻）
```

两种实现，事件形状完全一致：

| | **本地管线**（房间那套） | **云端 fun-asr**（他们的链路） |
|---|---|---|
| 音频去向 | `POST /audio`（HTTP 上行） | `ws://<relay>/asr`（WS 二进制帧） |
| 谁识别 | 服务器 whisper large-v3 | 阿里云 fun-asr-realtime |
| `partial` | **没有**（切句完成才出整句） | 有（流式） |
| 延迟 | 说完 ~1~2 秒 | 说完 ~0.3~1 秒（多一跳 relay） |
| 术语一致 | 与房间同一条翻译链路 | 需额外注入（见 §4） |
| 现场网差 | 只依赖 relay | 依赖 relay **和**外网 |
| 计费 | 0（GPU 已在） | 按量（并发/时长） |
| 额外前置 | 无 | 服务器配 `DASHSCOPE_API_KEY` / `ASR_WORKSPACE_ID` / `ASR_REGION` |

> **这一条正是等拍板的地方**（§7 第 1 条）。实现上切换只换后端，UI/翻译/播报/采集全部复用。
> 决策依据见 §8 的对比口径 —— 用同一段录音量出来，不靠意见。

## 4. 翻译契约（建议固定，不随 ASR 变）

```
输入：源文本 + 源语言 + 目标语言（+ 这一场的术语表 + 最近几句上下文）
输出：译文 + 元信息（用了哪个模型、有没有被校对改过、命中了哪几条术语）
```

**建议：走我们自己的 DeepSeek 链路，不走 qwen-MT。** 理由只有一个但很硬：
房间那边已经把术语注进去了（`亮亮视野 → LLVision`）。翻译官若走另一套 MT，
**同一个人会在两个页面看到两种译名**，用户没法判断哪个是对的。

代价：翻译官必须经过我们的 relay（而不是手机直连阿里云）。这在"服务器本来就在公网"的部署下不是问题。

## 5. 播报契约（TTS）

```text
TTS(text, lang) → 音频（16k/22k/44.1k 按实际，如实上报采样率）
```

两条实现，同一接口：

| | **手机系统 TTS**（先做） | **云端 qwen3-tts-flash**（后补） |
|---|---|---|
| 依赖 | 零（Android 内建） | relay `POST /tts` + Key |
| 离线 | 能 | 不能 |
| 音质 | 中文可以；葡语看机型 | 明显更好、音色稳定 |
| 首包 | 本地合成，通常 <200ms | 0.5~1 秒 |

播报规则（这几条是他们踩过坑的产品经验，照抄）：

1. **只听耳机/眼镜，禁手机外放**；没有可用输出设备时**明确拒绝**并说明，不"悄悄外放"；
2. **和实时传声二选一**：开始播报就停掉对方原声，恢复时再开（用户已选方案 1）；
3. **过期不播**：译文超过 12 秒还没轮到就不念了（会议里念 10 秒前的话是噪音）；
4. **积压丢弃**：队列超过 3 句就丢最旧的；
5. **播报时暂停采集**（否则自己的 TTS 被麦克风录回去，云端/本地识别出"译文再译一遍"，死循环）；
6. 长句**按标点切块**，第一块先播、后面的边合成边播（TTS 是整段 API，不切就得干等）。

## 6. 界面契约（我们自己的）

- 三语资源齐全（`values/` `values-en/` `values-pt-rBR/`），只用语义 token，不写死色值；
- 状态行必须能回答三个问题：**后端是什么**（本地/云端）、**现在在干什么**（识别中/翻译中/播报中/空闲）、**上一条错误是什么**（机器码 + 人话）；
- 不能出现"看着正常、其实没在工作"的界面状态（本项目反复踩过的坑）。

## 7. 需要拍板的两件事

| # | 问题 | 影响 | 我的建议 |
|---|---|---|---|
| 1 | 翻译官的 ASR 走**本地 whisper** 还是**云端 fun-asr**？ | 差 9~11 天工作量、是否依赖外网、能否"边说边出字" | 先用本地（5~6 天出可用功能），真机验收后若必须要流式再补云端（只换后端） |
| 2 | 翻译官的记录进不进「历史」？ | 数据层要不要新表/新字段 | 进，但用独立 `sessionId + kind='interpreter'`，与会议分开；存就整场提交一次 |

## 8. 给决策用的对比口径（同一段录音，两条链路各测一遍）

| 指标 | 怎么量 | 为什么重要 |
|---|---|---|
| 首字延迟 | 说完最后一个音节 → 屏幕上出现文字 | 直接决定"能不能边说边看" |
| 整句延迟 | 说完 → 出现完整译文 | 会议场景的真实体感 |
| 中文错字率 | 同一段录音，人工标注后算 CER | 已知本地 whisper 在这个语料上的基线 |
| 巴葡错字率 | 同上（需要真人葡语录音） | 他们文档里"尚未验收"的那条 |
| 现场网差表现 | 限速/丢包下的失败形态 | 云端路线的主要风险 |
| 成本 | 每分钟音频多少钱（云端） | 长期跑要算账 |

> 这张表是**唯一**应当用来拍板的东西。没有它，"本地还是云端"只是口味问题。

## 9. 版本门禁（已实现，5.26 / 5.27）

- 服务端通过 `GET /version` 公布**要求的客户端 versionCode**；手机比数字，不一致就弹**不可取消**的对话框；
- 比要求**旧**的客户端在 `/hello`、`/audio`、`/frame`、`/say` 上直接 **426**（因为门禁上线前的 APK 里没有检查代码，只能靠服务端拦）；
- **我们自己的脚本**（`check-live-audio`、`fake-phone`、`test-phrases`、探针）带 `X-Leion-App: tool`，显式放行。

## 10. 联调检查清单

1. `AudioCaptureArbiter.describe()` 在两条链路下都应为 `空闲`（离开页面后）；
2. 翻译官页 `onStop` 后：录音停、播报停、`/status` 里没有残留会话；
3. 房间页与翻译官页互相切换各 5 次，不出现"开麦失败"或"幽灵录音"；
4. 播报时开麦被拦住并说明原因；关播报后恢复；
5. 三语界面下所有服务端提示都不出现中文原话；
6. `node tests/run-all.mjs` 全绿（含静态门禁：不许裸 `new AudioRecord`、不许绕过仲裁器）。

## 11. 不碰的东西（沿用 v2）

- 房间协议、发言权状态机、邀请码、成员管理；
- `POST /audio` 的既有语义（本地后端会**复用**它，但不改它的契约）；
- 术语库的写入流程（翻译官只读）；
- 用户的密钥与账号存储位置。
