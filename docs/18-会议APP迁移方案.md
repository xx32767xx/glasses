# 会议 APP 迁移方案（原型 V0.3 → 现状系统的差距与路线）

> 原型：`prototype/translation-app-prototype.html`（**已存档进仓库**，见 `prototype/README.md`；V0.3，8 页 + 完整规则）
> 现状：本仓库（单麦 → 电脑识别 → 翻译 → 眼镜字幕）
> 本文只做**差距盘点 + 迁移路线 + 待确认问题**，不含实施代码。

## 1. 原型要的是什么（读下来的规格摘要）

**一个 APP、一个云端房间、能力随设备自动适配**。核心事实清单：

| 维度 | 原型规定 |
|---|---|
| 用户与房间 | 邮箱 + 验证码登录；6 位邀请码入会；创建者即管理者，可移交；≥2 人在房即保留 |
| 收音架构 | **一人一麦**：每人手机就是自己的麦克风，**音轨从源头分离，不靠说话人分离算法** |
| 发言权 | **互斥**：同一时刻最多一人开麦（点击开麦即保持），后开麦者顶替前者；可「锁定发言」，仅管理者能解除他人锁定 |
| 语言 | 中 / 英 / 巴葡（数据驱动可扩）；每人选「我的参会语言」；收听 = 其余语种 → 我的语言；发言 = 我的语言 → 其余语种；目标语 >2 时语音只播「主语言」 |
| 输出通道 | 眼镜＝镜片字幕 + 近耳播报；耳机＝耳内播报；手机＝收音 + 播报。**播报三通道互斥（耳机 ＞ 眼镜 ＞ 手机外放）**；面对面参与者**禁手机外放**；收音源同样互斥 |
| 节奏 | **字幕先行**：原文先上屏，译文约 1 秒后补齐；开麦期间暂停播报（防声学回环），关麦后补播 |
| 眼镜规范 | 黑底高亮绿、视野右下、单条 ≤2 行 ≤28 字、**新句覆盖旧句不滚动**、停留 = 语音时长 ×1.5 且 ≥3s、强光切高对比 |
| 术语库 | 创建/加入页**多选**启用，可一个都不选；管理在「我的 - 术语库管理」 |
| 会后 | 自动生成统计 + AI 摘要 + 行动项 + 按说话人/语种筛选转写；导出 Word、只读分享链接；历史 30 天 |
| 弱网 | 降级为「仅转写不翻译」，界面标记，恢复后补齐 |
| 翻译落地 | **本期按云端翻译**；「本地模型（中↔英端侧）」仅预留接口 |
| 合规 | 入会强提示「将被转写记录」；发起人可关录音仅留转写；纪要与录音默认 30 天 |

## 2. 现状系统是什么

```
手机（麦克风，16k/44.1k）──HTTP /audio──▶ relay（落盘 audio-in.pcm）
                                            │
                                    whisper_stream.py（能量切句 + 幻觉闸 + 热词提示）
                                            │ 一行一句话
                                       inbox.jsonl
                                            │
                                    plugin/core.mjs（翻译 + 术语归一 + 本句专名提示 + 校对 4b）
                                            │ 字幕帧（displaySeq + lines）
                                    bridge ──▶ 眼镜投屏 / 手机屏
```

**关键特性**：单麦克风、单条音频流、**只有中↔葡两个方向**、无账号、无房间、无播报（**全仓库没有 TTS**）、无历史与纪要、术语是按用户的单张表。

## 3. 差距盘点

| 原型能力 | 现状 | 结论 |
|---|---|---|
| 邮箱+验证码账号 | 无（relay 用共享密钥） | **新建** |
| 房间/邀请码/管理者移交 | 无（单 client） | **新建**（服务端状态） |
| 一人一麦 → 天然分轨 | 单麦单流 | **改造**：好处是**不用做说话人分离**；代价是 GPU 并发上升 |
| 发言权互斥 + 锁定 | 无 | **新建** |
| 多语（中/英/巴葡） | 仅中↔葡 | **改造**：翻译方向从固定一对变成 `N 人 × (N-1)` 扇出 |
| 实时字幕流（原文先、译文后） | 已有（inbox → 帧） | **复用** |
| ASR（切句/幻觉闸/热词提示） | 已有 | **复用**（改成每路音频一个实例） |
| 术语库（多选启用） | 单表 + 归一/hint/watch/rescue | **改造**：单表 → 多库叠加 + 会议级选择 |
| 眼镜字幕投屏 | 已有（含排版与分页） | **复用 + 对齐规范**（见 §6 差异） |
| 耳机/眼镜语音播报 | **完全没有** | **新建**（TTS + 通道仲裁） |
| 会后纪要（AI 摘要/行动项/导出） | 无 | **新建** |
| i18n（三语界面） | 无 | **新建** |
| 弱网降级 | 无 | **新建**（但逻辑简单：翻译失败即标「仅转写」） |

**一句话**：能复用的是「语音→文字→译文→字幕」这条链的五块（切句、热词、翻译、校对、眼镜投屏）；
要新建的是**房间与账号**、**播报**、**纪要**、**多语扇出**、**i18n**。

## 4. 建议的目标架构（三层）

```
┌─ 端（安卓 APP）──────────────────────────────────────┐
│ 收音：手机麦 / 眼镜麦 / 耳机麦（互斥，热插拔）          │
│ 显示：屏幕字幕 + 眼镜投屏（同一份帧，不同排版）          │
│ 播报：TTS 流播放（耳机 > 眼镜近耳 > 手机外放）           │
│ 上行：WebSocket 推 PCM（带 roomId/userId/speaking 状态） │
│ 下行：WebSocket 收「字幕帧 / 通道状态 / 发言权事件」      │
└──────────────────────┬──────────────────────────────┘
                       │  WebSocket（不是现在的 HTTP 追加文件）
┌─ 房间服务（云，Node）──┴──────────────────────────────┐
│ 房间状态：成员、发言权互斥、锁定、管理者移交、计时        │
│ 路由：把某人的音轨喂给 ASR，把某人的译文扇出给各目标语种   │
│ 存储：转写与纪要与录音（默认 30 天）                     │
└──────────────────────┬──────────────────────────────┘
┌─ 推理服务（GPU 机器）─┴──────────────────────────────┐
│ ASR：whisper_stream（切句 + 幻觉闸 + 热词提示）每路一份   │
│ 翻译：现有 core 的翻译/术语/校对逻辑（可抽成纯服务）      │
│ TTS：新增（原型要求近耳播报，不能省）                    │
└─────────────────────────────────────────────────────┘
```

**三个架构判断**：

1. **传输层必须换**。现在是「POST /audio 追加到一个文件 + 旁文件写采样率」，天生只能服务一个人。
   房间场景要 WebSocket 双向事件（音频上行、字幕/发言权下行）。relay 的**落盘与审计能力保留**（回放、复盘用）。
2. **翻译要扇出**。一个人说话，其它 N-1 个人各自要一份译文；3 人 3 语时一句话最多 2 次翻译调用。
   延迟预算会变紧（现在 1–2s/句），必须并行 + 缓存相同目标语。
3. **播报是新的一大块**，且它带来原型明确点出的**声学回环**问题（开麦期间必须暂停播报）。
   这块在本仓库里**零基础**，不能拿"字幕已经能用"来估它的工作量。

## 5. P0 垂直切片（我建议的最小可跑）

不做全量 8 页，先打通一条竖线，用真实 3 人验证「一人一麦 + 字幕先行 + 各看各的语言 + 眼镜投屏」：

- 房间：1 个房间、3 人、3 语（中 / 英 / 巴葡），邀请码入会，创建者即管理者
- 收音：手机麦为主（眼镜麦可选），**同一时刻只有一人开麦**
- 输出：先做**字幕**（屏幕 + 眼镜投屏），播放通道只做「手机外放（远程）/ 静音（面对面）」二元，不做 TTS
- 术语库：单库即可（多选留到 P1），复用现有归一 + hint
- 会后：保存转写（不做 AI 摘要），历史列表能回看
- 弱网：翻译失败标「仅转写」

**这条竖线跑通后再加**：TTS 播报 → 多库术语 → AI 摘要 → 多房间 → 端侧模型。

## 6. 必须注意的既有差异（别以为能直接搬）

| 项 | 现状 | 原型要求 | 需要做的事 |
|---|---|---|---|
| 眼镜字数 | 32px → 17 字/行 × 2 行 ≈ 34 字，**超了会翻页** | ≤28 字、**不滚动不翻页，新句覆盖旧句** | 改排版与截断策略（`docs/12` 的分页逻辑要按新规范重算） |
| 眼镜停留 | 现有分页节奏 | 停留 = 语音时长 ×1.5，且 ≥3s | 新增驻留计算 |
| 眼镜强光 | 未实现 | 强光自动高对比 | 新增亮度/对比自适应 |
| 翻译方向 | 固定 zh↔pt | 每人一个目标语，最多 N-1 个 | 改造为扇出 + 并行 |
| 术语 | 单表（含 watch/rescue） | 多库多选 | 库 → 表聚合，会议级快照（沿用现有「每场只读一次表」的设计） |
| 热词提示 | 按源语种判断「本句是否提到名字」 | 每目标语各一份提示 | 按目标语生成 hint |

## 7. 关键风险与难点（诚实版）

1. **GPU 并发**：一人一路 ASR。3 人同时说话（虽然互斥，但抢麦、多人环境噪声）时并发路数会升。
   现实里按「同时最多 1–2 路活跃」设计，其余路静音不送解码（现有 VAD 能直接省掉）。
2. **翻译扇出延迟**：一句话 N-1 次翻译，串行会 2–4s。必须并行；同一目标语命中缓存就直接复用。
3. **TTS 零基础**：选型（本地 vs 云）、延迟（<500ms 才不违和）、音色、多语种、断句都在「字幕」之外重新做。
4. **声学回环**：开麦暂停播报这条规则必须在播放通道与麦克风之间做状态仲裁，否则会把自己播的译文再翻一遍（原型专门点出来了）。
5. **合规**：转写提示、录音开关、30 天保留 —— 现在是"没有这个能力"，要新增而不是改造。
6. **多用户测试**：现在所有评测都是单机单流；3 人房间的端到端延迟、字幕是否错配发言人，都要新建测试办法。

## 8. 需要先跟老师确认的 6 件事（按影响排序）

1. **部署形态**：房间服务放哪？现有 `docs/10` 的云服务器够不够（WebSocket + GPU 分机）？
   还是要求「云端只做交换、推理在另一台机」？
2. **TTS 选型与是否必须**：原型 P1 才排「耳机播报」，P0 能不能**先只做字幕**？（决定工作量差一半）
3. **术语库的「多库」语义**：会议级多选聚合时，两库对同一中文名给了不同目标写法，谁赢？
   （现在是"同一条目内变体→规范写法"，没有跨库冲突规则）
4. **纪要的 AI 摘要**用哪个模型、在哪跑？（现在只做翻译与校对，没有摘要能力）
5. **账号体系**：邮箱+验证码自建，还是接老师那边的统一账号？
6. **一人一麦的物理前提**：面对面会议里每人一台手机？如果只有发起人有手机（我们现在的演示形态），
   「天然分轨」这条前提就不成立，得回到说话人分离 —— 这个假设必须先钉死。

## 9. 我的建议顺序

1. **先确认 §8 的第 6 条**（一人一麦是否真的一人一台手机）—— 它决定整个架构；
2. 确认 §8 第 2 条（P0 是否含 TTS）—— 它决定工作量；
3. 然后做 §5 的竖线：房间 + 一人一麦 + 字幕先行 + 各看各语言 + 眼镜投屏 + 转写存档。

> 复用的边界要说清：ASR 切句/幻觉闸/热词、翻译与校对、眼镜投屏这三块可以直接搬；
> 房间、播报、纪要、账号、i18n 是**新建**，不能拿现有进度去估。

## 10. 增量改造 vs 从零重建（结论：**分三层，各择其一**）

老师问的是二选一，但代码事实不支持一刀切。用一条判据先量：

> **"这段代码如果明天要支持 10 个房间，需要改多少？"**
> 引擎代码：0 改动（每房间一份实例）。外壳代码：全改。

### 10.1 现有资产的真实体量（这是"要不要重写"的依据）

| 资产 | 体量 | 里面沉淀了什么 |
|---|---|---|
| `plugin/core.mjs` | 2488 行 | 翻译管线、术语归一、本句专名提示、校对 4b 强制闸、排版 |
| `bridge/whisper_stream.py` | 1122 行 | 自适应能量切句、短句保护、幻觉闸、热词提示、重采样相位 |
| `relay/lan-relay.mjs` | 1235 行 | 5 个端点、共享密钥、落盘与审计、尾随 |
| `lib/terms.mjs` | 454 行 | 术语匹配规则（边界、危险邻接、实体重叠、折叠、幂等） |
| `android/` | 11 个 java 文件 · 370 KB | 取音（手机/眼镜/USB 44.1k）、投屏、诊断面板 |
| 测试 | JS 432 用例 · Python 337 断言 | 每一条都对着一次真实故障 |

**真正的资产不是行数，是那些"踩出来的数字"**：静音判定 800 / 短句保护 1100、
幻觉词表、热词边界规则、排版 31.6px 下界、`reasoningEffort` 必须显式传、温度回退的触发条件……
这些值写成文字只是几行，写在代码与测试里才是可回归的约束。**从零重建 = 把它们全部重踩一遍。**

### 10.2 三层分开定

| 层 | 决定 | 理由 |
|---|---|---|
| **引擎层**（ASR 切句/幻觉闸/热词、术语匹配、翻译+校对、眼镜排版与投屏、评测与测试） | **保留 + 抽成服务**（增量） | 逻辑与"有没有房间"无关；抽成独立进程后，现有插件和未来房间服务**共用同一份**。已有现成接缝：`translator.kind === 'http'` 那条路 |
| **传输与状态层**（`relay` 的 HTTP 追加单文件、插件依附 harness 的 `fs/llm/shell`） | **重写**（新建房间服务） | relay 是"单用户单流"设计（`POST /audio` 追加到一个 `audio-in.pcm`）；插件是 **harness 沙箱插件**（零 `import`、动态包、生成器一致性检查）。把沙箱插件改成服务端等于推翻它的全部前提，成本高于新建一层 |
| **端侧外壳**（原型 8 页 UI、账号、i18n、TTS、纪要导出） | **新建** | 仓库里零基础，没有可复用的东西 |

### 10.3 为什么不"全部增量"（把 relay/plugin 直接改成房间）

1. 多房间要**按用户隔离音频**，现在是"一个文件追加"；改造等于重写路由，却拿不到什么好处。
2. 插件受"零 `import` + 沙箱服务 + 动态包生成"三重约束，改成常驻服务端要重做生成器与双包一致性测试 ——
   这些测试正是交付物质量的门禁，动它们的风险远大于收益。
3. relay 的**落盘/审计/回放**能力值得留下，但它应该作为房间服务的一个模块，而不是被塞进房间协议里。

### 10.4 为什么不"全部从零"

1. 769 条测试与上面那批实测参数会一起丢掉；而会议 APP 的难点恰恰在语音与字幕这一侧。
2. 评测数据（`var/asr-eval/` 的 packs / spans / 报告）只对现有引擎有意义；
   重建后**无法与历史数字对比**，等于把"我们量过什么"清零。
3. 眼镜投屏与排版是硬件的坑（`LayoutParams`、跨块重采样、44.1k），重写会重踩。

### 10.5 落地方式（绞杀者模式，两个形态并存）

```
现在：单机链路（手机 → relay → whisper_stream → 插件 → 眼镜）   ← 原样保留，打 tag baseline-单机同传-v1
                                                              ↑ 作为回归基线与演示降级形态
新：  房间链路（APP → WS → 房间服务 → 翻译服务/ASR 服务 → 各端字幕）  ← 逐步接管
```

**第一步（可以立刻做、且不破坏任何东西）**：把翻译/术语/校对从 `core.mjs` 抽成
`翻译服务`（HTTP），让现有插件以 `translator.kind='http'` 指向它 —— 两边共用一份逻辑，
现有测试全绿即可证明"抽对了"。这一步做完，房间服务就有现成的翻译后端。

### 10.6 如果要把"远程接入"也算进目标

纯自建 WebSocket 房间对"多房间 + 远程音频"会越写越像 WebRTC。若老师的目标包含远程参会者
听实时音频，**建议评估引入现成实时通信基础设施（LiveKit/SFU 一类）**，只把我们的 ASR/翻译/字幕
挂进去。这条是选项，不是结论 —— 取决于 §8 第 1 条（部署形态）。
