# 收音策略：从手机麦克风到"一句完整的话"

> 这份文档回答一个问题：**声音进来之后，我们怎么决定"哪算一句话"。**
> 它记录的是**当前正在跑的缺省值**，以及每一个数字背后的实测依据 ——
> 所以它既是一份策略说明，也是一份可以直接对照代码核对的现状快照。
>
> 相关文档：[`04-语音识别验证.md`](04-语音识别验证.md) 记的是"测得准不准、每句多少延迟"，
> [`05-数据通路.md`](05-数据通路.md) 记的是"文件放哪、哪些是插件"。
> 本文只讲收音与切句这一段的策略。

---

## 0. 一句话说清这套策略

**手机只当麦克风，切句在电脑上做，每一句整段送识别。**

听起来平平无奇，但三个决定都是被实测逼出来的：

| 决定 | 为什么不是别的做法 |
|---|---|
| 识别放在电脑，手机只录音 | 手机自带的 `SpeechRecognizer` 在这台设备上**不可用**（已诊断定死：是设备问题，不是我们的代码）。而"整段送模型"需要 GPU，手机也没有 |
| 按**能量 + 静音时长**切句，不用 VAD 模型 | 同传要的是**整句**，半句翻出去毫无意义；而 Whisper 对 <1 秒的碎片识别质量急剧下降。一个能量门槛 + 静音时长在近场单人场景够用，且零额外依赖 |
| 每句**整段**识别，不做流式解码 | 同上。流式解码会不断吐出半句，那些半句既不好翻也不好读 |

**这套策略里真正的难点不是"把声音录清楚"，而是"在哪切断"。**
下面的每一条参数，都是围绕这一件事。

## 1. 这条路分了几层，每层负责什么

```
① 手机 App（android/…/MicUploader.java）
     16 kHz 单声道，每 1000ms 一块 POST /audio
     降级链 16000 → 44100 → 48000（哪个能开就用哪个，旁文件告诉电脑实际值）
     手机上的「听葡语/听中文」按钮 → 写 audio-in.lang
        │
        ▼  HTTP（局域网，同一 WiFi）
② 转发进程（relay/lan-relay.mjs）
     追加写 var/live/audio-in.pcm（裸 PCM，永不截断）
     写旁文件 audio-in.rate / audio-in.lang
     每个块在日志里记字节数 + 峰值 + RMS（排查收音问题的第一现场）
        │
        ▼  只追加的文件
③ 尾随（whisper_stream.py · PcmFollower + IdleTracker）
     按 100ms 对齐读块；半帧留住；被截断就退回 0；采样率变了就重采样
     判"上传是不是真的停了"（--idle-flush-ms 2000）
        │
        ▼
④ 切句（whisper_stream.py · UtteranceSegmenter）★ 策略核心
     自适应能量门槛 → 分清"有语音/没语音"
     静音超过 N 毫秒 → 认为一句话说完（--silence-ms 500）
     前导缓存 250ms、短句保护、到上限时按停顿断句
        │
        ▼  一句 = 一段 float32 音频
⑤ 识别（faster-whisper）
     整段送模型（beam 5 + 语种 + 提示词 + 低电平时归一化）
     四道闸过滤假结果：no_speech_prob / avg_logprob / 幻听惯用语 / 提示词回显
        │
        ▼  stdout 一行一句话
⑥ 收件箱（bridge/asr-bridge.mjs → var/live/asr-inbox.jsonl）
     交给插件翻译、排版、上屏
```

**只有第 ③④⑤ 层是"策略"，① ② 是搬运，⑥ 之后是另一份文档的事。**

## 2. 当前状态快照（缺省值总表）

> 这一节是**对照代码核对的清单**。所有值都能在 `bridge/whisper_stream.py --help` 里看到
> （`tests/python-suite.py` 里有断言直接钉住它们，防止有人改掉却不知道）。

### ① 采集（手机端）

| 参数 | 当前值 | 依据 / 改了会怎样 |
|---|---|---|
| 采样率 | 16 kHz 单声道 | Whisper 内部固定 16 kHz；高于它只是白费带宽 |
| 降级链 | 16000 → 44100 → 48000 | 某些安卓设备不支持 16 kHz 录音，硬要 16 kHz 会直接开不了麦 |
| 上传块长 | 1000 ms | 一块一 POST，太小则请求风暴，太大则端到端延迟变长 |
| 语种 | 手机按钮 → `audio-in.lang` | 手机上切「听葡语/听中文」**下一句就生效**，不用停止录音 |

### ② 传输（转发进程）

| 参数 | 当前值 | 依据 / 改了会怎样 |
|---|---|---|
| 单块上限 | 1 MB | 超了返回 400（约 32 秒音频，正常一块 1 秒，撞不到） |
| 落盘策略 | **只追加，永不截断** | 曾经 `fresh=1` 会把文件截成 0，本意是"新一次录音别管旧的"，实际会**静默丢掉已经录到的音频** |
| 旁文件 | `.rate` / `.lang` | 让"手机换了采样率/换了语种"能被电脑知道，而不是靠猜 |

### ③ 尾随

| 参数 | 当前值 | 依据 / 改了会怎样 |
|---|---|---|
| `--follow-poll-ms` | 80 | 检查新数据的间隔。纯 CPU 开销，80ms 已足够细 |
| `--idle-flush-ms` | **2000** | **必须明显大于上传间隔（1 秒）**。这个参数原来写成"5 次轮询"=400ms，比上传间隔还小，于是正常上传时反复误判"说话人停了"，按上传节奏把句子切开（详见 §4.2） |
| 开始位置 | 缺省从**文件末尾**跟 | 文件里可能攒着上一次的录音；从头读会把旧音频重新识别一遍，冒出莫名其妙的旧字幕 |
| `--stop-after-idle` | 生产**不设** | 只给测试用。注意：设成 4 秒时，真实上传里 6 秒的空档会让识别进程**直接退出** |

### ④ 切句（★ 核心）

| 参数 | 当前值 | 依据 / 改了会怎样 |
|---|---|---|
| 块长 | 100 ms | 能量判定的分辨率。100ms 意味着静音时长最多有 100ms 的量化误差 |
| 门槛 | **自适应**：噪声底 × 4，最低 0.004 | 固定门槛在会议室（说话声 0.008 低于门槛 → 整句丢失）和开空调的教室（底噪 0.02 高于门槛 → 永不收句）两头都不行 |
| 门槛的安全阀 | 最多到"语音档的一半" | 防止门槛高到把说话也判成静音 —— 那比切得太碎严重得多（一句话都出不来） |
| `--silence-ms` | **500** | **必须小于说话人句间的真实停顿**。句间停顿 500ms 时：判 500ms → 错字率 10.0%，判 700ms → 23.9%，判 1000ms → 27.0%（详见 §3.2） |
| `--min-speech-ms` | 500 | 短于 500ms 的碎片丢弃。实测 0.03~0.27 秒的碎片送进识别只产胡话（「你以後」这种） |
| `--preroll-ms` | 250 | 句首之前的 250ms 也带上。不带的话句首的轻声、塞音（p/t/k）会被削掉，转写丢字 |
| `--short-utterance-ms` / `--short-silence-ms` | 800 / 1100 | 短句保护：还没攒够 800ms 语音的片段，要等 1100ms 静音才收句 |
| `--max-speech-ms` | 15000 | 一直不停口也要断句，否则字幕永远不出来 |
| `--cut-pause-ms` | 200 | **到上限时优先在内部停顿处断**，而不是在固定样本上硬切 |

### ⑤ 识别

| 参数 | 当前值 | 依据 / 改了会怎样 |
|---|---|---|
| 模型 | **按设备自动选：GPU → large-v3，CPU → small** | 中文基准 30 条：small 18.9% / medium 7.4% / large-v3 3.9% 字错率。**模型大小是影响准确率最大的变量**。⚠️ 这个"自动选"是 `scripts/start-all.mjs` 做的；单独跑 `whisper_stream.py` 时它自己的缺省是 small/cpu |
| `--beam-size` | 5 | 基准实测 beam1 9.2% vs beam5 7.4%；GPU 上很便宜 |
| 语种 | 按旁文件（手机按钮），可命令行固定 | 固定语种比自动判定更准更快 |
| 提示词 | **缺省开**（中文「以下是普通话的句子，请用简体中文输出。」） | 实测 medium 字错率 7.4%→5.9%，疑似繁体 8 字→1 字。副作用（短片段回显）由回显闸挡住 |
| 归一化 | 只在**峰值低**（<0.3）时做 | 手机远距离录音电平偏低，归一化能把「测试语音」纠正成「这是一条测试语音」；而公开语料本来就录得正常，一律归一化反而略差 |
| 预热 | 缺省做 | 首次推理在 CUDA 上要十几秒；不预热的话**用户说的第一句话**会卡十几秒 |

### ⑤′ 四道闸（防假字幕）

| 闸 | 当前值 | 拦什么 |
|---|---|---|
| `no_speech_prob` | 0.60 | 模型自述"这里没人说话"。**但电平明显是人声时不让它否决**（曾经因此把用户正在说的话扔掉） |
| `avg_logprob` | -1.00 | 模型自己都不确定，就别显示 |
| 幻听惯用语 | 内置表（中文「请不吝点赞」「订阅」「谢谢观看」…；葡/英 `legendas`、`amara.org`…） | 模型在噪声/静音上凭空调出训练数据里的高频句 |
| 提示词回显 | 带**长度下限**（≥4 字且占提示词 ≥40%） | 模型把提示词当正文抄出来。上限是"整条/尾巴/重复两遍"都要拦得住，下限是"「中文」「输出」这类正常短句不能被吃掉" |

### 结果侧的观测值（每次运行都会打印）

`语音段数` / `丢弃段数` + 每段的 `音频秒数 / 识别耗时 / RTF / 电平`，
以及退出时的`自适应阈值（噪声底 × 倍数，语音档）` 和`理论最短延迟 = 静音判定 + 识别`。
**音频秒数总和**和**语音段数**是最有用的两个数：它们不对，就说明切句出问题了。

## 3. 策略背后的几条原则（每条都有实测支撑）

### 3.1 "没数据"不等于"静音"

这是**最贵的一条教训**（详见 §4.2）。前者是**传输状态**，后者是**音频状态**。
把两者混为一谈，就会造出**假的句子边界** —— 而且完全不报错：
程序在正常跑、字幕在正常出，只是切点是网络决定的。

**推论**：任何"多久没发生 X 就当作 Y"的判据，都要先问一句
**"X 的正常间隔是多久"**。这里的正常间隔是 1 秒（上传节奏），而阈值曾经是 0.4 秒 ——
阈值比正常间隔还小，误判是**必然**的，不是概率问题。

### 3.2 静音判定必须**小于**说话人句间的真实停顿

判太慢和判太快的代价**严重不对称**（带标准答案的中文语料，12 句）：

| 句间停顿 | 判 500ms | 判 700ms | 判 1000ms |
|---|---|---|---|
| 500ms（真人连着说） | **10.0%** | 23.9% | **27.0%** |
| 1500ms（说话人习惯停久） | 10.0% | **7.9%** | 7.9% |

判太慢要付 **+14~17 个百分点**，判太快只付 **+2 个百分点**。
所以缺省取**偏快**的一侧（500ms）—— 而且判得快顺带把"必须等对方停下来"的延迟从 0.7 秒降到 0.5 秒，
质量和延迟同时变好。

「把阈值提到 1 秒再整段送模型」这个思路方向上是对的（整句翻译确实更好），
但实测在这一层是**最差**的：句间只停 500ms 时判 1 秒会并出 13.9 秒的长段，错字率 27.0%。

### 3.3 门槛要**自适应**，而且估计方式不能有死锁

固定门槛两头都不行（见上表）。但自适应本身踩过一个死锁：
最初只在"没在说话"的块上更新噪声底 —— 而噪声一大（底噪 0.012 ≥ 阈值 0.01），
第一块就被判成"在说话"，于是**永远进不了"没在说话"分支**，噪声底永远测不出来，
自适应彻底失效，66 秒被并成 5 句，**字幕只能每 15 秒出一次**。

现在**每一块都进统计窗口**，用近 10 秒能量的 10 百分位当噪声底 ——
它不依赖"已经正确识别出静音"，所以卡不死。

### 3.4 到上限断句时，要落在**人给的边界**上

"一直不停口 15 秒就断"是必要的（否则字幕永远不出来），但**在哪个样本上断**很重要：
原来是在固定位置硬切，说话说到一半就被切断，两条字幕各拿半句。
现在先在缓冲里找**内部停顿**，并且要求切开后两头都够长，在这个前提下尽量靠后切；
实在找不到停顿才退回硬切。

同一个停顿，切在它上面和切在"第 15 秒那个样本"上，对下游的意义完全不同。

### 3.5 先加护栏，再放开被护栏保护的功能

提示词的经历是个正面例子：它被实测证明有用（+1.5 个百分点、压掉繁体），
但会带来"短片段被回显成假字幕"这个副作用。顺序是：
**先做回显闸 → 确认闸拦得住 → 再把提示词默认打开。**
反过来做（先开功能，等出事再加护栏）就会先给用户一段"眼镜在乱翻译"的体验。

### 3.6 宁可少一句，不可给一句假的

假字幕比没有字幕糟得多 —— 用户会以为眼镜在乱翻译，而且没有任何线索。
所以四道闸全部**宁可错杀**（幻听表、回显闸都是这个取向）。
**但错杀要有上限**：回显闸原来只看"是不是提示词的子串"，
而提示词全是常用字，于是「中文」「输出」「句子」这类正常短句会被**静默吃掉**。
现在要求 ≤4 字的短句一律放行，并要求匹配占到提示词的 40%。

### 3.7 不变量：送进去多少语音，就必须交出多少

切句器有一条不变量测试：**输入里有多少"有声音"的块，输出就必须交出多少块**。
这条测试是被两次事故逼出来的（都是"内容无声消失"）：
一次是切断后剩下的尾巴太短被丢弃，一次是算块数时用错了数组导致**整个前半段被扔掉**。
两次都表现为"程序在跑、字幕在出、就是少了几个字"。

### 3.8 切句的结果不能依赖**时序**

修完 §4.2 之后确立的：同样一段话，无论网络怎么抖，**切出来的句子必须一样**。
这条现在有回归测试钉着，也是"离线整文件跑"和"按真实节奏重放"必须给出同一结果的原因。

## 4. 收音相关的关键问题（都已修）

> 详细分析在 [`04-语音识别验证.md`](04-语音识别验证.md) 的 §6 / §13 / §14，这里只做汇总与指针。

### 4.1 汇总表（第 8 条在 §4.2 单独展开）

| # | 问题 | 症状 | 根因 | 现在靠什么防 |
|---|---|---|---|---|
| 1 | 自适应门槛**死锁** | 66 秒并成 5 句，每 15 秒才出一条字幕 | 只在"没在说话"的块上更新噪声底，而噪声大时永远进不了那个分支 | 每块都进统计窗口（§3.3）+ 回归测试 |
| 2 | 前导缓存被算进"说话长度" | 0.1 秒爆音被当成 0.35 秒的"一句话"送识别 | 用 buffer 总长度判断"够不够长" | 用**真正超过门槛的块数**计数 |
| 3 | `no_speech_prob` **误杀正常说话** | 用户说「你好 欢迎」，两段被判 0.68/0.87 丢弃（电平明明是 0.086/0.067） | 无条件相信模型自述 | `decide_no_speech`：**电平证据压过模型自述** |
| 4 | 提示词**被回显成假字幕** | 眼镜上出现「请用简体中文输出。」 | `initial_prompt` 在短/模糊片段上会被当成"接着写的文本" | 回显闸（带长度下限） |
| 5 | **15 秒处硬切** | 长对话被拦腰截断，两条字幕各拿半句 | 到上限时在固定样本上切 | 优先在内部停顿断句（§3.4）+ 负对照测试 |
| 6 | 静音判定**太慢** | 句子并成 12~14 秒的长段，错字率 23.9% | 缺省 700ms 大于真实句间停顿 | 缺省改 500ms（§3.2） |
| 7 | 幻听**漏网** | 假字幕「谢谢观看,下次见!」直接发到眼镜上 | 幻听表里没有这条 | 补进表里（实测逮到的） |
| 8 | **按上传节奏切句** ★ | "经常出现 `[丢弃 … 回显了提示词]`" | 把"下一块还没送到"当成了"说话人停下来了"，400ms 就塞假静音切句 | §4.2 + 回归测试 + 负对照 |

### 4.2 重点展开：第 8 条 —— 按上传节奏切句，目前最要命的一个

**症状**：用户报"经常出现丢弃"，而且日志里看不出丢的是什么（原来不打印被丢的文字）。

**定位**：同一段录音、同样参数，**只改"数据什么时候到"**：

| 喂法 | 切出来的段（秒） |
|---|---|
| 整文件一次性喂 | `[2.9, 4.9]` |
| 按真实上传节奏喂（每秒一块） | **`[2.6, 1.0, 0.9, 1.9, 2.0]`** |

**根因**：尾随循环里"没数据就补静音"那段，判据是"连续 5 次轮询没读到数据"，
而两次轮询之间睡的是 `--follow-poll-ms`（80ms）→ 实际只有 **400ms**，
比手机**每秒一块**的上传间隔还短。于是正常上传时它**反复**判定"说话人停了"，
塞 500ms 数字零，按上传节奏把句子切开。
重放里那段 1.0 秒片段的电平 `0.0664` 与 relay 日志里第 9 块**完全相同** ——
它就是"一整块上传音频"被切了出来。

**连环后果**：切出来的 1 秒碎片正好是 Whisper 最容易出幻觉的长度 ——
重放里两种坏结果各出现一次：一段被正确判为回显而**丢弃**（丢掉的是真回显），
另一段变成假字幕「谢谢观看,下次见!」**发到了眼镜上**。
所以**丢字幕只是症状，按上传节奏切句才是病。**

**修法**：判据改成按**毫秒**累计；阈值 `--idle-flush-ms` 缺省 **2000ms**（明显长于上传间隔）；
不再伪造数字零，直接把这半句交出去；并给被丢弃的文字加上日志。

**验证**：同一个真实节奏重放 → 恢复成 `[2.9, 4.9]`，**与离线整文件结果完全一致，0 丢弃 0 幻听**。

## 5. 已知的短板与边界（如实写）

**策略本身的边界**：

- **说话人句间只停 300ms 时，任何阈值都会同时切碎又合并。** 实测那一档下所有配置都是
  6~7 次合并 + 5~7 次切碎。这一档靠调阈值解决不了，只能靠**文字层面的缝合**
  （把连续几个片段在翻译前拼起来）—— 那件事还没做。
- **近静音的碎片仍会被切成"句子"送进识别。** 电平 0.0064 的片段也能满足"够长"，
  靠的是房间噪声的尖峰；目前由幻听/回显闸兜住。更靠前的拦法（在切句层就按整段电平否掉）**没做**。
- **嘈杂场景靠安全阀兜底，不是真的解决。** 门槛最高只到"语音档的一半"，
  如果背景人声一直很响（比如隔壁有人持续说话），切句仍会失准。
- **所有数字都来自近场单人的朗读语音。** 没有远场、没有多人抢话、没有回声/混响测试。

**环境相关的未知**：

| 未知项 | 卡在哪 |
|---|---|
| **真机麦克风** | 没有硬件。手机麦克风与眼镜麦克风的指向性、距离、降噪完全不同，这套门槛**肯定要重调** |
| 手机 App 在真机上录音 | APK 已构建核对，但**没在手机上装过**；安卓的采样率降级行为要真机验证 |
| 教室真实声学环境 | 混响会让"静音"不再安静，能量门槛可能整体失准 |
| 端到端延迟 | 目前是分段推算；插件里还没打时间戳 |

**还有一件事没验证**：这套参数**只用过一两次真实手机录音**（就是 §4.2 那次 22 秒）。
它在"能跑通"的意义上验证过，在"不同房间、不同人、不同语速都稳"的意义上**没有**。

## 6. 要换场景时，按什么顺序调

**顺序不能颠倒** —— 前面的不对，后面的调了也没意义（而且会互相掩盖）。

```
第 0 步：先确认真的录到声音了
        看 relay 日志每块的峰值/RMS，或 node scripts/debug-window.mjs
        ⚠️ 踩过：手机上传的音频 RMS 只有 0.0012（几乎静音），
           这时候调任何切句参数都是白费 —— 人声一般峰值 > 0.1
        │
        ▼
第 1 步：看"噪声底 × 倍数"和"语音档"这两个数（--stats 会打印）
        · 噪声底 ≈ 语音档  → 环境太吵，先解决收音（靠近麦克风/换位置），不是调参数
        · 门槛被"安全阀"压住 → 说明想要的倍数会把说话当静音，环境噪声太大
        │
        ▼
第 2 步：只有在这时才动 --silence-ms
        判据：数一段真实录音里"句子之间停多久"（通常是 300~800ms）
        然后取**比它小**的值，缺省 500 就是按"句间停 500ms"定的
        │
        ▼
第 3 步：再看 --min-speech-ms / --short-utterance-ms
        只在"出现胡话碎片"或"句子被切成两半"时才动
        │
        ▼
第 4 步：最后才动模型 / beam / 提示词
        它们影响"认得多准"，不影响"切在哪"
```

**几个"不要动"的忠告**：

- `--silence-ms` **不要为了"少切碎"而调大** —— 代价是不对称的（§3.2），
  而且会同时把延迟拖长。真要解决切碎，走文字缝合那条路。
- `--min-speech-ms` 不要调小来"多出字幕"：小碎片只会产胡话。
- `--no-prompt` 不要随手用来"排除干扰"：它实测值 1.5 个百分点，
  而它唯一的坏处已经被回显闸挡住。
- **改任何参数之前先记下现在的数**，否则"变好了还是变坏了"只能靠感觉 ——
  这正是 §4.2 那个 bug 能藏好几轮的原因。

## 7. 怎么复现这些结论 / 怎么诊断收音问题

| 工具 | 用途 |
|---|---|
| `node scripts/start-all.mjs` | 一键起齐（自动按设备选模型）。**改了代码必须重启它**，否则跑的还是旧代码 |
| `node scripts/debug-window.mjs` | 只读的实时监视：每块的分贝条 + "卡在哪一环"的结论 |
| `python asr-eval/asr_eval.py` | 带标准答案算字错率（中文 CER / 葡语 WER） |
| `python asr-eval/segment_eval.py` | 切句基准：直接 import 生产那个切句器，量"阈值该设多久" |
| `node scripts/fake-phone.mjs` | 用真实录音冒充手机逐块上传，不需要手机 |
| `var/logs/relay.log` | **收音问题的第一现场**：每块的字节数、峰值、RMS、到达时刻 |

**诊断口诀**（按顺序问，前三问能排掉九成问题）：

1. **relay 日志里那几块的峰值是多少？** 峰值 <0.1 → 根本没录到人声，别人都不用看了。
2. **到达时刻有没有大空档？** 有空档 → 先看 `--idle-flush-ms` 是否大于最大空档。
3. **识别日志里的"音频秒数"总和，和你说的话对得上吗？** 对不上 → 切句问题。
4. **扔掉的那些段，电平是多少？** 近静音 → 闸拦得对；电平正常 → 闸可能误杀（看它打印的原文）。
5. **换成整文件离线跑一遍，切出来的句子一样吗？** 不一样 → 就是"切句依赖时序"这类问题，
   用重放（按 relay 日志的时刻表喂）复现。

**关于"重放"的重要经验**：整文件离线跑**永远看不到**上传节奏类的 bug
（数据全都到位时它不触发）。所以 §4.2 是先把 relay 日志里的时刻表读出来、
按真实节奏重放才抓到的。**排查"时好时坏"的问题，重放必须连时序一起重放。**

## 8. 这套策略的验证强度

- `tests/python-suite.py`：**106 项断言**（不加载模型，秒级），其中与收音直接相关的有
  - 切句：干净环境 / 高噪声自适应 / 固定阈值对照 / 短响丢弃 / 到上限断句 + **负对照**
  - 不变量：**送进去多少语音就必须交出多少**
  - 尾随：追加增量 / 文件截断重来 / 半帧对齐 / 采样率降级重采样
  - **上传间隔不算句子结束** + 负对照（阈值调回 400ms 必须触发）
  - 防幻听、回显闸（含"常用短句不能被吃掉"）
- 另外 `tests/run-all.mjs` 的 **180 项**覆盖插件与接缝；真实 Cordis 组合另有一轮。
- **教训**：这些 bug 里没有一条是"看代码看出来的"，全部来自"真跑一遍 + 对照标准答案"。
  所以改这一层代码时，**先想清楚怎么证明它没坏**，再动手。
