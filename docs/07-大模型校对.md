# 大模型校对（第二遍）：先出译文，再回头改

> 这一页讲的是**讯飞那种"两遍"**：第一遍快速出译文并**立刻上屏**，
> 第二遍让模型回头检查这一句改掉错的地方。
> 代码在 `plugin/core.mjs`（配置项 `proofread`）。**现在缺省是开着的**（`'idle'`），
> 想关掉：电脑上加 `--no-proofread`，或者在手机「设置 → 校对（第二遍）」里关。
>
> 这一页只讲这一件事。收音与切句看 [`06-收音策略.md`](06-收音策略.md)，
> 识别准确率的实测看 [`04-语音识别验证.md`](04-语音识别验证.md)。

---

## 1. 它到底在修什么

第二遍拿到的输入是：**这一句的原文** + **已经上屏的译文** + **上一句的原文与译文**。

给原文是关键 —— 同传里最常见的错误不是"译得不好"，而是**听错了**。
Whisper 在短片段上尤其容易错（实测过：「这是一条测试语音」被切成两段后，
后半段被识别成「测试语音」甚至「你以後」）。只看译文是发现不了这类错的，
必须拿原文对照，甚至要往前看一句才能推断说话人到底想说什么。

所以要修的三类错：

| 类型 | 例子 | 第二遍靠什么发现 |
|---|---|---|
| **听错** | 原文听成了半句，译文跟着残缺 | 拿原文看：这半句不成话，结合上一句补全 |
| **巴葡口径** | 用了葡葡说法（`autocarro` / `telemóvel` / `tu`） | 术语表 + 政策规则 |
| **数字/专名** | 时间、金额、房间号、人名译错或漏掉 | 逐项对照原文 |

> ⚠️ **第三类里的"专名"已经移交出去**（决策见 [`15-热词对照表.md`](15-热词对照表.md) §14）。
> **已于 2026-10-22 落地（阶段 4b）**：`policy/br-pt.json` 的 `proofreadRules` 删掉了"人名、公司名"，
> 并新增"专有名词不由你负责……不要改动、替换、音译或意译"的禁改令。
> 因此：**上面表格里的"专名"一行只描述移交前的行为**（保留作历史）；
> **本文第 5 节那批实测数字产生于移交前，从这一版起口径不可比**（尚未重跑）。
> 移交的理由：专名的正确写法是**用户自己的事实**，模型只能猜
> （`亮亮视野 → LLVision` 是它的先验知识，换个不有名的名字它就音译）；
> 与其让专名的写法依赖模型先验，不如让用户上传热词表、由后处理**可复现**地保证。
> **代价是"表外专名不再有兜底"**，这一条已明确接受。

而**明确不做的**是"润色"：译文已经正确、自然就原样输出。这条写进了规则，
原因在下面第 5 节的实测里：正常句子上第二遍**一次都没动手**，说明"自己就对"是常态。

## 2. 架构：为什么第二遍只在**空闲**时做

这是整个设计里唯一真正重要的决定。

收件箱是**串行**处理的（`plugin/core.mjs` 的 `pump()`：同传不能并发，
否则字幕会互相穿插）。如果校对占着当前这一句不放，下一句的初译就得排队等它 ——
等于给每一句都加了一次模型往返。而实测初译本身只要 **0.44~0.96 秒**，加一次就翻倍。

所以校对挂在**收件箱轮询的那次 tick 上，位置在 `pump()` 之后**：

```
每次 tick（inboxPollMs，缺省 700ms）：
  ① 读收件箱 → 有新行就进队列
  ② pump()            ← 串行翻译，出初译并立刻上屏
  ③ if (队列空 && 没有翻译在跑) runOneProofread()   ← ★ 只有这时候才校对
```

第 ③ 步的位置是刻意的：`pump()` 已经返回，说明**现在这段时间本来就是闲着等的**。
放这里，校对既不占"下一句的初译"，也不会和翻译抢模型。

```
时间轴（连续两句，第二遍不占初译的时间）：

  第 1 句到 ──► 初译上屏（t=0.9s）──────────────► 观众已经在读了
                    └─► 空闲时校对 ─► 若改了就覆盖同一帧（t≈2s）
  第 2 句到 ──► 初译上屏（不等第 1 句的校对）
```

代价与边界（都是刻意的，都有测试钉着）：

| 保证 | 怎么做到的 |
|---|---|
| **初译绝不等第二遍** | 校对只在 `pump()` 之后、队列空时跑 |
| **校对绝不覆盖更新的字幕** | 每次上屏都让 `state.displaySeq` +1；校对结果只在"这个号还是我当时记下的那个"时才落屏，否则**丢弃**。否则屏幕会倒退回去显示上一句 —— 那是事故，比不校对严重得多 |
| **不把对的改错** | 验收闸 `revisionProblem()`：变长太多（不像校对）或折行超出 3 行（会把开头挤掉）就不上屏 |
| **不会一直等一句** | 超过 `proofreadMaxAgeMs`（缺省 8 秒）还没轮到的，直接放弃（观众早翻页了） |
| **不会积压** | 待校对队列上限 `proofreadMaxQueue`（缺省 2）；超了丢最老的 |
| **不并发** | 一次只跑一个校对（`proofreading` 标志） |
| **模型判定"无需改"是正常结果** | 记为 `same` 而不是 `fixed`：**大多数句子不该被改** |

## 3. 怎么开、怎么看它在干活

```powershell
# 一键启动时打开（推荐）
node scripts/start-all.mjs --proofread

# 只起大脑那一层时
node scripts/harness-side.mjs --proofread
```

**缺省已改为开启**（`proofread: 'idle'`，按用户要求）。代价要说清：**每句可能多一次模型调用**，
所以给了两个关掉它的入口（电脑侧 `--no-proofread`、手机侧开关）。
显式关掉之后，行为仍然与加这个功能之前**完全一样** ——
有测试专门钉住这一点（一句只调一次模型）。

开了之后，日志里能看到它改了什么：

```
[leion-pro] pt-BR→zh-CN  这是一条测试语音。
[leion-pro] ✎ 校对改了：Esta é uma mensagem de teste.
[leion-pro]            → Esta é uma mensagem de teste de áudio.
```

不想刷日志也没关系，随时可以问状态：

```
leion_selftest  →  notes 里会有一行：
  校对：idle（空闲时做）· 排队 0 句 · 已改 3 句 · 判定无需改 11 句
        · 丢弃 1 句 · 没通过验收 0 句 · 失败 0 次 · 最近：…
```

`leion_inbox` 的 `action: 'status'` 也会带同一份计数。**丢弃**是正常的：
它表示"轮到它的时候屏幕上已经不是这一句了，主动放弃了覆盖"。

### 配置项

| 配置 | 缺省 | 说明 |
|---|---|---|
| `proofread` | `'idle'` | `'off'` 关闭 / `'idle'` 只在空闲时做（目前只有这两档）。**缺省 `'idle'`** |
| `settingsPath` | `''` | 手机侧运行时设置的落点（`var/live/settings.json`）。留空 = 不读；读不到就按配置走 |
| `proofreadMaxAgeMs` | `8000` | 超过这么久还没轮到的就不改了 |
| `proofreadMaxQueue` | `2` | 待校对队列上限；超了丢最老的 |

规则本身（怎么算"错"、什么算"不用改"）在 **`policy/br-pt.json` 的 `proofreadRules`** ——
要调口气、加术语，改那个文件就行，不用碰代码。

## 4. 验证到什么程度（如实说）

**已验证**（`tests/run-all.mjs`，两个包装各跑一遍）:

| 断言 | 钉住的东西 |
|---|---|
| 校对缺省关闭：一句只调一次模型 | 不开就是**一点没变**，不会偷偷多花钱 |
| 校对开启：初译先上屏、空闲时回头改 | 主流程；并且**改的是同一帧**（替换），历史里不会多出一条重复的话 |
| 校对判定无需改动：屏幕不动、历史不多一条 | "不改"是正常路径，不是故障 |
| **校对绝不覆盖更新的字幕** | 用一条 600ms 的慢校对 + 中间插进来的第二句造出"换页"，断言过期结果被丢弃、且第二句自己的校对仍然正常生效 |
| 校对结果没通过验收就不上屏 | 变长过多 / 超显示预算的结果会被拒 |
| 关时状态里 `proofread: null` | 不虚报 |
| **改的那一帧也带着原文**（`source`） | 直接看**总线上的帧**：修订帧的 `source` 必须是原文，不能退化成译文（见第 6 节第 2 条） |
| 收件箱配了**相对路径**时响亮报错 | 相对路径以前会让插件**静默地永远读不到**收件箱 —— 现在是启动就抛错 |

其中"**绝不覆盖更新的字幕**"这条做过**负对照**：把 `displaySeq` 那道闸去掉再跑，
测试确实变红（而不是"看起来通过"）。同时那次负对照还顺带暴露了产物新鲜度门禁在起作用 ——
动态插件是 `core.mjs` 的生成物，改了源文件不重新生成，只有正式插件的行为会变。

**当时没验证的**（后来补上了，就是下面第 5 节）:

- ~~**第二遍到底有没有把译文变好，一次都没量过。**~~ 上面测的全是"流程对不对"
  （先上屏了吗、会不会覆盖错、验收闸拦不拦得住），用的是**假模型**。
  真实模型上"改了之后是变好还是变坏"当时是未知数。
- ~~因此**不知道 `fixed` 里有多少是改对、多少是改错**。~~
- **代价仍然没量全**：只知道"每句多一次模型往返"，真实模型下的往返耗时分布
  还没测（第 5 节给出了一个样本：约 2.4 秒后落定），`same`（无需改）的比例
  在正常语料上是 **18/18**，但这批句子是**念着说、没有识别错**的理想输入，
  真实即席发言里听错更多，`fixed` 的比例会高于这个数。

**怎么补上这个空缺**：做过了 —— 见下一节。

## 5. 校对到底有没有用：实测（真模型，隔离链路对比）

方法：在**另一条完全隔离的链路**上跑（独立端口 8789 + 独立数据目录，不动正在用的那条），
同一套句子分别跑"校对关"和"校对开"。校对开着那一版是从它自己的组合文件里**核对过**的
（`proofread: 'idle'`），不是"我以为开了"。

### 5.1 18 条正常的长难句：**一次都没改（0/18）**

初译在这些句子上**本来就对**：巴葡口径 0 处误用（含一句话踩五个术语的第 7 条）、
数字全保留（含 2.7 亿 → `270 milhões` 这种单位换算）、成语意译到位、
双重否定没翻反、专有名词保留（`Leion Pro / LLVision / Qualcomm`，安卓十二 → `Android 12`）。
**没有错可改，第二遍自然没有产出。**

> ⚠️ **方法论提醒（这条比结论本身重要）**：两次跑的译文有 **10/18 条文本不同**
> （`custo-benefício menor` vs `pior`、`captura` vs `captação`、语序调整……），
> 但它们**不是**校对改的 —— 那些句子每句只产生一帧（盯着总线 2.5 秒没有第二帧），
> 差异来自模型自己的随机性（temperature 0.2）。
> **所以单次 A/B 的文本 diff 不能用来判断"校对有没有用"**，会被随机性淹没。
> 能判断的是：**帧序列**（一句几帧）和大脑日志里的 `✎ 校对改了`。

### 5.2 6 条故意"听错"的句子：**1/6 被修对，1/6 该修没修**

按校对规则第一条（"语音听错导致译文跑偏，用上下文推断真正想说的意思"）造同音错字。
真实日志（大脑自己打的）：

```
[leion-pro] zh-CN→pt-BR  ...e ele usa um chip de alta potência.
[leion-pro] ✎ 校对改了：...um chip de alta potência.
[leion-pro]            → ...um chip da Qualcomm.          ★ 改对了
[转发] 📺 字幕已更新（第 43 帧）[...] um chip da Qualcomm.
```

把「高通」写成「**高筒**」，初译直译成 `alta potência`（高功率芯片），
约 1.9 秒后被改成 `chip da Qualcomm` —— 跑两遍，两遍都改对。

| 造的错 | 初译 | 结果 |
|---|---|---|
| ★ 高筒（高通） | `um chip de alta potência` | **被改对** → `um chip da Qualcomm` |
| 简提（简体） | `chinês simplificado` | 初译自己就对 |
| 雨音（语音） | `teste de áudio` | 初译自己就对 |
| 自错率（字错率） | `taxa de erro do reconhecimento` | 初译自己就对 |
| 会以室（会议室） | `sala de reunião` | 初译自己就对 |
| ✗ 同船（同传） | `sistema de bordo`（**错的**） | **该修没修** |

**结论**：校对的价值集中在**初译确实错了**的时候 —— 它能在"听错"这类错上把意思救回来，
但**不保证全抓**（同船那条它放过了）。正常句子上它基本不动手，这是设计如此（宁可不动）。

### 5.3 一句话的生命周期（开了校对之后，真模型实测）

```
688ms   增量     text="A"                          source=原文
861ms   定稿     text="...um chip de alta capacidade."  source=原文   ← 观众先看到这版
3264ms  修订     text="...um chip da Qualcomm."         source=原文   ← 约 2.4 秒后原地改掉
```

## 5.5 手机侧开关（运行时覆盖配置）

除了部署时的 `proofread` 配置，还有一个**运行时开关**：

```
手机「设置 → 校对（第二遍）」 ──PUT /settings──► var/live/settings.json ──► 插件下一场读取
```

三条约定（都在代码注释里）：

1. **以手机为准**：用户当场能摸到的那份更可信。文件里有 `proofread` 就用它，没有才看配置；
2. **每场只读一次**（排进第一条校对之前），所以"改了下次生效"是天然的；
3. **坏文件不算数**：读不到 / JSON 坏了 / 字段类型不对，一律忽略、按配置走 ——
   一个设置文件绝不能影响出字幕（`tests/contract-suite.mjs` 里有这条用例）。

手机界面上的开关**显示的是电脑上的真实状态**（`/status` 的 `settings.proofread`），
不是本地偏好 —— 否则会出现"界面上关着、电脑上还在每句多花一次调用"，那比没有开关更糟。

## 6. 几条踩过的坑与设计取舍（都写在代码注释里）

1. **验收闸是被代码读出来的，不是被测试逼出来的。**
   离线演示用的例句表适配器（`scripts/demo-phrasebook.mjs`）对**查不到的问句**
   会回一句「（离线演示：例句表里没有这一句…）」。校对请求当然查不到 ——
   如果不拦，它会**被当成校对结果**，把一句本来正确的字幕覆盖成这句演示提示。
   这类"把对的改错"的代价比"不校对"高得多，所以加了 `revisionProblem` 两道判据。
   顺带：`--proofread --offline` 这个组合会被明确告知"不会生效"，
   而不是让人以为开了却没效果。

2. **修订帧必须带上原文**（合并两个分支时才暴露的 bug）。
   这一行原本没传 `source`，于是修订帧的 `source` 退化成译文本身；
   而手机端是**按原文认"这是同一条字幕"**的 —— 认不出来就当成新句子，
   屏幕上于是**多出一行**（那一行的"原文"位置还显示成译文），而不是原地改正。
   写校对那会儿帧里还没有 `source` 这个字段，所以两个功能各自都测过、合起来才炸。
   `tests/contract-suite.mjs` 现在直接看**总线上的帧**把这条钉住了。

3. **"改错"比"不改"严重。** 提示词里明写了"拿不准就不改"、
   "译文已经正确就原样输出，不要润色"。理由是产品的：观众已经把初译读进去了，
   第二遍把一句正确的话改坏，比它什么都不做更糟。校对那一次的温度也压到 ≤0.2 ——
   要的是"稳定地判对错"，不是发挥。

4. **校对结果**不**流式上屏。** 翻译那一遍是流式的（边说边显），
   但校对要么整句替换、要么不动。边校边显只会让屏幕来回跳，反而更难读。

5. **上下文只在同向时才给。** 语向来回切的时候，上一句的译文是另一种语言，
   塞给模型只会把它带偏。所以 `state.recent` 里只有"同目标语言"的上一句会被当成上下文。

6. **校对失败绝不影响显示器。** 模型报错、路由不可用、抛异常 ——
   一律只记一笔（`failed` + `lastNote`）然后保持初译，屏幕上不会有任何变化。
   自检里它也不算成败判据：这是锦上添花的一环，坏了不该让整条链路报 FAIL。

7. **一句最多两次模型往返，上限是有意的。** 初译 + 校对，不做"再校一遍"。
   在还没有客观指标的情况下，多遍校对只是在烧钱（这一节的实测也说明：
   正常句子上第二遍根本不动手，多跑几遍同样是白跑）。
