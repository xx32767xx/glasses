# 大模型校对（第二遍）：先出译文，再回头改

> 这一页讲的是**讯飞那种"两遍"**：第一遍快速出译文并**立刻上屏**，
> 第二遍让模型回头检查这一句改掉错的地方。
> 代码在 `plugin/core.mjs`（配置项 `proofread`），开了之后用 `--proofread` 启动。
>
> 这一页只讲这一件事。收音与切句看 [`06-收音策略.md`](06-收音策略.md)，
> 识别准确率的实测看 [`04-语音识别验证.md`](04-语音识别验证.md)。

---

## 1. 它到底在修什么

第二遍拿到的输入是：**这一句的原文** + **已经上屏的译文** + **上一句的原文与译文**。

给原文是关键 —— 同传里最常见的错误不是"译得不好"，而是**听错了**。
Whisper 在短片段上尤其容易错（实测过：「这是一条测试语音」被切成两段后，
后半段被识别成「测试语音」甚至「你以後」）。只看译文是发现不了这类错的，
必须拿原文对照，甚至要往前看一句才能推断说话人到底想说什么。

所以要修的三类错：

| 类型 | 例子 | 第二遍靠什么发现 |
|---|---|---|
| **听错** | 原文听成了半句，译文跟着残缺 | 拿原文看：这半句不成话，结合上一句补全 |
| **巴葡口径** | 用了葡葡说法（`autocarro` / `telemóvel` / `tu`） | 术语表 + 政策规则 |
| **数字/专名** | 时间、金额、房间号、人名译错或漏掉 | 逐项对照原文 |

而**明确不做的**是"润色"：译文已经正确、自然就原样输出。这条写进了规则，
原因在下面第 5 节。

## 2. 架构：为什么第二遍只在**空闲**时做

这是整个设计里唯一真正重要的决定。

收件箱是**串行**处理的（`plugin/core.mjs` 的 `pump()`：同传不能并发，
否则字幕会互相穿插）。如果校对占着当前这一句不放，下一句的初译就得排队等它 ——
等于给每一句都加了一次模型往返。而实测初译本身只要 **0.44~0.96 秒**，加一次就翻倍。

所以校对挂在**收件箱轮询的那次 tick 上，位置在 `pump()` 之后**：

```
每次 tick（inboxPollMs，缺省 700ms）：
  ① 读收件箱 → 有新行就进队列
  ② pump()            ← 串行翻译，出初译并立刻上屏
  ③ if (队列空 && 没有翻译在跑) runOneProofread()   ← ★ 只有这时候才校对
```

第 ③ 步的位置是刻意的：`pump()` 已经返回，说明**现在这段时间本来就是闲着等的**。
放这里，校对既不占"下一句的初译"，也不会和翻译抢模型。

```
时间轴（连续两句，第二遍不占初译的时间）：

  第 1 句到 ──► 初译上屏（t=0.9s）──────────────► 观众已经在读了
                    └─► 空闲时校对 ─► 若改了就覆盖同一帧（t≈2s）
  第 2 句到 ──► 初译上屏（不等第 1 句的校对）
```

代价与边界（都是刻意的，都有测试钉着）：

| 保证 | 怎么做到的 |
|---|---|
| **初译绝不等第二遍** | 校对只在 `pump()` 之后、队列空时跑 |
| **校对绝不覆盖更新的字幕** | 每次上屏都让 `state.displaySeq` +1；校对结果只在"这个号还是我当时记下的那个"时才落屏，否则**丢弃**。否则屏幕会倒退回去显示上一句 —— 那是事故，比不校对严重得多 |
| **不把对的改错** | 验收闸 `revisionProblem()`：变长太多（不像校对）或折行超出 3 行（会把开头挤掉）就不上屏 |
| **不会一直等一句** | 超过 `proofreadMaxAgeMs`（缺省 8 秒）还没轮到的，直接放弃（观众早翻页了） |
| **不会积压** | 待校对队列上限 `proofreadMaxQueue`（缺省 2）；超了丢最老的 |
| **不并发** | 一次只跑一个校对（`proofreading` 标志） |
| **模型判定"无需改"是正常结果** | 记为 `same` 而不是 `fixed`：**大多数句子不该被改** |

## 3. 怎么开、怎么看它在干活

```powershell
# 一键启动时打开（推荐）
node scripts/start-all.mjs --proofread

# 只起大脑那一层时
node scripts/harness-side.mjs --proofread
```

**缺省是关闭的**（`proofread: 'off'`），行为与加这个功能之前**完全一样** ——
有测试专门钉住这一点（一句只调一次模型）。

开了之后，日志里能看到它改了什么：

```
[leion-pro] pt-BR→zh-CN  这是一条测试语音。
[leion-pro] ✎ 校对改了：Esta é uma mensagem de teste.
[leion-pro]            → Esta é uma mensagem de teste de áudio.
```

不想刷日志也没关系，随时可以问状态：

```
leion_selftest  →  notes 里会有一行：
  校对：idle（空闲时做）· 排队 0 句 · 已改 3 句 · 判定无需改 11 句
        · 丢弃 1 句 · 没通过验收 0 句 · 失败 0 次 · 最近：…
```

`leion_inbox` 的 `action: 'status'` 也会带同一份计数。**丢弃**是正常的：
它表示"轮到它的时候屏幕上已经不是这一句了，主动放弃了覆盖"。

### 配置项

| 配置 | 缺省 | 说明 |
|---|---|---|
| `proofread` | `'off'` | `'off'` 关闭 / `'idle'` 只在空闲时做（目前只有这两档） |
| `proofreadMaxAgeMs` | `8000` | 超过这么久还没轮到的就不改了 |
| `proofreadMaxQueue` | `2` | 待校对队列上限；超了丢最老的 |

规则本身（怎么算"错"、什么算"不用改"）在 **`policy/br-pt.json` 的 `proofreadRules`** ——
要调口气、加术语，改那个文件就行，不用碰代码。

## 4. 验证到什么程度（如实说）

**已验证**（`tests/run-all.mjs`，两个包装各跑一遍）:

| 断言 | 钉住的东西 |
|---|---|
| 校对缺省关闭：一句只调一次模型 | 不开就是**一点没变**，不会偷偷多花钱 |
| 校对开启：初译先上屏、空闲时回头改 | 主流程；并且**改的是同一帧**（替换），历史里不会多出一条重复的话 |
| 校对判定无需改动：屏幕不动、历史不多一条 | "不改"是正常路径，不是故障 |
| **校对绝不覆盖更新的字幕** | 用一条 600ms 的慢校对 + 中间插进来的第二句造出"换页"，断言过期结果被丢弃、且第二句自己的校对仍然正常生效 |
| 校对结果没通过验收就不上屏 | 变长过多 / 超显示预算的结果会被拒 |
| 关闭时状态里 `proofread: null` | 不虚报 |

其中"**绝不覆盖更新的字幕**"这条做过**负对照**：把 `displaySeq` 那道闸去掉再跑，
测试确实变红（而不是"看起来通过"）。同时那次负对照还顺带暴露了产物新鲜度门禁在起作用 ——
动态插件是 `core.mjs` 的生成物，改了源文件不重新生成，只有正式插件的行为会变。

**没验证**（这是这一版最大的空缺）:

- **第二遍到底有没有把译文变好，一次都没量过。** 现在测的全是"流程对不对"
  （先上屏了吗、会不会覆盖错、验收闸拦不拦得住），用的是**假模型**。
  真实模型上"改了之后是变好还是变坏"是未知数。
- 因此**不知道 `fixed` 里有多少是改对、多少是改错**。日志能看每一处改动，
  但目前没有客观标准答案来判它对不对。
- 代价也没实测：现在只知道"每句多一次模型往返"，真实模型下的往返耗时、
  以及 `same`（无需改）的比例有多高，都还没量。

**怎么补上这个空缺**（下一步，成本很低）：用 `docs/04` 里那套带标准答案的中文语料，
把同一批句子分别"只跑初译"和"跑初译 + 校对"，再对比质量。翻译质量需要参考译文 ——
可以用 FLORES-200 对齐的葡语参考（FLEURS 语料就是它的语音版），
或者用"中文→巴葡→中文"的往返一致性当无参考指标。
**在这件事做完之前，"校对有用"只是一个合理的预期，不是一个已测的事实。**

## 5. 几条踩过的坑与设计取舍（都写在代码注释里）

1. **验收闸是被代码读出来的，不是被测试逼出来的。**
   离线演示用的例句表适配器（`scripts/demo-phrasebook.mjs`）对**查不到的问句**
   会回一句「（离线演示：例句表里没有这一句…）」。校对请求当然查不到 ——
   如果不拦，它会**被当成校对结果**，把一句本来正确的字幕覆盖成这句演示提示。
   这类"把对的改错"的代价比"不校对"高得多，所以加了 `revisionProblem` 两道判据。
   顺带：`--proofread --offline` 这个组合会被明确告知"不会生效"，
   而不是让人以为开了却没效果。

2. **"改错"比"不改"严重。** 提示词里明写了"拿不准就不改"、
   "译文已经正确就原样输出，不要润色"。理由是产品的：观众已经把初译读进去了，
   第二遍把一句正确的话改坏，比它什么都不做更糟。校对那一次的温度也压到 ≤0.2 ——
   要的是"稳定地判对错"，不是发挥。

3. **校对结果**不**流式上屏。** 翻译那一遍是流式的（边说边显），
   但校对要么整句替换、要么不动。边校边显只会让屏幕来回跳，反而更难读。

4. **上下文只在同向时才给。** 语向来回切的时候，上一句的译文是另一种语言，
   塞给模型只会把它带偏。所以 `state.recent` 里只有"同目标语言"的上一句会被当成上下文。

5. **校对失败绝不影响显示器。** 模型报错、路由不可用、抛异常 ——
   一律只记一笔（`failed` + `lastNote`）然后保持初译，屏幕上不会有任何变化。
   自检里它也不算成败判据：这是锦上添花的一环，坏了不该让整条链路报 FAIL。

6. **一次只调两个模型往返的上限是有意的。** 一句最多两次（初译 + 校对），
   不做"再校一遍"。多遍校对在没有客观指标的情况下只是在烧钱。
