# 25 · 云端识别接入复盘：为什么这件事花了这么久

> 起因：巴葡（pt-BR）在同传里**一直没有字幕**。最后确实通了，但来回折腾了
> **8~9 轮**（每轮 = 我改代码 → 部署 → 用户重启 → 贴日志）。
> 这份复盘只做一件事：把"本来半小时能通、实际折腾两天"的原因写死，
> 包括我自己判断错的两次、以及**我给的处置建议本身引入的回归**。
>
> 相关实现记录见 `docs/21` §5.96 ~ §5.104。

---

## 1. 一句话结论

**真因只有一个：关闭握手白等 10 秒。** 识别早就完成了，我们在等一个永远不会来的"再见"。

把它找出来之后，一次改动的效果是 `11.20s → 2.24s`（RTF 1.40 → 0.28），字幕立刻就有了。

那么为什么找这么久？因为**症状只有一种**（"没字幕"），而**能区分层次的信息一条都没有**：

| 我当时的"证据" | 它其实什么都没说 |
|---|---|
| `[识别] 房间 … → 1.7s 出词 5` | `1.7s` 是**音频长度**，不是耗时。卡 30 秒也照样显示 1.7s |
| `[whisper_stream] 模型表：pt-BR=（沿用 default）` | 只打印 `languages[语种].model`；钉的是**策略**时也这么显示，和"什么都没配"一模一样 |
| `websockets.exceptions.InvalidHeaderValue: invalid Authorization header` | 第三方 traceback，既不说"是密钥"，也不说错在哪个字符 |
| `耗时 11.20s`（后来才有的） | 五个阶段只计了四段，**漏掉的那一段正好占 10 秒** |

**失败的根因不是某个 bug，而是"没有可测量的信号，只能靠推理"。**
推理在四层链路上必然慢：每一轮只能排除一个假说，而每个假说都需要用户重启一次才能验。

## 2. 那 8~9 轮到底在做什么

| 轮次 | 我的假说 | 结果 |
|---|---|---|
| 1 | 电平太低（**用户**提的假说，合理） | 部分对：丢了 2 段碎片（共 400ms），但不足以解释"整段没字幕" |
| 2 | 表里模型名旧了（`fun-asr-flash-*` 应为 `fun-asr-realtime`） | **错**。旧名字能用；我据此让用户 `--replace`，白跑一轮 |
| 3 | 侧车压住了表 → 建议 `rm asr-profiles/*.json` | **这是我自己引入的回归**：销掉侧车等于**取消了 pt-BR 的 pin**，于是它退回 whisper/large-v3。清理动作必须说清"这会取消什么"。（5.108 起这一层已整体删除，不会再出现这种局面） |
| 4 | 启动日志那行在说假话 | 对，但只是**日志**的 bug（§5.97）—— 用户正是被它误导来问我的 |
| 5 | 密钥里有换行（`InvalidHeaderValue`） | 对，是真 bug（§5.98）。但它只在**用户按我的指示重新 export** 之后才暴露 |
| 6 | 用户建议"单独测试识别功能" | **这是转折点**。工具做出来以后，一轮就定位了。我早该自己做 |
| 7 | 工具自身两个 bug（语种标签 `pt-BR` 崩、数据目录取到 live） | 仪器本身没校准 —— 代价翻倍（§5.101） |
| 8 | 服务端不回 `task-finished` → 干等 30 秒 | 部分对（有的模型会），但**不是这次的主因**（§5.99） |
| 9 | 分阶段计时：8 秒音频 11.8 秒 | 第一次看见"时间去哪了"：五段里只计了四段 |
| 10 | `close_timeout` 默认 10 秒 | **真因**（§5.103）。改完 2.24s，字幕出现 |

**如果第 6 轮（隔离工具）放在第 1 轮，第 2~5 轮基本不存在。**

## 3. 云上 ASR 为什么"特别难配"（可复用的九条）

不是某一家的问题，是**云端实时识别这一类接口**的共同形状。每一条都对应一次真实的踩坑：

1. **端点常常是账号专属的。**
   文档里的公共域名 `wss://dashscope.aliyuncs.com/...` 在实名工作空间下会
   **鉴权通过但报 `InvalidParameter`** —— 看起来像"参数错"，实际是"连错地方"。
   必须用控制台给的那个 `ws-xxxx.cn-beijing.maas.aliyuncs.com`。

2. **密钥形态特殊，而且报错完全不指向密钥。**
   DashScope 的 key 以 `sk-ws-` 开头、中间用点分段、总长几十个字符（这里**不写样例** ——
   仓库里有密钥扫描，写了就红）。这种长串复制时最容易被折成两行；
   一旦中间混进换行，HTTP 头校验直接拒绝，抛的是第三方 traceback
   （`InvalidHeaderValue`）。**错误信息里没有"密钥"两个字。**

3. **同一个模型有三套命名空间。**
   控制台「模型广场」显示的名字、兼容模式（OpenAI 风格）列表里的名字、
   **实时 WebSocket 端点认的名字**，三者可以完全不同。
   写错报 `ModelNotFound`，而文案又容易让人往"参数"上想。
   而且各账号可见的模型**不一样**（同一家公司，A 账号有 `fun-asr-realtime`、B 账号没有）。

4. **协议是有状态的时序。**
   必须 `run-task` → **等 `task-started`** → 才送音频 → `finish-task`。
   顺序反了报 `1007 invalid frame payload data` —— 这个错误名看起来像"音频格式不对"，
   实际是"时序不对"。**错误名和真因无关，是云端 API 的常态。**

5. **每条控制帧都要 `payload`。**
   `finish-task` 也要（只给 `header` 会报 `Missing required parameter 'payload'`），
   而错误里既不说哪条帧也不说哪个字段。

6. **结果是增量的，且不保证有"结束事件"。**
   `result-generated` 是"这句的最新文本"，直接拼接会得到
   `bom diabom dia, como vai`；必须按 `sentence_id` 取最后版本。
   更麻烦的是：**有的账号/模型永远不发 `task-finished`** ——
   把"等到 task-finished"当收尾判据，就会每段白等满超时。

7. **超时默认值会变成性能瓶颈。**
   WS 关闭握手的 `close_timeout` 默认 10 秒；对端不回关闭帧就是**真等 10 秒**。
   识别 1 秒 + 关闭 10 秒 = 每段 11 秒 ⇒ 队列越积越深 ⇒ "没字幕"。
   **纯等待的耗时最容易被当成"识别慢"，因为两者在日志上长得一样。**

8. **配额/开通/授权会伪装成参数错误。**
   腾讯云那次是 `AuthFailure.UnauthorizedOperation ... asr:SentenceRecognition has no permission`
   —— 签名和参数都完全正确，缺的是 CAM 授权与服务开通。

9. **语种码有三套。**
   厂商要 `pt`、我们内部流转用 `pt-BR`、whisper 用 `pt`。
   传错的表现是 `ValueError: 'pt-BR' is not a valid language code`，
   而且它发生在**模型已经加载完（39.8 秒）之后** —— 现场看起来像"模型坏了"。

**一句话：云 API 的失败几乎都是"配置形状错误"，但报错一律长得像"运行时错误"。**

## 4. 我们（我）做错了什么

### 4.1 方法上的错

| # | 错误 | 代价 | 现在的做法 |
|---|---|---|---|
| 1 | **先推理，后测量**：从日志推假说，每轮只能验证一个 | 8~9 轮 | 先说"哪一层"，再花 30 分钟做**单层隔离工具**（`scripts/asr-try.mjs`），一轮定位 |
| 2 | **相信"整体耗时"**：11 秒就以为是"识别慢" | 2 轮 | 必须**分阶段计时**，并打出"未归因余量"（`其他 x.xxs`），否则必漏 |
| 3 | **给了会改变状态的处置建议**（删侧车）却没说"这会取消 pin" | 1 轮 + 引入回归 | 处置建议必须写明"它会改变什么、怎么回滚"；清理类操作先备份 |
| 4 | **把"日志显示的正常"当成"配置正确"** | 2 轮 | 日志要能回答"**当前实际用的是哪个引擎/模型，值来自哪一层**"（§5.97） |
| 5 | **仪器没校准就交付**：`--language pt-BR` 崩、数据目录取到 `live` | 2 轮 | 诊断工具同样要有测试；它错了代价翻倍（§5.101） |
| 6 | **两次误判没及时撤销**（模型名、"肯定是不回 task-finished"） | 抢占了用户的注意力 | 假说被推翻要**当场说出来**并写进文档，否则下次还会走同一条弯路 |

### 4.2 代码上的错（都已修，且都有断言）

| 现象 | 真因 | 修法 |
|---|---|---|
| `pt-BR=（沿用 default）` 让人以为配置丢了 | 日志只打印 `model`，不打印"策略名 + 解析结果" | §5.97 按 `resolve_strategy` 的真实结果打印，策略名写错当场喊 |
| `InvalidHeaderValue` traceback | 密钥中间有换行 | §5.98 `normalize_api_key`：清空白、去 `export`/引号/`bearer` 前缀、端点填反直接说、非 ASCII 点名第几位；`asr-doctor` 启动前查形状 |
| 每段白等 30 秒 | 收尾判据是"等 `task-finished`" | §5.99 改成"拿到文本 + 安静 1.2 秒"；一个字段都没收到时才等满上限 |
| 日志里 `1.7s` 被当成耗时 | 那是音频长度 | §5.99 加 `耗时 x.xxs` |
| 每段再白等 10 秒 | `close_timeout` 默认 10 秒 | §5.103 显式给 0.35 秒，并把"断开"计入分阶段 |
| 没有隔离手段 | — | §5.99 `--try-queue` / `--try-audio`；退出码分 0/3/2 |

## 5. 以后遇到"没有输出"的标准动作（照这个顺序，快 5 倍）

```
① 先问"卡在哪一层"，别问"为什么坏了"
   手机 →(1)转发 →(2)切句 →(3)识别 →(4)大脑 → 字幕
   四层任意一层坏，表现完全相同。

② 立刻跑单层隔离（不要看日志推理）
   node scripts/asr-try.mjs --data-dir <数据目录>              # 队列里现有的段
   node scripts/asr-try.mjs --pcm <data>/audio/<房间>/x.pcm --rate 16000 --seconds 8
   退出码 0/3/2 = 出字 / 没出字 / 根本没跑到识别。

③ 看三样东西，按这个顺序
   1) 解析：策略 → 引擎/模型（值来自哪一层）   ← 是不是你以为的那个引擎
   2) 电平：RMS / 峰值                        ← "说得很轻"这个假说在这里就被排除
   3) 分阶段：连接/等开始/送音频/收结果/断开/其他 ← 慢，还是根本没出字

④ 只有 ③ 说"出字且不慢"时，才回去查 (1)(2)(4)
```

**判据式的说法，而不是形容词：**
- 不要报"很慢"，要报"音频 8.0s / 耗时 2.24s / RTF 0.28 / 断开占 1.00s"；
- 不要报"没字幕"，要报"队列里 5 段、累计转写 1 段、每段耗时 11.2s"。

## 6. 诊断信息的纪律（这次最贵的教训）

> **一行日志如果无法区分两种截然不同的状态，它就是 bug。**

要把日志当代码对待，具体三条：

1. **报决策，就要报出决策的全部输入。**
   `pt-BR=（沿用 default）` 少了"策略名"，于是"钉了策略"和"没钉"长得一样。
2. **报耗时，就要落到具体阶段，并打印未归因余量。**
   11.2 秒里有 10 秒没有名字 —— 正是这 10 秒让这次查了两轮。
3. **报错误，就要说人话并给出下一步。**
   `InvalidHeaderValue` → "API Key 里有 HTTP 头放不下的字符（换行最常见），重设一个干净的"。

配套做法（已落地）：
- 给日志内容写断言（`python-suite.py`：模型表那行必须出现"策略名 + 引擎/模型"；
  没有 `task-finished` 时必须说清是"等不到结束"而不是"没出字"）；
- 启动前体检（`scripts/asr-doctor.mjs`）从"是否设置"升级为"形状对不对"；
- 慢段自动摊开（队列消费者里 `耗时 > max(2s, 音频×1.5)` 就打分阶段）。

## 7. 还没解决 / 需要盯着的

1. **端到端延迟还没量过**：识别 2.2s、切句 `silence_ms=800`、翻译若干 —— 合起来用户的体感是多少，得真跑一场才知道。
2. **`收结果 0.87s` 是单段实测**，多段连续跑（连接复用与否、并发限流）还没测。
3. **关闭握手仍花 0.35 秒**（对端从不回关闭帧）。可以再压，但要先确认不会引起服务端异常。
4. **`fun-asr-flash-*` 与 `fun-asr-realtime` 到底差多少**：这次换完后总耗时被 10 秒掩盖了，两个模型的真实差别还没单独量。
5. **豆包（Volcengine 流式）还没接**：二进制帧协议，需要官方样例代码。
6. ~~**腾讯云**等 CAM 授权（`QcloudASRFullAccess`）后才能验~~ → **已验（5.126，2026-11-06）**：
   授权 + 开通服务之后一次就通，**没改任何代码**。这反过来证实了 §3 第 8 条那个判断 ——
   "配额/开通/授权会伪装成参数错误"，而 `AuthFailure.UnauthorizedOperation` 本身就是
   "签名与请求形状都对"的证据。实测数字见 `docs/26` §2.4。
