# 识别评测规程：怎么切测试集、怎么跑、按什么标准评分

> **给谁看**：做识别优化的人；以及要判断"这个数字可不可信"的人。
> **对应老师那份测试建议的 §二 / §三 / §四**（冻结测试包 → 统一评分规则 → 固定语言基准）。
> §五（连续录音的实时损失）、§七（双语自动选择）还没做，见 §9。

---

## 1. 为什么先冻结测试集与评分标准

老师把"先冻结一套起步测试包 + 统一数据和评分规则"放在最前面当地基，我完全同意，理由是一条已经吃过的教训：

> **没有冻结的切分与评分规则，后面每个数字都说不清是"模型变好了"还是"换了一批样本 / 换了口径"。**

`docs/04` 里那批数字（FLEURS 朗读 3.9%、CORAA 口语 13.3%）当初是拿"前 30 条 / 前 20 条"跑的，
而且那 30 条后来被反复看过 —— 按老师的说法，它们只能算**历史回归集**，不能再当"未见测试集"。

## 2. 怎么切测试集

### 2.1 四个命令

```powershell
python asr-eval/asr_pack.py --list       # 看能切哪些包、本地各有多少条（不写盘）
python asr-eval/asr_pack.py --build all  # 切出全部包
python asr-eval/asr_pack.py --verify     # 查切分卫生（可反复跑）
python asr-eval/asr_pack.py --keys       # 生成关键内容候选，供人工确认
```

`--list` 还会打印**语料实际在哪**。MagicData-RAMC 是仓库外的 19.8 GB 数据集（不进 `var/`），
所以它不写死在代码里，用 `--magicdata-dir <目录>` 指定，实际用的路径记进 `pack.json` 的 `corpus_root`：

```powershell
python asr-eval/asr_pack.py --build zh-speech-dev --magicdata-dir E:\MagicData
```

切出来的包：

| 包 | 条数 | 总时长 | 说话人 | 录音 | 语料 |
|---|---|---|---|---|---|
| `zh-read-dev` | 100 | 1169 s | — | — | FLEURS cmn_hans_cn（朗读） |
| `zh-read-holdout` | 227 | 2494 s | — | — | 同上 |
| `zh-speech-dev` | 304 | 1131 s | 38 | 19 | MagicData-RAMC（中文日常交流，官方 dev 划分） |
| `zh-speech-holdout` | 504 | 1949 s | 83 | 42 | 同上（官方 test 划分） |
| `pt-read-dev` | 100 | 1187 s | — | — | FLEURS pt_br（朗读） |
| `pt-read-holdout` | 217 | 2662 s | — | — | 同上 |
| `pt-speech-dev` | 300 | 1015 s | 300 | — | CORAA（巴葡真实口语） |
| `pt-speech-holdout` | 500 | 1394 s | 500 | — | 同上 |

> **⚠️ 条数比请求数多一点是正常的**（300 → 304、500 → 504）：切分是"按组整取"，
> 组不能拆开，所以实际值会略大于请求值。脚本如实报出来，不做四舍五入。
> 另外"录音"这一列只在**一场录音确实含多条片段**时才打印（FLEURS/CORAA 一句一条记录，
> 那个数字会等于条数，看着像覆盖了很多场，其实没有意义）。

### 2.2 命名规范（`<语种>-<语体>-<用途>`）

三段都是**封闭取值**，不是随手起的：

| 段 | 取值 | 含义 |
|---|---|---|
| 语种 | `zh` / `pt` | 中文 / 巴葡 |
| 语体 | `read` / `speech` | 朗读 / 真实口语（自发说话） |
| 用途 | `dev` / `holdout` | 开发集（可反复调参）/ 保留集（**只在最后用一次**） |

**为什么语体必须进名字**：它决定这批数字能不能代表产品 —— 实测 `read` 与 `speech`
差 **5~6 倍**（2.8% vs 16.8%，见 §6.1）。混在一起报就失去意义。

### 2.3 落盘位置

识别评测**单独一层**：代码在 `asr-eval/`，数据在 `var/asr-eval/`（两者一一对应，
见 [`../asr-eval/README.md`](../asr-eval/README.md)）。**不跟 `var/audio`（手机上传的原始音频）
和 `var/logs`（随便删的日志）混在一起** —— 理由写在 `lib/paths.mjs` 文件头。

```
var/asr-eval/packs/<包名>/                     ← 一个包一个目录（var/ 在 .gitignore，不进仓库）
├─ manifest.jsonl                     每条样本一行，字段见 §3
├─ pack.json                          这一包**怎么切出来的**：数据集·版本·种子·条数·
│                                     总时长·说话人数·切分规则·已知限制（审计用）
├─ key-candidates.jsonl               关键内容候选（`--keys` 生成，待人工确认）
└─ <包名>-0000.wav …                  音频（16 kHz 单声道，与 Whisper 要的格式一致）

var/asr-eval/results/<包名>__<模型>_<设备>_<精度>.json   ← 每一次评测的结果（见 §5.4）
```

### 2.4 四条切分纪律（每条都有原因）

| 纪律 | 为什么 |
|---|---|
| **确定性**：按 `original_id` 排序 + 固定种子打散 | 种子由 `base:source:split` 派生，**不依赖 parquet 行序**。换台机器、换次运行必须切出同一份，否则"对比"没有意义 —— 也正因为如此，`var/` 删了可以一条命令重建 |
| **与历史回归集不相交**：按 `original_id` / 文件名 / **参考文本** 三重排除 | 老评测集的 manifest **没记 `original_id`**，只按 id 比对会漏 —— 那 30 条会重新混进"新"保留集，而老师明确要求它们留作历史回归集 |
| **按整组切**：CORAA/FLEURS 按说话人，MagicData 按**录音** | 老师的原话："不能把**同一段录音**随机切开分到两组"。一场 31 分钟的对话有 ~350 条片段，按录音整组才真正对应"同一段录音" |
| **每场给名额**（只对"一场含很多片段"的语料）：`ceil(请求条数 ÷ 场数)`，向上取整 | 见下面那段"实测踩到的坑" |

#### ⚠️ 第四条纪律是**实测踩出来的**，不是设计出来的

第一次切 `zh-speech-dev` 时，结果是这样的：

```
✅ zh-speech-dev         382 条   1388.8 秒  说话人 2   →  var/asr-eval/packs/zh-speech-dev
```

**300 多条样本，只覆盖 2 个说话人。** 原因是我沿用 CORAA 的规则（按说话人分组、取前 N 组）：
分组表是按 key 排序的，所以"取前 N 组"= 取**字典序最靠前的那两个说话人**（每人 ~190 条）。
而 MagicData 一场 31 分钟的录音本身就有 ~350 条合格片段 —— 请求 300 条，
按说话人还是按录音分组，都躲不开"差不多就是一整场录音"这个事实。

改法（两处一起改，缺一不可）：

1. **按录音分组**，每场给名额 `ceil(spread ÷ 场数)`，再按场整取；
2. 名额要**向下传到读数据那一层**：读取时先只读转写（便宜）列候选，
   **每场打散后取前 N 条**，最后只给抽中的片段解码音频。

只做第 1 步会得到一个假的好结果：读取层"从头读够 1500 条就停"，
池子里其实**只有前 5 场录音**，按场分组后每场名额被算成 60 条 —— 覆盖度依旧很差。
这是实测出来的（改动前 `--verify` 打印的就是"录音 5"）。

改完之后的覆盖度：

```
✅ zh-speech-dev         304 条   1130.8 秒  说话人 38  录音 19
✅ zh-speech-holdout     504 条   1949.1 秒  说话人 83  录音 42
```

19 场**全部**覆盖、42/43 场覆盖。**"覆盖度"是硬指标**：一个只含 2 个说话人的 300 条包，
测出来的错误率代表不了这个语料 —— 所以 `--verify` 现在把说话人数和录音数直接打在包清单里，
让覆盖率一眼可见（`tests/python-suite.py` 里有 4 条断言钉住名额的算术）。

`--verify` 会把这几条都查一遍并打印结论，**不是"我看一眼就算"**。它同时报一个**软提示**：

> **"参考文本重复"不是失败。** 老师警告的是"同一段**录音**被切开分到两组"（样本泄漏）；
> 而文本相同、录音不同（同一句话由不同说话人各录一遍）是**两个独立样本**，对识别评测不构成泄漏。
> 但它确实削弱了"文本从未见过"这个说法，所以如实报出来，由读的人决定要不要介意。

### 2.5 必须知道的限制

1. **本地只有 CORAA 的 test 分片**（2113 条音频；dev 的元数据有、音频没有）。
   所以巴葡口语的 dev 是从 **test** 里切出来的，**不是官方 dev**。
   dev 与保留集之间按说话人编号做了不相交，但仍在同一批采集条件下 ——
   结论强度不如"官方 dev 调参 + 官方 test 验收"。这一点写在每个包的 `pack.json` 里。
2. **FLEURS 的 `id` 不是每条唯一**（409 行只有 150 个唯一 id）—— 它是**句子**编号，
   同一句由 2~3 个说话人各录一遍。所以：
   - `original_id` 必须带行号才唯一；
   - 排除历史回归集时按文本比对会**连带排掉同句的其它录音**（30 条排掉 82 行），
     这是正常的，也是保留集凑不满 300 条的原因之一。
3. **中文口语这一格是自己切的，不是官方基线**：包用的是官方划分（dev 19 场 / test 43 场），
   但**每一场的片段是我们从整场里抽的**（每场 16 / 12 条，见 §2.4）。
   所以它测的是"这套抽法下的表现"，不是"整个 MagicData-RAMC test 集上的表现"。
   `pack.json` 里 `per_session_cap` 记着每场取了几条、`pool_rows_cap` 记着池子上限，
   都是为了让读数字的人知道边界在哪。
4. **MagicData 的说话人身份里有一个占位标记 `G00000000`**：实测它出现在**全部 62 场**录音的
   转写里（一个人不可能在所有录音里），是"非注册说话人"这类标记，不是身份。
   它现在的合格片段是 **0 条**（dev 6627 / test 13198 条合格片段里一条都没有 ——
   它那些句子基本是"嗯/对"这类太短的回执或带事件标记），所以**当前切分下这个特判是空操作**。
   留着它的原因是门槛一放低就会踩到：那时它会同时让 dev/test 的"说话人不相交"检查
   **天天报假警报**，并且把"短回执"整类从保留集里精确删掉。

> **顺带一个有用的发现**：**中文与巴葡按 id 对齐**（实测 147 个共同 id，
> `zh 1510` 与 `pt 1510` 是同一句话的两种语言录音）。
> 这正好是老师 §七 要的"构造切换测试"的材料 —— 交替回放同一句的中/葡版本，
> 可以验证语言路由与状态切换，且**不依赖任何自录数据**。

### 2.6 四格齐了

| 组合 | 状态 | 语料 | 包 |
|---|---|---|---|
| 中文朗读 | ✅ 已切 | FLEURS `cmn_hans_cn` | `zh-read-dev` / `zh-read-holdout` |
| 中文口语 | ✅ 已切 | MagicData-RAMC（官方划分） | `zh-speech-dev` / `zh-speech-holdout` |
| 葡语朗读 | ✅ 已切 | FLEURS `pt_br` | `pt-read-dev` / `pt-read-holdout` |
| 葡语口语 | ✅ 已切 | CORAA | `pt-speech-dev` / `pt-speech-holdout` |

四个组合各有 dev 与保留集，共 8 个包。**中文口语这一格是最后补上的**：
在它到位之前，"中文口语识别率"只能靠中文朗读的数字**外推**——
而葡语那两格实测差 5~6 倍（2.8% vs 16.8%），外推显然不成立。

## 3. 每条样本存什么（老师的 §三）

`manifest.jsonl` 一行一条，字段：

| 分类 | 字段 |
|---|---|
| 样本身份 | `file` `dataset` `dataset_version` `split` `original_id` |
| 音频 | `seconds` `rate` `channels` |
| 会话信息 | `session` `speaker`（FLEURS 无说话人标注 → 如实为 `null`，不假装有） |
| 正确答案 | `reference`（原始转写）`reference_char_spaced`（逐字转写，FLEURS 有） |
| 分组标签 | `tags.register`（朗读/口语）`tags.accent` `tags.speech_style` `tags.noise_votes` `tags.overlap_votes` … |
| 关键内容 | `key_terms`（**人工确认过**才填；脚本只提候选，见 `--keys`） |

## 4. 评分标准（`asr-eval/asr_score.py`，版本 `asr-score-v1`）

老师要求"把评分规范冻结并绑定版本号"。下面**只是评分标准本身** ——
运行时的纪律（失败样本、可追溯）在 §5。

### 4.1 单位与主指标

| 语言 | 单位 | 主指标 |
|---|---|---|
| 中文 | **字** | CER |
| 巴葡 | **词** | WER |

**整体错误率 = 全部编辑错误数 ÷ 全部参考单位数**，中文与葡语**分别报**。

**不用"每句百分比的平均"** —— 短句权重过大（两个字的一句话，错一个字就是 50%）。
"每句平均"仍然会打印出来，但标明**仅供参考**。

### 4.2 归一化规则（比较前做什么、不做什么）

| 项 | 处理 | 为什么 |
|---|---|---|
| 大小写 | 统一小写 | |
| 弯引号 | `’` → `'` | |
| **中文按字** | `re.sub(r"[^\w]", "", text)` —— 标点**与空白一起去掉** | 中文里空白不是语义；FLEURS 的逐字转写字段是空格分隔的，不去掉会算错字数 |
| **葡语按词** | `re.sub(r"[^\w\s']", " ", text)` 再合并空白 | 标点是**换成空格**而不是删，否则 `hello,world` 会被粘成一个词 |
| **重音符号** | **保留**（`é` ≠ `e`） | 葡语里重音是有意义的 |
| **繁简** | **不转换**，繁体按错字计入 | base/tiny 会把简体输出成繁体，那是**真实缺陷**，不该被"转换后不算错"洗掉；同时单列"疑似繁体字数"（见 4.5） |
| **数字** | **不做等价归一** | 见 4.6 的说明（这是**待定的 v2 议题**：实测发现参考的阿拉伯数字与识别输出的中文读法会被算成删除，虚增指标 —— 详见 §6.3） |
| 语气词 / 重复 / 改口 | **计入**（按原始转写） | 主指标是**严格转写**口径 |

> ⚠️ **v1 是"照抄既有实现"，不是顺手改好** —— 旧实现产出的那批数字是所有结论的基线。
> 我第一版写了 NFKC 归一 + 中文保留空白，那会**悄悄改掉历史数字**，于是"改进了没有"再也说不清。
> 想改归一化就开 **v2**、把所有历史集重跑一遍。现在有一条测试把 v1 与旧实现**逐字对比**，
> 防止将来有人"顺手改好"。

### 4.3 替换 / 删除 / 插入（老师的 §八）

每条样本都存 `substitutions` / `deletions` / `insertions` 与总编辑距离，汇总也分开报。
定义**相对参考文本**：

| 指标 | 定义 | 通俗说法 |
|---|---|---|
| **替换** | 参考里有一个单位，识别里换成了别的 | 写错了 |
| **删除** | 参考里有，识别里没有 | **漏字 / 漏词** |
| **插入** | 识别里多出来的（参考里没有） | 多字 / 重复 |

三者之和 = 总编辑距离；所以 S、D、I 的百分比相加 = 整体错误率。

**为什么要拆开**：三类严重程度差得很远。**删除最危险** —— 听的人不知道自己漏了，
还以为听到了全部。实测中文的删除占总错误一半以上（整段整段少给字），
而葡语朗读的删除只占约 10%（主要是写错）。

### 4.4 关键内容专项（老师要求"不能只依赖整体 CER/WER"）

- `key_terms` **必须人工确认**，脚本只提候选：`--keys` 只提**客观可判**的两类
  （数字、拉丁字母词）；**中文人名机构名故意不提** —— 没有可靠启发式，硬提会把清单淹掉。
- 判据：关键项归一化后，在归一化后的识别输出里出现即算命中。
  **听错的数字不会被洗成正确**（`802` 听成 `800` → 未命中，有测试钉着）。
- 清单为空时报告里**明确写"这一项不可用"**，不假装有分。

### 4.5 单列项：疑似繁体字数

只统计"简体句里不该出现的繁体专用字"（87 字的表，**照抄既有实现** —— 换表等于换口径）。
指标名带"疑似"是因为这张表不完备，只覆盖口语里最常出现的一批。

### 4.6 明确**不做**的

| 不做 | 为什么 |
|---|---|
| **数字等价归一** | 老师指出"数字等价表达可以规范化，但**不能把听错的金额、否定词或名称洗成正确**"。而实测发现参考里的阿拉伯数字与识别输出的中文读法写法不同会**虚增**指标（见 §6.3），所以这是个**待定的 v2 议题**，不能在 v1 里悄悄改 |
| 繁简转换 | 同上：转换会把真实缺陷洗掉 |
| 语义判断 | 它只回答"识别出来的字/词与参考差在哪"，不判"意思对不对" |

## 5. 怎么跑测试

### 5.1 固定语言基准（老师的 §四）

```powershell
# 中文朗读（固定语种 zh）
node asr-eval/test-asr.mjs --set zh-read-holdout --model large-v3 --language zh --count 0

# 中文口语（固定语种 zh）—— 产品场景在这一格，调参也应该在这格做
node asr-eval/test-asr.mjs --set zh-speech-dev --model large-v3 --language zh --count 0

# 巴葡口语（固定语种 pt）
node asr-eval/test-asr.mjs --set pt-speech-dev --model large-v3 --language pt --count 0

# 两个"机制"实验也走同一个入口（样本来源不同，见 §6.7 / §6.7.2）
node asr-eval/test-asr.mjs --cut --count 20 --sweep 500/15000,800/30000,1200/30000
node asr-eval/test-asr.mjs --context --modes C1,T2     # 缺省就是这两个
node asr-eval/test-asr.mjs --context --modes all       # 全部五种喂法
```

`--context` **不是"某一种上下文方式"**，它一次在同一批段上比较几种喂法
（`C1` 不给上下文 ／ `T1` `T2` 文本续传 ／ `L` `R` 声学重叠），结论与取舍见 §6.7.2。
`--modes` 决定跑哪几种，**缺省只跑 `C1,T2`**（现状 vs 已选定方案）——
`T1`/`L`/`R` 已经被否掉，复核一个已定的结论不该每次付五遍算力。
只跑一部分时产物名带 `-C1T2`（`--limit` 冒烟测试带 `-nN`），
**不会和完整对照 `context_overlap__…json` 同名**；报告与 JSON 里也写明没跑哪几种。
真正**上产线**那只旋钮不在这个实验里，而是 `--cut --prompt-depth N`（见 §6.7.3）。

`--set` 后面跟的是 `var/asr-eval/packs/` 下的包名；**别处切好的包**（另一台机器、另一块盘、
临时实验目录）用 `--set-path <目录>` 直接指定，不必先拷进 `var/asr-eval/packs` ——
拷贝既费时间，又会让"测的到底是哪一份"变得说不清。
（结果文件名与打印的名字都取**目录名**，所以目录名要能认出是哪一包。）

> ⚠️ **`--count` 缺省是 30**（不传就只跑前 30 条）。跑全量必须显式 **`--count 0`**（0 = 不截断）。
> ⚠️ 小批运行的结果文件名会带 `-nN`（`zh-speech-dev-n2__…json`）—— 这样**不会覆盖**完整基线。
> 这条是踩出来的：曾经用 `--count 2` 的 2.8 KB 结果盖掉了 304 条的 238 KB 基线，文件名上看不出区别。

#### 参数速查（`--count` / `--sweep` 这些到底什么意思）

⚠️ **`--count` 一个名字三种含义**，这是最容易误读的一个：

| 用在哪 | `--count N` 的意思 | 缺省 | 备注 |
|---|---|---|---|
| `--set <包>` | 只测**前 N 条**；`0` = 全量 | **30** | 小批结果名带 `-nN`，不覆盖基线 |
| `--cut` | 从原始录音里**挑 N 段连续发言**（并固化成段清单） | 12（实验用 20） | 给了 `--spans-file` 就不挑新段 |
| `--context` | **不接受**（必须在已有段清单上跑） | — | 只想试几段用 `--limit N` |

⚠️ **`--sweep 500/15000,800/30000` 的斜杠两边是两个不同的参数**：

| 写法 | 含义 |
|---|---|
| `500/15000` | 一档产线切句参数：`silence_ms=500`（停顿超过 500ms 断句）／`max_speech_ms=15000`（一句话最多 15s，超了强制断） |
| `500` 不带斜杠 | 上限用产线缺省 `max_speech_ms=15000` |
| 逗号分隔 | 多个点，**一个点一档**，各跑一遍 A/C 对照（越宽越慢） |

`silence` 调大以后一段里会装进更多话，所以那几档**必须同时把上限抬到 30000**，
否则会被 15 秒硬切断 —— 那就不是"少切一点"，而是"被强制截断"，两件事不能混着比。

其余入口参数（`--prompt-depth`、`--modes`、`--skip-b`、`--spans-file`、`--refresh-spans`、`--limit`、
`--compare`、`--by-accent`、`--errors-above`、`--show`、`--out-json/--out-md`）的逐个解释见
[`../asr-eval/README.md`](../asr-eval/README.md) 的「参数速查」一节 ——
那份是随代码走的，避免这边抄一遍之后再对不上。

也可以直接调评测脚本（参数更多，`--vad-filter`、`--initial-prompt` 等）：

```powershell
python asr-eval/asr_eval.py --set var/asr-eval/packs/pt-speech-dev `
  --model large-v3 --device cuda --compute-type float16 `
  --language pt --count 0 --show 3 `
  --out-json var/asr-eval/results/我的结果.json
```

### 5.2 这一批属于哪种模式（**别误读**）

老师 §五 把连续录音分成三种模式。**现在这批不是"当前实时"**：

| 模式 | 做法 | 跑了吗 |
|---|---|---|
| **A 离线参考** | 用**人工标注的完整发言边界**，允许看到完整发言 | ✅ **本批是这一半** |
| **B 当前实时** | 按 1 倍速喂进**当前生产 VAD + 切句 + 识别**链路 | ❌ 没跑 |
| **C 候选策略** | 同上，只改一个处理因素 | ❌ 没跑 |

**本批的具体做法**：音频边界取自**语料官方的切分**（FLEURS 一句一条、CORAA 一段一条），
**不经过我们的生产 VAD**；每条**独立识别**、离线批量、**不是 1 倍速输入**；
没有生产链路里的切句错位、丢块、幻听闸误丢、增量提交。

> 这正是老师 §四 规定的那一步 ——「先按数据集原有片段送入 ASR，**不通过生产 VAD 重新切分**。
> 这样先回答：在源语言已知、音频边界已提供时，识别模型能达到什么水平？」

**所以这批数字是实时链路的「上界」，真实表现只会更差，不会更好。**
差多少要靠 §五 的 A/B/C 对照来量（还没做）。

### 5.3 运行纪律（三条，都不是可选项）

**① 失败样本不许静默排除。** 每条的加载与推理都单独兜住，失败记进 `failures`
并在报告开头显式列出（含分母是多少）。**静默排除会让"只测了 460/500 条"看起来像"全测完了"**，
而失败的那些往往是坏文件/异常音频，恰恰最该被看见。

**② 三类耗时分开报**（老师的 §八 要求分开，混在一起会误判）：

| 指标 | 含义 |
|---|---|
| **单条识别耗时 P50 / P95** | 从 ASR 调用开始计时。**P95 比平均重要** —— 同传怕的是尾巴 |
| **识别总耗时 / RTF** | 整批合计（RTF = 识别总耗时 ÷ 音频总时长，越小越好） |
| **模型加载与预热** | 单独报，不混进上面（CUDA 上每次约 11~15s） |

**③ 每次运行绑定可追溯信息。** 结果 JSON 里带 `provenance`：git 提交号、评分规则版本、
模型、设备、精度、beam、语种与候选集、提示词、是否峰值归一化、是否内置 VAD、
数据目录、**manifest 的 sha256 前 16 位**、样本数。
理由：报告一旦离开现场，"这个 12.2% 是哪一版代码、哪个模型、哪批数据算的"就没人说得清。

### 5.4 结果落在哪

```
var/asr-eval/results/<包名>__<模型>_<设备>_<精度>.json
   例：pt-speech-holdout__large-v3_cuda_float16.json
```

文件名由 `asr-eval/test-asr.mjs` 的 `resultPath()` 拼出（包名 + 双下划线 + 模型/设备/精度）。
逐条都存了参考原文、识别原文、S/D/I、耗时、分组标签，以及那次运行的 `provenance`。

| 测试包 | 条数 | 严格口径 | 规范化口径 | 差 | 单位数 严/规 |

| `pt-read-holdout` | 217 | 3.8% | **3.5%** | 0.2 pp | 4717 / 4833 |
| `pt-speech-dev` | 300 | 16.8% | **16.6%** | 0.3 pp | 2630 / 2662 |
| `pt-speech-holdout` | 500 | 17.6% | **17.4%** | 0.3 pp | 4553 / 4589 |

> ⚠️⚠️ **不要把这个"差"当成"声学错误率"，也不要从严格分里减掉它。**
> 这两件事的区别是**评审明确指出的**，本仓库为此改过一次做法：
> 原来输出过"真正要追的声学错误 ≈ 整体错误率 − 写法差异"（那张表给的是
> 中文朗读 3.4%、口语 12.7~15.3% 之类）。**那个数不可信，已撤**：
>   · 它是"从分数里扣掉几个**启发式分类桶**"得到的 —— 桶可能归错；
>   · 它既不是严格分、也不是规范分，却看起来像个分数；
>   · 它默认"扣掉的不影响翻译、剩下的都是听错"，这两句都没有证据。
> 现在的做法是**两套口径各自重新对齐算**（见 §6.6），差值只说明
> "同一批输出在两套规则下差多少"。两套的**分母也可能不同**，所以差为负
> 并不表示"规范化更糟"（看最后一列的单位数）。

**"好的句子"的判据是"该句自身错误率 ≤ 10%"** —— 这个 10% 是**我们定的**，老师没规定。
短句特别容易踩到它（两个字的一句话错一个字就是 50%），所以它只作参考，不当验收线。
**"好的句子"回答的是"有多少句基本能用"**，因为整体错误率是平均数、会被长句支配。

### 6.2 四件从这批数字里读出来的事

**① 决定性的因素是"朗读还是口语"，不是语种。** 按**规范化口径**（§6.6）：

```
朗读：中文 11.4% / 5.3%      葡语 2.7% / 3.5%
口语：中文 14.5% / 16.9%     葡语 16.6% / 17.4%
```

**口语比朗读差 3~5 倍，而且这个差距在两种语言上都成立。**
⚠️ 这一点**推翻了我之前的说法**：中文口语这一格没补上之前，我在文档里写过
"中文识别已经很好、葡语口语才是要优化的目标"—— 那是拿**中文朗读**去比**葡语口语**，
比错了对象。四格齐了之后看得很清楚：**两种语言的口语都不行（14.5~17.4%），
两种语言的朗读都还行（2.7~11.4%）**，产品是"会议里的口语"场景，所以
**要解决的是"口语"这一类问题，而不是"葡语"这一类问题**。

**② ⚠️ 中文朗读那个"删除占一半以上"：核对过内容，但**没有逐条听音频**（此处更正过两次）**

> **第一次更正**：原来写的是"中文 CER 里删除压倒性 → 识别整段整段地少给字"。
> 查下去发现删除集中在参考文本里的**外文括号注记**（`（Maciej Krezel ）`、`(NHK)`、
> `(Kashiwazaki Kariwa)`）—— 朗读时基本不会念出来。这一条**核对过每一条被删的内容**。
>
> **第二次更正（评审之后）**：我据此写过"剥掉后中文朗读只剩 2.8~3.7%"，
> 并把这一类归成"书面标注，往往本来就不念"。评审指出：
> **"拉丁字母/数字"不能默认没念** —— 产品型号、金额完全可能是真的漏了。
> 用新增的抽查功能（`--samples`）看实际样本，确实抓到了反例：
>
> ```
> zh-speech-dev-0010.wav  参考「哎哟就S C P」      识别「SAC」      ← 字母听错，不是"没念"
> zh-speech-dev-0099.wav  参考「对我们以后在四S店」 识别「在 4A 上」   ← 4S店 → 4A，真错
> ```
>
> **所以现在这一格不叫"计分假象"，叫"需听音频确认"**，而且**不作为任何扣减依据**。
> 中文朗读的"干净值 2.8%"这个说法**已撤**：在没听音频之前，它只是一个假设。
> 有据可依的只有规范化口径那一个数（11.4% / 5.3%）。

| | 删除占比（严格口径） | 其中拉丁字母/数字 | 状态 |
|---|---|---|---|
| 中文朗读 | 2.5%~8.2% | 87%~98% 的删除 | **待音频确认**（内容已看过，声音没听） |
| 中文口语 | 6.5%~7.1% | 1.1% | 实测有真错（`4S店→4A`），按"需听音频"单列 |
| 巴葡朗读 | 0.3%~0.4% | — | 不变 |
| 巴葡口语 | 7.9%~8.1% | — | 删除以内容词为主（见 §6.6） |

**③ 葡语口语的高错误率基本是真的。** 按新的归因（§6.6）：
删除里**内容词占 71~74%**，高频虚词只占 17~19%（而且那些虚词**可能有实义**，
不再当成"无信息"）。所以它不是靠"语气词没算"撑起来的 ——
这也解释了为什么调解码参数没有用（§8.2）。

**④ 口语的 RTF 反而更高（0.19~0.20 vs 0.09~0.12）。**
口语片段更短（中位 2.5~3.4s vs 朗读 10~12s），而每段的固定开销摊不掉。
**这对同传是坏消息 —— 我们的生产链路正好是短片段。**

### 6.3 ⚠️ 一个必须知道的"计分假象"（中文）—— 追查全过程

这条值得完整记下来，因为它是**"先猜机制 → 被实验证伪 → 改为逐条看内容"**的过程，
而且我第一版给的结论是错的。

**第一步：数字看着像 bug。** 中文 dev(12.3%) 与 holdout(5.4%) 差 2.3 倍。
按句分布 dev 的 P50 只有 **2.0%**、P90 却 **33.3%** —— 不是整体偏移，是**少数灾难样本**
（最差 5 条贡献了 dev 全部错误的 **42%**；holdout 里同样 5 条只占 18%）。

**第二步：猜机制，猜错了。** 读 faster-whisper 源码发现它内部有一道闸（见 §8.1）：
`no_speech_prob > 0.6` 且 `avg_logprob ≤ -1.0` 时**整段文字被丢弃**。
这看起来正好解释"整段少给字"。于是把两个阈值放宽（`no_speech_threshold=null`、
`log_prob_threshold=-2.0`）各跑一遍 zh-read-dev（100 条）——

> **结果与基线逐字节相同**（12.3%、S148/D325/I17）。**假设被证伪**：这道闸在这批音频上根本没触发。

**第三步：改为看"被删的到底是什么内容"。** 这才找到真因：

```
参考  波兰男子视障滑雪选手马切吉·克雷泽尔（Maciej Krezel ）和向导安娜·奥加津斯卡（Anna Ogarzynska）…
识别  波兰男子市场滑雪选手马切吉·克雷泽尔和向导安娜·奥加金斯卡…
丢掉的内容: ['maciejkrezel', 'annaogarzynska', '四', '十', '二', …]

参考  日本广播协会 (NHK) 还报道说，位于新泻县的柏崎刈羽 (Kashiwazaki Kariwa) 核电站运行正常。
识别  日本广播协会还报道说 位于新线线的博奇、刘宇和电站运营情正常
丢掉的内容: ['nhk', 'kashiwazakikariwa', '柏', '崎', '刈', '羽', …]
```

被删的几乎全是**参考里的外文括号注记** —— 朗读时读的是中文名，**括号里的拉丁字母根本没念**，
Whisper 自然不输出。在 v1 的严格口径下这些全算**删除**。
（剩下的还有**阿拉伯数字写法**：参考 `56 种` vs 识别 `五十六种`，2 删除 + 3 插入。）

**量化结果：**

| 测试包 | 全部 | 剥掉含括号注记的样本 | 只看含注记的那少数样本 |
|---|---|---|---|
| `zh-read-dev` | 12.3%（删除 8.2%） | **2.8%**（删除 0.1%）← 76 条 | 32.0% ← 24 条贡献了 **321/325** 的删除 |
| `zh-read-holdout` | 5.4%（删除 2.5%） | **3.7%**（删除 0.5%）← 195 条 | 13.8% ← 32 条贡献了 **167/200** 的删除 |
| `pt-read-dev` | 2.8% | 2.8%（无变化） | 只有 2 条，贡献 0 删除 |
| `pt-speech-dev` | 16.8% | 16.8%（**无变化**） | 没有这种样本 |

**结论：中文那个 12.3% 里约 77% 是计分假象；葡语不受影响（葡语语料没有这种注记）。**

**归因（同一批样本，只在评分前做不同处理）**：

| 处理 | zh-read-dev | zh-read-holdout | pt-read-dev |
|---|---|---|---|
| v1（现行口径） | 12.3% | 5.4% | 2.8% |
| 只做数字写法归一 | 11.8% | 5.3% | 2.8% |
| 只去掉括号注记 | **9.0%** | 5.0% | **3.4%**（反而变差） |
| 两者都做 | 8.6% | 4.9% | 3.4% |

**结论两层，第二层更重要：**
1. 中文 dev 的 12.3% 里，**约 3.3 个百分点（27%）来自"参考的注记约定"，不是识别错**。
2. **但不能用一个通用规则去掉它** —— 同一条规则在葡语上让指标**变差**（2.8% → 3.4%），
   说明"括号里的内容念没念"**因语料而异**。这正是老师 §三 要的两件事：
   **① 原始转写与评分用转写分开存；② 评分规范要冻结、并且能人工核对。**

> 所以 **v1 保持不动**：改口径必须开 v2 并把所有历史集重跑一遍。
> "评分用转写"该怎么定，需要**对着音频确认那些注记到底念没念** ——
> 这件事只能提出证据，不能替它拍板。

### 6.4 评测口径与产线口径的两处差别（已查、已量、已做成开关）

老师要求"保留现有解码参数"。查代码发现**评测原来有两处与产线不一致**：

| 参数 | 评测原缺省 | 产线 | 影响 |
|---|---|---|---|
| `vad_filter` | `True`（faster-whisper 内置 Silero VAD 再切一遍） | **`False`**（产线自己已按能量切好） | 评测多切了一次 |
| `initial_prompt` | **不发** | **默认发语种提示词**（zh:「请用简体中文输出」/ pt:「巴西葡语」） | 产线多一个先验 |

**实测差别（同一批 30 条样本，逐一核对过是同一条）**：

| 测试包 | 评测原口径 | 产线口径 | 差值 |
|---|---|---|---|
| `pt-speech-dev` | 18.1% | 18.5% | **+0.4pp** |
| `pt-speech-holdout` | 16.1% | 16.6% | **+0.4pp** |
| `zh-read-holdout` | 5.4% | **4.9%** | **−0.5pp** |

**结论：两处差别都小于 0.5 个百分点，不改变任何结论** —— §6.1 那张表仍然可用。
（顺带：那个"请用简体中文输出"的提示词在这 30 条上**没有减少繁体字**，都是 2 字 ——
说明它除了会被回显成假字幕之外，对繁体并没有可测的收益，见 `docs/04` §9 的更正。）

两个开关都在 `asr_eval.py` 上（`--vad-filter/--no-vad-filter`、`--initial-prompt`），
并且**写进 `provenance`** —— 以后跑"产线口径"只需加参数，不必改代码。

### 6.5 葡语口语那 16.8% 是真的吗？—— 基本是真的

用查中文那套办法（逐条看被删内容）查葡语口语，结果是**另一回事**：

被删最多的词是 `é`(27) / `eh`(18) / `eu`(16) / `que`(15) / `pra`(15) / `e`(12) /
`ah`(10) / `assim`(9) / `né`(7) / `aham`(7) / `cê`(6) —— 这些是**口语里的填充词与迟疑标记**。
而且 Whisper 会**把逐字转写里的自我重复合并掉**：

```
参考  colocar mais carros mais ônibus mais carros no sentido de ônibus mais veículos e
识别  Colocar mais carros, mais ônibus, mais veículos.
丢掉  [['e'], ['carros','no','sentido','de'], ['mais','ônibus']]
```

参考是**逐字转写**（含自我重复与填充词），而识别输出是**规范化后的可读文本** ——
对做字幕来说，后者其实**更好**，但严格口径把它算成错误。

**但这个假象比中文小得多**：

| | 删除占参考 | 其中落在保守填充词清单上 | 占参考 |
|---|---|---|---|
| `pt-speech-dev` | 8.1% | 35 词（占删除 17%） | **1.3%** |
| `pt-speech-holdout` | 7.8% | 84 词（占删除 24%） | **1.8%** |

> ⚠️ 这只是一个**线索统计**，**不能直接当规则用**（评审就是这么批评原来的做法的）：
> 清单里的词大多有实义 —— `é` 既是语气词（uh）也是系动词（is），`e` 是"和"，
> `a/o` 是冠词。盲目删除会把真错洗掉，正是老师警告的"不能把听错的词洗成正确"。
> 所以这一节的数字**只用来回答"这类词出现了多少次"**，不作为扣减依据。

**结论（按 §6.6 的新归因）：葡语口语的删除里内容词占 71~74%，
高频虚词只占 17~19% —— 而且那些虚词可能有实义。所以那个高错误率基本是真的，
不是靠"语气词没算"撑起来的。**

| | 规则 | 作用 |
|---|---|---|
| **严格口径** `asr-score-v1` | 标点/大小写/空白归一，其余都算错（繁简不转、数字不归一） | **与历史结果可比**，衡量转写一致性 |
| **规范化口径** `asr-norm-v1` | 只统一"同一个东西的写法"：标点 + **成对**繁简 + **数值+单位等价**的数字写法（中：`一百元`↔`100元`；葡：`vinte anos`↔`20 anos`） | 减少确定的写法差异干扰 |

迟早会漂成两套算法，而它们的差值本来是要拿来对比的。
结果文件里同时存 `weightedRate` 与 `normalizedRate`（以及各自的 S/D/I），
provenance 里记两套版本号与开关状态。

**规范化口径里默认不做的事**（评审逐条要求）：

| 不做 | 为什么 |
|---|---|
| 不删「那个/就是/然后」 | 它们在口语里可能实义（表顺序、表强调） |
| 不把葡语 `é / sei / cê` 当无信息 | 在具体句子里就是"是 / 知道 / 你" |
| 不删感叹词（`嗯/呃`…） | 默认**关**：漏掉用户听得出来（字幕变硬）。要开得显式加 `--norm-interjections` |
| 不折叠重复（`看看`→`看`） | 默认**关**：中文里 `看看/说说/慢慢` 是正常词，折叠会把真漏字盖掉（`--norm-collapse-repeats` 才开） |
| 不动人名、型号、金额、否定词 | 规范化只改"写法"，不删内容、不改数值、不动极性 |

### 6.7 切句本身的代价：整段 vs 逐句切 vs 产线切（**新做的受控实验**）

**问题**（用户提的）：口语那 14.5~17.4% 里，有多少是**切句本身**造成的？
如果切句就要吃掉好几个百分点，那优化方向就不是换模型，而是**少切一点**。

**做法**：从原始录音里取一段**连续**发言，同一段音频**三种喂法**、同一个参考、同一套解码参数，
只改"音频怎么切"：

| 喂法 | 做什么 | 段数（20 段合计） |
|---|---|---|
| **A 整段** | 整段一次识别（上下文全留） | 20 |
| **B 官方句边界** | 按官方逐句时间戳切，各自识别后拼接 | 142（平均 7.1 段/段） |
| **C 产线切句** | 用产线那个 `UtteranceSegmenter`（silence 500ms）切，各自识别后拼接 | 129（平均 6.5 段/段） |

```powershell
# 两个实验都走同一个入口（`asr-eval/test-asr.mjs`）；不带 --cut/--context 时它就是模型横评
node asr-eval/test-asr.mjs --cut --count 20          # 整段 vs 逐句切 vs 产线切句
node asr-eval/test-asr.mjs --cut --sweep 500/15000,800/30000,1200/30000,2000/30000
node asr-eval/test-asr.mjs --context                 # 提示词续传 vs 左邻/右邻重叠（§6.7.2）
```

产物自动落在（报告里含本次的完整重跑命令与段清单指纹）：

```
var/asr-eval/results/<实验>__<段清单名>__<模型>.json     ← 结构化
var/asr-eval/reports/<实验>__<段清单名>__<模型>.md       ← 人读（含逐段明细与全文）
```

底层引擎仍可单独调用（参数更多）：`python asr-eval/context_eval.py --help`、
`python asr-eval/context_overlap.py --help`。

⚠️ 三条公平性前提（不满足这个对照就不成立，都写进了脚本注释与测试）：
① 参考必须覆盖整段音频 → 选段时要求段内转写**全部干净**（无重叠/听不清/笑声）；
② 三种喂法用**同一套解码参数**（模型/语种/beam/VAD 都一样）；
③ 拼接**不加分隔符**（中文按字算，加空格会让切过的凭空多出单位、显得更准）。

**实测**（MagicData-RAMC dev，20 段 / 491 秒 / 1801 个参考字）：

| 喂法 | 严格口径 | 规范化 | S | D | I | 输出字数 |
|---|---|---|---|---|---|---|
| A 整段 | **11.7%** | 10.2% | 90 | 102 | 18 | 1741 |
| B 逐句切 | **16.3%** | 14.4% | 159 | 103 | 31 | 1749 |
| C 产线切句 | **16.8%** | 15.2% | 151 | 140 | 11 | 1682 |

```
A−B = +4.6 个百分点（95%CI +1.1 ~ +8.0；14/20 段更差、4/20 更好、2 段持平）
A−C = +4.9 个百分点（95%CI +2.7 ~ +7.2；14/20 段更差）
B−C = +0.5 个百分点（产线切句 ≈ 理想逐句切，基本持平）
```

**错法看得出来是哪一类坏了 —— 这一点比总分更有用：**

| | A → B（切短） | A → C（产线，还多丢碎片） |
|---|---|---|
| 替换 S | 90 → **159**（+69） | 90 → 151 |
| 删除 D | 102 → 103（**没变**） | 102 → **140**（+38） |
| 插入 I | 18 → 31 | 18 → 11 |
| 输出字数 | 1741 → 1749 | 1741 → **1682**（少 59 字） |

- **切短主要伤"替换"**：字没错位、也没丢，但**听成了别的字**（同音/近音选错）。
  这正是"丢上下文"的指纹 —— 模型在 2~4 秒里挑不出正确的那个词。
- **产线切句额外伤"删除"**：只覆盖了 **79.1%** 的音频，
  丢掉的部分主要是 <500ms 的碎片（这是设计如此，为的是防噪声爆音），
  代价是 +38 个删除、少了 59 个输出字。**这笔账以前没算过。**
- 顺带：切短之后**繁体输出略多**（A 1 字 → B 8 字）—— 与"短片段更容易跑偏"一致。
  （小模型上更明显：smoke test 里有一整句被输出成繁体。）

**怎么读这个结论（三条必须说清的边界）：**

1. **A 不是产线能做到的**。产线是流式的，必须切；A 只是"**不切能有多好**"的上界。
   所以这个实验的用法不是"别切了"，而是回答"**少切一点值多少**"。
2. **A 的上下文也就是 30 秒**：Whisper 的感受野本来就是 30 秒窗，
   我们的段正好 25~30 秒，所以 A 与 B/C 的差别**不是"无限上下文"的差别**，
   而是"一段话 vs 一句一句"的差别 —— 这恰好是产线真正面临的选择。
3. **样本量**：20 段、1801 个参考字，逐段方差很大（−10.2 ~ +28.4 个百分点），
   所以只能说到"**大约 1~8 个百分点**"这个量级，别当成精确值。

**下一步（这份结果直接指出的方向）**：既然代价来自"切得太碎、上下文太少"（而不是丢字），
那最值得试的就是 **C 的切句参数往"少切"一侧挪**：
`silence_ms` 500 → 800/1200/2000、`max_speech_ms` 15s → 30s，
量"CER 降多少 vs 字幕等待时间涨多少"。
同一个脚本换参数就能跑（`context_eval.py` 里的 `PRODUCTION_SEGMENTER`），
**这是目前唯一一个既能提高准确率、又不换模型的杠杆**。

#### 6.7.1 参数扫描的结果：**少切一点，确实更准**（已做）

按老口径 `1200` 只多等 2.31 秒，**实际是 6.2 秒**。段长由产线切句器实跑得出（不猜）。

**取舍（相对原产线）：**

| 配置 | 错误率 | 好处 | 字幕延迟 | 多等 | 判断 |
|---|---|---|---|---|---|
| `silence 500`（原产线） | 16.8% | — | 2.7s | — | 基准 |
| **`silence 800`（现产线）** | 15.5% | **+1.3 pp** | 3.8s | +1.1s | **上线取这一档**：拿一半延迟换一半准确率 |
| `silence 1200` | 13.3% | **+3.5 pp** | 6.2s | **+3.5s** | 更准但更晚；留作"愿意多等时"的下一档 |
| `silence 2000` | 12.2% | **+4.6 pp** | 12.8s | +10.1s | 准确率最接近"不切"，但等于放弃实时感 |

**为什么会更准（机制清楚，不是调参玄学）：**

- **段数 129 → 27**：一次识别拿到的是 3 秒 → 17.6 秒的完整语境，同音词选错的概率下降
  （替换 S 151 → 101）。
- **覆盖 79.1% → 96.9%**：`silence` 变大后，短促的一两个字不再被判成"碎片"丢掉
  （删除 D 140 → 109）。这条是**白捡的**收益，和上下文无关。

> ⚠️ **一个必须说的噪声事实**：同一配置 `B 逐句切` 我跑过两次
> （同一批段、同一套参数），结果是 **16.3% 和 15.6%** —— 差 0.7 pp，
> 而且差别集中在**插入**（I 31 → 17，短片段偶发多吐几个字），S/D 几乎不动。
> 所以：**1 pp 以内的差异不要当真**（这也让 `silence 800` 那一档的 +1.3 pp 变成"存疑"），
> 而 `silence 1200/2000` 的 +3.5/+4.6 pp 是可信的方向。
> ⚠️ 但上线取 800 之后**又实测了一次**（同一批段，`800 + 续传` vs `500 + 续传`：
> 13.9% vs 15.0%），差 1.1 pp —— 仍然在噪声边缘，所以这一档的收益要连着
> "零成本的续传"一起看：**续传那一项（−1.8p）才是这次最扎实的收益**。

**结论：`silence_ms` 是目前唯一一个"不换模型、不加显卡"就能明显提高口语准确率的旋钮。**
代价是字幕更晚出来，而**这正是产品要拍板的事**。实际拍板的结果是：
**取 `silence 800`（多等 1.1 秒、+1.3 pp），不取最准的 1200**（多等 3.5 秒换 +3.5 pp）——
理由是延迟这一项在真机上还没体验过，先取折中。
两个值都该在**真机**上再确认一次 —— 设备端的静音判定与电脑上的
`UtteranceSegmenter` 是不是同一套行为，目前只在电脑上量过（见 §9）。

#### 6.7.2 上下文能不能"白拿"：文本续传 vs 声学重叠（**用户提的想法，已实测**）

§6.7.1 说明"切碎伤在替换（S）"，也就是**语境不够导致同音词选错**。于是自然要问：
**能不能不增加等待、把语境补回来？** 提出的做法是"按 A B C 说话时，用 A、AB、BC 的顺序识别"。
把它拆成可测的四档，跑在**同一批 20 段、同一个参考**上（与 §6.7.1 的 C1 完全相同）：

```powershell
# 同一个人口（--context）：不给 --spans-file 就自动用 spans/ 里最新的那一份
node asr-eval/test-asr.mjs --context --modes all    # 本节这张表是五种全跑出来的
```

（`--modes` 缺省只跑 `C1,T2`；要复现下面这张完整表必须写 `--modes all` ——
只跑一部分时产物名带 `-C1T2`，不会覆盖本节这份完整结果。）

| 喂法 | 严格 | 规范化 | S | D | I | vs C1 | 算力 | 要等下一段? | 拼接分歧 | 结论 |
|---|---|---|---|---|---|---|---|---|---|---|
| C1 逐段（**现状**） | 16.8% | 15.2% | 151 | 140 | 11 | — | 1.00× | 否 | — | 基准 |
| T1 逐段 + 提示词（上一段文本） | 16.4% | 14.9% | 137 | 144 | 15 | −0.3p | 0.83× | 否 | — | **在噪声内，没用** |
| **T2 逐段 + 提示词（前两段文本）** | **15.1%** | 13.7% | 129 | 130 | 13 | **−1.7p** | 0.83× | 否 | — | **唯一明确有效** |
| L 左邻重叠（窗口=上段+本段，取本段） | 15.9% | 14.9% | **107** | **171** | 8 | −0.9p | 1.23× | 否 | **78/129** | 不如 T2 |
| R 右邻重叠（窗口=本段+下段，取本段） | 17.0% | 15.7% | 143 | 128 | **36** | **+0.3p** | 1.27× | **是** | 77/129 | 净负 + 要等一段 |

**逐段配对（段级错误率，以 C1 为基准）：** T2 **20 好 / 8 坏**；L 20 好 / 23 坏；R 23 好 / 26 坏。

**拼接分歧时谁对**（不一致的段里，用参考判谁更接近）：
L **20 赢 / 23 输** / 35 平；R **23 赢 / 26 输** / 28 平 —— **重叠版输多赢少**。

**这张表读出来的三件事：**

1. **声学重叠的信息增益，被"拼接时必须选一个"吃掉了。** 重叠窗口确实让**替换**大幅下降
   （L 的 S：151 → **107**，比 T2 的 129 还好），但代价是：
   - **删除涨了**（140 → **171**）：按词时间戳切边界会**丢词**（时间戳本身不精确，边界词归属也会错）；
   - **分歧率极高**：129 段里 **78 段**（60%）的窗口输出与逐段输出不一致，
     而不一致时**逐段版更对的次数更多**；
   - R 更糟：窗口里含下一段音频 → **插入从 11 涨到 36**（模型多吐字，取"前半"没切干净），
     而且它**必须等下一段说完**才能定稿。

2. **"文本续传"是更便宜也更有效的办法。** `initial_prompt = 前两段的文本`：
   **−1.7 个百分点**，**零额外等待**、**不增加识别耗时**（提示词只是一个字符串）。
   机制对得上：替换 151 → 129、删除 140 → 130，**两项都在降**。

3. **`condition_on_previous_text=True` 没有作为一档** —— 它只在**同一次 transcribe 调用内**、
   跨 30 秒窗口生效，而我们的片段只有 3 秒、只产出一句话，**设了不会有任何变化**。
   跨段的文本续传只能靠 `initial_prompt`。

**⚠️ 一个必须先查的实现细节（别直接上产线）：**
产线那道「提示词回显」闸 `looks_like_prompt_echo` 要求"输出占到提示词的 **40%**"，
这个比例是照着一条 **17 字**的固定提示词调的。把**上一段文本**当提示词之后提示词会长很多，
同一个阈值会**变松**（部分回显可能溜过去）。实测这一次的数据里没有回显：

| | 与提示词的最长逐字重合（平均） | 重合 ≥6 字的段数 |
|---|---|---|
| T2（带提示词） | 1.6 字 | 3 |
| 同一段、**不带**提示词的 C1 | 1.5 字 | 3 |

**增量是 0** —— 那 3 段的重合是**说话人自己重复了上一句的词**（如"只有不停的走"在参考里本来就重复），
不是回显。但"这次没发生"不等于"不会发生"，所以：
**要上产线就得先把回显闸的判据改成"与提示词的连续重合 ≥N 字"这类更贴切的形式**（不再用比例）。

**⚠️ 关于算力那一列要说准**：T1/T2 的识别耗时反而比 C1 低 17%（0.83×），
这**不像**是提示词的功劳，更像是 **C1 跑了第一轮、GPU 还在升温**（顺序效应）。
所以只能说"加提示词**不额外花算力**"（音频量没变），不能说"更省钱"。
L/R 实测是 **1.23/1.27×**（不是我原先估的 2×：6 秒窗口的每秒效率比两个 3 秒片段高）。

**结论与建议：**

- **不做声学重叠那套机器。** 在"最简单的拼接规则"下它输给文本续传，还要付算力、
  受拼接分歧与时间戳精度拖累，R 还多等一段。
  （**保留一句话**：如果换成有原则的提交策略 —— 例如只提交相邻两次解码的**最长公共前缀**
  （[Whisper-Streaming 的 LocalAgreement 那一类做法](https://ufallab.ms.mff.cuni.cz/~machacek/pre-prints/AACL23-2.11.2023-Turning-Whisper-oral.pdf)）
  —— 分歧问题可能被压下去；但**现在举证责任在重叠那边**：便宜的路已经拿到 1.7 个点。）
- **值得做的是 `initial_prompt = 前两段文本`**（T2）。这是本次实验里唯一"确定为正、代价为零"的一项。
- **下一步最值得试的是叠加**：T2（−1.7p，本次）+ `silence 1200`（−3.5p，§6.7.1）
  是两个独立机制（语境 vs 切多长），而两次实验的 C1 都是 **16.8%**，所以可以直接相加估算
  —— 大约 **13~14%**。要验证就得把提示词续传接进 §6.7.1 的扫描里再跑一遍。

| 不发提示词 | **15.55%** | **14.51%** | 352 | 45 |
| 发提示词 | 18.24% | 17.96% | **489** | **1** |

→ 多错 2.7~3.5 个百分点（伤害集中在**删字**），只换来繁体 45 → 1 字（≈0.8 个点）。
**所以中文缺省不再发那句提示词**；它仍然留在 `LANGUAGE_PROMPTS` 里供显式使用。
（葡语那句还没量过，方法现成，见 §9。）

**发现三：三个改动叠在一起是 21.9% → 13.9%（−8.0 个百分点）**：
`800ms` + `续传 2` + `撤提示词`（若把静音判定再放宽到 1200 则是 12.0%）。
其中续传那一项在"带提示词"的条件下更值钱（−5.4p），说明两者不是简单相加的关系 ——
**这正是"必须在产线条件下复量一遍"的意义**。

⚠️ 随之修正的一个**旧口径错误**：本节所有表格里的"等待"列原来只算
`静音判定 + 识别耗时`，**漏了"这一段本身有多长"**（字幕是整段识别完才发的）。
按真实口径重算：`silence 500` 平均 2.7s / P95 4.7s；`1200` 平均 **6.2s** / P95 11.8s。
`--stats` 与 §6.7.1 的表都已改成新口径（段内位置按平均算，明确标注是**估算**）。


## 7. 怎么读这些数字（三个容易搞混的点）

| 容易搞混 | 正解 |
|---|---|
| 把 RTF 与"单条耗时"当一回事 | RTF 是**整批**的吞吐比；单条耗时是**每句**的快慢。同传看 P95，不看平均 |
| 把"好的句子"当验收线 | 它是"有多少句基本能用"的**分布指标**，阈值 10% 是我们定的；验收线要用**整体错误率** |
| 把 dev 数字当结论 | dev 是**用来调参**的，会被反复看；**只有保留集的数字能当结论**。而且现在 dev/holdout 差 2.3 倍（§6.3），说明这个规模的切分本身噪声不小 |

## 8. 调参：能调什么、先调什么

Whisper 本身不是"一个黑盒模型"，faster-whisper 的 `transcribe()` 有 **35 个可调参数**。
但**不能盲调** —— 先看清两件事：哪些参数对着我们**已测出的错**，以及哪些参数的后果是"静默丢字"。

### 8.1 一个必须先知道的机制：**整段丢弃**

faster-whisper 内部有这道闸（实测读源码确认）：

```python
should_skip = result.no_speech_prob > no_speech_threshold        # 默认 0.6
if log_prob_threshold is not None and avg_logprob > log_prob_threshold:   # 默认 -1.0
    should_skip = False          # 模型对解码有把握 → 不跳
if should_skip:
    seek += segment_size
    continue                     # ← 这一段的文字**直接丢掉**
```

也就是说：**当 `no_speech_prob > 0.6` 且 `avg_logprob ≤ -1.0` 时，整段文字被丢弃**。
在我们的评分里，这表现为**纯删除**。

> ⚠️ **一个被实验证伪的猜测，留在这里当教训。**
> 我最初看到"中文删除占一半以上"，就断定这道闸是主因（因为它的后果正好是"整段少给字"），
> 并把它写进了这一节。**结果实测把两个阈值放宽/关掉之后，结果与基线逐字节相同** ——
> 这道闸在这批音频上根本没触发，假设是错的。
> 后来改为**逐条看被删的内容**才找到真因：参考里的外文括号注记（见 §6.3）。
>
> **教训：`no_speech_prob` 只说明"模型觉得没语音"，不说明"真的丢了东西"。**
> 把机制读懂了，不等于证明了它在我们这批数据上起作用 ——
> **要看数据，不要看机制像不像**。

反过来也要小心：把这两个阈值放宽（或关掉）会**增加在真静音上产生幻觉**的风险。
评测用的片段都是语料切好的、本来就是说话音频，所以离线放宽风险低；
但**产线不能照搬** —— 那里有真实静音，而产线自己的幻听闸在更外层。

### 8.2 第一批调参的实测结果（基本都是负结果）

按 §8.4 的规矩在 **dev** 上跑，一次只改一个参数：

| 测试包 | 配置 | 整体错误率 | 删除 | RTF | 结论 |
|---|---|---|---|---|---|
| `zh-read-dev` | 基线 | 12.3% | 8.2% | 0.114 | — |
| `zh-read-dev` | `no_speech_threshold=null` | 12.3% | 8.2% | 0.132 | **无变化** |
| `zh-read-dev` | `log_prob_threshold=-2.0` | 12.3% | 8.2% | 0.143 | **无变化** |
| `pt-speech-dev` | 基线 | 16.8% | 8.1% | 0.192 | — |
| `pt-speech-dev` | `beam_size=10` | **16.6%** | 8.1% | **0.297** | 换来 0.2pp，代价 **+55% 耗时** |
| `pt-speech-dev` | `no_speech_threshold=null` | 16.8% | 8.1% | 0.233 | **无变化** |

**三条结论：**

1. **解码参数基本救不了**。`beam_size` 5→10 只换来 0.2 个百分点（相对 1.2%），
   而耗时涨 55% —— 对同传是纯亏。而且 0.2pp 在我们已测到的噪声量级之内
   （dev/holdout 能差 2.3 倍），**不该凭这个换配置**。
2. **两个"整段丢弃"阈值在真实数据上没有效果** —— 见上面那条教训。
3. **所以葡语口语那 16.8% 不是解码参数问题**，而是**模型/领域**问题：
   自发巴葡语音（口音、语速、省略、填充词）。要动它得换方向 ——
   换模型（更大/更专的、或葡语微调过的）、或做领域适配（`hotwords` 喂专名与术语），
   而不是继续拧这些旋钮。

### 8.3 按"对着哪个错"排的调参清单

| 我们测出的错 | 该试的参数 | 为什么 | 风险 |
|---|---|---|---|
| **口语 12.7~15.3%（两种语言都是）** | `hotwords`（词偏置）、换更大/领域微调的模型 | 错误主要落在**内容字/词**上（占删除 43~74%），是声学与领域问题，不是解码参数问题 | 见下条 |
| 同上 | `initial_prompt` | 与 `hotwords` 相比是更弱的偏置通道 | 提示词会被回显成假字幕（`docs/04`） |
| 同上 | `beam_size`（5 → 10）、`patience` | 搜索更宽 | 实测只换来 0.2pp 而耗时 +55%（§8.2）——**基本可以排除** |
| **中文繁体字形（约 1pp）** | `suppress_tokens`、或输出后做繁→简转换 | 这是**字形**问题，不是声学问题；实测提示词无效（§6.4） | `suppress_tokens` 用错会压制正常字 |
| 数字写法（汉字↔阿拉伯） | —— | 不是错，是写法；做字幕时阿拉伯数字反而更好读 | 若改成"统一写法"要另开评分口径 v2 |
| 输出重复/循环 | `repetition_penalty`、`no_repeat_ngram_size` | 直接压重复 | 压过头会漏字 |
| 短片段 RTF 高（0.19~0.20） | `without_timestamps`、`beam_size=1`、`condition_on_previous_text=False`、批量推理 | 这些是**速度**参数，不是准确率参数 | 换速度可能牺牲一点准确率，要一起看 |
| ~~中文删除占一半以上~~ | ~~`no_speech_threshold` / `log_prob_threshold`~~ | **实测证伪**：那是参考里的外文括注造成的计分假象（§6.3），放宽这两个阈值**逐字节无变化** | 已排除 |

> ⚠️ **调参的目标包应该是 `zh-speech-dev` 与 `pt-speech-dev`**，不是朗读包。
> 产品场景是会议口语，而朗读包的错误率（2.5~3.4%）已经低到"调也调不动"，
> 拿它调参等于对着一个不是问题的问题调。

### 8.4 怎么调：一个参数一个对照，只在 dev 上

```powershell
# 基线（已有结果，见 §6.1）—— 调参要在**口语**包上做，那才是产品场景
node asr-eval/test-asr.mjs --set zh-speech-dev --model large-v3 --language zh --count 0

# 试一个参数：把专名/术语喂进词偏置通道
python asr-eval/asr_eval.py --set var/asr-eval/packs/zh-speech-dev --model large-v3 `
  --device cuda --compute-type float16 --language zh --count 0 --show 0 `
  --decode-json '{\"hotwords\": \"亮亮眼镜 高通 安卓\"}' `
  --out-json var/asr-eval/results/tune__zh-speech-dev__H-hotwords.json

# 跑完看"错在什么上"——分类变了没有，比总分更能说明问题
python asr-eval/asr_error_analysis.py var/asr-eval/results/tune__zh-speech-dev__H-hotwords.json
```

**`--decode-json` 可以把任意 `transcribe()` 参数透传进去**（不必为每个参数加命令行开关），
并且会写进 `provenance`。
⚠️ **参数名写错会直接报错**（`--decode-json 里有 transcribe() 不认的参数：[...]`），
不会静默忽略 —— 否则"我调了那个参数"会变成一句空话，实验结论就建立在没生效的配置上。

**四条纪律**（老师 §六 的原话加我们的实测教训）：

1. **只在 dev 上调参**；选定方案后再跑**保留集**，而且**只有一次**。
2. **一次只改一个因素** —— 否则分不清是哪个起的效。
3. **中文与葡语可以有不同的最优配置**（老师原话）。别强行统一。
4. **差异小就要做重复运行或配对统计**，不凭一次微小领先换方案 ——
   我们已经看到 dev/holdout 能差 2.3 倍，这个规模的噪声足以吞掉 0.5pp 的"改进"。
