# 24 · 功能测试清单（4.77 版）

> 用途：这一轮（4.55 → 4.77）改动很多，这里把**要测的东西**和**已知的边界**一次列清。
> 每条都写了"怎么点、应该看到什么、以及不该看到什么"。
> ⚠️ 标 `[服务端]` 的项必须先 `git pull` + **重启 relay**，否则测的是旧行为。
> APK：**4.77(106)**，`android/app/build/outputs/apk/debug/app-debug.apk`。

---

## 0. 开测前的准备（两分钟）

```bash
# 服务端
cd ~/glasses && git pull
systemctl stop leion || pm2 stop all          # 停掉旧进程
node scripts/doctor-db.mjs                    # 数据库必须显示"健康"；
                                              # 若显示"结构过旧"，重启一次 relay 会自动补列/建表
node scripts/start-all.mjs --public --data-dir /var/lib/leion/test --port 8789 ...   # 起回来
```

- 数据库这轮**自动补**了两样东西（都发生在 relay 启动、首次打开库时）：
  - 表 `history_hidden`（按账号删除历史记录）；
  - 列 `requests.hidden_at`（术语库申请可删除）。
- 手机端**必须**装 4.77(106)；旧 APK 看不到新增入口，也听不懂 `listen` 消息。

## 1.6 强制更新门禁（5.26）

前提：手机装的是当前这版 APK（版本号在「我的 → 关于」或设置页能看到，形如 `4.127(156)`）。

| # | 操作 | 应该看到 | 不该出现 |
|---|---|---|---|
| 1.6.1 | 版本一致时打开 App | **不弹任何框**，正常进登录页/首页 | 每次启动都弹一遍 |
| 1.6.2 | 服务器上执行 `node scripts/bump-version.mjs` + `node scripts/generate.mjs` 后重启 relay（**手机不重装**） | 打开 App 立刻弹出**不可取消**的框：「你的版本是 4.127，服务器要求 4.128」；返回键和点框外都关不掉 | 能关掉继续用 / 只是 toast 一闪 |
| 1.6.3 | 此时点「我已更新，重试」 | 提示「正在重新检查版本…」，然后**弹回同一个框**（还没更新） | 框消失、功能可用 |
| 1.6.4 | 1.6.2 的状态下按 Home 键再切回来、或从最近任务直接进房间 | 房间页同样被拦：麦克风按不动、也不录音 | 还能开麦说话 |
| 1.6.5 | 装上新 APK 再进来 | 框不再出现，功能正常 | 仍然拦着 |
| 1.6.6 | 把手机改成"服务端更新"（手机 versionCode 比服务器大）| 框里的话术变成「服务器比客户端旧，请联系管理员更新服务器」 | 让用户去重装 App |
| 1.6.7 | 停掉 relay 再打开 App | 不弹版本框（连不上时不该拿版本吓人），登录页照常提示连不上 | 弹出"版本不一致" |

> 服务端日志里能看到一行 `📱 客户端版本 4.127（服务器要求 4.127(156)）`，
> 不是最新版的手机第一次连上来也会打一行——排查"到底谁没更新"靠它。

## 1.5 注册：验证码要**真的收到**（5.17）前提：服务器（或本机 relay）配好了 `LEION_SMTP_*`，并且先跑过一次
`node scripts/check-mail.mjs --to <你的邮箱>` —— 它绿了再测手机，否则是在测 SMTP 配置不是测 App。

| # | 操作 | 应该看到 | 不该出现 |
|---|---|---|---|
| 1.5.1 | 注册页填邮箱点「获取验证码」 | 提示「验证码已发到邮箱，10 分钟内有效」；**邮箱里真的收到一封信**（含六位码） | "已发送"但其实没配 SMTP（那种情况只在局域网模式回码） |
| 1.5.2 | 立刻再点一次「获取验证码」 | 按钮这时是**禁用**的，文字是「重新发送 (47)」并每秒变小；点不动 | 按钮恢复正常、点了才弹 429 |
| 1.5.3 | 等过 60 秒（看着倒计时归零） | 按钮自己变回「获取验证码」；再点正常发出新码，**旧码失效**（用旧码注册应被拒） | 两个码都能用 / 要杀掉 App 才恢复 |
| 1.5.4 | 输错六位码 | 页内红字说明（不是弹窗），可继续改 | 直接跳到下一步 |
| 1.5.5 | 服务端**故意**配错 SMTP 密码再发码 | 手机显示"邮件没发出去"（502 `mail-failed`），控制台有打码的 SMTP 会话 | 假装发出去了 |
| 1.5.6 | 重启 relay 后再连续请求两次码 | 第二次仍然被 60 秒限制拦住（判据在库里，不在内存） | 重启就能绕过 |
| 1.5.7 | **用刚注册过的邮箱**再点「获取验证码」 | 直接提示「这个邮箱已经被使用了，换一个邮箱」；**不发信**、按钮立刻可再点（不进入倒计时） | 仍显示"已发到邮箱" / 自动切到登录 / 暗示"你已经有账号了" |
| 1.5.8 | 硬要再注册（比如另一台手机直接调接口） | 400 + `email-taken`，同一句「换一个邮箱」；库里**只会有一个**账号绑这个邮箱 | 又建出一个账号 / 同一个邮箱两个账号 |
| 1.5.9 | 注册页：用户名框输入一个**已存在**的名字，停手半秒 | 当场弹出「「张三」这个名字已经有人用了，换一个」 | 要等点「注册」才被拒 |
| 1.5.10 | 用户名换成没人用的 | 提示自动消失（不用再点一次） | 旧提示一直挂着 |
| 1.5.11 | 用**别人的大小写写法**注册（已有 `Zhang`，输入 `zhang`） | **允许注册**；提示「这个名字可以用；注意「Zhang」是另一个账号（只有大小写不同）」 | 被当成重名拒掉 |
| 1.5.12 | 用 `Zhang` 注册、然后用 `zhang` + 同一个密码登录 | 登录**失败**（这是两个账号，规则如此） | 登进了 `Zhang` 的账号 |
| 1.5.13 | 邮箱框输入一个已注册的邮箱，停手半秒 | 当场提示「这个邮箱已经被使用了，换一个邮箱」 | 走到发码才被拒 |
| 1.5.14 | 故意断开网络后改用户名 | **什么都不提示**（辅助校验，网络问题不该报错）；提交时服务端仍兜底 | 屏幕上出现"校验失败"之类的报错 |

> 关键实现：`lib/mail.mjs`（零依赖 SMTP）+ `auth_codes.issued_at`（5.17 新增列）。
> 判定细节见 docs/21 §5.17。

## 6.5 并发（两场会同时开）怎么测

> 前提：**两个不同账号**（同一账号会因单会话互踢）；两个**不同房间**。
>
> 服务端只需**一条命令**：`node scripts/start-multi.mjs`（4.88 起）。
> 6.5.1 / 6.5.2 验的是"音频分得开"，6.5.3 验的是"字幕分得开"（一条命令版），
> 6.5.3b 是它的手工等价版（排查单场会问题时用）。
> **注意缺省是翻译管线串行**（显存只够一份模型）：两场会的**音频**永远分得开，
> 但**字幕**同一刻只服务一场；要两场同时出字幕得 `--parallel-translate`（显存够才用）。

### 6.5.1 一台手机，两个房间顺序测（验“归属不串”）

| # | 操作 | 应该看到 | 不该出现 |

| 1 | 账号 A 进房间 X，开麦说 5~10 秒后停下 | `ls -l /var/lib/leion/test/audio/` 出现 `room-X.pcm` 并在长 | 只有全局 `audio-in.pcm` 在长 |
| 2 | 记下 X 的字节数 | `curl -s .../audio/rooms` 里只有 X | 列出别的房间 |

### 6.5.3 字幕要真并行：一条命令（推荐）

**4.88 起不用手敲四条命令了**；4.89 起默认按「生产者-消费者」跑（显存只够一份模型）：

```bash
cd ~/glasses && source /opt/leion/venv/bin/activate
export HF_HOME=/opt/leion/models DSH_CHECKOUT="$HOME/deepseek-harness"
export DEEPSEEK_API_KEY='sk-...'
node scripts/start-multi.mjs --public --data-dir /var/lib/leion/test --port 8789 \
     --whisper-model large-v3 --compute int8_float32
```

它起的东西（房间由手机决定，脚本每 3 秒看一眼）：

```
[转发]      relay/lan-relay.mjs --bus <buses 目录>            1 个，读目录
[识别]      bridge/asr-worker.mjs --queue-dir ...             **只有 1 个**，模型只加载一次
  切句·X    whisper_stream.py --segment-dir ... --tag room-X  每场 1 个（纯 CPU，不占显存）
  大脑·X    harness-side.mjs --bus buses/room-X.json          每场 1 个（不占显存，并行）
```

| 它会 | 它不会 |
|---|---|
| 两场会**都**持续出字幕（各自慢一点） | 同时跑两份模型（显存不够会 OOM，现象像"识别挂了"） |
| 队列积压时**报**深度与最长已等 | 丢数据（用户拍板：先只报不丢） |
| 房间散了 / 没人了，**宽限 60 秒**再收 | 立刻杀掉（他退出去看一眼消息，回来要重等模型加载） |
| 一场会的切句或大脑挂了只收这一场 | 一个房间坏了把另一场停掉 |
| 识别消费者或转发挂了 → 全体停 | 假装还能跑（它们所有房间共用） |

常用开关：`--translate-mode serial|parallel`（换回整场串行 / 各场并行）、
`--depth-report-s 10`（更频繁地报队列深度）、`--whisper-model medium`、`--compute int8_float16`、
`--only <房间id>`、`--dry-run` 先看它会起什么（不会真起）。

**验收（一条命令版）**：

| # | 看什么 | 预期 |
|---|---|---|
| 1 | 开一场会后，终端 | `▶ 房间 room-…（邀请码 …）`，下面跟着 `[切句·…]` `[大脑·…]` 两行 |
| 2 | 再开第二场会 | 又出现一组；**识别还是那一个**（不会起第二个模型） |
| 3 | 两场会**同时**各说几句 | 两边都能出字幕，但**延迟都变大**（一份模型在分时）——这是正常的 |
| 4 | 终端每 30 秒 | 出现 `队列深度 N 段，最长已等 X 秒`（N 长期很大 = 该加卡或降模型） |
| 5 | `ls -l /var/lib/leion/test/queue/asr/` | 有声音时看到 `<时间>-<房间>.pcm/.json` 在出现、被消费后消失 |
| 6 | `ls -l /var/lib/leion/test/asr-inbox-*.jsonl` | **每场一个**，各自在长（写进去的是各自房间的话） |
| 7 | 把第一场会关掉（发起者散会） | 60 秒后 `■ 房间 … 的管线已收`，第二场照常 |
| 8 | Ctrl-C | 全部停下（含切句/识别的 python），日志归档到 `var/logs/archive/<时间戳>/` |

### 6.5.3b 手动分终端（想自己控每个进程时）

这一节是"一条命令"的**等价手工版**，也是排查"某一场会不工作"时最直接的取证方式。

**先把两种 `--bus` 分清楚**（上一版文档把它们混在一起了，已纠正）：

| 这个 `--bus` 给谁 | 写成什么 | 它在干什么 |
|---|---|---|
| **relay（转发进程）** | **目录** `/var/lib/leion/test/buses` | 读目录里每个 `&lt;roomId&gt;.json`，当成不同房间的字幕 |
| **大脑（翻译管线）** | **文件** `/var/lib/leion/test/buses/room-X.json` | 把这一场的字幕**写进这一个**文件 |

也就是说：**relay 是读者（读目录），管线是写者（各写一个文件）**。
`node scripts/start-all.mjs --bus <目录>` 是**错的**用法 —— start-all 是"单套管线"启动器，它的 `--bus`
只能是文件（且 4.86 之前它甚至没把这个参数传下去，已修）。

**两场会并行的完整命令（四个终端）**

```bash
D=/var/lib/leion/test
SECRET=<你的共享密钥>

# 终端 1：relay —— 只有这一个进程职责是"手机↔电脑"，它读目录
node relay/lan-relay.mjs --data-dir $D --port 8789 --public --secret $SECRET \
     --bus $D/buses

# 终端 2：房间 X 的翻译与识别（各自一套）
#   先起大脑：它启动时会**清空收件箱**（防止重放上次的句子）；后起识别，第一句才不会被清掉
node scripts/harness-side.mjs --data-dir $D --inbox $D/asr-inbox-X.jsonl \
     --bus $D/buses/room-X.json
node bridge/asr-bridge.mjs --inbox $D/asr-inbox-X.jsonl \
     --whisper-follow $D/audio/room-X.pcm --format json

# 终端 3：房间 Y 的同样两个进程（只换名字，顺序同上）
node scripts/harness-side.mjs --data-dir $D --inbox $D/asr-inbox-Y.jsonl \
     --bus $D/buses/room-Y.json
node bridge/asr-bridge.mjs --inbox $D/asr-inbox-Y.jsonl \
     --whisper-follow $D/audio/room-Y.pcm --format json
```

> `room-X` / `room-Y` 就是**房间的 id**（在手机房间页顶部的邀请码旁边，或 `GET /org/rooms`）；
> `$D/audio/room-X.pcm` 就是 6.5.1 里看到的那个分流文件 —— 两者同名是巧合也是约定：流程都用房间 id 命名。
>
> 想确认命令拼得对不对，先跑 `node scripts/start-multi.mjs --dry-run --data-dir $D --port 8789`
> —— 它会把"现在有哪些房间、每场会的命令长什么样"逐行打出来，不启动任何进程。

**验收**：

| # | 看什么 | 预期 |
|---|---|---|
| 1 | 手机1 房间 X 的字幕 | 只有 X 自己的句子 |
| 2 | 手机2 房间 Y 的字幕 | 只有 Y 自己的，**不会出现 X 的话** |
| 3 | 把终端 2 两个进程停掉 | Y 的字幕照常（互不影响） |
| 4 | `ls -l $D/buses/` | `room-X.json`、`room-Y.json` 各自在更新 |

### 6.5.4 先用脚本造数据（不用手机）


### 6.5.5 三语术语（5.02）怎么验

术语表现在是**三栏**：中文 / 巴葡 / 英语，三种写法彼此等价。真实词表常常缺一栏，
所以**允许两栏**（缺的那栏留空 = 这一侧没有等价关系），只有一栏则直接拒绝。

**第一步：电脑端逻辑（不用手机、不用模型）**

```bash
node tests/run-all.mjs        # 里面三组直接相关：
                              #   用户热词对照表 —— 「5.02 三语」四组（三栏/两栏/一栏、英语侧检查、跨栏冲突、id 稳定）
                              #   术语匹配器     —— 「normalize（英语）」三组（英语车道 / 老条目不乱换 / 缺栏不删词）
                              #   术语观测       —— 中→英 观测、缺栏不观测、英语的校对专名闸
```

**第二步：填一条真的三语术语，看三个方向都生效**

1. 电脑：管理台 → 术语库 → 某库（例：`leion-core`）→ 加一条 `亮亮眼镜 / Leion Pro / Leion Pro`；
2. 手机：开一场会，**译成英语** → 说「我们和亮亮眼镜合作」→ 译文里应是 `Leion Pro`，**不是** `Liangliang Glasses`；
3. 再把目标语言换成葡语、中文，各说一遍 —— 三种语言下都应该是 `Leion Pro`；
4. 反方向：用葡语/英语说 `Leion Pro`，译成中文时应是「亮亮眼镜」。

**第三步：缺栏必须"不假装有"**

加一条**只有中 + 英**的术语（例：`货代 / freight forwarder`，葡语留空），然后：

| 检查 | 期望 |
|---|---|
| 上传/提交时 | 通过，但报告里有 `WARN_SIDE_MISSING`「缺巴葡写法」 |
| 译成英语 | 术语生效（`freight forwarder`） |
| 译成葡语 | **不注入**术语提示（由模型自己译），日志里也**不**记"没按对照写法显示" |
| 只填中文就提交 | 被拒，提示「至少两种语言」 |

**第四步：老数据不能被弄坏**

- 升级前已有的两栏词条（`zh` + `pt`）必须原样可用，`id` 不变（回读管理台看条目还在、条数没变）；
- 房间不选目标语言时仍然是中↔葡互译（与 4.99 行为一致）。

## 6.6 「会议里听不到别人说话」怎么查（4.91）

这条链有四段，**每一段坏了的表现都一模一样**（对方什么都听不到），所以别猜，按顺序测：

```
① 说话的人有没有发     /audio?room=…   有没有带上房间号
② 听的人有没有订阅     WS {"type":"listen","on":true}
③ 服务端有没有扇出     broadcastRoomAudio 找到人、发出二进制帧
④ 手机有没有播         AudioTrack 起没起来（这一段只能在手机上查）
```

**第一步：用脚本把 ①②③ 一次测完（不需要手机）**

```bash
# 本机端到端：自己起转发进程 + 两个账号 + 一个房间，模拟"甲说话→乙听到"
node scripts/check-live-audio.mjs --self-test

# 查真服务器：只做"听"这一半，连续听 30 秒（期间让另一个人说话）
node scripts/check-live-audio.mjs --host http://117.50.180.93:8789 \
     --secret "$(cat /var/lib/leion/test/relay-secret.txt)" \
     --user <用户名> --token <该用户的 token> --room <房间id或邀请码> --watch 30
```

它会逐条打印结果，四条判定：订阅有回执 / 订阅者收到音频（字节数对得上）/ 服务端告知采样率 /
持麦者不收回声。**哪一条先红，问题就在那一段。**

**第二步：如果服务端全绿，问题在手机上，按这四条查**

| # | 检查 | 怎么看 |
|---|---|---|
| 1 | 「听别人说话」开关有没有开 | 房间页那个按钮；**4.91 起缺省是开的**（旧版本缺省关，必须手点） |
| 2 | 是不是**自己**在说话 | 自己说话时服务端故意不收自己的声音（防回声），说完**会自动听回来**（4.91 修） |
| 3 | 手机/服务器版本 | 实时传声是 4.76 的功能；`audio-meta`（采样率）是 4.91。两边都要跟上 |
| 4 | 播放器起没起来 | `adb logcat -s RoomAudio` —— 4.91 起播放器失败会打 `Log.w`，不再静默 |

**4.91 修掉的那个真 bug（用户报的"音频传不到另一个人"就是这个）**

旧代码在拿到发言权时执行 `if (holding && listening) stopListening()` ——
**把倾听永久关掉了**，松开麦克风之后不会恢复。而两个人开会本来就是你一句我一句，
于是每个人一开口就把自己的耳朵关掉，看起来就像"声音传不过去"。
现在把「我想听」（`listenWanted`）与「此刻在放」（`listening`）分开：
说话时暂停播放但**保留意图**，说完自动恢复；重连后也会自动重新订阅。

**顺带修掉的两个隐患**

- **采样率**：播放器原来写死 16 kHz，而手机录音可能降级到 44.1 kHz —— 声音会快放/慢放，
  听起来像"卡"或"叽叽声"。现在服务端在采样率变化时先发一帧 `{"type":"audio-meta","rate":…}`，
  播放器据此重建 `AudioTrack`。
- **静默失败**：`AudioTrack` 建不起来原来是**一声不响**地 return（logcat 里一个字都没有）。
  现在失败原因、丢弃块数都会打到 `logcat -s RoomAudio`。

## 8. 已知边界（看着像 bug，其实是设计）

| 现象 | 原因 | 以后是否要做 |
|---|---|---|
| 只有**一场会**能真正实时翻译；两场会同时开时字幕会串 | 字幕总线、音频文件、识别算力都是**单份** | 是：并发第二步/第三步（见 §9） |
| 两场会都有人说话时，历史里可能少一条转写 | 归属推不出来时**宁可不记**（写错会议比少一条糟） | 是：帧里带 roomId 就精确（已预留） |
| 听者开外放时会听到回声 | 回声来自"听者手机扬声器 → 听者麦克风" | 是：AEC |
| 拔插耳机后不会主动切到眼镜 | 设备优先级还没做，现在只跟随系统默认路由 | 是（见 §9） |
| 旧 relay + 新 APK：点「听声音」没声音、历史页读不到 | 服务端还没这些接口 | 重启 relay 即可 |
| 会议纪要那一页没有 | 老师建议砍掉，整块不做（导出也不含摘要/行动项） | 否 |

## 9. 未来可能加入的功能（按建议顺序）

**A. 并发与音频（最该做，因为直接决定"能不能两场会同时开"）**
