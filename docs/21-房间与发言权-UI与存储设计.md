> 2. 下一步做**房间 + 发言权互斥**，配套**全新 UI**：现有安卓界面彻底重构，向老师原型 V0.3「译连 TransLink」的会议室形态靠拢。

## 1. 信息架构（5 个界面）

```
启动 ─→ ① 登录/注册（全屏）
              │
              └→ ② 房间大厅（列表 / 创建 / 加入）
                        │
                        └→ ③ 房间内（核心：字幕 + 发言权）
                                  ├→ ④ 成员与发言权面板（抽屉）
                                  └→ ⑤ 设置（抽屉）
```

原则：**③ 是唯一常驻界面**，其余都是它的"上一层"或"抽屉"。现场使用时不应该有任何需要"退到外面再点进来"的操作。

## 2. 每个界面写清楚（文案即最终中文文案）

### ① 登录 / 注册（全屏，无顶栏）
- 品牌区：`译连 TransLink`（大字）+ 一行说明「中 ↔ 巴西葡语 同声传译」
- 输入：`用户名`、`密码`（密码可切换明文）
- 主按钮：`登录`（禁用态直到两项都非空）
- 次链接：`注册新账号`（→ 邮箱 → 验证码 → 用户名/密码，四步在一个页面内递进）
- 错误提示条（在按钮上方，红字）：账号停用/过期时显示服务端原文，例如「这个账号已被停用，请联系管理员」
- 底部小字：当前服务器地址（点按可进 ⑤）

### ② 房间大厅
- 顶栏：`译连` + 右侧头像（→ ⑤）
- 主区：**房间列表**，每行 = 房间名 + 成员数 `3 人` + 状态标签：
  - `空闲`（灰）、`有人发言`（绿点）、`等待发言`（黄点）
- 主按钮（底部大按钮）：`创建房间`
- 次按钮：`加入房间`（输入 6 位房间码 或 点列表项）
- 空态文案：「还没有房间。创建一个，把房间码告诉对方。」

### ③ 房间内（核心界面）
自上而下四块，**字幕占最大面积**：

1. **状态条**（细，一行）：`房间：圣保罗洽谈` · `3 人` · 连接指示（绿点/黄点/红点 + 文字 `已连接 / 重连中 / 未连接`）
2. **字幕区**（占屏幕 55~65%）
   - 主字幕：**对方语言的译文**，大字号（如 34sp），最多 3 行，超长自动缩小
   - 副字幕：自己语言的原文，小字号（16sp）、低对比度，紧贴主字幕下方
   - 新字幕入场：从下往上推一行，旧行淡出（不做花哨动画）
   - 字幕为空时显示引导：「按住下方按钮开始说话」
3. **发言权区**（高约 120dp，视觉重心）
   - 中央大圆按钮，直径约 96dp，四种状态：
     | 状态 | 文案 | 颜色 |
     |---|---|---|
     | 无人持有 | `按住说话` / `点击发言` | 主色实心 |
     | 自己持有 | `正在发言` + 计时 `00:12` | 绿色实心 + 呼吸动画 |
     | 排队中 | `排队中 · 第 2 位` | 黄色描边 |
     | 他人持有 | `对方正在发言` | 灰色禁用 |
   - 圆按钮下方一行辅助按钮（等距三个）：`申请发言`、`放弃发言`、`静音`
   - 发言中若 30 秒无语音，自动释放并在字幕区出现一条系统提示：「发言权已自动释放（30 秒无语音）」
4. **底部条**：语种切换（`我听：葡语` ⇄ `我听：中文`）+ 麦克风电平条（细，随音量变化，仅作反馈）

### ④ 成员与发言权面板（抽屉，左滑出）
- 「当前发言人」卡片：头像首字母 + 用户名 + 已发言时长 + 主持人按钮 `收回发言权`
- 「排队」列表：顺序 + 用户名 + `批准 / 拒绝`（主持人可见）
- 「成员」列表：全部成员 + 角色标签（`主持人` / `成员`）+ `移出房间`（主持人可见）
- 主持人可点 `移交主持人`（选择成员）

### ⑤ 设置（抽屉）
- 服务器地址（可编辑 + `测试连接` 按钮，复用现有 `check-relay` 逻辑的服务端端点）
- 共享密钥（只显示前后各 4 位）
- 我说话的语言 / 我听到的语言
- 术语库（勾选参与本房间的库；进入房间时冻结一份快照）
- 录音自动上传：开 / 关
- 关于：版本号、`导出诊断日志`

## 3. 发言权互斥：状态机（后端唯一真相）

```
        ┌──────── idle ────────┐  （无人持有）
        │        ▲             │
   request│       │release      │grant
        ▼        │             ▼
   queued ──► holding ──► releasing ──► idle
        │（FIFO 自动上位）      ▲
        └──────────── 超时/强制收回 ┘
```

规则（都写进代码与测试）：
1. **同一房间同一时刻最多一人 `holding`** —— 由服务端原子保证（DB 事务 + `floor_state` 单行主键）。
2. 申请进 FIFO 队列；持有者释放/超时/被收回后，**队首自动上位**并广播。
3. 持有超时：**30 秒无有效语音**（服务端按收到的音频块与 VAD 判定）自动释放，附原因。
4. 主持人可：批准指定排队者（跳到队首）、强制收回、移交主持人。
5. 客户端只做**乐观 UI**（点击即变色），最终状态以服务端广播为准；冲突时回滚并提示。

## 4. 存储：SQLite（表结构）

客户端（Android，`SQLiteOpenHelper`，不加新依赖）：

| 表 | 关键列 | 说明 |
|---|---|---|
| `settings` | `key PK, value` | 服务器地址、密钥、语种、增益档 |
| `rooms` | `id PK, name, code, host, created_at, last_seen_at` | 本地房间历史（离线可看） |
| `utterances` | `id PK, room_id, speaker, src_lang, src_text, dst_text, started_at, is_final` | 字幕历史，支持翻页回看 |
| `drafts` | `id PK, room_id, text, updated_at` | 未发出的文字/语音草稿 |

服务端（Node）：`rooms / room_members / floor_requests / floor_state / utterances`，结构与上表同源，另加：
- `floor_state(room_id PK, holder, since, mode)` —— 互斥的落点，**单行主键即互斥锁**
- `floor_requests(id PK, room_id, user, state, requested_at)` + `INDEX(room_id, state)`
- `PRAGMA journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout=3000`

**迁移**：现有 `accounts.json / libraries/*.json / requests.jsonl` 一次性导入 SQLite（写 `scripts/migrate-sqlite.mjs`，导入后两端只读 SQLite，JSON 留作归档）。

## 5. 待老师/今晚会议拍板的 4 个问题

1. **服务器侧 SQLite 用什么**：`node:sqlite`（需 Node ≥22，我们目前要求 20）还是 `better-sqlite3`（加一个原生依赖）？—— 客户端一律原生 SQLite，不受影响。
2. **发言权是否强制互斥**：默认"强行互斥"（只有一人能说），还是允许主持人放开"多人自由发言 + 只标注谁在说"？
3. **是否需要"房间码 + 密码"双要素**，还是房间码足够？
4. **字幕历史保留多久**（默认 7 天自动清理？涉及隐私）。

## 6. 验收标准（可测）

- 单元/接口：两人并发申请 → 只有一人 `holding`；排队顺序 FIFO；超时自动释放并上位。
- 客户端：断网重连后发言权状态以服务端为准；离线可看历史字幕。
- 现场：两部手机同一房间，A 说话时 B 的按钮显示「对方正在发言」且无法上传音频。
