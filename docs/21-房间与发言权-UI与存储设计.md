## 1. 与上一版的关键差异（我的假设错了，以原型为准）

| 项 | 我上一版（作废） | 原型（采用） |
|---|---|---|
| 发言权 | 申请 → 排队 FIFO → 主持人批准 → 30 秒超时释放 | **点击开麦即持麦**（无需长按），再点关闭；**后开麦者顶替先开麦者**（抢麦），被顶替者收到提示 |
| 防打断 | 无 | **锁定发言**：锁定期间他人开麦被拒，提示「XX 正在发言（发言已锁定）」；**仅管理者可解除他人锁定**；同一个按钮在"锁定/解锁"之间切换 |

| 入会 | 房间码 + 可选密码 | **6 位邀请码是入会唯一凭证**，无密码；校验通过后带出会议主题供确认 |
| 界面布局 | 底部大圆按钮 + 左抽屉 | **主区留给发言与译文字幕流**；右侧**竖向悬浮条**（当前发言人 + 投屏/扩声/收音状态）+ 右侧抽屉（人员与设备合并） |

## 2. 界面（5 个，③ 常驻）

```
启动 → ① 登录/注册（全屏）→ ② 首页（创建/加入）→ ③ 实时房间（核心）
                                                      ├→ ④ 右侧抽屉（发言人 + 设备）
                                                      └→ ⑤ 设置（服务器/语言/术语/隐私）
```

### ③ 实时房间（核心页）
- **主区 = 字幕流**（占绝大部分）：每句两条 —— 主行是**我的语言**的译文（大字 32~34sp），副行是原始发言（小字 16sp、低对比）。新句从下往上推。
- **底部单行控制**：`🎙 点击开麦`（开麦后变 `正在发言 00:12` 绿色呼吸）/ `锁定发言`（锁定后变 `解锁`）/ 原文-译文切换。**不用长按**。
- **右侧竖向悬浮条**（固定常驻、不轮播）：
  - 上格：**当前发言人**（头像 + 姓名；发言中绿环，空闲显示「麦克风空闲」）
  - 下格三项状态：**投屏 / 扩声 / 收音**（本项目手机-only：投屏=手机屏，扩声=耳机或关闭，收音=手机麦克风）
- **系统提示行**（插在字幕流里，灰色斜体）：
  - 会议开始：`— 会议开始 · 发言权互斥已启用：同一时刻仅一人开麦 —`
  - 抢麦成功：`你已接管麦克风 · 对方已被自动静音`
  - 被抢：`XX 接管了麦克风`
  - 被拒：`XX 正在发言（发言已锁定）`

### ④ 右侧抽屉
- 上半「发言人」：当前发言人 + 全员头像（**发言过即点亮**）+ 提示
- 下半「设备」：手机（收音/播报）能力开关；未连接设备置灰
- 管理者额外可见：解除他人锁定、移出成员

### ② 首页
`创建同传会议（生成邀请码）` / `加入同传会议（输入 6 位邀请码）` / `同传翻译官（单向收听）`，右上头像进 ⑤。

### ① 登录/注册
按原型：`用户名 + 邮箱 + 验证码`（新用户注册 / 老用户登录同一入口），底部勾选《用户协议》《录音与隐私政策》。

## 3. 服务端：发言权状态（`node:sqlite`）

```sql
CREATE TABLE floor_state (
  room_id TEXT PRIMARY KEY,        -- 单行主键 = 互斥锁本身
  holder  TEXT,                    -- 当前持麦者（NULL = 空闲）
  locked  INTEGER NOT NULL DEFAULT 0,  -- 是否锁定发言
  since   INTEGER NOT NULL
);
```

规则（实现即测试）：
1. **开麦请求**在一个事务里完成：查 `floor_state` → 空闲则直接置我；他人持有且**未锁定**则顶替（广播"被接管"）；他人持有且**已锁定**则拒绝（提示"XX 正在发言（发言已锁定）"）。
2. 同时到达按**到达顺序**处理（单写者 + 事务串行化即可，不做队列）。
3. **锁定**：持麦者可锁自己；**仅管理者**可解除他人锁定；锁定与解锁共用一个按钮。
4. 关麦即释放；断线超过 `N` 秒（建议 15 秒）视为释放，广播"XX 掉线，麦克风已释放"。
5. 客户端乐观 UI，最终以广播为准；冲突回滚并提示。

其他表：`rooms(id, name, code, host, langs, created_at)`、`room_members(room_id, user, joined_at)`、`utterances(room_id, user, src_lang, src_text, dst_text, start_at, is_final)`、`accounts`、`libraries`、`library_entries`、`requests`（原 JSON 内容迁入）。
`PRAGMA journal_mode=WAL; foreign_keys=ON; busy_timeout=3000`。

## 4. 存储与迁移

- **服务端**：`node:sqlite`（Node 22 内置，零依赖）。`scripts/migrate-sqlite.mjs` 一次性导入现有 `accounts.json`、`libraries/*.json`、`requests.jsonl`，之后只读写 SQLite，JSON 留档。
- **客户端**：原生 `SQLiteOpenHelper`（不加依赖）：`settings`、`rooms`（本地历史）、`utterances`（字幕回看，**7 天清理** `DELETE WHERE start_at < now-7d`）、`drafts`。
- **隐私**：7 天自动清理字幕与音频元数据；设置页提供「清空本房字幕」。

## 7. 验收

- 接口：并发开麦只有一个 holder；未锁定可被顶替并广播；已锁定时开麦被拒；管理者可解除他人锁定；断线 15 秒释放。

**本机只用于开发与跑自动化测试；所有应用侧测试都在服务器进行。**

| 环境 | 数据目录 | 谁用 | 说明 |
|---|---|---|---|
| 开发 | `<仓库>/var/live`、`var/live-test` | 本机（Windows） | 只跑 `node tests/run-all.mjs` 与离线脚本；不装 App、不联调 |

4. 启动横幅与 `preflight.cjs` 都会打印实际数据目录，避免"以为在测试、其实写进了生产"。

### 4.33 修复（2026-10-27，用户报的两条）

1. **房间页不再有「术语库」按钮**。选库本来就该在**建房那一步**完成（`RoomsActivity` 建房后立刻弹选库、
   存快照），房间里那个按钮是重复入口，而术语在进房时已冻结 —— 会中改不了，留着只会误导。
   现在 `page_room.xml` 底部只剩：开麦 / 开始同传 / 退出 / 锁定发言。
2. **「莫名其妙掉登录」的根因是 `authWhoAmI()` 返回错了形状**：`LanClient` 那个方法原来是
   `return requestWithCode(...)`，返回的是 `{ code, json }` **外壳**，而 `HomeActivity` 读的是
   `optBoolean("ok")` —— 外壳里没有 `ok`，于是**每次启动都判成没登录**。
   更麻烦的是连锁反应：重登会吊销该账号的旧 token（**单会话**是刻意设计），所以另一台手机
   下一次请求就 401 —— 用户看到的就是"另一台莫名其妙掉登录"。
   现在：方法返回**拆过包的正文**（带 `_status`），界面按三种情况分别处理 ——
   `200 + ok` 进首页；`401` 才清本地 token 回登录页；**连不上服务器不许踢登录**（网络抖一下就踢，
   用户会以为掉登录，然后重登又把另一台踢掉，把问题扩大成两台都掉）。

> ⚠️ **单会话仍然生效**（用户 2026-10-27 要求）：同一账号在第二台手机登录，第一台会被踢。
> 这不是 bug。若要两台同时在线，得改成"多设备 token"（服务端 `login` 不再吊销旧 token）。

### 4.34 修复：被顶替后客户端不停上传（"发言人显示 B，A 的同传按钮还亮着"）

**现象**（用户 2026-10-27 报）：A 先开麦、B 后开麦 → 右侧发言人条显示 B（服务端裁决是对的），
但 A 那边「开始同传」还是蓝色，麦克风仍在录音上传。

**根因在客户端，服务端没问题**（`lib/floor.mjs` 的顶替/锁定/租约逻辑与测试都正确）：

1. **2 秒轮询只刷文字**：`takingChanged()` 改了按钮文案与发言人条，却**从不停止
   `MicUploader`** —— A 的音频继续灌进同一个识别流，两路音频交错，字幕错乱，
   而界面上看着"一切正常"。这是最隐蔽的一种：**界面说 B，数据里是 A+B**。
2. **按钮没有两态**：上传中与空闲都是同一个蓝色，用户根本没有视觉依据判断
   "我是否还占着麦"。

**修法**：

| 位置 | 改动 |
|---|---|
| 轮询 `scheduleFloorPoll` | 发现"我不是持麦者"（`wasHolding \|\| mic != null`）→ `onFloorLost(holder)` |
| `onFloorLost` | 停 `mic`、按钮回灰、hint + **Toast**「XX 接管了麦克风 · 已自动停止同传」<br>（hint 行会被下一条字幕刷掉，所以必须再用 Toast 说一次） |
| `heartbeatIfDue` | 服务端回"不是持麦者"→ **立刻停**，不等下一轮 2 秒轮询 |
| 点「开麦」结束发言 | 若正在上传也一起停（否则"麦放了、音频还在传"） |
| `updateUploadButton` | 蓝 `#1565C0` = 正在上传（停止同传）／灰 `#263238` = 空闲（开始同传） |

**已知边界（刻意没做）**：服务端**不校验** `/audio` 的持麦身份 —— 客户端已经停了，服务端只管
"谁是持麦者"。一个卡死不动、还在上传的旧版本客户端仍可能双路灌音频；要彻底挡住得让
`/audio` 带上 `room`+`user` 并按 `floor_state` 拒收 —— 那会碰音频热路径（每块都要查库），
等真出现再说。

### 4.35 新增：发言权推送通道 `/ws`（WebSocket，2026-10-27）

**为什么**：发言权原来靠"每 2 秒 GET 一次 `/floor`"。于是被顶替的那一方最多要 2 秒才知道
自己被静音了 —— 4.34 修的是"知道了会不会照做"，这一条修的是"**知都不知道**"。
改成推送后是**一推即到**（本机实测 1~3 ms）。

**两端都不是现成组件，这是刻意的**：

| 半边 | 实现 | 为什么不用现成的 |
|---|---|---|
| 服务端 | `lib/ws-hub.mjs`，手写 RFC 6455（握手 + 帧编解码 + 掩码校验 + 分片 + ping/pong + 关闭） | Node **没有内置 WS 服务端**；而仓库零第三方依赖（`package.json` 的 dependencies 是空的，`run-all` 有一条断言钉着"没有裸包名 import"），装 `ws` 就破了这条，部署机也少一次 `npm install` |
| 客户端 | Java-WebSocket 1.6.0（+ slf4j-api 1.7.30） | Android 没有内置 WS 客户端。这两个 jar 在**本机 Gradle 缓存里就有** → 离线可构建（版本不许乱改） |

**协议**（都是 JSON 文本帧，单条上限 64 KB）：

```
服务端 → 客户端   {type:'floor', roomId, holder, locked, since, leaseMs, at}
客户端 → 服务端   {type:'ping'} → {type:'pong'}；{type:'snapshot'} → 重发一次当前状态
```

- **连上立刻收到一条 `floor`**，客户端不用再问一次；
- 推送的是**完整快照**，整条替换，不做增量 —— 丢一条不会让状态变形；
- 认证与普通请求同一套：`X-Leion-Secret`（或 `?secret=`）+ `X-Leion-Token`（或 `?token=`），
  token 决定"我是房间里的谁"；房间用 id 或 6 位邀请码都行（`?room=`）；
- 同一用户重复连进来 → **旧连接被顶掉**（手机切网/重连很常见，否则会"两个我"各自收状态）；
- 房内最多 8 条、全局 64 条连接；服务端每 20 秒 ping 一次，两个周期没回音就断开。

**断线不是故障**：`RoomActivity` 的 2 秒轮询一直在跑，WS 只负责更快。分工是：

| 通道 | 频率 | 作用 |
|---|---|---|
| `/ws` 推送 | 状态一变就推 | 主通道 |
| `GET /floor` 轮询 | WS 活着时 **10 秒**（看门狗）／WS 断了 **2 秒** | 兜底：发现"推送假死"和老服务端 |

⚠️ 两个必须记住的细节（都有测试钉住）：

1. **心跳不能靠推送消息顺带**：轮询放慢到 10 秒后，只靠它续租会贴到服务端 15 秒租约的红线上，
   所以心跳自己按 5 秒走（`scheduleHeartbeatTick`）。
2. **轮询与推送必须走同一个 `applyFloorState`**：否则会出现"推送很快，但忘了停上传"这种
   不对称 bug —— 那正是 4.34 的现象（界面说 B，A 的麦克风还在传）。

**这一条通道只推"谁在说话"**，不推字幕、不推音频：
字幕仍走 `/frame` 长轮询；音频目前只有"手机→电脑"一个方向（要做"电脑→手机"的音频流，
WS 是合适的载体，但前置条件还没满足 —— 见 §遗留）。

### 4.36 接上字幕保留期清理（P4，2026-10-27）

**为什么**：字幕里是**真实会议内容**。库存在服务器上、管理员还看得到，"永久保留"既不是需要的能力，
也不是用户同意过的事。`purgeOldUtterances` 早就写好了，但**全仓库零调用点** —— 等于没做。

**现在的行为**：

| 项 | 值 |
|---|---|
| 保留期 | 7 天（`--utterance-retention-days <n>` 可调） |
| 时机 | **启动先清一次**（补上停机期间该删的）+ 之后**每小时一次** |
| 失败处理 | 只打一行日志，**绝不影响同传**（维护动作不在主链路上） |
| 可见性 | `/status` 里的 `utterancesPurged`（累计删除条数）与 `utteranceRetentionDays` |

实现上多了一个薄封装 `purgeUtterancesIn(dataDir, now, days)`：`openDb` / `close` 成对出现很容易漏，
漏一个就是没释放的 sqlite 句柄，而定时任务一小时跑一次 —— 一天漏 24 个。封装之后只有一处能拿到 db。

### 4.37 删掉 `--from` / `--to`：语种跟着每一句话走（2026-10-27）

**为什么删**：这两个参数是"整路固定语种"。只有在"这一路音频只会有一种语言"时才安全，
而它是**安静地错**：实测把葡语音频硬当中文识别，词错率 **100%**，输出还不是乱码 ——
是**中文译文**（`sequer olhavam pra você` → `甚至看不見你`）。看起来像正常工作。

**现在怎么走**（没有任何命令行参数）：

```
手机开始/切换录音 → /audio?lang=zh-CN
        ↓ relay 写进 audio-in.lang 旁文件
whisper_stream.py 按它解码 → 把**这一句实际用到的语种**写进 json 行
        ↓ {"text":"…","from":"zh-CN"}
asr-bridge 原样透传（每行自带语种，行里的字段优先于任何全局标记）
        ↓
插件 parseInboxLine：from 有就用 from，目标语种 = 另一种语言（core.mjs:2525-2529）
```

具体改动：

| 位置 | 改动 |
|---|---|
| `bridge/whisper_stream.py` | 新增 `--format text|json`；`json` 时每句输出 `{"text":…,"from":…}`；`transcribe()` 把**实际用到的语种**（显式指定或模型检测）一起返回 |
| `bridge/asr-bridge.mjs` | 删除 `--from/--to`；`createInboxWriter` 支持结构化行（对象或 JSON 字符串）**透传**，行内 `from/to/speaker` 优先于构造时的全局 tags |
| `scripts/start-all.mjs` | 删除 `--from/--to` 的解析、校验与转发；识别进程一律拿 `--format json` |
| 测试 | bridge-suite 换成"每句自带语种透传"；start-all-suite 断言"传 `--from` 就是未知选项"；python-suite 加 8 条（json 行带 from、表外语种不硬编、缺省 text 不受影响） |

⚠️ 仍然保留 `whisper_stream.py --language zh|pt`（**它自己的**开关，不是 --from）：那是给
"我确定这一路只有中文"的离线评测用的，与产线链路无关。

### 4.38 音频文件轮转（长期跑别把磁盘写满，2026-10-27）

**问题**：`audio-in.pcm` 是"只追加、永不清空"的（4.13 那次刻意的选择：`fresh=1` 时清空会把
**还没被识别进程读走**的音频永久删掉 —— 用户录了三段，每段都被下一次清掉，一条都没识别出来）。
代价是它会一直长：16k 单声道 ≈ 32 KB/秒 ≈ **115 MB/小时**，而 `start-all` 重启时**并不会清它**。

**现在的行为**：

| 项 | 值 |
|---|---|
| 上限 | `--audio-max-bytes <n>`，缺省 **1 GB**（≈ 9 小时连续音频），`0` = 不轮转 |
| 触发 | 写入前判断：**这一块**放不下就先把旧文件轮转，再整块写进新文件（不会被劈成两半） |
| 轮转 | `audio-in.pcm` → `audio-in.pcm.1`（覆盖上一份）→ 新建空文件 |
| 磁盘占用 | 约 **2× 上限**（只留一份 `.1`） |
| 可见性 | `/status` 里的 `audioMaxBytes`、`audioRotations`、`audioBytes` |
| 重启后 | 启动时按文件真实大小初始化 `audioBytes` —— 否则上限每次重启都从头算，等于没设 |

**为什么是轮转而不是原地清空**：识别进程（`PcmFollower.read`）发现路径上的文件**变小**时，
会把读指针退回 0 重读（python-suite 钉着这条分支）。轮转正好让它"换到新文件继续跟"，
而旧的一份留着排查。原地清空则会让"还没读走的那几秒"直接消失。

### 4.40 修「点结束同传后弹『上传出错：thread interrupted』」（2026-10-27）

**现象**（用户报）：同一台设备上点「开始同传」再点「结束同传」，下方弹出一行小字
「上传出错：thread interrupted」。

**真因**：`MicUploader.stop()` 直接 `interrupt()` 录音线程。而那一刻线程多半**正卡在上传**
（每秒一块的 HTTP 请求）里 —— 被打断的 I/O 会抛一个消息就叫 `thread interrupted` 的异常，
`upload()` 的 catch 把它当故障报给界面。用户点结束是**预期行为**，却渲染成红字。

**同一处还有第二个隐患**：`interrupt` 唯一的效果就是打断正在上传的那一块 ——
于是「停止时会把最后不足一块的尾巴也发出去」这条设计**实际失效**：最后半句话被丢掉。
而录音循环里没有 `sleep`/`wait`，`interrupt` 并不能让它更快退出。

**修法**：

| 改动 | 说明 |
|---|---|
| 新增 `stopping` 标志 | `stop()` 里**先**置位，再让线程退出。`upload()` 的 catch 与录音循环的 catch 都据此判断：主动停**不报错** |
| `start()` 里复位 `stopping` | 否则停过一次之后，后续**真正的**上传错误会被永远吞掉 —— 用户再也看不到"为什么没字幕" |
| `stop()` **不再立刻 interrupt** | 改成起一个看门狗线程 `join(2s)`：先给录音线程 2 秒把尾巴发完；还赖着才 `interrupt()`（兜底底层 read 卡死） |

**顺带修好的**：4.34 的「被顶替」路径也会调 `mic.stop()`，以前同样会把这个假错误顶掉
「B 接管了麦克风」的提示。

**测试**（android-order-suite）：`stopping` 标志存在；`stop()` 里置位 → `join(STOP_GRACE_MS)`
→ 才 `interrupt()` 的顺序；上传失败分支先看 `stopping`；录音循环判 `running && !stopping`；
`start()` 里复位 `stopping`。

### 4.41 两处 UI 修正 + 「被顶下线」不再静默（2026-10-27）

**① 建房后邀请码被选库框挡掉**

现象：点建房 → 立刻弹「本场术语库」对话框 → 页面上的邀请码被整个盖住，用户来不及抄。

修法（三处一起，任何一处单独都能让人看不到码）：

| 位置 | 做法 |
|---|---|
| 建房成功瞬间 | `Toast.makeText(..., "本场邀请码：" + code, Toast.LENGTH_LONG)` —— **Toast 显示在对话框之上** |
| 选库框标题 | 「邀请码 123456 · 本场术语库（会中不可改）」 |
| 选库框正文 | 再写一次「把 123456 告诉对方即可入会」 |

~~不~~采用"先关对话框再看码"的做法：那等于把"选库在建房这一步"的规则破了。

**② 被挤下线的那台设备完全静默**

现象：两台设备同一账号，后登录的踢掉前一个 —— 但**被踢的那台什么都不知道**，
界面上一切正常，直到某次点按钮失败（用户 2026-10-27 报的）。

| 结果 | 行为 |
|---|---|
| 200 | 什么也不做（静默是常态，不能每 10 秒闪一下） |
| 401 | 回调 → Toast 说明原因、清本地 token、回登录页 |
| 网络失败 | **什么也不做** —— 连不上 ≠ 被踢（4.33 的教训：网络抖动被当成掉登录，重登又把另一台真的踢掉） |

装在三处：**首页**（`showHome` 后）、**房间大厅**（`RoomsActivity.onCreate`）、
**房间内**（2 秒/10 秒的发言权轮询顺带判 `httpStatus == 401` → `showKicked()`）。
房间里还会清 token 并 1.5 秒后退出房间 —— 身份已失效，留在这里只会让用户以为网络卡了。

**顺手把 B3 做了**：`checkSession()` 调用 `throwIfSessionExpired(wrapper)`，
所以 `SessionExpiredException` / `throwIfSessionExpired` 不再是**零调用点的死代码**，
401 的人话消息只写在那一处。

### 4.42 锁定态的掉线不再永久占麦（B2，2026-10-27）

**问题**：`takeFloor` 里那条"断线释放"判断带 `!locked` —— 意思是**锁定中的持麦者永远不会因
掉线而释放**。于是"锁了麦然后手机没电 / 掉网"会永久占着麦克风：房间里谁都开不了口，
只能等发起人发现并手点「强制收回」。那是一种没人会想到的运维动作，等同于故障。

**为什么当初写成 `!locked`**：锁定就是"这五分钟别打断我"，所以不想让网络抖动把锁弄丢。
但"别打断"不等于"永远归我" —— 两者的区别在于**时长**，而不是有无。

**修法**：

| 项 | 值 |
|---|---|
| 普通持麦租约 | 15 秒（不变） |
| **锁定持麦租约** | **60 秒**（`FLOOR_LOCKED_LEASE_MS`；心跳 5 秒一次，60 秒足够区分"在说话"与"人没了"） |
| 抢麦时 | 超过对应租约 → 直接顶替，回执带 `reason: previous-lease-expired` 与 `releasedLocked` |
| **没人抢时** | `GET /floor`（房间页每 2 秒问一次）先 `sweepExpiredFloor()` 清掉过期状态，返回 `released` / `releasedLocked` |
| 广播 | 清扫掉了就 `wsHub.broadcastFloor(roomId, {released, releasedLocked})` —— 让**全房间**都看到，不只是正在轮询的那台 |
| 客户端 | 收到 `released` 就提示「XX 掉线，麦克风已释放（含锁定）」 |

### 4.43 字幕也搬进 WS（B4，2026-10-27）

**为什么做**：`/frame` 是长轮询（服务端把请求挂住最多 25 秒）。它本身延迟不高，但：

- 每个客户端**常驻一条挂起的 HTTP 连接**，服务端要维护 waiter 集合；
- 它带着一套"序号重置"的历史包袱（转发进程重启后序号回到 0，客户端序号比服务端大会永远等不到）。

4.35 已经把"谁在说话"搬上 `/ws`，字幕顺着同一条连接走是最自然的一步。

**服务端**：新帧产生的地方（`publishFrame`）在 `notifyWaiters()` 之后加一句
`wsHub.broadcastFrame({type:'frame', seq, frame})`；`lib/ws-hub.mjs` 新增 `broadcastFrame`，
推给**所有**连接（字幕总线本来就是一场会议一条，房间维度只有"谁在说话"那一层）。

**客户端**：`FloorSocket` 的 `onMessage` 多认一个 `type === 'frame'`，回调 `onFrame(JSONObject)`；
`RoomActivity` 抽出 `applyFrame(text, lines, source, partial, termsMissing)` ——
**长轮询与 WS 都走它**，否则两条路迟早渲染得不一样（"长轮询能显示、WS 显示不出来"这种
只在一半设备上出现的分裂）。

**`/frame` 不删**：WS 断了要有兜底。分工与发言权一致 —— WS 是主通道，长轮询是看门狗。

**测试**：ws-suite 新增"写一帧到字幕总线 → WS 客户端收到 `type=frame`（含 seq 与帧内容）"；
android-order-suite 钉住"两条通道都走 `applyFrame`"与"长轮询没被删掉"。

### 4.44 三个 bug：选库框被挤掉 / 锁定按钮文案不对 / 发起者退出不赶人（2026-10-27）

**① 选库框里一个库都没有（4.41 改坏的）**

我在 4.41 为了把邀请码塞进选库框，给它加了 `setMessage(...)`。而 AppCompat 的 `AlertDialog`
在**同时**设置 `message` 与 `multiChoiceItems` 时，会把多选列表挤掉 —— 框还在，列表没了。

修法：去掉 `setMessage`，邀请码只写在**标题**里（标题不会被挤掉）；建房那一刻的长 Toast 保留。
测试改成反向断言：**这里不许出现 setMessage**（带一条注释说明为什么）。

**② A 锁麦时，B 的按钮也显示「解锁」**

原来所有人统一 `isLocked ? "解锁" : "锁定发言"`，而 B 根本按不动 —— 按钮写着「解锁」却不响应，
比"灰着"更让人困惑。现在文案与权限一致：

| 我的身份 | 锁定时 | 未锁时 | 可点 |
|---|---|---|---|
| 持麦者 | 解锁 | 锁定发言 | ✅ |
| 发起者（锁在别人手上） | 解锁（他人） | 锁定他人 | ✅ |
| 其他人 | **发言已锁定** | 锁定发言 | ❌（灰） |

**③ 发起者退出后，其余人还留在房间里**

直到某次操作失败 —— 这是最糟的一种"看起来正常"。

修法（三层，缺一层就会有人在空屋里）：

| 层 | 做法 |
|---|---|
| 推送 | `wsHub.closeRoom(roomId, 'host-left')`：先推 `{type:'closed', reason}`，再发关闭帧断开连接 |
| 轮询兜底 | `GET /floor` 对已结束的会议返回 **410 + `closed: true`**；房间页判到就退出 |
| 界面 | `leaveBecauseClosed()`：停止上传、Toast 说明原因、1.2 秒后退出房间 |

### 4.45 「被顶下线」改走推送（2026-10-27，用户要求）

**用户原话**：用户需要通过轮询检查自己有没有被挤下去，能否针对同时登录的情况加速状态更新。

**能，而且能压到一秒内**。关键在于：**服务端在吊销旧 token 的那一刻就知道**，不需要客户端去问。
4.41 的 `SessionWatch` 是"每 10 秒问一次"，最坏要 10 秒 —— 现在改成推送优先。

**做法：一条很轻的会话通道** `/ws?session=1`（与房间通道同一个服务端，只是不带 `room`）

| 侧 | 改动 |
|---|---|
| `lib/ws-hub.mjs` | 支持 `?session=1` 连接（注册到 `sessions: Map<user, conn>`，同一用户顶掉旧的）；新增 `notifyKicked(user)`：先推 `{type:'kicked', reason}` 再关连接（4002） |
| `relay/lan-relay.mjs` | 登录/邮箱注册成功（会吊销旧 token）后调 `notifyKickedIfReplaced(username)` |
| `SessionSocket.java`（新） | 连 `/ws?session=1`，收到 `kicked` 回调；连上就告诉界面"可以放慢轮询了" |
| `SessionWatch` | 间隔可调：推送在线 **60 秒**、推送断开 **10 秒** |
| `HomeActivity` / `RoomsActivity` | 同时开 `SessionSocket` + `SessionWatch`；收到 `kicked` → Toast「账号已在别处登录」+ 清 token + 回登录页 |

**为什么轮询不删**：推送是"服务端说"，轮询是"我主动问"，两条独立的路。WS 断开、服务端重启、
代理掐长连接时，推送是**静默失效**的 —— 只有轮询能发现。但既然推送已经把延迟压到一秒内，
兜底就不必跑那么勤（60 秒）。

### 4.46 「散会没通知」的兜底与可诊断性（2026-10-27）

**用户复测**：4.44 之后发起者退出，其他人**仍然收不到通知**。

**查下来是两件事叠在一起**：

1. **服务端没更新就完全无效**。`closed` 推送、`/floor` 的 410、`notifyKicked` 全是服务端行为：
   APK 更新了但服务器还在跑旧代码（`git pull` 后没重启 relay）时，客户端拿不到任何信号 ——
   而它**看起来像客户端的 bug**。这是最贵的一课：**功能跨两端时，先确认服务端版本**。
2. **我给的兜底不成立**。4.44 里我写的是"轮询判 `httpStatus == 410`"，但 `unwrap()` 只有在
   响应体**没有** `error` 字段时才补 `httpStatus` —— 而 410 的响应体恰好带 `error`，
   所以那个判断**永远不成立**。

**修法（三层，全部可诊断）**：

| 层 | 做法 |
|---|---|
| 权威信号 | `roomById` 起带 `closed`（相加性改动）；`GET /org/rooms/<id>` 因此能直说这场散没散 |
| 客户端兜底 | 房间页每 5 轮轮询（WS 在线约 50 秒、离线约 10 秒）调一次房间详情，`closed=true` → `leaveBecauseClosed()`。**这条对老服务端也成立**（只要它返回 `closed`） |
| 可诊断 | `RELAY_FEATURES` 加 `frame-ws` / `room-closed-push` / `session-push`；`LanClient` 记下 `/hello` 的 features；房间页在**缺少 `room-closed-push` 时直接在状态行写**「⚠️ 服务端版本较旧：会议结束时不会主动通知」 |

### 4.50 登录/注册改显式切换 + 修「自己把自己踢下线」（2026-10-28）

**① 登录时不该出现邮箱与验证码**

4.49 我做成了"填了邮箱/验证码就是注册"，于是登录页一直摆着邮箱与验证码 —— 让人以为都要填，
而且用户填了邮箱去登录还会被当成注册（报错看不懂）。

现在：主按钮下方一个切换链接（`homeRegisterToggle`），**默认登录态**：
- 登录：只留 用户名 + 密码（邮箱那一整排 + 验证码都收起，切换时还会清空内容）；
- 注册：放出邮箱 + 获取验证码 + 验证码（服务端 `/auth/register-email` 要四样）；
- 按钮文案跟着变：`登录` / `注册并登录`。

**② 点登录弹「账号已在别处登录」——真因是同一台设备踢自己**

服务端日志 `[ws] xxx 的旧会话被挤下线` 是真的，但被踢的那条连接**属于自己这台**：

1. `logout()` 停了 `sessionWatch`，**漏了 `sessionSocket`** → 这条会话连接（用的还是刚被吊销的 token）
   继续挂在服务端 `sessions[user]` 上；
2. 用户再登录 → 服务端 `notifyKicked(username)` → 踢掉的正是这条陈旧连接；
3. 客户端收到 `kicked` 就弹"账号已在别处登录" —— 自己踢自己。

**三层修法**（缺一层就会复现）：

| 层 | 做法 |
|---|---|
| 客户端 | `logout()` 里**也** `sessionSocket.stop()`；断开后置空 |
| 服务端 | 会话连接记住自己的 `tokenHash`；`notifyKicked(user, reason, keepToken)` 遇到"就是刚发的那个 token"**不踢**（同一台设备重新登录不该被通知） |
| 客户端 | 收到 `kicked` **先 `checkSession()` 核实**：还能通过 whoami 就说明被踢的是陈旧连接 → 忽略（只打一行调试）；真的 401 才提示并回登录页。连不上服务器按"不踢人"处理（4.33 的教训） |

> 教训：**推送是"服务端说"，但服务端说的是"那条连接死了"，不等于"你这个人被踢了"**。
> 判断"我在不在线"的权威只有一个：`/auth/whoami`。

### 4.51 修「点会议房间就崩」+ 加一道类型门禁（2026-10-28）

**现象**：点「会议房间」→
`ClassCastException: android.widget.TextView cannot be cast to android.widget.Button`
（`RoomsActivity.setSpeakLang` 第 129 行）。

**真因**：4.47 改视觉时，我把大厅的两颗语言胶囊从 `<Button>` 换成了 `<TextView>`
（胶囊本来就不该是 Button），但 `RoomsActivity` 还在 `Button zh = findViewById(R.id.roomsLangZh);`。
`findViewById` 的泛型被擦成 `View` 再强转 —— **编译完全通过，一进页面就崩**。

**为什么之前的门禁没抓住**：已有的检查是"每个 `R.id.*` 在布局里存在"，它只验证**存在**，
不验证**类型**。这正好落在"编译能过、运行就崩"的缝里 —— 和 `android-order-suite` 开头说的
"字段先用再构造"是同一类问题。

**修法**：

| 项 | 内容 |
|---|---|
| 代码 | `RoomsActivity` 的 `zh/pt` 改为 `TextView`（`setText`/`setBackgroundResource`/`setTextColor` 本来就都在 TextView 上） |
| 门禁 | `android-order-suite` 新增「findViewById 类型必须与布局标签一致」：解析所有布局的 `id → 标签名`，再解析 Java 里的字段声明/局部声明/强转，三者不一致就报错。声明成 `View` 视为安全（它是祖先类） |
| 反向自检 | 把"`private Button zh;` + `findViewById(R.id.someLang)`（布局里是 TextView）"喂给判据，**必须报出来**；再验"声明成 View 不误报"。没有这一步，判据可能永远是绿的 |

**教训**：`findViewById` 的类型错误是 Android 上最典型的"编译期盲区"。
凡是"改布局控件类型"的改动，都要同时搜索 Java 里对这个 id 的取值类型 ——
现在的门禁替我们搜了。

### 4.53 房间页四个 bug（2026-10-27 用户实测）

**① 一句话显示成三张卡，其中一张停在「识别中」，译文只剩半句**

产线上**一句话会来三帧**：增量帧（partial）→ 定稿帧 → 校对修订帧。
4.52 的去重判据是「这一帧是不是 partial」，于是定稿帧被当成新的一句 → 三张卡；
停在「识别中」的那张保留的是**半句增量译文**。

**为什么不能只按原文判**（插件里三帧都带 `source`，看起来够了）：**增量帧的原文是流式不完整的**，
定稿帧才是完整原文 —— 两者不相等，只按原文判恰好会把「增量 + 定稿」拆成两条。

最终判据（三选一，按强度排序）：

| # | 条件 | 依据 |
|---|---|---|
| ① | **上一帧是增量态** → 这一帧是它的定稿/修订 | 产线**逐句串行**，一句话的增量之后不可能突然变成另一句 |
| ② | 原文与上一条相同 | 校对修订帧带的原文与定稿相同 |
| ③ | 增量帧没带原文 | 兜底 |

命中就**原位更新**：改文字、改状态（`识别中…` → `已完成`）、按开关同步原文可见性，并滚到底。

**② 顶部邀请码显示 `#------`、会议主题不显示、角色永远是「参与者」**

同一个根因：`loadRoomHeader()` 写在 `client = new LanClient(...)` **之前**，
线程里 `client` 还是 null → NPE → 被 `catch (Exception ignored)` 静默吞掉。
三个症状都来自「房间详情一次都没拉到」。修法：挪到 `client.start()` 之后调用。

> 教训：`catch (Exception ignored)` 会把「初始化顺序错」变成「界面上什么都没发生」。

**③ 抽屉里一个成员都没有**

`listMembers` 返回的是对象数组 `{username, lang, joinedAt}`，却按字符串取了（`optString(i)`）→ 空串。
改为 `optJSONObject(i).optString("username")`。

**④ 状态行显示「发言权推送已连上」这类调试文本**

用户不需要看通道连接细节。现在 `onState` 只写 logcat（`LeionRoom`）；
状态行只留给**会影响使用**的信息：连接失败、被顶替、会议结束、服务端版本过旧。
`onHello` 也不再打印「已连接 · 40×3」，只在缺 `room-closed-push` 时提示一句后果。

### 4.54 M2 收尾：移出成员 + 抽屉管理者操作 + 系统事件行（2026-10-28）

**① 服务端：移出成员**（`POST /org/rooms/:id/members/remove {user}`）

| 规则 | 实现 |
|---|---|
| 只有发起者能移人 | `removeMember()` 比对 `room.host`，否则 409「只有发起者可以移出成员」 |
| 不能移自己 | 409「发起者不能移出自己（要结束会议请用退出）」 |
| 不在房间里 | 409「`xxx` 不在这个房间里」 |
| **顺手释放他的麦** | 被移出的人若正持麦，置空 `floor_state` 并回 `releasedFloor: true`；relay 收到后广播一次发言权，全屋立刻看到麦空了 |
| 语义是**软移除** | 置 `left_at`，不删行 —— 对方凭邀请码还能重新加入。想「再也进不来」要另做黑名单，本轮不做 |

**② 抽屉里的管理者操作**

- 成员行：头像首字 + 姓名（自己带「（我）」）；
- 发起者看到别人的「移出」（**移出自己走退出**，那是结束会议）；
- 当前持麦者已锁定时，发起者看到「解除 `xxx` 的锁定」（复用 `force-release`）；
- 移出前有二次确认，并说明后果（「他仍可以凭邀请码重新加入」）。

**③ 系统事件行**（原型：以弱化的居中文字出现在字幕流里）

`addSystemEvent()`：不带头像、不加边框、次要色居中，前后加破折号。已接入五处：
会议开始（发言权互斥已启用）、被顶替 / 掉线释放、锁定、解锁、发起者收回发言权、成员被移出。

> 与字幕卡片的区别是刻意的：事件不是「谁说了什么」，扫读字幕时它应该退到背景里。

### 4.55 用户实测三处：抽屉不刷新 / 被移出的人留在屋里 / 两个按钮的样子（2026-10-28）

**① 人员与设备的抽屉做不到实时更新，要重开才变**

原来抽屉内容只在 `toggleDrawer()` 打开的那一下拉一次房间详情。开了之后屋里再进人、
设备再变，抽屉就一直是打开那一刻的样子。

改法：抽屉**开着**时每 2.5 秒重拉一次（`DRAWER_REFRESH_MS` + `drawerTick` 自循环），
关闭时 `removeCallbacks` 停掉。

> 为什么用轮询而不是推送：WS 房间频道目前只推发言权/字幕/散会/被移出四类事件，
> 成员进出与设备状态没有事件源。加事件源要动服务端的成员变更路径（进出房间、
> 上下线、设备注册），那是 M5 之后的活儿。轮询的代价只在抽屉开着时发生 ——
> 关着不发请求，所以不做成常驻定时器。

**② 被移出会议的人，界面还停在房间里**

`removeMember` 是服务端行为（4.54），客户端完全不知情：页面照旧、麦克风照旧可点。

两层修复：

| 层 | 做法 |
|---|---|
| 推送（需要新服务端） | `ws-hub.removeUserFromRoom()` 对那一个人的连接推 `{type:'removed'}` 后以 4003 断开；`FloorSocket` 新增 `onRemoved`，`RoomActivity.leaveBecauseRemoved()` 先 `leaveRoom("你已被发起者移出这场会议")` 再收尾 |
| 兜底（老服务端也管用） | `checkRoomStillOpen()` 拉到成员数组后判断**自己还在不在**；不在就当场离场 |

兜底那条有个坑：成员数组为空**不能**当成「我不在了」—— 一次「房间详情拿到了但成员表读失败」
就会把整屋子人踢出去。所以判据是 `members.length() > 0 && !stillHere`。

**③ 锁定发言换成上锁/解锁图片；「原文 开」换成文字 + 开关**

- `roomLock` 从 `Button` 改成 `ImageButton`，图标 `ic_lock` / `ic_unlock`；
  无障碍描述承接原来的文案规则（持麦者「解锁发言」、他人锁着时「发言已锁定（只有发起者能解除）」）。
  **图标跟着「我能不能按」走**：别人的锁、我又不是发起者 → 显示锁着的锁 + `setEnabled(false)` + 半透明。
  显示一把能开的锁却不给按，是上一版文字方案的老毛病，这次一并修掉。
- `roomSourceSwitch`：左边 `TextView`「原文」，右边 `Switch`（默认开）。
  用 `Switch.setOnCheckedChangeListener` 会在 `setChecked()` 时再次触发自己，所以加了
  `syncingSwitch` 守卫；真正的显隐仍由 `syncSourceVisibility()` 统一处理已画出的卡片。

**门禁**：新增一轮「4.55」断言（抽屉轮询的启停、`removed` 推送到离场、空成员数组不误踢、
`ImageButton` + 两个图标、`Switch` + `syncingSwitch`），并把 4.44 的旧文案断言改成图标方案的
等价断言（`setEnabled(canLock)` / `setAlpha`）。

> 顺手修掉一处门禁自身的缺陷：`loadRoomHeader();` 现在也出现在抽屉轮询里，而 4.53 的断言
> 用全文件 `indexOf` 判「在 client 之后调用」，被前面那段抢先匹配到 → 误报。改成只在
> `onCreate` 正文里判先后，并给 `loadRoomHeader()` 自己加了 `client == null` 守卫。

### 4.56 界面三语：中文 / 巴西葡语 / 英文（2026-10-28）

用户澄清了一次需求：要的不是"说话人的语言支持英文"，而是**界面文字**有三个版本。这两件事
在代码里必须分开，否则以后一定有人把它们接错。

| | 存哪 | 干什么 | 界面位置 |
|---|---|---|---|
| 我的语言 `speakLang` | `leian` prefs | 我说话用哪种语言 → 决定识别与翻译方向 | 登录页表单里、设置页第二段 |
| 界面语言 `uiLang` | `leian` prefs | 按钮和标题用哪种语言写（纯显示） | 登录页「我的语言」三颗胶囊、设置页 |

**① 机制**（`UiLang.java`，不依赖任何第三方库）

- 三套资源：`values/strings.xml`（中文，默认）+ `values-en` + `values-pt-rBR`；
- **没选过 = 跟随系统**：`wrap()` 在 `uiLang` 为空时把 base 原样返回，让 Android 自己按系统语言挑
  —— 英文手机装上就是英文，不用先猜一遍再切；
- 选了才覆盖：`createConfigurationContext()` 换掉 Configuration 的 locale；
- 每个界面都得在 `attachBaseContext()` 里走一趟 `UiLang.wrap(base)`，否则**只有先创建的那页生效**
  （Android 上"语言只改了一半"的经典原因）；
- 改语言的页面自己 `recreate()`；已经在返回栈上的页面靠 `UiLang.trackShown(this)`（在
  `onResume` 里比对上次画出来时用的语言，变了就重建）—— 官方 per-app language 也是这个思路。
- ⚠️ 房间页是例外：**正在开麦上传时不自动重建**（`if (mic == null)`）—— 重建会把这一段发言直接打断，
  而换语言是低频操作：宁可让它多留一会儿旧语言，也不能把会议说断。

**② 抽文案**：会议室五页（登录/注册、房间列表、房间、设置、隐私）全部改成 `@string/...` /
`getString(R.string...)`，新增 219 个键。以前这些文案**连一个**都没进 strings.xml（旧版
"同传 App" 那 250 个键只覆盖它自己那几页）。

> 判定口径：房间页那批"发言人：/ 未接入/ 我说中文"之类的短句最容易在代码里被拼出来
> （`"发言人：" + holder`）。这类拼接一律改成 `getString(R.string.room_speaker_prefix) + holder` ——
> 连 `startsWith()` 解析那处也一起改了，否则换语言之后解析必然失效（同一份文案两个语言，
> 拼一半就再也对不上）。

**③ 登录页那行空状态栏**

用户报的"登录页上面还有一行小状态栏，写着已注销"。根因不是文案错，是**那块卡片永远存在**：
`homeStatus` 是带底色带边框的 TextView，文本为空时也画出一条空条；注销时又特地写了
`setText("已注销")`。改法：`setStatus()` 统一入口，**空字符串就整块 `GONE`**，布局默认也不占位，
注销后不再写任何字。

**④ 门禁**（`tests/android-order-suite.mjs` 新增两轮）

- 英/巴葡键集合必须一致，且都出现在中文里（漏译一边迟早有人踩空）；
- 五页布局与 Java **真正引用到**的每个键，三份资源里都必须存在；
- 五页布局里不许有裸中文（`android:text/hint/contentDescription` 与文本节点都查）；
- 五页 Java 里不许有裸中文界面串（`Log.*` 与 `debugLine()` 除外——那是诊断日志）；
- 五个界面都必须在 `attachBaseContext` 里换语言、且 `onResume` 会自检；
- 选择器在登录页与设置页各有一组，语言名用它自己的语言写（`Português` / `English`）。

> 顺带把 12 条**旧断言**从"字面中文"改成"引用哪个 string 键"——那批断言原本把文案焊死在测试里，
> 抽资源后必然红。这也说明：断言该锁**行为与键名**，不该锁字面文案。

**⑤ 没做的**

- 旧版"同传 App"（`MainActivity` / `page_live` 等）**仍是纯中文**：那一版要拆掉，不投入翻译；
- ~~服务端推来的错误文本（`error` / `hint`）仍是服务端语言~~ → **已在客户端翻掉（4.59）**；
  新增服务端错误文案要在 `ServerText` 里加一条，门禁会盯着（见 §4.59 ⑤）
- 语言切换后 `values-night` 的深色适配未逐一核对（颜色本来就全是 token，风险低）。

### 4.59 服务端返回的 error / hint 也走三语（2026-10-28）

4.56 只翻了**界面自己写的**文案，服务端那半句还是中文：

```
建房失败：房间名不能为空        ← 前半句（客户端）翻了，后半句（服务端）没翻
```

葡语/英语用户看到的是「Criar sala falhou: 房间名不能为空」。

**① 为什么在客户端翻，而不是让服务端返回错误码**

服务端已经在正式服上跑。改成返回错误码要先发版 → 再让运维重启 relay，中间那段时间界面还是
中文；而客户端映射表**对现在这台老服务端也立刻生效**，装上 APK 就能看到效果。两件事都做才是
最优，这一轮先把用户能感知的那半做掉。

**② `ServerText`：三层查表**

| 层 | 例子 | 说明 |
|---|---|---|
| 整句 `EXACT` | `用户名或密码不对` → `srv_auth_failed` | 服务端原话，一次对一整句 |
| 前缀 `PREFIX` | `没有这个接口：…`、`每个 IP 每分钟最多…` | 带变量的句子，变量丢掉 |
| 后缀 `SUFFIX` | `张三 不在这个房间里` | 变量在**前面**的句子（`startsWith` 认不出来，只能按后缀） |
| 机器码 `CODES` | `host-left` / `removed-by-host` / `elsewhere-login` | WS 推送与部分接口用的码 |

> 带数字的句子（`密码至少 6 位`）**只按前缀认、不带数字**：那 6 是服务端配置，写死在客户端
> 迟早对不上。

**顺手修掉一个老毛病**：`leaveBecauseClosed(reason)` 以前把 WS 推来的 `reason` 直接拼进括号，
用户看到「会议已结束（host-left），已退出房间」。现在 `reason` 先过 `ServerText`，
`host-left` → 「发起者已结束这场会议」。

**③ 查不到时的规矩**（不然等于白做）

- 界面是中文 → 原样显示服务端原话（对中文用户，原话比"未知错误"有用）；
- 界面是英文/巴葡 → **不许出现中文**：给一句本语言的通用说明，原文写 logcat；
- `Connection refused` / `timeout` 这类技术英文 → 原样保留，那种不该翻译。

**④ `MicUploader` 一并收拾**

它会产生一堆**给用户看**的句子（麦克风打不开 / 录音中断 / 上传音频失败 / 采样率降级提示），
以前全是写死的中文，会漏进房间页的提示行。现在构造时传 `Context`（Activity 那个，Configuration
已按界面语言改过），12 条文案进 strings.xml；同时去掉房间页外面那层「上传出错：」——它已经
是完整句子，套起来变成「上传出错：上传音频失败：xyz」。

**⑤ 门禁：这张表不许悄悄腐烂**

单靠人工维护映射表一定会烂（服务端改个措辞，映射就失效，用户又看到中文）。断言做成**双向**：

1. 从 `relay/*.mjs`、`lib/{rooms,floor,accounts,ws-hub}.mjs` 里扫出所有中文错误串
   （跳过 `⚠️` / `[ws]` 内部日志），**条条**必须能对上 `ServerText` 的某条映射；
   对不上的要么补映射，要么进 `IGNORE` 清单并写清为什么（管理端接口、只有客户端发错类型才会触发）；
2. 反向：映射表里的每句服务端原话必须**仍然存在**于服务端源码 —— 服务端改词后这里会红，
   逼着一起改；
3. 映射用到的键三份资源必须都有；
4. 四个页面里不许再出现裸 `optString("error"/"hint")`。

> 已做反向自检（负向对照）：删掉「只有发起者可以移出成员」这一条映射，断言立刻红，
> 报错信息直接点出是哪句漏了。

### 4.60 「我的语言」到底是谁的语言（用户纠正，2026-10-28）

4.56 我把"界面语言"理解成了一个新开关，于是在登录页**顶部另加了一排**三颗胶囊，还在设置页
加了一段"界面语言"。用户指出这是误解，正确的模型是：

| 在哪里选 | 选的是什么 | 存在哪 | 影响什么 |
|---|---|---|---|
| 登录页「我的语言」 | **界面语言** | `uiLang` | 按钮/标题的文字（中文 / English / Português） |
| 建房页「我在会里说哪种语言」 | **说话语言** | `speakLang` | 识别方向与翻译方向（中 → 巴葡 或反过来） |

所以这一轮改回来了：

- 删掉登录页顶部那排 `homeUiLang*`（同一个选择器不该在一个页面上出现两次）；
- 「我的语言」那三颗胶囊改成切界面语言：`中文 / English / Português`；
- **English 从此可选** —— 4.49 时它被禁用是对的，因为那时它管的是"说话语言"，而服务端只做
  中↔巴葡；现在它只管界面文字，禁用反而是 bug。原来那句"英文暂不支持（服务端只做中 ↔ 巴葡）"
  改成「只改界面文字；说话用哪种语言在创建会议时选」；
- 登录页不再写 `speakLang`（`applySpeakLang`/`refreshLangPills` 一并删掉）—— 说话语言由建房/
  加入那一步写入，那才是它真正起作用的地方。

> 教训：一个"语言"胶囊放错页面的代价是**语义漂移**。界面上只要出现两组语言选择，
> 就必须能在文案上说清"这组管什么"，否则用户（和我）都会以为是同一件事。

### 4.61 主页面重构：三个核心入口 + 已支持语言 + 底部导航（2026-10-28）

登录后的那一屏以前是「一张卡 + 两个按钮（会议房间 / 设置）+ 一行退出登录」，看不出这个产品
有哪几件事可做。按原型重做成"一屏说清三个任务"。

**① 结构**（`page_home.xml` 的 `homeMainBox`）

```
顶部卡片   晚上好，张三                     [中文 ▾]
           中文 · 手机麦克风 · 在线

第一行     ┌ 创建同传会议 ┐ ┌ 加入同传会议 ┐     ← 同级、等宽
第二行     ┌ 同传翻译官  即将上线 ─────────┐     ← 通栏、独立场景
           └───────────────────────────────┘
语言卡     ┌ 已支持语言                    ┐
           │ [中文] [巴西葡萄牙语]          │
           │ 更多语言持续扩展中              │
           └───────────────────────────────┘
弱化行              旧版界面（默认隐藏） · 退出登录
─────────────────────────────────────────────
底部导航           首页          历史          我的
```

**② 几个刻意的决定**

| 决定 | 为什么 |
|---|---|
| 创建 / 加入**同级**、图标+名称+一句说明 | 它们是一次会议的两半，不该一个当主按钮一个当次按钮 |
| 同传翻译官**通栏 + 淡品牌底 + 品牌描边** | 它是另一个场景（眼镜/连续讲话），靠尺寸与底色分层，而不是靠再放一个按钮 |
| 同传翻译官**没有点击监听**，卡上写「即将上线」 | 还没做。摆一个能点但什么都不发生的入口，比标一句"即将上线"更让人困惑 —— 也不做假能力 |
| 语言入口是**弹三选一**，不是循环切换 | 循环切换在两种语言之间会"点一下变一种"，用户判断不了自己跳到哪了 |
| 摘要行写 **界面语言 · 设备 · 在线状态** | 刚切过语言的人能立刻核对；在线与否是"我现在能不能开会"的最短回答 |
| 「历史」导航**灰着、没有动作** | 下一步才做（会议记录）。这里只留位置，不假装有内容 |
| 设置从按钮挪进「我的」 | 主导航本来就该承载"我的"，设置属于那里，不占首页版面 |
| 旧版界面降级为**弱化文字链接**（默认隐藏） | 它是给开发对照用的，不属于用户的三个任务 |

**③ 顺带做的两件事**

- **创建 / 加入进来就落在对应那半**：两张卡都进房间列表，但带上 `EXTRA_FOCUS`，页面直接把光标
  放到"会议名称"或"6 位邀请码"上；
- **登录页抬头会收起**：进首页后品牌行（`homeLoginHeader`）隐藏，否则一屏两个"标题"
  （首页问候 + 品牌名）会互相打架。

**④ 门禁**

新增两轮断言，其中一条是**通用**的：

- 主页面结构：三张卡的数量与层级（`weight=1` 同级 / 通栏）、每张卡都有名称+说明+图标、

### 4.62 「我的」页面 + 术语库管理（2026-10-28）

用户给的结构：

```
页面标题「我的」
蓝绿色渐变个人卡片：头像 / 姓名 / 组织 / 服务版本
我的设备          设备名称 · 能力摘要 · 连接状态
术语库管理
翻译服务及有效状态
帮助与反馈
退出登录
底部一级导航（首页 / 历史 / 我的）
```

**① 组织那一行为什么不写公司名**

这套系统里**没有组织信息**：账号只有角色（admin / user / dev）。编一个公司名等于骗人，
所以这一行写的是角色 + 账号类型（「管理员 · 组织账号」/「普通成员 · 个人账号」），
它是真实存在的信息。

**② 「翻译服务及有效状态」的有效期从哪来**

以前 `whoami` 只回 `{user, role}`，没有任何有效期信息。这一版给 `/auth/whoami` 加了两个字段：

```json
{ "ok": true, "user": "...", "role": "user", "status": "active", "expiresAt": "2026-11-05T..." }
```

- 永久账号**没有** `expiresAt` → 服务端省略该字段（不是 null）；
- 客户端读不到时明确显示「有效期未知（服务端未提供）」，**不假装长期有效** ——
  老服务端没重启之前就是这个状态，那是事实，不该美化；
- 状态 `disabled` 直接显示「已停用」。

**③ 术语库管理：只能提申请，不能改库**

用户要求"直接调用相关接口即可"，用的就是 docs/19 那套审批流：

| 动作 | 接口 |
|---|---|
| 列库（名称 / 分类 / 条目数） | `GET /org/libraries` |
| 提申请（新增 / 修改 / 删除） | `POST /org/requests` |
| 我的申请（含状态） | `GET /org/requests/mine` |
| 撤回还没被审的 | `POST /org/requests/<id>/withdraw` |

> ⚠️ **不**做成"直接编辑"：一个人随手改错，所有选了该库的会议都跟着错，而且改完无从追查
> （这是用户 2026-10-23 定的规矩）。按钮因此叫「申请修改」，提交后进「我的申请」等审批。
> 申请人是**服务端从 token 解出来的**，请求体里不放 `applicant`。

表单三种类型共用一张 `dialog_term_request`：新增/修改要中文 + 葡语译文 + 理由；删除只填中文。

**④ 底部导航抽成公共片段**

首页与「我的」都要有同一条导航，复制两份一定会漂。抽成 `inc_bottom_nav.xml`，
两个页面各自 `<include>`；高亮逻辑集中在 `NavTabs.apply(activity, 哪一页)`：
当前页用品牌色，其它用灰；**历史永远灰**（它还没有内容）。

**⑤ 「我的」替代了原来的设置入口**

设置不再是首页的一个按钮：底部导航「我的」→ 「翻译服务及有效状态」那行 → 设置页。
设置页本身没删（服务器地址/密钥、说话语言、界面语言、校对、清空记录都在那儿）。

**⑥ 门禁**

- 四行的顺序、每行的必备内容（设备摘要要读 `Build.MODEL`、在线状态要来自真的
  `whoami` 而不是写死）；
- 渐变卡片两端色必须是 `brand_grad_start/end`；
- 术语库页必须调 `orgCreateRequest` / `orgMyRequests` / `orgWithdrawRequest`，
  且**不许**出现 `body.put("applicant")`；
- 两个新页面必须注册进 manifest；
- `whoami` 必须返回 `status` / `expiresAt`（服务端那半也要有对应断言）。

### 4.63 「提申请显示没有权限」：权限表漏了交账号 + 提示说不清（2026-10-28）

用户实测：在「我的 → 术语库管理」里提交申请，界面弹「账号没有权限」。

**① 根因：不是校验写错，是权限表把测试账号挡在门外**

```js
// 改之前
'request.create': ['admin', 'user'],   // dev（测试账号）不在里面 → 403
```

这句 `deny()` 的原话是「当前角色（dev）不能做 request.create」，客户端把它翻成了
「当前账号没有权限做这个操作」—— 于是用户只看到一句笼统的拒绝，**看不到是哪个角色**。
这是两个问题叠在一起：策略问题（dev 不该被挡）＋ 表达问题（提示说不清）。

**② 策略：dev 也能提申请**

- 提申请**没有破坏性**：要管理员审批才会写进库（`library.write` 仍然只有 admin）；
- 测试账号正是要走完这条流程的人，挡住它等于这条流程没法验收；
- 于是 `request.create` 改成 `['admin', 'user', 'dev']`，并把原来那条
  「dev 只读：不能写库、不能提申请」的断言改成「dev 能提申请但仍不能写库」——
  断言就是决策记录，改策略就要一起改它，否则下一个人会以为代码错了。

> ⚠️ 这是**服务端**改动：要 `git pull` + 重启 relay 才生效。没重启时客户端拿到的是老服务端的
> 403，但下面的改进让那句拒绝变得可读。

**③ 表达：403 要说清"谁不能做什么"**

- 服务端 `deny()` 除中文原话外，多给机器可读字段：`code:'forbidden'` + `role` + `action`；
- 客户端 `ServerText` 两条路都能读：新服务端看 `code`，老服务端解析「当前角色（X）不能做 Y」
  这句固定格式 → 显示「当前账号（dev）没有权限做这件事（request.create）」；
- 术语库页进页面就先问一次 `whoami` 拿角色，**没权限时连「申请修改」按钮都不画**，
  并在提示里写明角色（点了才被拒最气人）；
- 角色未知时不拦（老服务端可能不给 `role`），交给服务端判并给出准确原因。

**④ 门禁**

- `request.create` 必须含 dev；
- `deny()` 必须给 `code/role/action`；
- `ServerText` 必须同时认得结构化 403 与老服务端中文原话；
- 术语库页没权限时**不画**按钮，且提示里带角色。

### 4.64 申请记录可自行删除 + 三语下卡片对齐（2026-10-28）

**① 已有结论的申请可以由申请人自己删掉**

用户报了"通过/未通过的申请堆在列表里没法清"。加一个删除动作，但**删的是记录，不是数据**：

| 层 | 做法 |
|---|---|
| 接口 | `POST /org/requests/<id>/delete`（申请人本人；`pending` 必须先撤回） |
| 存储 | `requests` 表加 `hidden_at`（幂等 `ALTER`，老库自动升），**不删行** |
| 读 | `visibleOfMine()` 过滤 `hidden`，`GET /org/requests/mine` 不再返回 |
| 界面 | 非 `pending` 的行出现「删除记录」，二次确认里写明"审批记录仍留在服务端（审计用）" |

> 为什么不硬删：审批记录是审计材料 —— 删了就说不清"这条是谁批的、为什么批"。
> 也不许删 `pending`：那不叫删除叫撤回，走 `withdraw`（否则管理员那边的待审列表会凭空少一条，
> 而申请人以为自己"没提过"）。

**② 两张任务卡在中文下不对齐，英文却对齐**

根因不是布局参数写错，而是**文案长度随语言变**：中文说明「用对方给的邀请码进房」一行就够，
英文 `Enter the code you were given` 折成两行 —— 于是中文时左边卡比右边矮一截。
这种问题不能靠"调间距"解决，得让高度**不依赖文案长度**：

- 两张卡的说明统一 `minLines="2"` + `maxLines="2"`：无论哪种语言都占两行；
- 名称 `maxLines="2"`：长语言下换行而不是被截断；
- 保留 `card_task_min_height` 兜底（字体放大时也不会一边高一边矮）。

**三语布局的通则**（这轮之后按这个来）：

1. 对齐只靠**约束**（`weight` / `minLines` / `minHeight` / `Gravity`），不靠"文案大概多长"；
2. 横排的两个控件，要么同 `weight`，要么都写死高度；`wrap_content` 并排 = 一定会在某个语言下错位；
3. 文案要短、要能被截断（`maxLines` + 省略），因为葡语普遍比中文长 30%~50%；
4. 门禁里对**每一对并排卡片**断言"说明锁 2 行"，新加卡片时照抄这条。

**③ 顺带补上的翻译漏洞**

门禁扫服务端中文错误串时，之前**没有扫 `lib/requests.mjs`** —— 于是「必须写申请理由」
「这个中文名库里已经有一条了」这些提示在葡语/英语界面全是中文（或退化成一句通用话）。
这轮把 `requests.mjs` 纳入扫描，并把 19 条申请相关文案接进 `ServerText`。

### 4.72 历史记录「按账号删除」+ 详情页三段（2026-10-29）

**① 先把语义改对**

第一版我做成了**设备本地隐藏**（SharedPreferences 记一份 id 列表）。用户指出不对：
要的是**按账号在服务端删** —— 只影响这个账号的历史列表，其它参与者照旧看得到。

```
├─ 设备本地隐藏（错）：换台手机登录同一账号，删掉的又回来了
└─ 按账号删除（对）：  账号维度一致；同账号换设备也不出现；别人不受影响
```

实现：

| 层 | 做法 |
|---|---|
| 表 | 新增 `history_hidden(room_id, username, hidden_at)`，主键 `(room_id, username)` |
| 建表 | 走 `TABLE_PATCHES` + `reconcileTables()`，**每次 openDb 都跑**（4.68 的教训：不能放在版本门禁里） |
| 接口 | `POST /org/history/<roomId>/delete`，只允许删**自己参加过**的会 |
| 查询 | `listHistory` 用 `LEFT JOIN history_hidden ... WHERE h.room_id IS NULL` 过滤 |
| 客户端 | `LanClient.orgDeleteHistory()`；列表**长按** + 详情页按钮两个入口 |

> 为什么必须校验"自己参加过"：否则任何人都能往**别人**的历史里塞过滤条目。
> 删除只影响自己，但"能操作谁"这件事仍然要拦。

**② 详情页按原型三段，会议纪要整块砍掉**

老师建议去掉会议纪要，所以详情页只留：

```
① 统计概览（三列，数值用主色）：会议时长 / 使用语种 / 发言人数
② 转写全文（含筛选入口 —— 格式下一轮定，现在点了明说还没做）
③ 导出 Word（只导出这条记录已有的历史内容）
```

**不做**的：AI 摘要、行动项（含勾选与责任人）、只读分享链接 —— 它们都属于纪要，
纪要砍掉就一起砍，不留半成品入口。

**③ 导出 Word 是手写的**

项目硬规矩是"不引第三方库"，而 docx 本质就是"装了若干 XML 的 zip"：
用 JDK 自带的 `ZipOutputStream` 写 `[Content_Types].xml` / `_rels/.rels` /
`word/document.xml` 三个部件即可（`HistoryDocx.java`）。为了分享给别的 App，
清单里加了 `androidx.core.content.FileProvider`（authority `${applicationId}.fileprovider`），
只开放缓存目录下的 `exports/`。

> 用 Apache POI 能少写代码，但会多背十几 MB —— 为一个导出功能不值。

**④ 转写全文现在是空的，而且如实显示**

服务端目前**没有任何代码往 `utterances` 表里写字幕**（只有清理任务在读它），
所以详情页的转写区显示「这场会议还没有转写内容」。下一轮用户会细化转写格式
（时间戳 / 说话人 / 原文与译文怎么排），那时才会真正有内容。

**⑤ 门禁**

- 服务端：隐藏表存在、只删自己参加过的、列表按我自己过滤；
- 客户端：**不允许**再出现设备本地第二套实现（`HistoryStore` 已删）；
- 详情页：三段顺序固定，三列数值用主色；**不许出现摘要/行动项/责任人**（剥注释后判）；
- 导出：必须是真 docx（zip + 三个部件），且生成器里不含摘要/行动项。

### 4.73 转写全文：多张字幕卡 + 固定高度框内滚动（2026-10-29）

用户给的要求：**转写内容由多个框组成，每个框的格式与会议中的字幕一致；
大框长度一定，里面的内容可以上下滑动**。

**① 结构**

```xml
<ScrollView id=transcriptScroll  height=@dimen/transcript_box_height(360dp)>  <!-- 外框定高 -->
  <LinearLayout id=transcriptList vertical/>                                  <!-- 里面多张卡 -->
</ScrollView>
<TextView id=transcriptEmpty/>                                                <!-- 没内容时只留一句话 -->
```

没有内容时**收起空框**、只留一句「这场会议还没有转写内容」——
留一个 360dp 的大白框比什么都不显示更像坏了。

**② "格式与会议中的字幕一致"怎么保证**

会议室里那张卡是 `RoomActivity` 用代码搭的（它要支持"同一句三帧原地更新"，
改成 inflate 会把那条热路径搞复杂）。所以这次的做法是：

- 把外观落成 `item_subtitle_card.xml`（头像 / 姓名 / 语言标签 / 状态 / 原文 / 译文）；
- 渲染集中在 `SubtitleCard.render()`，与会议室共用同一套素材与度量
  （`bg_card` / `bg_subtitle_self` / `bg_avatar` / `bg_chip` + `subtitle_*` 那组 dimens）；
- **门禁断言两边一致**：卡片用了同款 drawable、同款字号与内边距，会议室那张卡也仍是
  同一套素材 —— 哪天有人改了其中一边，断言会红。

自己的发言换底色（`bg_subtitle_self`）与会议室同一规则。

**③ 数据从哪来**

新增 `GET /org/history/<roomId>/transcript`：读 `utterances` 里 `is_final = 1` 的行，
按 `start_at` 正序，最多 500 条；**只给参加过这场会的人**（字幕是会议内容）。

**④ 一个必须说清的缺口**

`utterances` 表**目前没有任何代码往里写**（只有保留期清理在读它），
所以这个接口现在返回空数组，界面显示"还没有转写内容" —— 这不是 bug，是还没接线。
要真正有内容，需要先定一件事：**字幕帧怎么和"哪场会议"关联**。
现在的 `/frame` 长轮询是**全局**的（谁在推就谁看），跟房间无关；
而 `utterances.room_id` 要求知道归属。可行的两条路：

1. 在房间里开麦时，由客户端把"我在哪场会"带给收件箱/转发进程，relay 按房间写；
2. relay 侧按"当前房间的持麦者"推断归属（更省事，但持麦者切换时容易错帧）。

这一条留到下一轮和转写格式一起定，本轮不做猜测性实现。
