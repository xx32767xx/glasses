> 依据：老师原型 `translation-app-prototype.html`（V0.3 译连 TransLink）已对发言权与入会方式做了**明确说明**，
> 本文件以原型为准重写，不再沿用我上一版"申请-排队-批准"的假设。
>
> 三条已定：① 服务端用 **`node:sqlite`**（服务器已装 Node 22）；② 发言权与房间准入按原型规则；③ 字幕 **7 天清理**。

## 1. 与上一版的关键差异（我的假设错了，以原型为准）

| 项 | 我上一版（作废） | 原型（采用） |
|---|---|---|
| 发言权 | 申请 → 排队 FIFO → 主持人批准 → 30 秒超时释放 | **点击开麦即持麦**（无需长按），再点关闭；**后开麦者顶替先开麦者**（抢麦），被顶替者收到提示 |
| 防打断 | 无 | **锁定发言**：锁定期间他人开麦被拒，提示「XX 正在发言（发言已锁定）」；**仅管理者可解除他人锁定**；同一个按钮在"锁定/解锁"之间切换 |
| 并发裁决 | 队列 | **按服务端到达顺序**裁决，后到者收到「XX 正在发言」 |
| 入会 | 房间码 + 可选密码 | **6 位邀请码是入会唯一凭证**，无密码；校验通过后带出会议主题供确认 |
| 界面布局 | 底部大圆按钮 + 左抽屉 | **主区留给发言与译文字幕流**；右侧**竖向悬浮条**（当前发言人 + 投屏/扩声/收音状态）+ 右侧抽屉（人员与设备合并） |

## 2. 界面（5 个，③ 常驻）

```
启动 → ① 登录/注册（全屏）→ ② 首页（创建/加入）→ ③ 实时房间（核心）
                                                      ├→ ④ 右侧抽屉（发言人 + 设备）
                                                      └→ ⑤ 设置（服务器/语言/术语/隐私）
```

### ③ 实时房间（核心页）
- **主区 = 字幕流**（占绝大部分）：每句两条 —— 主行是**我的语言**的译文（大字 32~34sp），副行是原始发言（小字 16sp、低对比）。新句从下往上推。
- **底部单行控制**：`🎙 点击开麦`（开麦后变 `正在发言 00:12` 绿色呼吸）/ `锁定发言`（锁定后变 `解锁`）/ 原文-译文切换。**不用长按**。
- **右侧竖向悬浮条**（固定常驻、不轮播）：
  - 上格：**当前发言人**（头像 + 姓名；发言中绿环，空闲显示「麦克风空闲」）
  - 下格三项状态：**投屏 / 扩声 / 收音**（本项目手机-only：投屏=手机屏，扩声=耳机或关闭，收音=手机麦克风）
- **系统提示行**（插在字幕流里，灰色斜体）：
  - 会议开始：`— 会议开始 · 发言权互斥已启用：同一时刻仅一人开麦 —`
  - 抢麦成功：`你已接管麦克风 · 对方已被自动静音`
  - 被抢：`XX 接管了麦克风`
  - 被拒：`XX 正在发言（发言已锁定）`

### ④ 右侧抽屉
- 上半「发言人」：当前发言人 + 全员头像（**发言过即点亮**）+ 提示
- 下半「设备」：手机（收音/播报）能力开关；未连接设备置灰
- 管理者额外可见：解除他人锁定、移出成员

### ② 首页
`创建同传会议（生成邀请码）` / `加入同传会议（输入 6 位邀请码）` / `同传翻译官（单向收听）`，右上头像进 ⑤。

### ① 登录/注册
按原型：`用户名 + 邮箱 + 验证码`（新用户注册 / 老用户登录同一入口），底部勾选《用户协议》《录音与隐私政策》。

## 3. 服务端：发言权状态（`node:sqlite`）

```sql
CREATE TABLE floor_state (
  room_id TEXT PRIMARY KEY,        -- 单行主键 = 互斥锁本身
  holder  TEXT,                    -- 当前持麦者（NULL = 空闲）
  locked  INTEGER NOT NULL DEFAULT 0,  -- 是否锁定发言
  since   INTEGER NOT NULL
);
```

规则（实现即测试）：
1. **开麦请求**在一个事务里完成：查 `floor_state` → 空闲则直接置我；他人持有且**未锁定**则顶替（广播"被接管"）；他人持有且**已锁定**则拒绝（提示"XX 正在发言（发言已锁定）"）。
2. 同时到达按**到达顺序**处理（单写者 + 事务串行化即可，不做队列）。
3. **锁定**：持麦者可锁自己；**仅管理者**可解除他人锁定；锁定与解锁共用一个按钮。
4. 关麦即释放；断线超过 `N` 秒（建议 15 秒）视为释放，广播"XX 掉线，麦克风已释放"。
5. 客户端乐观 UI，最终以广播为准；冲突回滚并提示。

其他表：`rooms(id, name, code, host, langs, created_at)`、`room_members(room_id, user, joined_at)`、`utterances(room_id, user, src_lang, src_text, dst_text, start_at, is_final)`、`accounts`、`libraries`、`library_entries`、`requests`（原 JSON 内容迁入）。
`PRAGMA journal_mode=WAL; foreign_keys=ON; busy_timeout=3000`。

## 4. 存储与迁移

- **服务端**：`node:sqlite`（Node 22 内置，零依赖）。`scripts/migrate-sqlite.mjs` 一次性导入现有 `accounts.json`、`libraries/*.json`、`requests.jsonl`，之后只读写 SQLite，JSON 留档。
- **客户端**：原生 `SQLiteOpenHelper`（不加依赖）：`settings`、`rooms`（本地历史）、`utterances`（字幕回看，**7 天清理** `DELETE WHERE start_at < now-7d`）、`drafts`。
- **隐私**：7 天自动清理字幕与音频元数据；设置页提供「清空本房字幕」。

## 7. 验收

- 接口：并发开麦只有一个 holder；未锁定可被顶替并广播；已锁定时开麦被拒；管理者可解除他人锁定；断线 15 秒释放。

## 8. 环境与数据目录（2026-10-25 定）

**本机只用于开发与跑自动化测试；所有应用侧测试都在服务器进行。**

| 环境 | 数据目录 | 谁用 | 说明 |
|---|---|---|---|
| 开发 | `<仓库>/var/live`、`var/live-test` | 本机（Windows） | 只跑 `node tests/run-all.mjs` 与离线脚本；不装 App、不联调 |

规则：
1. **一份代码 + 一个 `--data-dir` = 一套环境**，不靠机器身份判断；

3. 服务器上每个环境一个独立 `leion.db`；删测试环境不影响生产；
4. 启动横幅与 `preflight.cjs` 都会打印实际数据目录，避免"以为在测试、其实写进了生产"。

### 4.33 修复（2026-10-27，用户报的两条）

1. **房间页不再有「术语库」按钮**。选库本来就该在**建房那一步**完成（`RoomsActivity` 建房后立刻弹选库、
   存快照），房间里那个按钮是重复入口，而术语在进房时已冻结 —— 会中改不了，留着只会误导。
   现在 `page_room.xml` 底部只剩：开麦 / 开始同传 / 退出 / 锁定发言。
2. **「莫名其妙掉登录」的根因是 `authWhoAmI()` 返回错了形状**：`LanClient` 那个方法原来是
   `return requestWithCode(...)`，返回的是 `{ code, json }` **外壳**，而 `HomeActivity` 读的是
   `optBoolean("ok")` —— 外壳里没有 `ok`，于是**每次启动都判成没登录**。
   更麻烦的是连锁反应：重登会吊销该账号的旧 token（**单会话**是刻意设计），所以另一台手机
   下一次请求就 401 —— 用户看到的就是"另一台莫名其妙掉登录"。
   现在：方法返回**拆过包的正文**（带 `_status`），界面按三种情况分别处理 ——
   `200 + ok` 进首页；`401` 才清本地 token 回登录页；**连不上服务器不许踢登录**（网络抖一下就踢，
   用户会以为掉登录，然后重登又把另一台踢掉，把问题扩大成两台都掉）。

> ⚠️ **单会话仍然生效**（用户 2026-10-27 要求）：同一账号在第二台手机登录，第一台会被踢。
> 这不是 bug。若要两台同时在线，得改成"多设备 token"（服务端 `login` 不再吊销旧 token）。

### 4.34 修复：被顶替后客户端不停上传（"发言人显示 B，A 的同传按钮还亮着"）

**现象**（用户 2026-10-27 报）：A 先开麦、B 后开麦 → 右侧发言人条显示 B（服务端裁决是对的），
但 A 那边「开始同传」还是蓝色，麦克风仍在录音上传。

**根因在客户端，服务端没问题**（`lib/floor.mjs` 的顶替/锁定/租约逻辑与测试都正确）：

1. **2 秒轮询只刷文字**：`takingChanged()` 改了按钮文案与发言人条，却**从不停止
   `MicUploader`** —— A 的音频继续灌进同一个识别流，两路音频交错，字幕错乱，
   而界面上看着"一切正常"。这是最隐蔽的一种：**界面说 B，数据里是 A+B**。
2. **按钮没有两态**：上传中与空闲都是同一个蓝色，用户根本没有视觉依据判断
   "我是否还占着麦"。

**修法**：

| 位置 | 改动 |
|---|---|
| 轮询 `scheduleFloorPoll` | 发现"我不是持麦者"（`wasHolding \|\| mic != null`）→ `onFloorLost(holder)` |
| `onFloorLost` | 停 `mic`、按钮回灰、hint + **Toast**「XX 接管了麦克风 · 已自动停止同传」<br>（hint 行会被下一条字幕刷掉，所以必须再用 Toast 说一次） |
| `heartbeatIfDue` | 服务端回"不是持麦者"→ **立刻停**，不等下一轮 2 秒轮询 |
| 点「开麦」结束发言 | 若正在上传也一起停（否则"麦放了、音频还在传"） |
| `updateUploadButton` | 蓝 `#1565C0` = 正在上传（停止同传）／灰 `#263238` = 空闲（开始同传） |

**已知边界（刻意没做）**：服务端**不校验** `/audio` 的持麦身份 —— 客户端已经停了，服务端只管
"谁是持麦者"。一个卡死不动、还在上传的旧版本客户端仍可能双路灌音频；要彻底挡住得让
`/audio` 带上 `room`+`user` 并按 `floor_state` 拒收 —— 那会碰音频热路径（每块都要查库），
等真出现再说。

### 4.35 新增：发言权推送通道 `/ws`（WebSocket，2026-10-27）

**为什么**：发言权原来靠"每 2 秒 GET 一次 `/floor`"。于是被顶替的那一方最多要 2 秒才知道
自己被静音了 —— 4.34 修的是"知道了会不会照做"，这一条修的是"**知都不知道**"。
改成推送后是**一推即到**（本机实测 1~3 ms）。

**两端都不是现成组件，这是刻意的**：

| 半边 | 实现 | 为什么不用现成的 |
|---|---|---|
| 服务端 | `lib/ws-hub.mjs`，手写 RFC 6455（握手 + 帧编解码 + 掩码校验 + 分片 + ping/pong + 关闭） | Node **没有内置 WS 服务端**；而仓库零第三方依赖（`package.json` 的 dependencies 是空的，`run-all` 有一条断言钉着"没有裸包名 import"），装 `ws` 就破了这条，部署机也少一次 `npm install` |
| 客户端 | Java-WebSocket 1.6.0（+ slf4j-api 1.7.30） | Android 没有内置 WS 客户端。这两个 jar 在**本机 Gradle 缓存里就有** → 离线可构建（版本不许乱改） |

**协议**（都是 JSON 文本帧，单条上限 64 KB）：

```
服务端 → 客户端   {type:'floor', roomId, holder, locked, since, leaseMs, at}
客户端 → 服务端   {type:'ping'} → {type:'pong'}；{type:'snapshot'} → 重发一次当前状态
```

- **连上立刻收到一条 `floor`**，客户端不用再问一次；
- 推送的是**完整快照**，整条替换，不做增量 —— 丢一条不会让状态变形；
- 认证与普通请求同一套：`X-Leion-Secret`（或 `?secret=`）+ `X-Leion-Token`（或 `?token=`），
  token 决定"我是房间里的谁"；房间用 id 或 6 位邀请码都行（`?room=`）；
- 同一用户重复连进来 → **旧连接被顶掉**（手机切网/重连很常见，否则会"两个我"各自收状态）；
- 房内最多 8 条、全局 64 条连接；服务端每 20 秒 ping 一次，两个周期没回音就断开。

**断线不是故障**：`RoomActivity` 的 2 秒轮询一直在跑，WS 只负责更快。分工是：

| 通道 | 频率 | 作用 |
|---|---|---|
| `/ws` 推送 | 状态一变就推 | 主通道 |
| `GET /floor` 轮询 | WS 活着时 **10 秒**（看门狗）／WS 断了 **2 秒** | 兜底：发现"推送假死"和老服务端 |

⚠️ 两个必须记住的细节（都有测试钉住）：

1. **心跳不能靠推送消息顺带**：轮询放慢到 10 秒后，只靠它续租会贴到服务端 15 秒租约的红线上，
   所以心跳自己按 5 秒走（`scheduleHeartbeatTick`）。
2. **轮询与推送必须走同一个 `applyFloorState`**：否则会出现"推送很快，但忘了停上传"这种
   不对称 bug —— 那正是 4.34 的现象（界面说 B，A 的麦克风还在传）。

**这一条通道只推"谁在说话"**，不推字幕、不推音频：
字幕仍走 `/frame` 长轮询；音频目前只有"手机→电脑"一个方向（要做"电脑→手机"的音频流，
WS 是合适的载体，但前置条件还没满足 —— 见 §遗留）。

### 4.36 接上字幕保留期清理（P4，2026-10-27）

**为什么**：字幕里是**真实会议内容**。库存在服务器上、管理员还看得到，"永久保留"既不是需要的能力，
也不是用户同意过的事。`purgeOldUtterances` 早就写好了，但**全仓库零调用点** —— 等于没做。

**现在的行为**：

| 项 | 值 |
|---|---|
| 保留期 | 7 天（`--utterance-retention-days <n>` 可调） |
| 时机 | **启动先清一次**（补上停机期间该删的）+ 之后**每小时一次** |
| 失败处理 | 只打一行日志，**绝不影响同传**（维护动作不在主链路上） |
| 可见性 | `/status` 里的 `utterancesPurged`（累计删除条数）与 `utteranceRetentionDays` |

实现上多了一个薄封装 `purgeUtterancesIn(dataDir, now, days)`：`openDb` / `close` 成对出现很容易漏，
漏一个就是没释放的 sqlite 句柄，而定时任务一小时跑一次 —— 一天漏 24 个。封装之后只有一处能拿到 db。

### 4.37 删掉 `--from` / `--to`：语种跟着每一句话走（2026-10-27）

**为什么删**：这两个参数是"整路固定语种"。只有在"这一路音频只会有一种语言"时才安全，
而它是**安静地错**：实测把葡语音频硬当中文识别，词错率 **100%**，输出还不是乱码 ——
是**中文译文**（`sequer olhavam pra você` → `甚至看不見你`）。看起来像正常工作。

**现在怎么走**（没有任何命令行参数）：

```
手机开始/切换录音 → /audio?lang=zh-CN
        ↓ relay 写进 audio-in.lang 旁文件
whisper_stream.py 按它解码 → 把**这一句实际用到的语种**写进 json 行
        ↓ {"text":"…","from":"zh-CN"}
asr-bridge 原样透传（每行自带语种，行里的字段优先于任何全局标记）
        ↓
插件 parseInboxLine：from 有就用 from，目标语种 = 另一种语言（core.mjs:2525-2529）
```

具体改动：

| 位置 | 改动 |
|---|---|
| `bridge/whisper_stream.py` | 新增 `--format text|json`；`json` 时每句输出 `{"text":…,"from":…}`；`transcribe()` 把**实际用到的语种**（显式指定或模型检测）一起返回 |
| `bridge/asr-bridge.mjs` | 删除 `--from/--to`；`createInboxWriter` 支持结构化行（对象或 JSON 字符串）**透传**，行内 `from/to/speaker` 优先于构造时的全局 tags |
| `scripts/start-all.mjs` | 删除 `--from/--to` 的解析、校验与转发；识别进程一律拿 `--format json` |
| 测试 | bridge-suite 换成"每句自带语种透传"；start-all-suite 断言"传 `--from` 就是未知选项"；python-suite 加 8 条（json 行带 from、表外语种不硬编、缺省 text 不受影响） |

⚠️ 仍然保留 `whisper_stream.py --language zh|pt`（**它自己的**开关，不是 --from）：那是给
"我确定这一路只有中文"的离线评测用的，与产线链路无关。

### 4.38 音频文件轮转（长期跑别把磁盘写满，2026-10-27）

**问题**：`audio-in.pcm` 是"只追加、永不清空"的（4.13 那次刻意的选择：`fresh=1` 时清空会把
**还没被识别进程读走**的音频永久删掉 —— 用户录了三段，每段都被下一次清掉，一条都没识别出来）。
代价是它会一直长：16k 单声道 ≈ 32 KB/秒 ≈ **115 MB/小时**，而 `start-all` 重启时**并不会清它**。

**现在的行为**：

| 项 | 值 |
|---|---|
| 上限 | `--audio-max-bytes <n>`，缺省 **1 GB**（≈ 9 小时连续音频），`0` = 不轮转 |
| 触发 | 写入前判断：**这一块**放不下就先把旧文件轮转，再整块写进新文件（不会被劈成两半） |
| 轮转 | `audio-in.pcm` → `audio-in.pcm.1`（覆盖上一份）→ 新建空文件 |
| 磁盘占用 | 约 **2× 上限**（只留一份 `.1`） |
| 可见性 | `/status` 里的 `audioMaxBytes`、`audioRotations`、`audioBytes` |
| 重启后 | 启动时按文件真实大小初始化 `audioBytes` —— 否则上限每次重启都从头算，等于没设 |

**为什么是轮转而不是原地清空**：识别进程（`PcmFollower.read`）发现路径上的文件**变小**时，
会把读指针退回 0 重读（python-suite 钉着这条分支）。轮转正好让它"换到新文件继续跟"，
而旧的一份留着排查。原地清空则会让"还没读走的那几秒"直接消失。

**为什么**：服务器地址与共享密钥原来**只能在登录页填**（改一次就得先退出登录）；语言与校对开关

### 4.40 修「点结束同传后弹『上传出错：thread interrupted』」（2026-10-27）

**现象**（用户报）：同一台设备上点「开始同传」再点「结束同传」，下方弹出一行小字
「上传出错：thread interrupted」。

**真因**：`MicUploader.stop()` 直接 `interrupt()` 录音线程。而那一刻线程多半**正卡在上传**
（每秒一块的 HTTP 请求）里 —— 被打断的 I/O 会抛一个消息就叫 `thread interrupted` 的异常，
`upload()` 的 catch 把它当故障报给界面。用户点结束是**预期行为**，却渲染成红字。

**同一处还有第二个隐患**：`interrupt` 唯一的效果就是打断正在上传的那一块 ——
于是「停止时会把最后不足一块的尾巴也发出去」这条设计**实际失效**：最后半句话被丢掉。
而录音循环里没有 `sleep`/`wait`，`interrupt` 并不能让它更快退出。

**修法**：

| 改动 | 说明 |
|---|---|
| 新增 `stopping` 标志 | `stop()` 里**先**置位，再让线程退出。`upload()` 的 catch 与录音循环的 catch 都据此判断：主动停**不报错** |
| `start()` 里复位 `stopping` | 否则停过一次之后，后续**真正的**上传错误会被永远吞掉 —— 用户再也看不到"为什么没字幕" |
| `stop()` **不再立刻 interrupt** | 改成起一个看门狗线程 `join(2s)`：先给录音线程 2 秒把尾巴发完；还赖着才 `interrupt()`（兜底底层 read 卡死） |

**顺带修好的**：4.34 的「被顶替」路径也会调 `mic.stop()`，以前同样会把这个假错误顶掉
「B 接管了麦克风」的提示。

**测试**（android-order-suite）：`stopping` 标志存在；`stop()` 里置位 → `join(STOP_GRACE_MS)`
→ 才 `interrupt()` 的顺序；上传失败分支先看 `stopping`；录音循环判 `running && !stopping`；
`start()` 里复位 `stopping`。

### 4.41 两处 UI 修正 + 「被顶下线」不再静默（2026-10-27）

**① 建房后邀请码被选库框挡掉**

现象：点建房 → 立刻弹「本场术语库」对话框 → 页面上的邀请码被整个盖住，用户来不及抄。

修法（三处一起，任何一处单独都能让人看不到码）：

| 位置 | 做法 |
|---|---|
| 建房成功瞬间 | `Toast.makeText(..., "本场邀请码：" + code, Toast.LENGTH_LONG)` —— **Toast 显示在对话框之上** |
| 选库框标题 | 「邀请码 123456 · 本场术语库（会中不可改）」 |
| 选库框正文 | 再写一次「把 123456 告诉对方即可入会」 |

~~不~~采用"先关对话框再看码"的做法：那等于把"选库在建房这一步"的规则破了。

**② 被挤下线的那台设备完全静默**

现象：两台设备同一账号，后登录的踢掉前一个 —— 但**被踢的那台什么都不知道**，
界面上一切正常，直到某次点按钮失败（用户 2026-10-27 报的）。

根因：单会话只是**吊销旧 token**，没有任何推送；被踢方如果不主动问，就永远不知道。

修法：新增 `SessionWatch` —— 每 10 秒 `GET /auth/whoami`：

| 结果 | 行为 |
|---|---|
| 200 | 什么也不做（静默是常态，不能每 10 秒闪一下） |
| 401 | 回调 → Toast 说明原因、清本地 token、回登录页 |
| 网络失败 | **什么也不做** —— 连不上 ≠ 被踢（4.33 的教训：网络抖动被当成掉登录，重登又把另一台真的踢掉） |

装在三处：**首页**（`showHome` 后）、**房间大厅**（`RoomsActivity.onCreate`）、
**房间内**（2 秒/10 秒的发言权轮询顺带判 `httpStatus == 401` → `showKicked()`）。
房间里还会清 token 并 1.5 秒后退出房间 —— 身份已失效，留在这里只会让用户以为网络卡了。

**顺手把 B3 做了**：`checkSession()` 调用 `throwIfSessionExpired(wrapper)`，
所以 `SessionExpiredException` / `throwIfSessionExpired` 不再是**零调用点的死代码**，
401 的人话消息只写在那一处。

### 4.42 锁定态的掉线不再永久占麦（B2，2026-10-27）

**问题**：`takeFloor` 里那条"断线释放"判断带 `!locked` —— 意思是**锁定中的持麦者永远不会因
掉线而释放**。于是"锁了麦然后手机没电 / 掉网"会永久占着麦克风：房间里谁都开不了口，
只能等发起人发现并手点「强制收回」。那是一种没人会想到的运维动作，等同于故障。

**为什么当初写成 `!locked`**：锁定就是"这五分钟别打断我"，所以不想让网络抖动把锁弄丢。
但"别打断"不等于"永远归我" —— 两者的区别在于**时长**，而不是有无。

**修法**：

| 项 | 值 |
|---|---|
| 普通持麦租约 | 15 秒（不变） |
| **锁定持麦租约** | **60 秒**（`FLOOR_LOCKED_LEASE_MS`；心跳 5 秒一次，60 秒足够区分"在说话"与"人没了"） |
| 抢麦时 | 超过对应租约 → 直接顶替，回执带 `reason: previous-lease-expired` 与 `releasedLocked` |
| **没人抢时** | `GET /floor`（房间页每 2 秒问一次）先 `sweepExpiredFloor()` 清掉过期状态，返回 `released` / `releasedLocked` |
| 广播 | 清扫掉了就 `wsHub.broadcastFloor(roomId, {released, releasedLocked})` —— 让**全房间**都看到，不只是正在轮询的那台 |
| 客户端 | 收到 `released` 就提示「XX 掉线，麦克风已释放（含锁定）」 |

### 4.43 字幕也搬进 WS（B4，2026-10-27）

**为什么做**：`/frame` 是长轮询（服务端把请求挂住最多 25 秒）。它本身延迟不高，但：

- 每个客户端**常驻一条挂起的 HTTP 连接**，服务端要维护 waiter 集合；
- 它带着一套"序号重置"的历史包袱（转发进程重启后序号回到 0，客户端序号比服务端大会永远等不到）。

4.35 已经把"谁在说话"搬上 `/ws`，字幕顺着同一条连接走是最自然的一步。

**服务端**：新帧产生的地方（`publishFrame`）在 `notifyWaiters()` 之后加一句
`wsHub.broadcastFrame({type:'frame', seq, frame})`；`lib/ws-hub.mjs` 新增 `broadcastFrame`，
推给**所有**连接（字幕总线本来就是一场会议一条，房间维度只有"谁在说话"那一层）。

**客户端**：`FloorSocket` 的 `onMessage` 多认一个 `type === 'frame'`，回调 `onFrame(JSONObject)`；
`RoomActivity` 抽出 `applyFrame(text, lines, source, partial, termsMissing)` ——
**长轮询与 WS 都走它**，否则两条路迟早渲染得不一样（"长轮询能显示、WS 显示不出来"这种
只在一半设备上出现的分裂）。

**`/frame` 不删**：WS 断了要有兜底。分工与发言权一致 —— WS 是主通道，长轮询是看门狗。

**测试**：ws-suite 新增"写一帧到字幕总线 → WS 客户端收到 `type=frame`（含 seq 与帧内容）"；
android-order-suite 钉住"两条通道都走 `applyFrame`"与"长轮询没被删掉"。

### 4.44 三个 bug：选库框被挤掉 / 锁定按钮文案不对 / 发起者退出不赶人（2026-10-27）

**① 选库框里一个库都没有（4.41 改坏的）**

我在 4.41 为了把邀请码塞进选库框，给它加了 `setMessage(...)`。而 AppCompat 的 `AlertDialog`
在**同时**设置 `message` 与 `multiChoiceItems` 时，会把多选列表挤掉 —— 框还在，列表没了。

修法：去掉 `setMessage`，邀请码只写在**标题**里（标题不会被挤掉）；建房那一刻的长 Toast 保留。
测试改成反向断言：**这里不许出现 setMessage**（带一条注释说明为什么）。

**② A 锁麦时，B 的按钮也显示「解锁」**

原来所有人统一 `isLocked ? "解锁" : "锁定发言"`，而 B 根本按不动 —— 按钮写着「解锁」却不响应，
比"灰着"更让人困惑。现在文案与权限一致：

| 我的身份 | 锁定时 | 未锁时 | 可点 |
|---|---|---|---|
| 持麦者 | 解锁 | 锁定发言 | ✅ |
| 发起者（锁在别人手上） | 解锁（他人） | 锁定他人 | ✅ |
| 其他人 | **发言已锁定** | 锁定发言 | ❌（灰） |

**③ 发起者退出后，其余人还留在房间里**

服务端本来就把房间标成 `closed`，但**没有任何人告诉屋里的人**：界面照旧、按钮照旧，
直到某次操作失败 —— 这是最糟的一种"看起来正常"。

修法（三层，缺一层就会有人在空屋里）：

| 层 | 做法 |
|---|---|
| 推送 | `wsHub.closeRoom(roomId, 'host-left')`：先推 `{type:'closed', reason}`，再发关闭帧断开连接 |
| 轮询兜底 | `GET /floor` 对已结束的会议返回 **410 + `closed: true`**；房间页判到就退出 |
| 界面 | `leaveBecauseClosed()`：停止上传、Toast 说明原因、1.2 秒后退出房间 |

### 4.45 「被顶下线」改走推送（2026-10-27，用户要求）

**用户原话**：用户需要通过轮询检查自己有没有被挤下去，能否针对同时登录的情况加速状态更新。

**能，而且能压到一秒内**。关键在于：**服务端在吊销旧 token 的那一刻就知道**，不需要客户端去问。
4.41 的 `SessionWatch` 是"每 10 秒问一次"，最坏要 10 秒 —— 现在改成推送优先。

**做法：一条很轻的会话通道** `/ws?session=1`（与房间通道同一个服务端，只是不带 `room`）

| 侧 | 改动 |
|---|---|
| `lib/ws-hub.mjs` | 支持 `?session=1` 连接（注册到 `sessions: Map<user, conn>`，同一用户顶掉旧的）；新增 `notifyKicked(user)`：先推 `{type:'kicked', reason}` 再关连接（4002） |
| `relay/lan-relay.mjs` | 登录/邮箱注册成功（会吊销旧 token）后调 `notifyKickedIfReplaced(username)` |
| `SessionSocket.java`（新） | 连 `/ws?session=1`，收到 `kicked` 回调；连上就告诉界面"可以放慢轮询了" |
| `SessionWatch` | 间隔可调：推送在线 **60 秒**、推送断开 **10 秒** |
| `HomeActivity` / `RoomsActivity` | 同时开 `SessionSocket` + `SessionWatch`；收到 `kicked` → Toast「账号已在别处登录」+ 清 token + 回登录页 |

**为什么轮询不删**：推送是"服务端说"，轮询是"我主动问"，两条独立的路。WS 断开、服务端重启、
代理掐长连接时，推送是**静默失效**的 —— 只有轮询能发现。但既然推送已经把延迟压到一秒内，
兜底就不必跑那么勤（60 秒）。

**顺带说明**：房间里的人被顶下线仍然由房间通道的 401 兜住（4.41），那条路本来就快（2 秒轮询）。

### 4.46 「散会没通知」的兜底与可诊断性（2026-10-27）

**用户复测**：4.44 之后发起者退出，其他人**仍然收不到通知**。

**查下来是两件事叠在一起**：

1. **服务端没更新就完全无效**。`closed` 推送、`/floor` 的 410、`notifyKicked` 全是服务端行为：
   APK 更新了但服务器还在跑旧代码（`git pull` 后没重启 relay）时，客户端拿不到任何信号 ——
   而它**看起来像客户端的 bug**。这是最贵的一课：**功能跨两端时，先确认服务端版本**。
2. **我给的兜底不成立**。4.44 里我写的是"轮询判 `httpStatus == 410`"，但 `unwrap()` 只有在
   响应体**没有** `error` 字段时才补 `httpStatus` —— 而 410 的响应体恰好带 `error`，
   所以那个判断**永远不成立**。

**修法（三层，全部可诊断）**：

| 层 | 做法 |
|---|---|
| 权威信号 | `roomById` 起带 `closed`（相加性改动）；`GET /org/rooms/<id>` 因此能直说这场散没散 |
| 客户端兜底 | 房间页每 5 轮轮询（WS 在线约 50 秒、离线约 10 秒）调一次房间详情，`closed=true` → `leaveBecauseClosed()`。**这条对老服务端也成立**（只要它返回 `closed`） |
| 可诊断 | `RELAY_FEATURES` 加 `frame-ws` / `room-closed-push` / `session-push`；`LanClient` 记下 `/hello` 的 features；房间页在**缺少 `room-closed-push` 时直接在状态行写**「⚠️ 服务端版本较旧：会议结束时不会主动通知」 |

**升级检查**（下次先跑这一步，再怀疑客户端）：

```bash
curl -s "http://127.0.0.1:8788/hello?secret=$(cat /var/lib/leion/live/relay-secret.txt)" | jq .features
# 期望看到 frame-ws / room-closed-push / session-push —— 没有就是服务端还没更新/没重启
```

**M4 落地**：`doLogin()` 第一件事就是查勾选，没勾 → Toast + 不做任何网络请求。
点协议文字直接打开隐私政策页（`PrivacyActivity`）。

**一个按钮两种意图**：原型只有一个「注册／登录」，而服务端有两条路
（`/auth/register-email` 要邮箱+验证码+密码；`/auth/login` 要用户名+密码）。
判定规则：**填了邮箱或验证码就是注册，否则是登录**；只填一半会提示
"注册需要邮箱和验证码（只想登录就把这两项留空）"。这样既保留原型的单按钮，
又不让人猜自己在干嘛。

**几处刻意的不一致（都写进了代码注释）**：

| 项 | 做法 | 原因 |
|---|---|---|
| 密码输入框 | **保留**（原型没有） | 服务端注册/登录都要密码。等 M7（验证码直登）定了再删 |
| English 胶囊 | 显示但**禁用** | 服务端 `LANGS` 只有中/巴葡；能点就是骗人。灰着能说明"将来支持" |
| 服务器地址/密钥 | 收在「服务器设置（高级）」 | 原型主表单里没有；但换了服务器要能改，藏起来不等于删掉 |

**出厂默认配置**（`res/values/app_config.xml`）：地址预填生产机；**密钥默认空**。

> 用户提议"把 IP 和密钥打包进 APK 省得每台手输"。判断是：**地址可以打包，密钥不行（默认留空）**。
> 理由：APK 能被反编译，密钥一搜就出来，而它能做的事是**往服务器推字幕、灌音频**（`/say`、`/audio`）。
> 现有缓解手段：公网 TLS（docs/10 §4.3，尚未启用）、换密钥（删 `relay-secret.txt` 重启）、
> 真要多机就别靠共享密钥。想"装完即用"可在本地填上再构建，但别提交那个文件。
